## 一、结论先行

**1）“卡”不是选型问题，是实现链路问题。** 现状是：Chromium 以 1440×900 全分辨率 JPEG 编码 → 服务端每 90ms 广播一帧 → **base64 塞进 SSE 文本** → 前端用 `data:image/jpeg` 字符串整块重渲染。实测项目自己的历史帧：单帧 JPEG 8–243 KB（内容密集页 140–243 KB），base64 后 11–333 KB，11 fps 下内容密集页就是 **17.6–30.3 Mbps 的本地文本流**，且**面板切到别的画布标签后仍然挂载、仍然推流、仍然每帧触发整块 React 重渲染**。换成 Playwright 或任何别的引擎，只要还走“全分辨率 JPEG + base64 + 全量重渲染”，一样卡。

**2）“不知道 Agent 在干嘛”是数据层缺失，不是界面不好看。** 服务端只广播 `frame / state / tabs / closed` 四类事件，**没有任何“第几步、访问了哪个 URL、读到了什么、在等什么”的事件**。前端为“显示 Agent 正在操作”写好的 `agent-action` 事件（虚拟鼠标 + 气泡）**服务端从未发出过，是死代码**。`browser_snapshot` 读到的正文（最多 5000 字）与元素清单（最多 140 个）只在这张**默认折叠**的工具卡里以 JSON 出现，且要等工具调用完全结束才可见。

**3）选型结论：引擎不用换，传输按需升级，可观测性必须补。** 自研 CDP 是合理的（零依赖、可接管、隐私本地）；Tier 1 只改传输与渲染（约 1–3 天，收益最大）；Tier 2 才考虑 WebRTC/二进制 WS（仅在需要 30–60 fps 真实操作时）；Tier 3（Electron/WebView2 桌面壳、托管浏览器）**明确不建议**，且触碰 `AGENTS.md §4.2` 硬约束。

## 三、根因清单（按证据强度排序）

### R1【高】帧太重：全分辨率 JPEG 不经压缩分级，base64 再放大 33%

- 服务端参数：`FRAME_QUALITY=70`、`FRAME_MAX_WIDTH=1600`、`FRAME_MAX_HEIGHT=1000`、`everyNthFrame=2`、`MAX_FRAME_BYTES=900000`（`server/内置浏览器.mjs:36-43`），`startScreencast` 参数见 `:602-609`。
- 真实页面单帧 8–243 KB（内容密集页 140–243 KB，附录 A），base64 后 11–333 KB，11 fps 下内容密集页对应 17.6–30.3 Mbps（附录 B）。
- 关键点：**帧大小由“页面内容分辨率”决定，而当前配置把 1440×900 原尺寸推给面板**；面板只占画布一栏宽度（通常远小于 1440 px），等于把数倍于显示需求的数据编码、传输、解码。

### R2【高】面板隐藏后仍在推流、仍在重渲染

- `App.jsx:2863-2867`：只要画布存在 `browser` 标签就渲染 `<BrowserPanel>`，用 `canvas-hidden`（`display:none !important`）隐藏，**组件不卸载**。
- 组件挂载即订阅 SSE（`内置浏览器面板.jsx:75-168`），隐藏期间 `subscriberCount > 0` → 服务端继续 screencast（`内置浏览器.mjs:657-667`）。
- 每帧 `setFrame` 触发整个面板重渲染（状态在最顶层、无 `React.memo` 拆分），即使用户正在看地图/文档。
- 现成的 `browserAdaptiveStream` 开关（`server/运行开关.mjs:97-98`）**默认关**，且只监听 `document.hidden`（`内置浏览器面板.jsx:170-181`），**不感知画布标签切换**，所以即使打开也解决不了这个问题。

### R3【高】渲染方式：`<img src="data:image/jpeg;base64,...">` 每帧换 200–330 KB 字符串

- `内置浏览器面板.jsx:646-653`：每帧生成新的 data URL 字符串，交给 `<img>`。
- 后果：每帧一次大字符串分配 + data URL 解析 + 图片解码 + 旧字符串进入 GC；11 fps 即约 2–3.6 MB/s 的字符串垃圾。这是“面板里滚动/点击发涩、整个界面掉帧”的直接来源。
- 现成对照：同一文件里已有 `downloadBase64()` 用 `Blob + URL.createObjectURL` 的写法（`:469-478`），改造方向明确，但画面渲染路径没走这条。

### R4【中高】服务端节流是“按固定 11 fps 无差别推”，不是“按内容变化推”

- `queueFrameBroadcast` 固定 90ms 合并（`内置浏览器.mjs:573-591`），静态页面也在持续推帧；页面越复杂帧越大，带宽不降。
- `maxFramesInFlight: 2` + 每帧 `screencastFrameAck`（`:1145`）意味着 Chromium 侧始终有编码压力。
- 结果：静止时浪费、滚动时又不够顺（因为单帧太重）。

### R5【中】SSE 背压“丢帧”策略正确，但丢帧后用户看到的是画面停滞

- `server/index.mjs:2462-2494`：帧只保留最新一帧、`res.writableNeedDrain` 时直接丢（`:2518`）。策略正确（不会无限缓冲），但代价是：**高峰期丢的正是关键帧**，面板表现成“一顿一顿”。`MAX_FRAME_BYTES=900000` 单帧上限也意味着极端页面整帧被丢弃（`:575-576`）。

### R6【中】交互延迟：三段串行 + 每次操作后额外补一帧

- 用户点击 → `queueBrowserInput` 队列（`内置浏览器面板.jsx:184-190`）→ POST `/api/browser/input`（`server/index.mjs:2536`）→ CDP `Input.dispatchMouseEvent`（`内置浏览器.mjs:1284-1286`）→ `waitForLoad(8000, settle 1200, grace 800)`（`:1289`）→ `syncFrameSoon` 再截一帧（`:1523-1531,1624`）。
- 一次点击的“感知路径”包含 HTTP 往返 + CDP 往返 + 最多 1.2 s 的稳定窗 + 一次完整截图；这是“操作慢半拍”的来源之一，与帧流带宽叠加。

### R7【中】打开网页期间没有任何进度反馈

- `NAV_TIMEOUT_MS=8000` + `NAV_SETTLE_MS=2500` 的等待（`内置浏览器.mjs:27-31,1207-1238`）是**轮询式**（150ms 探针 + 200ms 内容探针），期间只有一个 `loading` 布尔（`state.loading`）。
- `tool_call_progress` 事件只在模型流式生成工具参数时发（`server/agent.mjs:5005,5018`），**工具执行期间不发任何进度**。所以打开一个慢站点时，用户看到的是：工具卡转圈 + 面板空白/旧画面，不知道在等什么。

### R8【中】可观测性：唯一的“Agent 正在操作”UI 是死代码

- 前端 `内置浏览器面板.jsx:122-128` 监听 `agent-action` 事件，渲染虚拟鼠标、气泡文案（`:406-417,657-670`），样式齐全。
- 服务端 `broadcast` 只发 `frame / state / tabs / closed`（`server/内置浏览器.mjs:583,776,931,1433`），**当前工作区服务端代码中不存在任何 `agent-action` 发送点**（对 `server/` 全目录 grep 无匹配；`git log -S agent-action` 显示历史上曾有相关改动）。
- 因此：**“Agent 正在点击哪个元素/正在输入什么”这一能力实际从未上线**。

### R9【低-中】长连接预算让帧流是可牺牲的

- 每标签页并发长连接上限 3（`client/src/长连接预算.js:21`），对话流与全局事件流是 essential，`browser-frames` 优先级 3 且非 essential（`内置浏览器面板.jsx:143`），必要时会被顶掉 → 面板进入重连循环（`:100-110`），表现为“画面突然不动，然后恢复”。

### R10【低】冷启动与若干额外截图

- 每会话独立 profile 启动浏览器（`内置浏览器.mjs:20,545`），首次打开含进程启动与 CDP attach；`Page.loadEventFired` 里又主动 `captureFrame()`（`:1161`），与 screencast 叠加。

## 四、可观测性现状盘点

| 用户想知道 | 现在能看到什么 | 结论 |
|---|---|---|
| Agent 在操作浏览器吗 | 面板自动展开（仅 `browser_open/click/type/press/scroll` 触发，`ChatPanel.jsx:45,2772`）；顶栏活动点（默认关） | 勉强 |
| 当前第几步 / 共几步 | 无。工具卡只有一张一张的调用，没有步骤号 | ❌ 缺 |
| 正在访问哪个 URL | 面板地址栏与标题会更新（`state.url/title`） | ✅ 部分 |
| 正在等什么（导航/稳定/元素） | 无，只有 `loading` 布尔 | ❌ 缺 |
| 读了哪些内容 | `browser_snapshot` 结果在工具卡里（默认折叠），JSON 里 `{url,title,elements[],text}`，正文截断 5000 字、元素最多 140 个（`内置浏览器.mjs:359-390`） | ⚠️ 事后、可读性差 |
| 操作是否点到了 | 无 `agent-action` 事件（死代码 R8）；只有面板画面 | ❌ 缺 |
| 失败原因 / 重试 | 工具卡 error + 面板 `state.error`；无步骤级归因 | ⚠️ 弱 |
| 历史轨迹回看 | 无；`.oaw/browser-shots/` 的截图只有 `browser_screenshot` 结果卡可回看（`ChatPanel.jsx:7750-7756`） | ❌ 缺 |

**本质**：现在的模型是“**一个画面 + 一堆工具卡**”，而用户需要的是“**一条能读懂的执行时间线**”（T1 打开必应 → 读取 12 条结果（3 842 字）→ 点击第 3 条 → 等待页面稳定 1.8 s → 读取正文 5 000 字 → 截图）。业界可类比 Playwright Trace Viewer 的 Actions + film strip 思路，但那是事后回放（[trace viewer 文档](https://playwright.dev/docs/trace-viewer)，2026-11-06 访问）；实时场景需要自己补事件流。

## 五、可观测性方案（建议 P0 落地）

### 5.1 事件契约（挂到 `server/事件注册表.mjs`）

新增 4 个事件，全部 `lifecycle: true`；`browser_step` 落盘（可回放），`browser_progress` 高频不落盘（对齐 `tool_call_progress`，`事件注册表.mjs:48`）。

```js
// 步骤开始
{ type: "browser_step_start", lifecycle: true, persist: true,
  schema: { required: ["runId","toolCallId","kind","url"],
            types: { runId:"string", toolCallId:"string", kind:"string", url:"string", title:"string", step:"number", targetText:"string" } } }
// 步骤结束
{ type: "browser_step_end", lifecycle: true, persist: true,
  schema: { required: ["toolCallId","status"], types: { toolCallId:"string", status:"string", durationMs:"number", error:"string", url:"string", title:"string" } } }
// 读取内容（snapshot/extract 专用）
{ type: "browser_read", lifecycle: true, persist: true,
  schema: { required: ["toolCallId","url"], types: { toolCallId:"string", url:"string", title:"string", chars:"number", elementCount:"number", preview:"string" } } }
// 等待/进度（高频，不落盘）
{ type: "browser_progress", lifecycle: true, persist: false,
  schema: { required: ["toolCallId","phase"], types: { toolCallId:"string", phase:"string", detail:"string", elapsedMs:"number" } } }
```

`kind` 取值：`open | snapshot | click | type | press | scroll | screenshot | tabs | back | wait | extract | act | select`。

### 5.2 服务端落点（最小侵入）

- **不要**在 `server/内置浏览器.mjs` 里 import 事件总线（该模块目前零业务依赖）。用**注入式回调**：`browserOpen(key, url, { onProgress })` 之类，或更简单——在 `server/agent.mjs` 已有的 `browser_*` 工具定义处（`:2450` 起）统一包装：调用前 `emit("browser_step_start")`，`await` 后 `emit("browser_step_end")`，`browser_snapshot` 结果额外 `emit("browser_read")`。**一处改动覆盖全部工具**，且天然带 `toolCallId`。
- 长等待（`waitForLoad`、`browser_wait_for`）内部通过注入的 `onPhase` 回调发 `browser_progress`（阶段：`navigating | settling | waiting-condition | capturing`）。

### 5.3 前端 UI（复用现有组件）

1. **对话侧「浏览器活动」时间线**：一个可折叠区块，每步一行 `序号 · 图标 · 动词短语 · 目标(URL/元素文本) · 读取 N 字 · 耗时 · 状态`；点击展开看该步 snapshot 预览（前 300 字 + 元素数）。挂在 `ChatPanel.jsx` 工具卡流之上，事件消费沿用现有 SSE。
2. **浏览器面板顶部「当前动作条」**：`正在读取：cn.bing.com（第 3 步）· 等待页面稳定 1.2s`，数据来自 `browser_progress`。
3. **步骤列表与帧流联动**：点某步 → 面板显示该步截图（复用 `browser_screenshot` 落盘与 `/api/browser/shot`，`server/index.mjs:2402`）。
4. 把死代码 R8 二选一：**要么补齐服务端 `agent-action` 广播**（点击坐标、输入文本、导航 URL，客户端已能渲染），**要么删掉**，避免“看起来有这个功能其实没有”。

## 六、选型结论

### 6.1 传输方案对比

| 方案 | 延迟 | 带宽（1440×900 内容页） | 依赖 | Windows 可行 | 项目适配 | 结论 |
|---|---|---|---|---|---|---|
| **现状：CDP screencast + SSE + base64 JPEG** | 100–300 ms | 7.8–30.3 Mbps（实测换算） | 无 | ✅ | 已实现，零依赖 | 保留，改造 |
| CDP screencast + **二进制 WebSocket** | 80–200 ms | 降 25%（去 base64/JSON 包装） | 无（Node 内置 WS + 浏览器 WS） | ✅ | 改动集中：`内置浏览器.mjs` 广播 + 新增 `/ws/browser` + 前端 canvas | **Tier1 首选** |
| CDP screencast + 只推**变化区域/降采样** | 60–150 ms | 降 50–80%（内容相关） | 无 | ✅ | 需处理 `Page.screencastFrame` 的 region 逻辑 | Tier1 配套 |
| MJPEG over HTTP | 150–400 ms | 高（每帧独立 JPEG） | 无 | ✅ | 无背压优势 | 不推荐 |
| noVNC / RFB over WebSocket | 80–200 ms | 低（增量编码） | 无/websockify | ⚠️ 需 VNC 服务端 | 引入第二套协议与守护进程 | Tier2 备选 |
| WebRTC（neko / Selkies / Kasm 一类） | 50–150 ms | 最低（H.264/VP8） | ffmpeg/GStreamer 或原生 WebRTC stask | ⚠️ Windows 打包复杂 | 大改造，需独立信令 | Tier2，仅 30–60 fps 需求时 |
| 视频编码（H.264/VP8） | 50–150 ms | 最低 | 编码器 | ⚠️ | 复杂度最高 | 不推荐现阶段 |

### 6.2 引擎对比

| 方案 | 观察方式 | 实时画面 | 依赖/体积 | 隐私 | 项目适配 |
|---|---|---|---|---|---|
| **自研 CDP（现状）** | 自研语义快照（`SNAPSHOT_SCRIPT`） | 已有 | 零 | 本地 | ✅ 保留 |
| Playwright / @playwright/mcp | 可访问性树，非像素；可 `--cdp-endpoint` 接管现有浏览器 | **MCP 本身不提供 UI 实时画面**（有 trace/video 工具，属事后） | `playwright` 数十 MB + 浏览器二进制策略 | 本地 | ⚠️ 只换“驱动层”，不解决“卡”和“可观测” |
| chrome-devtools-mcp（Google 官方） | Puppeteer 驱动 + DevTools 性能洞察 | `--experimentalScreencast` **需要 ffmpeg** | puppeteer + Chrome | ⚠️ 默认上报使用统计、性能数据可能发 CrUX | ❌ 不适合本地优先产品 |
| Puppeteer / Selenium | DOM 驱动 | 无 | 中等 | 本地 | ❌ 收益小 |
| Browserbase/Hyperbrowser 等托管 | 云端 | 云端 live view | 云依赖 | ❌ 数据外传 | ❌ 违反本地优先 |

Playwright MCP 与 chrome-devtools-mcp 的关键事实（2026-11-06 访问其 README）：
- Playwright MCP：“Uses Playwright's accessibility tree, not pixel-based input.”（[microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp)）
- chrome-devtools-mcp：`--experimentalScreencast` “Exposes experimental screencast tools (requires ffmpeg)”，且 usage statistics 默认开启（[ChromeDevTools/chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp)）

**结论**：两者都不会让画面变快——它们解决的是“怎么可靠地驱动页面”，不是“怎么低延迟地把画面给人看”。本项目的驱动层已经够用，**换引擎属于高成本低收益**。

### 6.3 三层建议

| 层级 | 内容 | 改动面 | 预期收益 | 需要用户拍板 |
|---|---|---|---|---|
| **Tier 1（必做）** | ① 面板不可见即停推流/退订；② 帧参数分级（quality 55–60、maxWidth 1280、广播间隔 120–150ms、静止页降频）；③ data URL 改 Blob/`createImageBitmap`+canvas；④ 补 `browser_*` 步骤事件与时间线 UI；⑤ 修复/删除 `agent-action` | `App.jsx`、`内置浏览器面板.jsx`、`内置浏览器.mjs`、`agent.mjs`、`事件注册表.mjs` | 隐藏态负载归零；稳态带宽降约 50–70%；“看得见在干嘛” | 否（Tier1 属缺陷/体验修复） |
| **Tier 2（可选）** | 帧流改二进制 WebSocket；交互后只截变化区；必要时上 WebRTC 像素流 | 新增 `/ws/browser` 或独立 WS 端口；前端渲染层重写 | 延迟再降 30–50%；高帧率可行 | 是（新增传输通道/依赖，需 ADR） |
| **Tier 3（不建议）** | 换 Playwright 驱动；Electron/WebView2 内嵌视图；托管浏览器 | 大 | 与“卡/看不见”无直接关系 | 是，且触碰 `AGENTS.md §4.2` |

**AGENTS.md 约束核对**：Tier1 全部在现有技术栈内，属缺陷修复与体验优化，不引入依赖、不新增服务、不改 SSE 契约语义（只新增事件，需登记）；Tier2 新增传输通道/可能引入依赖，按 §4.3 需先取得确认并补决策记录；Tier3 的桌面壳、托管服务分别触碰 §4.2 禁止项与本地优先原则。

## 八、风险与不做清单

**不做**：
1. 不为“更丝滑”引入 Playwright/Puppeteer —— 不解决画面问题，反而破坏零依赖基线。
2. 不上 Electron/WebView2 桌面壳 —— 触碰 `AGENTS.md §4.2`，且 WebView2 内嵌第三方页面会受 `X-Frame-Options` 限制，无法替代“接管真实浏览器”。
3. 不接托管浏览器（Browserbase 等）—— 违反本地优先与隐私约束。
4. 不在 P0 阶段动 SSE 契约——新增事件可以，改语义不行。

**风险**：
1. 降低帧质量可能影响“读小字”体验，需要面板尺寸自适应（面板宽 < 700px 时 1280 足够，全屏时按 1.5× 采样）。
2. 事件新增会进入回放/落盘链路，需按 `事件注册表` 约定补测试（否则 `scripts/事件注册表测试.mjs` 会失败）。
3. 面板卸载/重挂会丢“最后一帧”，需要首帧兜底（已有 `captureFrame` 路径，`server/内置浏览器.mjs:615-619` 与 `server/index.mjs:2524`）。
4. 调研期间另一会话正在改 CAD 文件，`server/index.mjs` 等共享文件可能持续变化，实施前需重新核对行号。

## 附录 B：编码开销实测（Node v24，本机）

`node docs/audits/2026-11-06-内置浏览器体验调研/bench/encoding-overhead.mjs` 输出：

| JPEG | base64 | SSE 单条文本 | 膨胀 | JSON 往返 | base64 解码 | 11 fps 带宽 | 11 fps 主线程 |
|---|---|---|---|---|---|---|---|
| 64 KB | 85.3 KB | 85.4 KB | 1.333× | 0.08 ms | 0.04 ms | **7.8 Mbps** | 1.3 ms/s |
| 145 KB | 193.3 KB | 193.4 KB | 1.333× | 0.41 ms | 0.12 ms | **17.6 Mbps** | 5.9 ms/s |
| 250 KB | 333.3 KB | 333.4 KB | 1.333× | 0.51 ms | 0.13 ms | **30.3 Mbps** | 7.0 ms/s |

**关键判断**：JSON+base64 的**纯 CPU 开销不大**（< 10 ms/s），真正的代价是 ① 带宽/内存拷贝量（17–30 Mbps 文本流）、② 浏览器端解析 data URL 与图片解码、③ 每帧触发整块 React 重渲染、④ Chromium 侧 JPEG 编码。因此**优化优先级应是“减帧重 + 减重渲染”，而不是“优化 JSON 解析”**。
