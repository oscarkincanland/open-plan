# 偶发"会话历史读取失败 / 产物打开失败"排查

> 状态：只读排查（未改代码）　日期：2026-11-10　服务：v0.13.25，`127.0.0.1:3002`，`healthy=true`
> 症状（用户）：偶发出现会话历史读取失败、工作区产物打开失败
> 方法：服务端接口压测（Node，无浏览器连接数限制）+ 浏览器内确定性复现 + 服务端日志时间线 + 代码路径核对

## 0. 结论

**服务端本身没有偶发错误，失败来自浏览器侧的连接饥饿，叠加服务端偶发卡顿重启。**

- 服务端：并发 8 路打 `会话详情 / 产物 open / 产物 html / 会话列表 / Run 列表`，**0 失败 0 超时**；会话详情 30–360ms、产物 open 43–165ms、产物 html 冷启动 2.75s。
- 浏览器：在同一页面注入 6 条同源 SSE（页面本身已有 2 条必需流）后，`/api/sessions` 与 `/api/status` **全部 12s 超时**——服务端空闲，是 Chrome 同源 HTTP/1.1 **6 连接槽**被长连接占满。
- 客户端控制面请求超时阈值正是 `CONTROL_TIMEOUT_MS = 8000`，超时后界面就是"XX读取失败，已保留上一次可用数据"；产物打开走同一个 `fetch` 通道，报"打开失败: …"。
- 另外服务端日志有大量 `健康检查连续失败，正在重启服务…（端口仍在监听，疑似卡住）` 与 `服务异常退出`；每次重启期间所有请求必失败。今天 13:26、13:28 各有一次健康检查失败（13:41 是手动重启）。

## 1. 服务端压测数据（排除服务端慢/错）

| 接口 | 并发 1 平均/峰值 | 并发 8 平均/峰值 | 失败 |
|---|---|---|---|
| `/api/sessions/:id?view=chat&limit=50` | 70 / 158ms | 101 / 171ms | 0 |
| `/api/doc/<docx>`（open） | 43 / 79ms | 165 / 195ms | 0 |
| `/api/doc/<docx>/html`（officecli 转 HTML） | 949 / **2750ms**（冷启动） | 387 / 464ms（已缓存） | 0 |
| `/api/sessions` | 157 / 416ms | 191 / 240ms | 0 |
| `/api/runs?...includeEvents=latest` | 187 / 447ms | 310 / 440ms | 0 |

大会话读取也正常：8.08MB 会话全文 243ms、chat 视图 362ms；6.81MB 会话 171ms / 48ms。

## 2. 浏览器侧确定性复现（根因）

在真实页面里，先看现有流占用（`window.__oawStreams`：全局事件流 1 条 + 对话流 1 条），再注入 6 条同源 `EventSource`：

```
opened = 6
GET /api/sessions  → TimeoutError 12003ms
GET /api/status    → TimeoutError 12014ms
```

服务端完全空闲（同一时刻 Node 侧请求都是毫秒级）。说明这是**浏览器同源连接池饥饿**，不是服务端故障。

#### 为什么会饿死

- `client/src/api.js`：控制面请求 `CONTROL_TIMEOUT_MS = 8000`，超时文案即用户看到的"读取失败"。
- `长连接预算.js`：每标签页 `MAX_STREAMS = 3`。
- `跨标签页流配额.js`：全局 `GLOBAL_MAX_STREAMS = 4`，但**必需流（对话流 / 全局事件流）永不拒绝**——多窗口各自开 2 条必需流时，3 个窗口就是 6 条 = 池满，配额层无法阻止。
- `跨标签页流租约.js` 已把"全局事件流"收敛为每 origin 1 条，所以典型占用是「N 个窗口 × 1 条对话流 + 1 条全局流」；**3 个以上窗口即占满 6 槽**，控制面请求排队到 8s 超时。
- 该现象在代码注释里已有记录（2026-11-02 实测同文案报错），防护只覆盖单标签页与全局配额，未覆盖"多窗口必需流总数"。

#### 产物打开为什么也失败

`open` 本身快（43–165ms），但它和 raw/html 共用同一 fetch 通道；连接池被占时，`open` 也会排队超时 → `打开失败: …`。冷启动 html 转换要 2.75s，若与 Agent 正在跑的 officecli 争用会进一步变慢，但这不是"偶发失败"的主因。

## 3. 服务端卡顿/重启（第二条原因）

`运行日志/服务监督.log` 中反复出现：

```
健康检查连续失败，正在重启服务：/api/status 不可用或服务版本不匹配（端口仍在监听，疑似卡住）
服务异常退出（signal SIGTERM / exit 3221226505 / exit 4294967295）
```

10-30/10-31 有多轮"每几分钟重启一次"；今天 13:26/13:28 也有健康检查失败。**重启窗口内所有请求必然失败**，与连接饥饿叠加，形成"偶发"体感。

疑似卡顿源：同步解析大 JSONL（8MB 会话）、`listRuns` 全量解析（本次已加摘要缓存）、officecli/浏览器子进程、画布导出 CDP。未定位到单点，需专门加事件循环延迟采样。

## 4. 修复方向（需确认后实施）

| 方案 | 作用 | 代价 |
|---|---|---|
| A. 合并同标签页两条必需流为一条 SSE（服务端多路复用 channel） | 每窗口 2 条 → 1 条，3 窗口只剩 3 条，留 3 槽 | 需改事件流协议与消费端，跨端契约变更 |
| B. 必需流也做全局硬上限，超出时后续窗口**降级轮询** | 根本不让池被占满 | 后台窗口实时性下降 |
| C. 控制面请求超时后**释放可放弃流并重试一次** | 自愈，不改协议 | 只缓解、不根治 |
| D. 失败提示区分"服务重启中/连接被占"，给一键重试 | 用户可感知、可恢复 | 体验层 |
| E. 服务端卡顿治理：事件循环延迟采样 + 大 JSONL 解析缓存/分片 | 减少重启 | 需先埋点定位 |

推荐组合：**C + D 先做（低风险、当天可验证）→ B 或 A 择一（治本）→ E 另立计划**。
