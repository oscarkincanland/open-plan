  2. **全新 Run 出现 `run_recovered` 事件**：三个并发任务都带 `run_recovered(status=recovering)`，但服务本次没有重启。首要嫌疑是**另一个 server 实例**（如 `npm run verify` 的 3199 实例）扫描了同一个 `.oaw/runs` 并执行 `recoverActiveRuns`；这会把生产中的活动 Run 标记成 recovering，属于测试/多实例隔离风险。

## 3. 功能审查（并发与会话链路）

### 3.1 并发模型

- Agent 管理器以 `agentKey(client, thread)` 为键（`server/index.mjs` 的 `agentKey`；`server/agent.mjs` 的 `sessions`），因此：
  - 不同 client（不同浏览器/标签页预算）可以并行；
  - 同一 client、不同 thread（同一浏览器的多个会话）也可以并行；
  - 同一 client + thread 才会排队（`entry.busy/promptChain`）。
- 实测：
  - 不同 client ×3：A/B/C 三个任务都完成；
  - 同 client ×2 thread：X/Y 都完成，没有写冲突。

### 3.2 写锁

`server/写入协调.mjs` 的 `withWriteLock` 对 `bash`/`officecli`/地图工具使用**工作区根目录**作为锁目标（`withWorkspaceWriteLock`）；`write` 工具目标则是具体文件。`findExternalOverlap` 会让“文件写”与另一个任务的“工作区根锁”重叠，从而：

- C 任务第一次写 `chart.html` 得到：

```text
WRITE_CONFLICT
写入范围与其他任务冲突：D:\Claude code文件\office-agent-web\office-workspace
```

- `acquireWriteLockWithRetry` 以 350ms 退避、20s 超时重试，C 后续成功；
- 如果另一个任务的 `bash` 命令持续超过 20s，C 的写入会最终失败。

这是高并发下的**可重试限流**，不是数据损坏；但会表现为“任务偶尔失败/很慢”，需要产品层面明确。

### 3.3 会话切换

- 2 个标签页各 20 次切换，全部 `success`，没有 `SESSION_BUSY` 恢复警告；
- 每页连接数：leader 2 条（事件+对话），follower 1 条（对话），服务端同一 client 共 3 条；
- 切换期间控制面 p50/p95：

| 接口 | 样本 | p50 | p95 | max |
|---|---:|---:|---:|---:|
| `GET /api/sessions` | 34 | 4.5ms | **192.5ms** | 303.9ms |
| `GET /api/files` | 33 | 6.1ms | **192.3ms** | 305.3ms |

- 浏览器 console 异常：0；加载失败横幅：0。

### 3.4 `run_recovered` 异常

三个并发任务的 `eventTypes` 都有 `run_recovered: 1`，数据为 `status: recovering`，发生在 Run 开始后不久；但 `service:status` 的 uptime 从测试前到测试后保持稳定（本次没有重启）。结合代码：

- `run_recovered` 只在 `recoverActiveRuns()`（服务 **listen 成功后**）写入（`server/runs.mjs`）；
- `scripts/验证脚本.mjs` 会在 3199 端口启动一个独立 server，但**没有隔离 `OAW_RUNS_DIR`**，它会扫描同一个 `.oaw/runs`；
- 如果验证/测试 server 与主服务同时运行，它会把主服务正在执行的 Run 标记为 `recovering`。

本次测试期间没有在 3199 看到监听（可能已退出），因此不能 100% 证明是该实例；但事件与服务 uptime 矛盾，属于**必须排查的跨实例恢复污染**。建议复现步骤：主服务跑一个长任务，同时 `npm run verify`，观察主任务是否出现 `run_recovered`。

## 7. 问题与建议

### P1-1：多实例恢复污染（E-04）

- **风险**：测试/验证 server 与主服务共享 `.oaw/runs` 时，`recoverActiveRuns` 会把主服务活动 Run 标记 recovering；用户可能看到“任务被恢复/只读”，甚至任务被误收尾。
- **建议**：
  1. `scripts/验证脚本.mjs` 启动 server 时设置临时 `OAW_RUNS_DIR`（以及必要时 `OAW_WRITE_LOCK_DIR`），测试结束清理；
  2. 或增加 `OAW_DISABLE_RECOVERY=1` 仅用于测试实例；
  3. 生产侧给 `.oaw` 增加实例所有权/租约，非 owner 不得改写活动 Run；
  4. 加回归测试：主实例执行长任务时启动 second server，断言主 Run 不被标记 recovering。

### P1-2：并发写锁粒度过大（E-01）

- **风险**：同一工作区并发任务时，一个 `bash` 命令持有工作区根锁，其他任务的文件写入会 `WRITE_CONFLICT`；20s 重试对长命令不够。
- **建议**：
  1. 对可静态识别的 `bash` 写入路径做路径级锁（至少把脚本输出的子目录纳入锁范围）；
  2. 或把写冲突作为 Agent 可见错误码，让模型等待/改路径，而不是只依赖工具内部重试；
  3. 为 `acquireWriteLockWithRetry` 记录等待时长/冲突次数，作为 Run 指标；
  4. 允许不同子目录的任务并行写，产品上明确“同工作区根目录写入串行化”的边界。

### P2：测试会话与工作区清理

- 本次创建了多个测试会话（E2E、LOAD A/B/C、SAME X/Y）和临时产物；文件已清理，测试会话仍可按标签识别。建议后续测试使用独立工作区（`office-workspace/_l4/`）并在结束后删除会话，避免污染用户会话列表。
- 现有 `.oaw/runs` 还保留测试 Run；报告用 Run ID 作为证据。

### P2：无自动化并发回归

- 目前 `test:*` 没有“3 个任务并发 + 会话切换 + 写冲突”的自动化场景；建议增加 `test:multi-task-load`（API 级 3 任务 + 20 次切换 + 断言无 fatal、记录 WRITE_CONFLICT 次数）。
