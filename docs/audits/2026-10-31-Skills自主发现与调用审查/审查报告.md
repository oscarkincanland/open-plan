# Skills 自主发现与调用审查报告

> 状态：审查结论（未修改代码）
> 日期：2026-10-31
> 基线：`fix/session-file-flow`（含 `082e7bea` 稳定性改造与后续合并提交）
> 审查对象：Open Plan 的 Skills 发现、选择、注入与调用链路；Harness 中 `skills_search` / `skills_read` / 技能预检
> 关联：AGENTS §5「产品内 Agent 能力边界」、PRD R6「技能广场、技能与工作流」、Harness 文档 `docs/2026-10-27-ZCode-Harness与Open-Plan功能需求对照.md`
> 结论：**“不会自主调用/发现 Skills”不是单一模型问题，而是当前链路没有把“发现”变成可执行动作**；同时 `@技能` 入口存在实际断链。

## 1. 结论先行

把现象拆成三个问题：

| 问题 | 结论 | 证据 |
|---|---|---|
| Skills 是否存在、能不能被读到 | **存在且可读**；65 个本地 Skill，`skills_search/skills_read` 工具可用 | `/api/skills` 返回 65 个；显式实验成功读取 `baoyu-echarts` |
| 默认会不会主动发现/调用 | **不会**；普通任务没有触发任何 `skills_search` / `skills_read` | 真实 Agent 实验：自动任务 0 次 Skill 工具调用；显式任务 4 次搜索 + 1 次读取 |
| 用户点「调用 Skill」是否可靠 | **不可靠**；UI 插入 `@技能[...]`，服务端只解析 `#技能[...]`；任务 payload 也不携带 skills | 解析实验：`@技能` 得到 0 条引用，`#技能` 得到 skill 引用且状态 `deferred`；`ChatPanel.startAgentTask` 与 `startAgentTask` payload 检查 |

一句话：**当前实现是“用户显式点名 + 模型自愿读取”的半手动能力，不是 Harness 意义上的按需自动发现。**

## 2. 审查范围与方法

### 2.1 证据来源

1. **静态链路**：`server/agent.mjs`（资源加载、系统提示词、自定义工具）、`server/task.mjs`（能力计划/路由）、`server/context.mjs`（引用解析）、`server/index.mjs`（skills API、预检、prompt admission）、`client/src/components/ChatPanel.jsx`（发送与 `@技能` 插入）、`SkillsManager.jsx`。
2. **Skill 清单**：`GET /api/skills`，统计数量、来源、描述解析质量。
3. **解析实验**：直接调用 `server/context.mjs` 的 `parseReferences` / `resolveReference`，验证 `@技能` 与 `#技能`。
4. **真实 Agent 对照实验**（同一模型 `opencode-go/deepseek-v4.1-flash`，同一工作区）：
   - A：只给任务，不提示 Skill；
   - B：同一任务，明确要求先 `skills_search`、命中后 `skills_read`。
5. **运行事件核对**：`/api/runs/:id` 的 `tool_start/tool_end`、`capability_plan`、Run 终态与产物文件。

### 2.2 限制

- A 组第一次运行（`run_fcb71a62…`）遇到服务重启被收尾，不作为核心证据；重新运行 A 组得到 `run_2c73eb19…`。
- 实验只覆盖一个“ECharts 图表”任务，不能代表所有 Skill 类别；但静态链路对所有普通任务一致。
- 没有修改代码，也没有把任何 Skill 内容或用户文件写入仓库。

## 3. 当前 Skills 链路

### 3.1 发现：有目录扫描，但默认不进入上下文

`server/agent.mjs` 创建 Pi Runtime 时显式设置了：

```js
const loader = new DefaultResourceLoader({
  ...
  noSkills: true, // 不把全局 160+ 个 Skill 的目录摘要注入每一轮模型上下文
  ...
});
```

同时工作台自己提供 `skills_search` / `skills_read` 两个只读工具（`server/agent.mjs:2218-2265`）。也就是说：

- **Pi 原生 Skills 目录注入被关闭**；
- 模型看到的是工具，不是 65 个 Skill 的名单；
- 系统提示词只写了两句与 Skills 有关的话：
  - `.claude/skills/` 内置了 `localSkillCatalog().length` 个技能（示例 `docx/pptx/xlsx/baoyu-*/lark-*/ultimate-ppt-master`）；
  - “需要对应能力时遵循其 SKILL.md 指引”。

**没有一句要求模型“先调用 `skills_search` 发现技能”**，也没有告诉模型：不搜索时有哪些可匹配名称。

### 3.2 选择：能力计划只标记，不驱动调用

`server/task.mjs:251` 只有在文本命中 `@工作流[...]`、`@技能[...]`、`workflow`、`skill` 等关键词时，才把 `skills` 能力标为 `planned`；否则 routing 是：

```js
skills: workflow ? "preflight" : "available_on_demand"
```

问题在于 `available_on_demand` **没有任何执行者**：

- 模型没有收到“按需搜索”的指令；
- 预检 `preflightSkills` 只检查 SKILL.md 是否存在/可读，不读取内容、不注入、不执行；
- `task.skills` 只在服务端 admission 计算 `requestedSkills` 时使用，`agent.mjs` 的 `_promptEntry` 没有读取它（已核对 `runContext.task` 的使用）。

### 3.3 调用：`skills_read` 只是“读取说明”，不是“执行技能”

`skills_read` 的实现返回 SKILL.md 文本（默认可截断），并不会执行技能里的脚本或依赖：

- `RUNTIME_FLAGS.skillInjection` 默认 **false**（`server/运行开关.mjs:204`；当前 `/api/status` 也是 false）；
- flag 关闭时，`skills_read` 返回 `# name` + 原文，并且 **不写 `skill_injected` 事件**；
- 因此即使模型读取了 SKILL.md，Run 事件里也没有“注入了哪个 Skill”的权威记录，只能从 `tool_start: skills_read` 间接推断。

### 3.4 用户入口：`@技能` 与服务端 `#技能` 不一致

这是本轮新发现的直接断链：

- `client/src/components/ChatPanel.jsx:1502` 的 `startAgentTask` 生成：

```js
const skillMarkers = (payload.skills || []).map((name) => `@技能[${name}]`);
```

- `server/context.mjs:90` 只解析：

```js
/#技能\[([^\]]+)\]/g
```

实测（直接调用 `parseReferences`）：

```json
{
  "at": [],
  "hash": [{ "kind": "skill", "target": "baoyu-echarts", "status": "deferred" }]
}
```

- 即使使用正确的 `#技能`，`resolveReference` 对 skill 也返回 `deferred`（`server/context.mjs:200`：由清单解析）；`readReference` 只处理 session/knowledge/template，没有 skill 分支。
- `ChatPanel.send` 的 `/api/agent/prompt` task payload（约 `ChatPanel.jsx:3545`）也没有 `skills` 字段；`SkillsManager` 的「调用」只把文本写进输入框，**不会把结构化 skills 交给服务端**。

因此「技能广场 → 调用」的常见路径是：输入框出现 `@技能[xxx]` → 服务端不识别 → 任务 payload 没有 skills → 模型只能靠自由意志调用 `skills_read`。这解释了“点了调用但没感觉”。

## 4. 证据

### 4.1 Skill 清单质量

`GET /api/skills`：

- 总数：**65**
- 来源：项目 `.claude/skills` 50、用户 `.claude/skills` 14、用户 `.agents/skills` 1
- **description 解析异常：10 个**（值为 `>` 或 `|`，来自 YAML block scalar）：

```text
axi-front-design, codex, debugging-agent, design-review,
humanizer, llm-wiki, prompt-optimizer, qa, review,
ultimate-ppt-master-skill
```

原因是 `localSkillCatalog` / `scanSkills` 用单行正则：

```js
/description:\s*["']?([^"'\n]+)/
```

遇到 `description: >` / `description: |` 时只截到 `>`/`|`，没有读取后续缩进文本。结果是这些技能在搜索里只剩名字可匹配，简介为空。

### 4.2 搜索匹配质量

`searchLocalSkills` 的规则是：查询按空格切词，**每个词都必须同时出现在 `name + description`**，然后取前 N 条。对常见中文任务查询实测：

| 查询 | 命中数 | 命中 Skill |
|---|---:|---|
| `ECharts 柱状图` | 0 | — |
| `ECharts` | 1 | baoyu-echarts |
| `PPT 演示` | 0 | — |
| `文档审查` | 0 | — |
| `设计评审` | 0 | — |
| `Word 批注` | 0 | — |
| `数据分析` | 0 | — |
| `飞书` | 0 | — |
| `生成图表` | 0 | — |

这不是模型“不会搜”，而是**搜索器本身把自然语言任务拆成 AND 词面匹配**：`ECharts 柱状图` 要求简介同时含“echarts”和“柱状图”，而 `baoyu-echarts` 的简介只有“ECharts 图表生成…”，所以 0 命中；只有单独搜 `ECharts` 才命中。显式实验里模型因此连续试了 4 次（包括空查询）才找到目标 Skill。

### 4.3 真实 Agent 对照实验

同一工作区、同一模型，任务都是“生成 ECharts 柱状图 HTML”：

| 组 | Run | 耗时 | 工具调用 | Skill 工具 | 结果 |
|---|---|---:|---|---|---|
| A 自动（不提示） | `run_2c73eb19-fc4e-4f0c-adfa-f1daa97ebda1` | 31s | `todo, ls, write, bash, complete_task` | **0** | 直接写 HTML 完成 |
| B 显式要求 | `run_f09657a1-0964-499b-9308-d549191705cd` | 61s | `skills_search ×4, skills_read, write, bash, complete_task` | **5** | 找到并读取 `baoyu-echarts`，按 `bar-simple` 生成 |

A 组 Run 的 `capability_plan` 里虽然出现了 `skills` 条目标记为 `planned`，但没有任何 `skills_search` / `skills_read`；B 组则明确多出了 4 次搜索（含空查询）和 1 次读取。两条 Run 都完成了产物文件，区别只在“有没有人/提示词逼它去发现”。

第一次 A 组（`run_fcb71a62…`）因服务重启被收尾，已排除；A 组重跑结果稳定。

### 4.4 解析实验

```text
parseReferences("请使用 @技能[baoyu-echarts] 完成任务") -> []
parseReferences("请使用 #技能[baoyu-echarts] 完成任务") -> [{kind:"skill",target:"baoyu-echarts"}]
resolveReference(#技能[baoyu-echarts]) -> status: "deferred"
```

UI 生成的 `@技能` 不会进入 references；即使手工写对 `#技能`，引用也只是 `deferred`，不会被 `context_read` 展开为 SKILL.md 内容。

## 5. 根因分析

| ID | 根因 | 影响 | 严重度 |
|---|---|---|---|
| S-01 | `noSkills:true` + 不注入技能清单 | 模型不知道 65 个 Skill 的名称/能力，只能盲猜或完全不搜 | **P1** |
| S-02 | 提示词没有“先搜索再执行”的强制/建议规则 | 普通任务不会触发 `skills_search`；自动实验 0 次 | **P1** |
| S-03 | `@技能` 与解析器 `#技能` 不一致；task payload 不携带 skills | “技能广场 → 调用”常见路径断链 | **P1** |
| S-04 | `skills` 只做预检，SKILL.md 内容不注入；`skillInjection` 默认关 | 即使点名 `#技能`，也不能保证模型看到技能内容；事件不可见 | P1 |
| S-05 | 搜索是 AND 词面匹配；无同义词/中文/排序 | 常见任务查询 0 命中；显式使用也要多次试错 | **P1** |
| S-06 | frontmatter 描述解析不支持 `>`/`|` block scalar | 10/65 Skill 简介为空，进一步降低发现率 | P2 |
| S-07 | 无“自动选择”测试；`Skill注入契约测试` 只测格式化 | 回归无法发现 S-01–S-06 | P2 |
| S-08 | 项目默认 `skills: []`，Agent 的 skills 只作为 @mention 文本，不结构化下发 | 预置智能体的技能不能自动生效 | P2 |

### 5.1 直接回答“有没有主动性”

- **发现主动性：没有。** 默认 Agent 只有 65 个 Skill 的事实和两个只读工具；没有“遇到任务先检索技能”的指令、触发器或服务端选择器。
- **执行主动性：也没有。** 找到 SKILL.md 后是否遵循完全依赖模型；`skills_read` 只返回说明，不执行脚本；`skillInjected` 默认不记录。
- **能力本身：有。** 显式提示后模型能搜索、读取并遵循；工具链不是坏的，是“路由/提示/入口”没接上。

## 6. 与需求的关系

PRD R6 当前写的是：

> 技能广场：分类展示、@ 调用、导入/导出、管理与搜索。

它只要求 **@ 调用**，没有要求“自动发现/自动选择”。因此：

1. **`@技能` 断链**属于 PRD 既有能力的实现缺陷（应修）；
2. **“自主发现/主动调用”**属于尚未定义的新需求；如果要把它作为 Harness 功能，需要先补 PRD R6 的验收口径，否则实现会被误判为“模型不主动”。

建议新增一条明确需求（编号可在 R6 下细分）：

> R6.x Skills 按需发现：对非显式点名的任务，系统应能根据任务意图检索本地 Skills；命中后读取 1–2 个最相关 SKILL.md 并在本轮上下文中使用；未命中时不得伪造技能或阻塞主任务；Run 事件记录 `skill_selected/skill_read` 以便审计。

## 7. 改进方案（建议，不在本轮实施）

### P0（先修断链，1–2 天）

1. **统一标记语法**：`parseReferences` 同时接受 `@技能[...]` 与 `#技能[...]`；或者把 `startAgentTask` 改为 `#技能[...]`。推荐两者都支持，兼容历史输入。
2. **把 skills 结构化下发**：`ChatPanel.send` 的 task payload 增加 `skills`；`startAgentTask` 不再只拼文本；服务端 `requestedSkills` 接收并预检。
3. **`context_read`/`readReference` 支持 skill**：按 name 找到 `SKILL.md`，返回内容；或明确提示“请使用 `skills_read`”。
4. **修正 frontmatter 解析**：支持 `description: >` / `|` 的缩进块；统一 `localSkillCatalog` 与 `scanSkills`，避免两套解析漂移。

### P1（补“自动发现”，2–4 天）

1. **提示词加入按需规则**（不是每轮必搜）：
   - “当任务可能受益于本地 Skill（办公/设计/审查/图表/飞书/工程流程等），先调用 `skills_search`；命中后 `skills_read` 1–2 个最相关技能并遵循；未命中继续主任务，不要反复空搜。”
   - 明确“`skills_search` 返回的是候选，`skills_read` 才读取内容”。
2. **服务端确定性预选**（可与提示词并用）：
   - 在 admission 阶段用轻量分类器/关键词表产生候选（不必调用模型）；
   - 把候选名称、描述和“是否已读取”写入 task/capability plan；
   - 对项目设置或 `@智能体` 的 skills，自动预检并注入其 SKILL.md 摘要（仍需预算）。
3. **搜索器升级**：
   - 中文分词/同义词（如 `柱状图 → bar / 图表`、`审查 → review / qa`）；
   - OR + 评分（名称命中 > 描述命中），返回 top N 及命中理由；
   - 空查询返回分类清单而不是全量无序列表。
4. **可观测性**：`skills_search`、`skills_read`、选中的 skill、hash/截断统一写 Run 事件；flag 只控制注入格式/预算，不控制“是否有事件”。

### P2（体验与治理）

- Skill 广场显示“最近使用/适用任务/依赖工具”，项目设置可选择默认 Skill 集；
- 预置 Agent 的 skills 结构化下发，而不是只在 mention 文本里；
- 增加 `test:skill-discovery`：标记解析、描述解析、中文查询命中、自动/显式两组行为、无命中不阻塞；
- 评估 `noSkills:true` 是否长期合理：若模型能稳定按需搜索，可以保持；否则考虑注入压缩后的技能索引（名称+一行描述），而不是全量 SKILL.md。

## 8. 验收口径（建议）

| 场景 | 期望 |
|---|---|
| 普通“生成 ECharts 图”任务 | 至少一次 `skills_search`；命中后一次 `skills_read`；Run 事件有记录；未命中不阻塞 |
| 用户点击 Skill 广场「调用」 | task payload 含结构化 `skills`；服务端预检通过；模型读取对应 SKILL.md |
| 手工输入 `@技能[baoyu-echarts]` | 与 `#技能[...]` 等价，均能解析为 skill 引用并读取 |
| 10 个 block scalar 描述 | `/api/skills` 返回完整描述，不再为 `>`/`|` |
| 中文查询 `PPT 演示`、`文档审查`、`设计评审` | 至少 1 个合理候选；结果含命中理由 |
| 无匹配 Skill | 主任务继续，不出现“找不到技能”阻塞或虚构技能 |
| 审计 | Run 可查到 `skill_search`/`skill_read`/选中技能/注入字节数 |
