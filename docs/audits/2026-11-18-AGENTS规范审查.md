## 2. P1：可执行性缺陷（会导致规则跑不通）

### 2.1 S2 / S3 无条件要求 `test:ui-smoke`（§7.2 表格）

原文：S2「受影响 `test:*` + `npm run verify` + `test:ui-smoke`」；S3「收尾跑 `npm run verify` + `test:ui-smoke`」。

问题：S2 可能是**纯服务端/脚本**改动（例如 3 个 `server/*.mjs` 文件），`test:ui-smoke` 需要浏览器打开聊天界面，与改动无关却成为硬要求——要么跑无关测试浪费时间，要么事实上不执行导致条款失真。

**建议**：改为「+ `test:ui-smoke`（仅当触及 `client/`）」。

### 2.2 §7 第 4 步没接入新门禁（§7 第 4 步）

原文：「先跑目标测试，再跑 `npm run verify`；触及关键链路时跑对应 `test:*` 与 CI 同款脚本。」

问题：本轮新落地的 G1/G2/G3（`test:ui-smoke`、`test:known-failures`、`check:commit-gate`）只出现在 §10 索引，不在工作流第 4 步。规则写了却不在流程里 = 实际不会跑。

**建议**：第 4 步末尾补一句：
「提交前依次跑：`npm run test:known-failures` → `npm run check:commit-gate`；触及 `ChatPanel`/会话流/`styles.css` 时加 `npm run test:ui-smoke`（详见《[运行时验收与门禁规范](docs/规范/运行时验收与门禁规范.md)》）。」

### 2.3 §7 第 0 步的引用写法不统一且不可解析

实测并存两种写法：`§7.0`（2 处：§7.2 表格内「即 §7.0 的文档」、§7.2 豁免条目）+ `§7 第 0 步`（2 处：§4.2、§4.3）。

问题：`§7.0` **不是章节号**（第 0 步是 §7 内的列表项，没有独立标题），人/工具都无法按编号定位；同一文件两种写法易漂移。

**建议**：全量统一为「§7 第 0 步」。

### 2.4 S1「限单个文件」过严（§7.2 S1 判定列）

问题：最常见的 S1 恰恰是"同一条文案在 2 个文件各改一次"（如标题 + 按钮），按现行判据会被迫升 S2，走四件事 + 审查，与"两三句话能改完"的原始意图相反，实际会诱发绕过。

**建议**：判定改为「**限 1–2 个文件，且不新增交互状态 / 分支 / 契约**」。

### 2.5 §7.3「独立子代理」与 §5.1「官方不支持 subagent」表面冲突

- §5.1：「官方不支持 subagent / plan mode；项目通过 `server/子代理编排器.mjs` … 模拟」——讲的是**产品内** Agent 能力；
- §7.3：「必须安排一个独立子代理（subagent / 独立会话）」——讲的是**开发期**智能体工具。

两处都在讲 subagent，但没有一句区分，新接手的 agent 容易以为矛盾。

**建议**：§7.3 首句补「（指开发期智能体的子代理能力，与 §5.1 产品内子代理无关）」。
