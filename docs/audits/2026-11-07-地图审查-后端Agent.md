#### P0-1 `map_save_analysis` 引用未绑定变量 `name`，Work 模式“保存为正式图层”必然失败

- **类别**：事实缺陷（协作编辑断链）
- **证据**：`server/agent.mjs:3667`；上下文 `server/agent.mjs:3654-3700`（`execute`）、`server/agent.mjs:1358`（`_create` 作用域起点）、`server/agent.mjs:3003/3063/3226/3358/3395`（其余工具的 `const name` 均在自己 `execute` 内）
- **关键代码**（`server/agent.mjs:3654-3700`）：

```js
execute: async (_toolCallId, params) => {
  const action = entry.lastMapAnalysis;
  if (!action?.geojson) return { content: [{ type: "text", text: "当前没有可保存的地图分析结果…" }], details: {} };

  await requireToolApproval({ entry, tool: "map_save_analysis", input: `${project}/${layerId}`, … });
  await withPathWriteLock(ctx, "map_save_analysis", path.join(ctx.workspace, "maps", name), async () => {  // 3667：name 未定义
    …
    await map.importLayer(project, layerId, action.geojson);
```

- **现象**：`path.join(ctx.workspace, "maps", name)` 在取锁之前求值 → 立即 `ReferenceError: name is not defined`。`name` 不在 `mapSaveAnalysisTool.execute`、`_create`、模块任一作用域内（已用作用域扫描 + Node 全局变量验证确认，见 §1.3-1/2）。`wrapCustomTool` 的 try/catch 只在 `RUNTIME_FLAGS.toolErrorEnvelope` 打开时兜底（`server/agent.mjs:234-244`），而该开关默认关（`server/运行开关.mjs`：`toolErrorEnvelope: readFlag("OAW_TOOL_ERROR_ENVELOPE") || HARNESS_ALIGN`）→ 异常直接抛给 Pi SDK，最坏情况整轮对话以工具异常收尾。
- **影响**：
  - R10 明确列出的 Agent 工具 `map_save_analysis`（`REQUIREMENTS.md:246`）与验收口径“可转正的分析结果保存为正式图层”（`REQUIREMENTS.md:251`、`REQUIREMENTS.md:274`）在 Work 模式不可用；
  - Chat 对话栏“保存为正式图层”按钮会 `send("把刚才的地图分析…保存为正式图层。")`（`client/src/components/ChatPanel.jsx:4831`），模型必然调用该工具 → 失败；AI 画布向导的“确认后再保存为正式图层”提示同样落空；
  - 前端 MapPanel 自带的“临时层转正”走 REST `/api/map/project/:name/import`（`client/src/components/MapPanel.jsx:1771-1772`），因此 UI 自测容易误判“转正可用”，这是测试漏检的关键原因。
- **修复建议**：`path.join(ctx.workspace, "maps", project)`（与 map_import/map_reset 一致）；补行为级回归：直接构造 `entry/ctx/approval` 桩调用该 `execute`，断言不抛异常且落盘；`npm run verify` 增加 ESLint `no-undef`/scope 检查或至少对该文件做一次 `node --check` 之外的作用域静态扫描；`toolErrorEnvelope` 默认开启另行立项。
- **分类**：事实缺陷。

#### P1-1 `map_save_analysis` 没有审批 ask 规则：声明“需审批”，实际默认放行

- **类别**：契约不一致（安全/审批）
- **证据**：`server/审批策略.mjs:19-63`（无 `map_save_analysis` 的 ask 规则，仅 57 行 `shared/*` deny）；`server/agent.mjs:3663-3666`（调用 `requireToolApproval`，input 为 `${project}/${layerId}`）；`server/工具元数据.mjs:276-285`（`needsApproval: true`）；`REQUIREMENTS.md:246`（写工具仅 Work + 审批）；§1.3-3 实测命中 `default.0.*.*.allow`。

- **影响**：即使修复 P0-1，Agent 也能不经用户审批把分析结果（可能来自演示数据）写成正式图层；与 `map_edit/map_import/map_reset/map_project_create` 的“写操作需审批”不一致，违反 R10/工具元数据契约。
- **修复建议**：在 `审批策略.mjs` 的 `DEFAULT_RULES` 中、`shared/* deny` 之前加 `{ tool: "map_save_analysis", pattern: "*", action: "ask" }`；补 `matchToolDecision` 单测覆盖每个地图写工具；`工具元数据.mjs` 与策略表建立一致性测试。
- **分类**：契约不一致。

#### P1-2 共享数据集可被 `map_import` 覆盖：`shared/*` deny 规则不可达，锁定检查只看 `locked` 标志

- **类别**：一致性/领域约束（共享数据污染）
- **证据**：
  - 规则：`server/审批策略.mjs:56`（`{ tool: "map_import", pattern: "shared/*", action: "deny" }`）、`server/审批策略.mjs:47`（catch-all ask）；
  - 工具实际 input：`server/agent.mjs:3238-3242`（`input: String(rel || "")`，是工作区文件路径，不是 `shared/xxx`）；
  - 覆盖写入：`server/map.mjs:1457-1504`（`importLayer` 对已存在 layer 直接覆盖 `layers/{id}.geojson` 并重建瓦片；`existed` 分支只写 config/tiles，无回收站备份）；
  - 锁定检查只覆盖 `locked` 标志：`server/agent.mjs:3229-3237`（`cfg.layers.find(l => l.id === layerId && l.locked)`）；
  - 默认项目共享层 `highways` 为 `locked:false, origin:shared, source.kind:builtin`（§1.3-5）；
  - `markLayerOwnership` 对共享 id 返回 false（`server/图层仓库.mjs:210-216`），即数据被覆盖但归属仍显示“共享”。
- **现象**：用户说“把我改好的 `highways.geojson` 导入”，Agent 以 `layerId=highways` 调 `map_import` → 审批只展示文件路径（`maps_data/highways.geojson`），不展示“将覆盖共享数据集 highways”；用户允许后共享高速层 GeoJSON 与瓦片被替换。`deny` 规则永远命中不到；`map_save_analysis` 的 `shared/*` deny 同理不可达（input 是 `项目/图层`）。
- **影响**：公共底图数据被单个工作区污染，且 `.trash` 无旧数据（与“替换数据旧数据进回收站”“共享数据集不允许往里新增文件”的设计目标冲突）。
- **修复建议**：在工具层解析 `layerId → shared|workspace`（复用 `图层仓库.isSharedLayerId/layerRef`）后再组成审批 pattern；对 shared 目标在工具代码里硬 deny 并提示“导入到新图层 id”；`importLayer` 增加 `overwriteShared` 显式开关 + 覆盖前 `moveLayerToTrash` 备份；审批 input 同时带目标 layerId 与归属。
- **分类**：契约不一致（同时含安全/数据完整性）。

#### P2-7 地图写工具的台账/事件缺口与 `actor` 误标

### 4.3 临时分析层（map_action）一致性结论

- `map_action` 登记为 `lifecycle:true, persist:false`（`server/事件注册表.mjs:168`），由 `emitChannelSafe` 推当前会话通道（`server/agent.mjs:6939-6957`），根级事件流 `appendEvent` 因 `shouldPersistEvent` 返回 false 丢弃（`server/事件存储.mjs:220-229`）——**历史会话/重启后临时层不回放**，与 `REQUIREMENTS.md:274`“临时分析层仍不回放（需后续持久化）”一致，属**设计取舍**，不是缺陷。
- 影响面：刷新页面/重连（同 Runtime、通道历史未被挤出时可通过 `map_action` replay 恢复，`server/index.mjs:5442-5470`）；但进程重启/会话重建（新 streamId、通道历史空）后临时层丢失，`entry.lastMapAnalysis`（`server/agent.mjs:3655`）也不持久化 → 重启后无法再保存重启前的分析结果。建议在文档/UI 明确“重启后需重新生成”，或在后续版本持久化分析结果。

## 5. 专题：并发与一致性

1. **锁粒度**：地图工具用项目目录级锁（`agent.mjs:1729-1742`，target=`ctx.workspace/maps/<name>`），`写入协调.overlapping` 会做双向包含判断（`写入协调.mjs:67-71`），因此与同目录文件级锁互斥；不同项目互不阻塞（合理）。
2. **锁覆盖不足**：REST/前端写完全绕过锁（P1-5）；`map_edit` 读 style 在锁外（3103-3130 解析/读取，3187 才取锁）；`map_project_create` 无锁；同步瓦片构建期间锁被长时间持有（可能 20s 超时 → 其他 Run 报 WRITE_CONFLICT，`写入协调.mjs:265-300`）。
3. **版本 CAS**：只有 `write/edit` 暂存发布做 CAS（`写入协调.mjs:409-430`、`文件版本.mjs`）；地图 style/config/layers 无 revision 字段，`map.mjs` 全是 read-modify-write，最后由 `atomicWriteFile` 保证“整文件不截断”，但不能防丢更新。
4. **原子性**：style/config/baseline/settings 用 `atomicWriteJson`（好）；import 的 GeoJSON、archive 的 config、settings.local 非原子（P3-1）。
5. **半成品**：replace 先移旧数据再导入（P1-4）；import 的 config/data/tiles/style 四步无事务；`resetProject` 先复制快照再应用基线（快照可人工恢复，但 layers 已入 `.trash`）。
6. **多会话同项目**：服务端允许两个会话绑定同一 `mapProject`（无唯一性约束），各自 task 项目可不同（P2-13）；写锁只在真正同时写时互斥，读/渲染不互斥；变更通知按会话通道（P2-15）。
7. **直接写文件与 REST/地图工具的冲突**：提示词允许直写（P2-4），直写走 `write/edit` 的 stage/CAS，但与地图工具的“项目目录锁”只在发布阶段可能重叠；直写不会触发 `map.mjs` 的 config 归一化/基线/日志，导致同一项目两套写路径产生不同状态，是最容易产生“用户看到 A、Agent 看到 B”的来源。
