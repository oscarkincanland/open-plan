## 0. 结论先行

**ask_user 的卡片本身"能用"，问题不在视觉，而在三处结构性错位：**

1. **语义错位**：所有提问都套用"需要你确认"的确认卡，但 43% 的提问是"接下来做什么/是否继续/要不要写回"这类**收尾确认**，另有 32% 是写作澄清——两类问题的心智模型完全不同，却共用一套标题、按钮和"跳过"。
2. **交互层级错位**：消息流卡片（`AskBlock`）、输入栏待答条（`PendingActionBar`）、审批卡三处并存；没有"当前唯一待处理交互"的概念，没有焦点转移规则，也没有多问题排队形态（当前靠服务端单槽位硬拒第二个问题来兜底）。
3. **时间语义错位**：默认阻塞 30 分钟且卡片上没有倒计时/自动继续提示；超时后只留一行"已超时"，用户不知道 Agent 按什么假设继续了。

**一句话重设计**：把 ask 从"弹一张卡等你"改成"**默认假设 + 只在真阻塞处停 + 三种语义卡片（澄清/确认/预览）+ 统一状态机与焦点规则**"；提问总量应下降一半以上（目标触发率 ≤15%），卡片只是这条规则链路的末端表现。

### P2（打磨）

- 无 `aria-live` 播报策略（是否有新问题只靠视觉）；无 `role="dialog"`/焦点陷阱（当前不是模态，可能合理）；无"已回答"状态的撤销/修改（回答后不可改，只能发新消息）。

## 3. 重设计

### 3.1 设计目标与非目标

**目标**
1. 把提问总量降下来：只问"不问就做错"的信息缺口；收尾确认一律默认执行 + 可撤销。
2. 让每张卡"一眼知道该做什么"：澄清 / 确认 / 预览三种语义，标题与按钮随语义变化。
3. 建立唯一状态机与焦点规则：卡片是主状态，待答条是"缩略与定位"，审批是独立并列交互。
4. 时间语义可预期：超过 90 秒未答即按假设继续（可配置），并把假设明示在回执里。

**非目标**
- 不做独立模态弹窗打断用户输入（除非用户主动点"处理"）。
- 不改服务端工具协议的核心字段（`question/options/fields/previewFile` 保留），只**增加可选** `intent` 与 `assumption`。
- 不引入新的卡片视觉体系，沿用 DESIGN 的边框/圆角/字号档位。

### 3.2 触发规则（先于卡片：提问预算）

| 场景 | 动作 |
|---|---|
| 关键信息缺失且**不猜会做错**（文档类型、产物格式、必须包含的数据、覆盖范围） | 允许问 1 个，合并成一张卡（`fields` 多字段，最多 3 个必填） |
| 篇幅、受众、风格、语气、章节顺序 | **不问**，给默认值并在结果/假设卡里标注 |
| 收尾确认（是否继续/下一步/是否写回） | **不问**：直接执行默认动作或给出"可撤销"说明 |
| 高风险不可逆（覆盖原文件、批量删除、对外发布） | 允许确认卡（这类必须问） |
| 连续任务中已问过同一主题 | 不再问，复用上次假设（工作区记忆） |

**服务端建议**：`ask_user` 增加必填 `intent: "clarify" | "confirm" | "review"`（默认 clarify）与可选 `assumption`（超时后按什么继续）；`assumption` 进入回执与 Run 事件。

### 3.3 交互状态机

```
                ┌──────────── 收到 ask_user 事件 ────────────┐
                ▼                                            │
           [asked 未处理] ──用户点卡片/待答条"处理"──▶ [focused 已聚焦]
                │  │                                          │
                │  └── 用户继续在输入框打字 ──▶ 保持 asked（不抢焦点，只出角标）
                │                                             ▼
                │                                       [editing 填写中]
                │                                         │        │
                │                              提交        │        │ 跳过
                │                                 ▼        ▼        ▼
                └── 30min/90s 超时 ──▶ [expired]  [submitting]  [skipped]
                                              │
                                    成功 ──────┴──── 失败（404/网络）──▶ [failed 可重试 | expired]
                                              ▼
                                        [answered 回执]
取消/新指令 ─────────────────────────────▶ [cancelled 回执]

回执统一：一行，含"问题摘要 + 结果 + （超时）按假设继续：<assumption> + 可展开原文"
```

规则：
- 同一会话同时只有 1 张活动卡（沿用服务端单槽位）；若未来开放并行，输入栏显示"还有 n 个问题"。
- 回答提交时立即置 `submitting` 并禁用按钮（幂等：同一 `askId` 的重复提交返回第一次结果）。
- 断线/刷新：从 `/api/agent/pending` 恢复为 `asked`，**不自动聚焦**；用户回到会话顶部时显示"有 1 个问题待处理"。
- 新指令：旧卡立即变 `cancelled` 回执，文案"已被你的新指令作废"。

### 3.4 三种卡片形态

**① 澄清卡（clarify）**
- 标题：`需要你补充`；右上角：`来自本轮任务` / 计时（仅剩余 <5 分钟时显示）。
- 正文：问题一句 + 必要时 1 行"为什么问"（可选字段 `reason`，从 `options` 的 description 派生）。
- 交互：`fields` 表单（推荐）或 `options` 单选列表；始终保留"其他（自己写）"。
- 按钮：`继续`（主）、`按默认假设继续`（次，等价 skip）。

**② 确认卡（confirm）**
- 标题：`请确认`；正文：动作 + 目标 + 影响（例如"把 41 条批注写回原文件（原文件将被修改，已生成备份）"）。
- 按钮：`确认`（主）/ `取消`（次，不得用"跳过"）。
- 高风险动作：主按钮文字必须带动作（"写回原文件"），不能只写"确认"。

**③ 预览确认卡（review / previewFile）**
- 触发：`previewFile` 存在。
- 形态：紧凑条 + 右侧预览已自动打开：`草稿已打开：<文件名>`；按钮 `确认并继续` / `我要改（在下方输入）` / `先不确认`。
- 若用户正在预览其他文件：不自动切换，改为卡片上"打开草稿"按钮 + 提示。

### 3.5 卡片解剖（澄清卡线框）

```
┌──────────────────────────────────────────────────────────────┐
│ 💬 需要你补充                                    本轮 · 29:12 │  ← 标题/归属/倒计时（<5min才显示）
├──────────────────────────────────────────────────────────────┤
│ 这份汇报材料要写成哪种用途和形式？                            │  ← 问题（14px）
│                                                              │
│  ○ 完整汇报材料（Word，约 5000–7000 字，含分期表）             │  ← 选项=单选行，含描述
│  ● 精简汇报版（Word，约 2000–3000 字）                        │
│  ○ 口播稿（约 1500 字，不带表格）                             │
│  ○ 其他（自己写）                                             │
│                                                              │
│ ┌ 补充说明（可选）──────────────────────────────────────────┐ │
│ │ 例如：给县领导看、需要突出投资口径                          │ │
│ └──────────────────────────────────────────────────────────┘ │
│                                                              │
│ [继续]        [按默认假设继续]                    [定位/收起] │
└──────────────────────────────────────────────────────────────┘
```

**表单一屏最多 3 个字段**；超过 3 个必须拆两步或改用自由文本。

### 3.6 焦点与浮层策略

| 用户状态 | 行为 |
|---|---|
| 用户在会话底部、空闲 | 卡片插入后**不抢键盘焦点**；右侧/顶部出现一次 `aria-live="polite"` 提示"Agent 有问题待确认"；卡片本身带 `tabIndex=-1`，可被"定位"聚焦 |
| 用户正在输入框打字 | **绝不打断**：只在发送按钮旁显示角标（`1`）与待答条；Enter 仍发送用户消息（新指令会作废旧提问） |
| 用户滚动到历史 | 输入栏待答条常驻；点击"定位"滚动到卡片并把焦点给第一个选项 |
| 用户切到别的会话/窗口 | 任务中心/会话列表显示"待回答"状态点；回来后恢复 |
| 多个交互并存（ask + 审批） | 输入栏按到达顺序显示，各自独立按钮；不合并成一张卡 |

**不做模态弹窗**（`aria-modal`）的理由：ask 不是阻塞式系统对话框，模态会打断用户正在写的下一句；但可以做一个**非模态浮层**（右下角小卡）用于"会话不在前台"时提醒，点击后滚动定位。

### 3.7 文案

| 场景 | 文案 |
|---|---|
| 澄清卡标题 | 需要你补充 |
| 确认卡标题 | 请确认 |
| 预览卡标题 | 草稿已就绪 |
| 超时回执 | 已超时（30 分钟未回答），Agent 已按假设继续：`<assumption>` |
| 取消回执 | 已被你的新指令作废；如需继续，请在下方说明 |
| 跳过按钮 | 按默认假设继续（不再用"跳过"） |
| 高危确认按钮 | 用动作命名：写回原文件 / 覆盖并保存 / 删除这 3 个文件 |

### 3.8 键盘与可访问性

- `1–9`：选择对应选项；`Enter`：提交（表单校验通过时）；`Esc`：收起浮层/回到输入框，不清空已填内容。
- 中文输入法 composition 期间不拦截 `Enter`/数字键。
- 卡片 `role="group"` + `aria-labelledby`（标题）+ `aria-describedby`（问题）；回执 `role="status"`。
- 焦点顺序：标题 → 选项/表单 → 主按钮 → 次按钮 → 定位；"定位"后焦点落在第一项。
- 颜色不是唯一状态载体：`已超时/已取消` 同时有文案与图标。

### 3.9 与审批条、待答条的关系

- **卡片 = 唯一事实源**；`PendingActionBar` 降级为"缩略条"：只显示"待回答：<前 60 字>" + "处理"按钮 + 选项（仅 ≤4 个时） + "按默认假设继续"。
- **审批卡**保持独立样式（红色拒绝描边、允许一次/总是允许/拒绝），不要和 ask 共用"待答"措辞。
- 两者并存时，输入栏显示两行，高度不超过两行；超过则折叠为"2 个待处理交互"入口。

### 3.10 验收清单（可测断言）

1. 用户发一条 10 页 PPT 需求（含主题、受众、页数）→ 0 次 clarify 提问（或 ≤1 次且带 assumption），Run 正常产出。
2. 收尾阶段不再出现"接下来做什么/是否继续"类 ask（事件流可 grep）。
3. ask 事件到达时，若焦点在输入框：`document.activeElement` 不变，输入内容不丢。
4. 卡片出现 5 秒内 `aria-live` 区域有播报；`role/aria-*` 断言通过。
5. 点击"定位"后：卡片滚入视口且焦点在第一个选项。
6. 超时回执包含 `assumption` 文本；`expired` 卡片不可再输入。
7. 同一 `askId` 双击提交只产生一次回答（服务端幂等）。
8. 刷新/切会话回来，待答卡可恢复且不重复；已回答卡不重复出现在消息流。
9. 窄屏 560px：卡片不横向溢出；长选项换行而非撑破。
10. `file` 字段提交后，Agent 收到的回答能定位到实际文件（而不是只有文件名）。
