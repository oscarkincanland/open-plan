## 0. 结论先行

**用户"梳理不清"不是因为符号太多，而是因为四套触发器共用了两套互不知道的状态机、三套渲染层，且设计规范只承认其中一套。**

| 现象 | 直接原因 |
|---|---|
| "调用之后好像还是显示文字" | 插入的是**纯文本标记**（`@文件[...]`、`#技能[...]`、`@智能体[...]`）；发送后气泡里原样显示，chip 只对部分类型渲染（`ReferenceChips` 只认 @文件/@知识库/@模板/&会话，**不认 `#技能/#插件/@技能`**） |
| "打字好像又干扰" | `@` 同时触发**两个弹层**：`composer-suggestions`（文件）与"提及智能体"菜单；Enter 的语义按"提及 > 命令 > 发送"三级优先，同一按键三种结果 |
| "分不清 / @ # 命令" | `/` 是动作、`@` 既可能是文件也可能是智能体、`#` 既可能是技能也可能是文件、`&` 是会话；设计规范 `DESIGN.md:296` 只定义了 `#` 一组，其余是代码层"顺手加的" |
| "`#` 里看不到技能" | `#` 菜单只读 `project.settings.skills`（`ChatPanel.jsx:1250`），而 7/7 个项目该值都是 `[]`（子报告 02 实测）；66 个已装技能不在菜单里 |

**一句话方案**：把"符号"降级为"入口"，把交互统一成**一个候选面板 + 一套 token 状态机 + 三态一致 chip**（输入态 / 气泡态 / 服务端解析态），`/` 命令改为"选中即执行"、不再以文本形式进入消息流。

## 2. 现状：两套状态机 + 三套渲染层

### 2.1 两套状态机（互相不知道）

```
composerMenu = { symbol, query, start }     ← composerTrigger(value)
   ▲ onChange 时计算；Enter/↑↓/Esc 由 5179-5193 处理
mentionState = { start, query }            ← detectMentionTrigger(value, caret)
   ▲ onChange 时同时计算；Enter/↑↓/Esc 由 5164-5178 处理（优先级更高）
```

**同一时刻两个都可能非空**：`onChange` 里先后 `setComposerMenu` 与 `setMentionState`（`5205-5212`），渲染层也同时渲染两个浮层（`5131-5157`）。用户输入 `@` 后，文件菜单和智能体菜单会叠在一起，视觉上像"打字被干扰"。

### 2.2 三套渲染层

| 层 | 渲染对象 | 位置 | 缺口 |
|---|---|---|---|
| 输入框（textarea） | 纯文本，标记原样可见 | `5158-5213` | 无 chip、无颜色、无法整体删除 |
| 输入栏引用条 | `references` 状态（来自点击/选择器，不来自文本标记） | `5012-5022` | 与 textarea 里的标记**重复/不同步**；删 chip 不会删文本 |
| 消息气泡 | `ReferenceChips`（`msg-reference-chip`） | `6886-6902` | 只渲染 `@文件/@知识库/@模板/&会话`；**`#技能/#插件` 不会变 chip**，用户只看到文字 |
| 服务端 | `Reference` 对象（含 status：ok/missing/deferred） | `context.mjs:76-105`、`index.mjs:4880-4939` | 解析结果不回传前端气泡，用户看不到"解析成功/失败" |

## 4. 统一方案

### 4.1 信息架构：符号 = 入口，面板 = 唯一出口

- 输入 `/ @ # &` 任一符号（行首或空白后）打开**同一个候选面板**；符号只决定默认分组：
  - `/` → 命令组（动作，选中即执行）
  - `@` → 引用组（文件/知识库/模板/会话/智能体，选中插入引用 chip）
  - `#` → 标签组（技能/插件，选中插入引用 chip）
  - `&` → 会话组（历史会话，选中插入会话 chip）
- 面板顶部显示分组 tab（`动作` / `引用` / `技能与插件` / `会话`），允许 `Tab`/`←→` 切换；搜索框对全部分组检索。
- **同一时刻只允许一个面板**：`composerMenu` 统一状态为 `{ group, query, start, activeIndex }`，删除 `mentionState` 独立状态；`@` 后用户继续输入 `@智能体` 时自动切到"智能体"子分组。

### 4.2 Token 状态机（输入态）

```
idle ──输入符号──▶ open(group, query, start)
open ──继续输入──▶ open(过滤 query)
open ──Enter/Tab/点击──▶ committed(token)
open ──Esc/失焦/空白──▶ idle（保留已输入文本）
committed ──退格──▶ token 整体删除（原子）
committed ──点击 chip──▶ 弹出"编辑/移除"
```

- 文本层建议：保留 textarea，但在其下渲染一行 **chip 预览条**（`引用：@文件[a.docx] ×`、`技能：#技能[...] ×`），与 textarea 内标记双向同步；标记文本可以显示为浅色/短标签（如 `@a.docx`），长路径不硬塞输入框。
- 更彻底方案（P2）：contenteditable 或 textarea + token 覆盖层，真正"所见即 chip"。

### 4.3 三态一致的 chip

| 态 | 展示 |
|---|---|
| 输入态 | 输入框下方 chip 条，可 × 删除；未知类型黄色描边 |
| 气泡态 | 用户消息内渲染 chip（替代原始标记文本）；`@文件` 显示文件名、`#技能` 显示技能名、`&会话` 显示会话标题；chip 带状态点：已解析（默认）/待解析（灰）/未找到（红） |
| 服务端态 | admission 返回 `references[]`（含 status/message）后，前端更新对应 chip 的颜色与 tooltip；解析失败点击可看原因与修复建议 |

实现要点：
- 扩展 `parseReferenceMarkers`（`ChatPanel.jsx:627-649`）补齐 `@/#技能`、`#插件`、`#文件`；
- 发送时把"标记文本"从气泡展示文本中剥离，仅渲染 chip（保留原文供编辑回填）；
- 服务端 `/api/agent/prompt` 响应或 SSE 首事件回传 references 解析结果，供 chip 更新。

### 4.4 命令与消息分离

- `/` 面板的选项**选中即执行**（不再插入文本）：`/compact` 立即压缩、`/new` 立即新建、`/chat|agent|review` 立即切换、`/help` 打开帮助面板、`/goal` 打开目标设置浮层。
- 需要参数的命令（`/goal`）打开一个小浮层收集参数，命令本身不进消息流。
- 不提供"文本形式的历史命令"；执行结果以系统提示/系统消息呈现（现有 `pushSystem` 风格）。
- 保留"正文里输入 `/`"能力：只有行首或空白后的 `/` 才触发命令面板，其余当普通文本。

### 4.5 面板线框

```
┌─ 引用 ──────────────────────────────────────────────┐
│ 🔍 搜索文件/技能/会话…                               │
│ [引用] [技能与插件] [会话] [动作]                     │  ← Tab 切换；当前「引用」
├──────────────────────────────────────────────────────┤
│ 📄 汇报材料初稿.docx          工作区 · 刚刚修改       │
│ 📄 金东区农村公路规划.pdf      工作区                  │
│ 🧠 ultimate-ppt-master        技能 · 做 PPT 演示      │
│ 💬 上一轮：新昌工可汇报（会话）                        │
├──────────────────────────────────────────────────────┤
│ ↑↓ 选择   Tab 切组   Enter 插入   Esc 关闭            │
└──────────────────────────────────────────────────────┘
```

### 4.6 气泡线框

```
┌──────────────────────────────────────────────────┐
│ 用这份材料做一个 10 页汇报 PPT，面向县领导          │
│ ┌──────────────┐ ┌────────────────┐              │
│ │📄 汇报材料.docx│ │🧠 ultimate-ppt │ ← chip 可点击 │
│ │  已解析        │ │  master 待解析 │              │
│ └──────────────┘ └────────────────┘              │
└──────────────────────────────────────────────────┘
```

### 4.7 键盘与输入法规范

- 统一 keydown 分发（一个 handler，按"面板是否打开"分流）：
  - composition 中：全部放行（不拦截 Enter/Tab/数字/Esc）；
  - 面板打开：`↑↓` 移动、`Tab/Shift+Tab` 切组、`Enter` 选中、`Esc` 关闭（只关面板，不退出输入）；
  - 面板关闭：`Enter` 发送、`Shift+Enter` 换行、`Esc` 清空面板状态。
- 数字键 `1–9` 仅在面板打开且当前组有对应项时选中，否则当普通输入。
- `IMM` 组合结束后再计算触发（`compositionend` 后 `requestAnimationFrame` 重算 `composerMenu`），避免拼音中间态误开面板。

### 4.8 失败兜底

- 发送前：扫描标记，若存在无法识别的类型/空目标，气泡上方提示"有 1 个引用无法识别：`#技能[xxx]`（未找到技能）"，允许"仍然发送"或"移除"。
- 发送后：服务端 admission 预检失败（如技能不存在、文件越界）返回结构化错误；前端把对应 chip 标红并在消息流插入一条系统提示，不静默丢弃。
- 命令失败：`/compact` 失败等给 toast + 可重试，不写入消息流。

### 4.9 可访问性

- 面板 `role="listbox"` + `aria-activedescendant`，分组 tab 用 `role="tablist"`；
- chip 为 `button`（可点击查看详情/移除），`aria-label` 含类型与状态；
- 状态不只靠颜色：chip 附图标（已解析 ✓ / 未找到 ! / 待解析 …）。

## 5. 验收清单（可测断言）

1. 输入 `@` 只出现**一个**面板；文件与智能体在同一面板的不同分组。
2. 选中文件后：textarea 出现标记、chip 条出现对应 chip、删除 chip 同时删除标记。
