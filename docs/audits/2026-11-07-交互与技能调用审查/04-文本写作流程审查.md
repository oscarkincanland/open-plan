## 1. 结论先行

一句话：**写作"慢"的主因不是模型推理慢，而是"一次工具调用 = 一个模型回合"的回合数爆炸 + 没有回合上限；"机械"的主因不是文风模板，而是强制澄清/阶段闸门/每 6 轮进度播报这三套仪式。**

| 问题 | 结论 | 关键证据 |
|---|---|---|
| 一次写作到底多慢 | 写作类 Run 时长 p50 **3.1 分钟**、p90 **15.5 分钟**、实测最长 **49.4 分钟**（单篇汇报材料） | 96 个写作 Run（n=96，事件流统计）；42 个实际产出 docx/pptx 的 Run p50 6.9min、p90 21.8min |
| 首字多慢 | 提交→首个正文 delta：p50 **8.07s**、p95 **56.2s**；服务端准备只占 **0.55s**，其余是模型思考 | `/api/agent/timing`（n=8~9）；准入 468ms + 派发 78ms + 首个 provider 事件 35ms |
| 慢在哪 | 回合内模型开销占总时长 **45%**（225/499 分钟），工具执行 40%（198 分钟，含在回合内），`ask_user` 等待 13%（66 分钟），流水线阶段 4% | 94 个 ≤180min 写作 Run 时间预算分解 |
| 回合为什么爆炸 | 49 分钟 Run 中 **430/440 个回合恰好只有 1 次工具调用**；单篇文档调了 **367 次 officecli**（其中 `set` 266 次） | `run_bdc227db-…`：440 回合 / 442 工具 / 8.4min 工具时间 |
| 为什么没有上限 | 运行预算默认"无上限"（`OAW_RUN_BUDGET_UNLIMITED` 默认 true），25/45 回合软/硬预算默认**不生效**，只剩每 6 轮一次的进度播报 | `server/运行开关.mjs:66-70`、`server/轮次预算.mjs:11-16` |
| 机械感来源 | ①41% 写作 Run 触发"缺 ≥2 项"澄清闸门（36% 真的问了，13% 总时长在等回答）②22% 写作 Run 命中闸门拒绝（CLARIFICATION_REQUIRED / OFFICE_PIPELINE_REQUIRED）③每 6 轮进度播报（全量 543 次；单个 Run 74 次），逼出大量 80 字以内、逐步播报式的"机器人旁白" | `server/task.mjs:293-331`、`server/office规范/执行闸门.mjs:256-303`、`server/轮次预算.mjs:43-51` |
| 文风机械感 | 终稿文风模板不是主因（只有 7% 回复用 `## 结论`）；真正固定的是"模板优先 + 六步写作流程 + 收尾四件套"；仓库里已有 humanizer（33 条反 AI 文风规则）与 doc-coauthoring，但**没有接入默认写作链路** | 56 条写作终稿统计；`server/task.mjs:563-583`；`.claude/skills/humanizer/SKILL.md` |
| 用户今天未提交的改动 | `ChatPanel.jsx` 把默认推理档从 `default` 改为 `high`，是**真实生效的**（11-07 06:45 的 Run 事件 `thinking_level requested=high effective=high`）；但它是加速项而非 49 分钟主因，且相对该用户 11-04～11-06 常用的 `max` 反而是降档 | `git diff client/src/components/ChatPanel.jsx`；事件流 `thinking_level`；`server/agent.mjs:5828-5845` |

**总体判断**：写作链路已经"能力齐全"（模板、场景、版式、流水线、验收都有），但控制流过重、执行流过碎。精简方向不是再加能力，而是**砍回合、砍仪式、把写作变成一次成稿**。

## 3. 现状链路（代码事实）

### 3.1 入口路由：四路由 + 澄清计划（每个 Run 开始前确定）

`server/task.mjs:232-290` 用关键词把需求分成 `template`（模板写作）/ `edit`（改既有文档）/ `generate`（原生生成）/ `read`（只读）。同时 `assessClarification()`（`server/task.mjs:310-331`）用**正则**检查最小信息集 5 项：文档类型、篇幅、受众、素材/数据来源、风格（`server/task.mjs:82-113`）；**缺失 ≥2 项 → `shouldAsk=true`**，只问最阻塞的一项。

这个判定是"机械"的第一层：它不区分"用户已经说清楚"和"表述里没出现关键词"。例如"帮我写一份某区农村公路的汇报材料，3-4 页左右，公文版式"只命中类型/篇幅，受众/来源/风格三项判缺 → 仍会进入提问计划（用户原文已脱敏改写）。

### 3.2 写作路由强制提示词（每轮注入）

`server/agent.mjs:1416-1426` 的 `.agent-context.md` 固定注入写作规则：

- **主动询问（重要）**：写作关键信息不明确必须 ask_user，"**只在缺失 ≥2 项时提问，每次只问一个最阻塞的问题**"；只缺 1 项按默认值继续并在结果中注明假设。
- **模板优先（重要）**：写交通规划文体必须先用 read 读 `templates/traffic-material/` 对应模板，按章节骨架/必备图表/格式规则写，"不要凭记忆自造结构"。
- **草稿确认**：已生成 Markdown 草稿时，ask_user 用 `previewFile` 指向草稿让用户先确认。
- 另有"改文档先读后改""复杂任务待办""收尾直接给最终答复"等 10 余条。

写作路由还会追加 `officeWritingPlaybook()`（`server/task.mjs:563-583`）的**六步固定顺序**：读模板 → editorial_pipeline → 逐章 write+add → 用预置样式 → validate/view issues 自检 → 直接收尾；并明确"不要用 bash 写生成脚本、不要手写 styles.xml、不要跑 help 探索"。对确定性有帮助，但也意味着**所有写作任务走同一条流水线脚本**。

### 3.3 三道闸门（为什么"走不动"）

| 闸门 | 位置 | 行为 |
|---|---|---|
| 澄清前置 | `server/office规范/执行闸门.mjs:256-265`；`OfficeCLI调用规约.mjs:107-115` | 写作路由下，只要 `clarificationPending` 存在，任何写工具（write/edit/officecli 写命令/editorial_pipeline）直接 `CLARIFICATION_REQUIRED`；ask_user 发出后解除 |
| 管线前置 | `执行闸门.mjs:273-303`；`OfficeCLI调用规约.mjs:116-130` | 写作路由下禁止 bash 生成 docx/pptx、禁止 write/edit 写 Office 二进制或生成脚本、禁止 `officecli add --type markdown`、**管线未产出前禁止 officecli create/set/add/batch** |
| 流水线强制 | `server/agent.mjs:5012-5020` | 写作路由 10 回合仍未走 `editorial_pipeline` → steer 提醒"请立即改用编辑流水线" |

闸门本身是防止"脚本乱生成"的正确设计（v0.13.3 落地），但它把**所有失败都变成一次被拒 + 一次改路 + 一次重试**，在长回合任务里被放大。

### 3.4 编辑流水线（四阶段模型调用）

`server/编辑流水线.mjs:31-38`：Planner（规划结构）→ Writer（撰写正文）→ Formatter（原生 OOXML 直写）→ Evaluator（确定性检查 + 可选模型语义复核，revise 回环最多 1 轮，`编辑流水线.mjs:416-528`）。

关键成本点：

- 未提供 `sourceMarkdown` 时，Planner 与 Writer 是**两次独立的子会话模型调用**（`编辑流水线.mjs:353-413`），实测 Planner 约 98s、Writer 约 127s（49 分钟 Run）；两者都要求"只输出 JSON"，解析失败即整个阶段失败（实测 Writer 有 4 次"未返回可解析的 JSON"）。
- `autoClarify=true` 时，缺 ≥2 项直接 `needs_clarification` 返回、不产成品（`编辑流水线.mjs:248-277`），把"问"提到最前面。
- 验收失败会触发 revise 回环（实测样本中 5 次 `revise`、1 次 `fail`），每次回环再跑 Writer/Formatter/Evaluator。

### 3.5 收尾与验收

- `server/终稿.mjs` 只做"只思考不出文本"的终态识别（避免把进度文本当最终答复），不涉及"是否完成"的自动判定。
- `server/成果验收.mjs` 在 Run 结束/产物发布时做 officecli validate + 文本/图片检查；`server/成果管理.mjs` 管理确认/发布。
- 回合循环里还有 `complete_task` 声明仪式（`completion_nudge` 共 13 次，提示"工具执行已结束但未声明完成"）。

## 4. 慢在哪里（量化）

### 4.1 总体基线

| 指标 | 写作类 Run（n=96，事件流） | 写作类任务（n=125，会话侧） |
|---|---|---|
| 总时长 p50 / p90 | **188s / 929s（3.1 / 15.5 分钟）** | 71s / 552s（1.2 / 9.2 分钟） |
| 最长 | 2,943s（49.4 分钟，单篇汇报材料） | 17,611s（跨天会话，异常未收口） |
| 模型回合 p50 / p90 / max | 9 / 44 / **440** | 9 / 43 / **430** |
| 工具调用 p50 / p90 | 12 / 62 | 10 / 52 |
| officecli 调用 p50 / p90 / max | 0 / 32 / **367** | — |
| ask_user 触发率 | **36%**（35/96） | **31%** |
| 闸门拒绝命中率 | **22%**（21/96，45 次拒绝：管线 22 + 澄清 21 + 其它 2） | — |
| 实际产出 docx/pptx 的 Run（42 个） | p50 **6.9 分钟** / p90 **21.8 分钟**；回合 p50 16 / p90 51；officecli p90 61 | — |

按路由看（写作 Run）：

| 路由 | n | 时长 p50/p90 | 回合 p50/p90 | officecli p50/p90 | 提问 Run 占比 |
|---|---|---|---|---|---|
| template | 28 | 2.3 / 21.8 min | 9 / 123 | 0 / 85 | 61% |
| generate | 11 | 4.6 / 7.8 min | 15 / 20 | 6 / 10 | 82% |
| edit | 3 | 3.6 / 6.8 min | 9 / 69 | 5 / 61 | 0% |
| read（误入写作词） | 27 | 0.6 / 10.5 min | 10 / 46 | 0 / 7 | 22% |
| 无计划（旧 Run） | 27 | 3.5 / 15.5 min | 4 / 38 | 2 / 30 | 26% |

模板路由反而最容易变成 20 分钟级长任务（p90 21.8min、回合 p90 123）——因为"读模板→强制流水线→逐章写→逐项排版→验收→返工"的链路最长。

### 4.2 首字延迟：服务端已经不是瓶颈

`GET /api/agent/timing`（当前进程，n=9；`firstTextDeltaAt` n=8）：

| 分段 | p50 | p95 |
|---|---|---|
| 提交→服务端收到 | 5ms | 20ms |
| 服务端收到→准入完成 | 468ms | 700ms |
| 准入→SDK 派发 | 78ms | 164ms |
| SDK 派发→首个 provider 事件 | 35ms | 58ms |
| **提交→首个正文 delta** | **8,073ms** | **56,211ms** |
| 首个 delta→DOM 文本 | 53ms | 1,564ms |

结论（已验证）：**服务端准备 0.55s、网关首事件 35ms、前端渲染 0.05s；首字的 90%+ 是模型"想完才出字"**。这与 v0.11.47（`变更日志.md:2792-2810`）的结论一致：服务端准备已从 4.6s 降到 0.4s，剩余 5.4–7.6s 由模型推理主导。

准入内部的细分跨度显示：`beforeFiles`（运行前文件/快照预检相关）p50 **906ms**、p95 **3000ms**，`snapshot` p50 106ms、`modePolicy` p50 50ms——也就是说个别 Run 的准入会被文件快照拖到 3s，但整体不是首字主因。

### 4.3 单次写作的时间都花在哪

94 个 ≤180min 写作 Run 的时间预算（合计 499 分钟）：

| 组成 | 分钟 | 占总时长 | 说明 |
|---|---|---|---|
| 回合内时间（含工具） | 423 | **85%** | 模型生成 + 工具执行都在回合内 |
| 其中工具执行 | 198 | 40% | 与回合重叠，officecli 49min、bash 45min、ask 66min 等 |
| 其中模型开销（回合-工具） | **225** | **45%** | 每轮读上下文、思考、写工具参数 |
| ask_user 等待（工具外单独计） | 66 | 13% | 35 个 Run 有提问，其中 10 次 ≥4 分钟 |
| 流水线阶段 | 20 | 4% | 18 个 Run 使用，失败/返工拉长 |
| 其它（准入、事件、落盘） | 约 10 | 2% | — |

**每轮成本**：49 分钟 Run 平均 `turn_started→首个 assistant 事件` 3.8s、`首个事件→回合结束` 2.9s，合计约 6.7s/回合。按 440 回合计算，仅"模型回合"就约 49 分钟——与总时长几乎相等。

### 4.4 回合数为什么爆炸：1 回合 = 1 个工具

`run_bdc227db-0d24-4270-a507-0e981fff1019`（2026-11-07 06:45，单篇汇报材料，49.4 分钟）的完整分解：

- 440 回合 / 442 次工具；**430 个回合恰好 1 次工具调用**，6 个回合约 2 次，4 个回合无工具 → 本质是"一条命令一个来回"。
- 工具构成：**officecli 367**（`set` 266、`view` 23、`query` 24、`get` 19、`batch` 16、`help` 7、`validate` 7、`add` 4、`move` 1）+ bash 40 + read 10 + write 5 + todo 4 + editorial_pipeline 3 + 其它。
- 工具总耗时只有 8.4 分钟（17%），其余 40.9 分钟（83%）是模型在每轮之间读上下文、思考、生成下一条命令。
- 失败 33 次（7.5%），**重复同参调用 119 次（27%）**；`help` 被调用 7 次（提示词明确说不要用 help 探索）。
- 同一 Run 有 6 次闸门拒绝（1 次 CLARIFICATION + 5 次 OFFICE_PIPELINE），74 次进度播报 steer。
- 该 Run 的 officecli 中 `set` 266 次，说明"版式精修"是逐属性单条命令（字体/字号/行距/对齐……），没有用一次 `batch` 批量下发。

这不是单个模型的坏运气：`run_0d7a7ae3…`（改稿，21.8 分钟）有 3 次 `officecli set` 各 131s 的超时；`run_2e054070…`（PPT，21.8 分钟）4 次 editorial_pipeline 调用共约 375+273+… 秒，Evaluator 连续 `revise` 3 次后 `fail`。

### 4.5 回合预算默认关闭

`server/运行开关.mjs:66-70`：

```js
/** 运行预算：默认无上限（不再按 25/45 回合、80/160 工具、45/90 分钟强制收尾）。
    显式 OAW_RUN_BUDGET_UNLIMITED=0 可恢复旧的限额行为。 */
runBudgetUnlimited: readFlagDefault("OAW_RUN_BUDGET_UNLIMITED", true),
```

因此 `server/运行预算.mjs:16-21` 的 25/45 回合、80/160 工具、45/90 分钟预算**默认全部不生效**，只剩 `turnNoticeKind()` 的每 6 轮进度播报（`server/轮次预算.mjs:14-16`）。49 分钟 Run 在 440 回合内没有收到任何"硬预算/收尾"信号，只有一路"请先给 2-3 行进度小结"。

这是"慢"的第一结构性原因：**系统明知长任务会失控，但默认把刹车拆了。**

### 4.6 进度播报本身也在制造回合

- 事件流中 `steer` 共 592 次，其中 `turn-progress` **543 次**；写作 Run 内 285 次；49 分钟 Run 74 次（440/6 ≈ 73，正好每个 6 轮触发一次）。
- 每次 steer 的文案要求"先在正文里给用户一段 2-3 行的进度小结，写完再继续，不要在小结里调用工具"（`server/轮次预算.mjs:47`）——这等于**每 6 轮强制插入一个非工具回合**。
- 实测该 Run 共 223 条 assistant 文本消息、17,706 字符，其中 165 条（74%）短于 80 字，是典型的逐步旁白（"先读模板…""模板已读完…""已定稿…"）。用户看到的"机械感"，很大一部分就是这 223 条高频短播报。
- 折算（推断）：74 次 steer 至少多 74 个回合 × 6.7s ≈ 8 分钟，占该 Run 16%；同时把正文切成碎片，干扰写作连贯性。

### 4.7 ask_user 阻塞：13% 总时长，且历史上大量空等

`.oaw/pending-asks.json`（93 条）：

| 指标 | 数值 |
|---|---|
| 已答 / 超时 / 待答 | 75 / **16（17%）** / 2 |
| 用户回答等待 p50 / p90 | **11.4s / 72.6s**（答了的情况其实很快） |
| 超时提问的历史耗时 | 14 条 × 5 分钟 = **70 分钟**（2026-11-04 前的 5 分钟超时；之后默认 30 分钟，见 `agent.mjs:667-668`） |
| 提问分类（本次复核口径） | 确认类 28、写作澄清 32、其它 33（Lead 侧先行统计为 40/30/其余，口径更宽；两者都表明约 1/4~4/10 是"是否继续/接下来"类非必要提问） |
| 写作 Run 内的 ask 阻塞 | 35/96 个 Run，合计 66 分钟，占写作总时长 13%；单 Run 最高占 54%（p90） |

关键点：**答得快的时候不慢（p50 11 秒）；慢的是"问完用户没在看"**——14 次超时×5 分钟、2 次待答 30 分钟封顶。而提问内容中约 1/4~4/10 是"接下来怎么做/要不要继续/是否写回"这类**收尾确认**，不是真正阻塞写作的信息缺口。这类提问即使被回答，也只是把"已经能做的下一步"推迟了一次。

### 4.8 上下文与每轮注入

以 2026-11-06 15:29 起的长会话（680 个 assistant 回合）为例：

| 项 | 数值 |
|---|---|
| 系统提示分段（JSON 体积） | 约 18KB：`project_context` 14.3KB + `docs` 1.4KB + `rules` 790B + `tools` 1.2KB + preamble/cwd |

| 会话上下文 token（每请求 prompt） | 第 2 轮 34K → 第 101 轮 88K → 第 301 轮 272K → **第 680 轮 524K** |
| 压缩（compaction） | 仅 3 次（第 451/457/668 轮附近），远晚于 128K 窗口 |
| 末 100 轮平均 prompt | **479,619 tokens** |

已验证的后果：该 Run 每轮 TTFT 前 20 轮平均 1.93s、末 20 轮平均 3.88s（翻倍）；即使有 prompt cache（cacheRead ≈ 99%），**每轮仍需为 50 万 token 的上下文付出调度/校验成本**。长会话把"单篇写作"拖进了"整段历史反复重读"。

### 4.10 今天未提交的推理档位改动（单独核实）

- 事实：`git diff client/src/components/ChatPanel.jsx` 显示工作树新增 `DEFAULT_THINKING_EFFORT = "high"`、一次性迁移键 `oaw_thinking_level_v3`、`effectiveEffort` 降级链（`ChatPanel.jsx:89-92、1129-1137`）。HEAD 版本默认 `default`（跟随模型）。
- 服务端接线：`requestedThinkingLevel = effort || "default"`；`"default"` 表示不主动改档，非 default 时走 `resolveThinkingLevel()` 并 `setThinkingLevel()`（`server/agent.mjs:5828-5845`）。
- 真实生效证据：2026-11-07 06:45 Run 的 `thinking_level` 事件为 `requested=high, effective=high`；此前 11-04～11-06 的事件多为 `requested=max, effective=max`；更早有 low/high 混合。
- 影响判断：
  - **对首字**：影响真实存在——首字时间 90% 是思考阶段（provider 首事件 35ms，首正文 delta 8s），档位越高思考越长。若模型的"跟随默认"低于 high，改为 high 会让首字变慢约 1–3s（推断；无 A/B）。
  - **对总时长**：不是主因。49 分钟 Run 在 `high` 下核心成本是 440 回合；即使用 `max`，用户此前每天的写作 Run 也常是 20–50 分钟。
  - **对当前用户**：其 11-04～11-06 的历史档位是 `max`，今天改为 `high` **相对是降档**（更浅、更快），与"最近变慢"的直觉相反；因此不能把本次抱怨归因于这次改动。
- 结论：该改动值得保留讨论（写作场景更适合 medium/低档 + 先出正文），但**不能当成"慢"的替罪羊**；归因优先级仍是回合数 > 上下文 > 仪式 > 档位。

## 5. 机械在哪里（量化）

### 5.1 强制澄清：用正则判断"用户没说清楚"

- 41% 写作 Run 的 `capability_plan.clarification.shouldAsk=true`（39/96）。
- 36% 的写作 Run 真的调用了 ask_user（45 次）；写作类提问在提问台账里占 32/93。
- 提问本身经常是"文档类型/篇幅/受众/风格"这类**可以在正文里默认并标注假设**的项；提示词自己已写明"只缺 1 项按默认值继续"，但正则同时缺 3–4 项时必然触发。
- 用户侧体验：一段已经相当具体的需求（含页数、版式、主题）仍可能被反问；一次写作最多出现 2 次提问（实测 `run_24c48fa3`），每次最长阻塞 30 分钟。

### 5.2 闸门拒绝：22% 的写作 Run 至少被拒绝一次

- 事件流中 `tool_gate_denied` 共 55 次：`OFFICE_PIPELINE_REQUIRED` 22 次、`CLARIFICATION_REQUIRED` 21 次，其余为内存/只读类。
- 21/96 个写作 Run 至少命中一次；`run_2f554414` 单 Run 7 次、`run_bdc227db` 6 次。
- 每次拒绝 = 模型白写一条命令 + 下一轮改路 + 可能触发 ask_user / pipeline 重试；在 440 回合里这就是 6 个额外来回（约 40 秒），更重要的是**打断写作节奏**。
- 这些闸门是"有意的强约束"，问题不在"要不要闸门"，而在**闸门出现在执行中途，而不是在 Run 开始前一次性把路径定好**。

### 5.3 阶段仪式：模板优先 + 固定六步

- 28/96 写作 Run 走 template 路由，提示词要求先 read 14 份交通模板之一，按其章节骨架与必备图表写作（`agent.mjs:1417`、`task.mjs:563-583`）。结果是同类文档**章节名、顺序、表格位置高度一致**——这是设计目标，但也是"每篇都一个模子"的直接来源。
- 写作 playbook 固定六步、固定顺序、固定自检项；模型没有"这篇短、直接写"的分支。
- 流水线四阶段（Planner→Writer→Formatter→Evaluator）本来是为"结构化长文"设计；实测 18/96 个 Run 使用，且多数在 `sourceMarkdown` 直通后跳过 Planner/Writer（17 次 skipped）——说明**真正需要四阶段的场景不多，但每次启用都要付模型调的固定成本**（约 2–6 分钟）。

### 5.4 进度播报与收尾仪式

- 全量 `turn-progress` steer 543 次；49 分钟 Run 74 次；同一 Run 的 assistant 文本中 74% 短于 80 字，属于"做完一步报一步"的机器旁白。
- `completion_nudge` 13 次；"本轮已结束但未声明完成"会再催一轮 `complete_task`。
- 最终答复统计（56 条写作终稿）：p50 667 字、p90 1,820 字；34% 出现"已完成/顺利完成/已全部完成"类套话，16% 出现"通过校验/验证通过"，29% 出现"建议/期待/供参考"，18% 用编号清单，14% 用"**加粗前缀**："列表；仅 7% 用 `## 结论`、4% 用 `## 关键结果`。也就是说：**回复并非固定小标题模板，但收尾话术高度同质**（完成宣告 + 产物路径 + 校验通过 + 建议）。

### 5.5 工具链的"机械动作"

- 写作 Run 中 officecli 子命令累计：`set` 480、`view` 214、`get` 120、`add` 94、`query` 73、`batch` 63、`remove` 57、`validate` 26、**`help` 27**。
- 重复同参调用：长 Run 中 119/442（27%）、`run_2f554414` 82/213（38%）。
- 说明：模型把"排版"理解成"逐条 set 属性"，而不是"一次批处理 + 一次校验"。`batch` 已经存在（63 次使用），但没有成为默认路径。

### 5.6 稀缺的"文风"输入：没有 voice sample / few-shot

- 默认写作提示词中没有任何"用户文风样例"机制：模板只给结构，写作 playbook 只给步骤，`template` 只给章节骨架；**没有任何一条规则告诉模型"短句、少套话、不要重复结论、要给数字"**。
- 仓库里其实有成熟方法论：
  - `humanizer`：33 条 AI 文风识别规则 + voice calibration（读用户样例，匹配句长/用词/段落开头/标点习惯）；
  - `doc-coauthoring`：Context Gathering → Refinement & Structure → Reader Testing 三阶段，先把上下文问清再写；
  - `research-writing-skill`：evidence-driven writing、分章写作、文献综述。
- 但这些是 Skills，只有模型主动 `skills_read` 才会生效；写作路由的强制提示词没有把它们接进来（代码检索：`agent.mjs` 写作段落未引用 humanizer/voice）。因此"文风"完全依赖模型默认先验，再叠加 14 份模板的骨架 → **结构统一、措辞默认、套话自然出现**。

### 5.7 机械感来源排序（本次判断）

| 排序 | 来源 | 可量化证据 | 对用户感受的贡献 |
|---|---|---|---|
| 1 | 高频进度播报 + 分步旁白 | 543 次 steer；单 Run 223 条短文本 | 高：看起来像"执行日志"，不像"在写东西" |
| 2 | 强制澄清/收尾确认 | 36% 写作 Run 提问；16/93 超时；约 1/4 是"是否继续" | 高：打断、空等、重复问答 |
| 3 | 模板骨架 + 固定流程 | 28/96 模板路由；六步固定 playbook | 中高：同类文档结构、节奏一致 |
| 4 | 收尾套话 | 34% "已完成"、16% "通过"、29% "建议" | 中：完成语感同质 |
| 5 | 逐条 set 式排版 | 266 次 set；help 7 次 | 中：过程冗长，产物"精修感"来自命令堆叠 |
| 6 | 缺少用户文风样例 | 提示词无 voice/few-shot；humanizer 未接入 | 中：措辞默认、个性弱 |

## 6. 精简后的写作流程方案

### 6.1 目标指标（由基线反推）

| 指标 | 当前基线 | 目标（P1 完成时） | 依据 |
|---|---|---|---|
| 首字（提交→首正文 delta）p50 / p95 | 8.07s / 56.2s | **≤4s / ≤10s** | 服务端准备 0.55s，剩余取决于思考档位；写作默认 medium + 先出标题/第一段 |
| 单次写作总时长 p50 / p90 | 3.1min / 15.5min | **≤2min / ≤6min** | 回合 p90 44→≤20；officecli 批处理；去掉播报回合 |
| 模型回合 p90（写作） | 44（最长 440） | **≤20（硬上限 60）** | 1 回合 1 工具是主成本；批处理可把 367→<40 |
| 用户确认次数 | 0–2 次，最长阻塞 30min | **≤1 次，阻塞 ≤90s** | 默认假设卡 + 异步提问 |
| officecli 调用/文档 | p90 61、max 367 | **≤40** | `batch` 一次下发样式；验收一次 |
| 闸门拒绝/写作 Run | 0.57 次/run（55/96） | **≤0.1** | 路径在 Run 开始前一次性确定 |

> 说明：目标值取"可比样本内可达"的下沿，不是拍脑袋——回合 p90 44 中约 20 来自排版/校验往返（可压缩），stеer 与 ask 是纯仪式成本（可归零）。

### 6.2 新流程（默认一次成稿）

```
用户提出写作需求
  ↓ (0) 预检（并行，<1s）
     读当前文档/引用 + 模板骨架 + 项目偏好；确定文体与产物格式
  ↓ (1) 默认假设卡（不阻塞）
     一次给出 3–5 条假设：文档类型/篇幅/受众/风格/数据来源
     用户可一键改；90s 未改按假设继续；假设写入结果
  ↓ (2) 一次成稿
     直接写 Markdown 正文（不先出大纲；用户显式要求或 >8000 字才附可选大纲）
     ↓ 同一份 Markdown 直接进 docx/pptx 排版（sourceMarkdown 直通，跳过 Planner/Writer）
  ↓ (3) 预览即终稿
     前端直接打开 Markdown/草稿预览（previewFile），不额外发起"确认轮"
     ↓ 一次自动验收（officecli validate + 规则闸门），失败自动修一次
  ↓ (4) 交付
     最终答复 3 句：做了什么 / 产物路径 / 3 条假设与未完成项
```

配套规则（写进提示词，替换现有六步 playbook）：

1. **只在真正阻塞时提问**：缺"文档类型/产物格式/必须包含的数据"才问；篇幅、受众、风格一律默认并标注。**删除"是否继续/接下来/要不要写回"类提问**。
2. **大纲可选**：默认不产出独立大纲；用户说"先列大纲"或预计 >8000 字时，大纲折叠在正文前的可选项里。
3. **草稿与终稿合一**：Markdown 即终稿；`docx` 由同一份 Markdown 直通生成；不再有"草稿确认→再生成"的两段式。
4. **预览即确认**：前端预览文件即视为最终预览；用户改了就重排一次，不重新走流程。
5. **一次验收**：确定性校验（validate + 规则闸门）通过即交付；模型语义复核默认关闭（仅长文/高风险开启）。
6. **假设可复用**：同一项目/同一文档的假设存入工作区记忆，下次写作不再重复问。

### 6.3 文风去机械（写作宪法 + 样例机制）

新建一份写作宪法，作为**写作路由的系统提示（替换现有"模板优先必须套骨架"的强度）**：

**A. 禁用清单（对齐 humanizer 的高频项，中文版）**
- 禁止空转套话：高度重视、扎实推进、紧紧围绕、不断提升、有效推动、进一步加强（除非用户指定公文口吻且逐条有具体动作）。
- 禁止"意义拔高"：标志着、彰显了、体现了…的重要意义（除非有事实来源）。
- 禁止重复结论：结论只在开头出现一次；结尾不重复"综上所述/总而言之"。
- 禁止三段等长：段落长度与信息量匹配，允许 1 句段与 8 句段并存。
- 禁止"首先/其次/最后"式空序列（有真实先后关系才用）。
- 禁止"我们将/将持续"无主语承诺；每条承诺必须有时间/责任/数字。

**B. 具体化要求**
- 每 500 字至少 3 个可核验事实：数字、日期、地名、文件名、来源（无来源就写"待核实"，不许编）。
- 每段第一句必须是信息句（不是"随着…的发展"）。
- 引用资料写清"哪份文件的哪一节"，禁止"相关研究表明"。

**C. 结构与节奏**
- 结构跟随文体（汇报/可研/讲话稿/总结各不同），模板只取骨架，不抄措辞、不硬凑必备图表之外的内容。
- 长文允许"一段一意"，不强制每节等长；讲话稿按口语停顿断句。
- 每篇至少一处"用户自己的材料里的细节"（来自工作区/附件），避免通用稿。

**D. voice sample / few-shot**
- 首次为某用户写作时，请用户给 200–500 字自己的旧文（或从工作区挑一篇），存为 `memory/style-{project}.md`；后续写作注入"匹配其句长/用词/段落开头"。
- 每类文体维护 1 篇"参考稿"（人工挑选、注明只学结构与语气，不抄句子）。
- 交付前跑一次规则自检（可脚本化：套话词表、重复句、段长方差、无数字段落比例），不通过则重写该段。

### 6.4 性能改造（按收益排序）

### 6.5 分阶段实施与验收

**P0（1–2 天，配置+提示词，可回退）**
- 写作路由关闭周期播报；恢复 60/30 回合预算；提示词加入"batch 排版/禁止逐条 set"；删除"是否写回/是否继续"类提问；写作默认 thinking=medium。
- 验收：10 个历史写作需求重放（只读回放/事件重算，不调真实模型）+ 1 个真实小样本（由用户执行）；指标：回合 p90、officecli 次数、steer 次数、ask 次数。
- 回归：`npm run test:first-token-latency`、`test:first-token-fix`、`test:office-*`、`test:editorial-pipeline` 保持通过。

**P1（约 1 周，流程）**
- 一次成稿链路（Markdown 直通 + preview 即终稿）、假设卡/异步提问、写作宪法 + 自检脚本、voice sample 机制、回合硬上限 60。
- 验收：真实写作 10 例 A/B；p50 总时长 ≤2min、p90 ≤6min；首字 p50 ≤4s；ask ≤1 次/任务且阻塞 ≤90s；人工盲评（3 人、5 分制）文风 ≥4 分、结构自然度 ≥4 分。

**P2（约 2 周，架构）**
- 单一"写作执行器"：一次模型写作（Markdown）+ 确定性排版/验收，去掉多段模型调用；上下文分层与压缩策略；指标看板接入 `/api/agent/timing` 与事件流。
- 验收：写作类 Run 回合 p90 ≤20、officecli ≤40/文档、首字 p95 ≤10s；线上事件回流观察 1 周。
