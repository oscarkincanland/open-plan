## 0. 一页结论

**四个问题看似独立，实际共用一套病根：产品把"稳妥"写成了默认路径，但缺少"确定性选择器"和"刹车"，于是每个不确定点都变成一次提问、一次闸门、一段旁白、一次重试。**

| # | 用户感知 | 调查结论（一句话） | 最优先动作 |
|---|---|---|---|
| 1 | ask_u 卡片/弹窗流程乱 | 卡片本身可用，但**语义错位**（纯提问也叫"需要你确认"）、**43% 的提问本不该问**（"是否继续/下一步"类）、**17% 的提问超时作废**；卡片、待答条、审批条三处并存，缺统一状态机 | 先立"提问预算"与"默认假设+可撤销"，再改卡片形态与浮层策略 |
| 2 | 会话卡在下载依赖、PPT master 屡次不成功 | **不是模型能力问题，是六环叠加**：描述解析坏（10/66）→ 中文搜索 0 命中 → 读取被 16k 字符截断（正切掉核心步骤）→ 本机无 Python 3.10 → pip 失败且 120s 后台化返回坏 payload → 写作闸门禁止技能脚本 | 修解析/搜索/截断 + 声明式依赖预检 + 禁止自动装依赖 + 闸门开技能白名单 |
| 3 | `/ @ #` 分不清、调用后还是文字、打字被干扰 | 输入区实际上有**四套触发器 + 三套弹层**（`/`命令、`@`文件、`@`智能体提及、`#`技能/插件/文件、`&`会话），设计规范只承认 `#`；插入是纯文本标记，发送后无 chip 渲染；`@` 会同时打开两个菜单 | 统一为"一个面板 + 两个分区"，输入态/气泡态/解析态三态一致的 chip |
| 4 | 写作慢且机械 | 慢的主因是**一工具一回合、回合无上限**（最长 49.4 分钟 / 440 回合 / 367 次 officecli）+ 上下文膨胀；机械的主因是**强制澄清 + 每 6 轮进度播报 + 固定六步模板**，不是文风模板 | 砍回合（batch、回合硬上限）、砍仪式（不播报、少提问）、一次成稿 |

**共同根因（按影响排序）：**

1. **规范与实现漂移**：`DESIGN.md` 只定义 `#` 提及与四类命令中的一种；设置面板还写着"简单/复杂才检索"，实际 `auto` 与 `always` 完全等价；ask 卡文案写死"需要你确认"。
2. **"稳妥优先"叠了三层，却没有一层在入口把路径定好**：澄清闸门 → 管线闸门 → 流水线强制，都在执行中途拦截，每次拦截 = 一个额外回合。
3. **默认拆掉刹车**：运行预算默认无上限（`OAW_RUN_BUDGET_UNLIMITED=true`），25/45 回合软硬预算失效，只剩每 6 轮播报在制造回合。
4. **依赖与环境是隐性契约**：技能包假设 POSIX + Python 3.10 + 可联网；产品假设 Windows 单机 + 无 Python。双方都没有声明与预检，只能靠模型现场"装环境"。
5. **一套事实源被拆成多套名字/语法**：技能有目录名/frontmatter 名/口语名三套；输入区有四种符号；提问有两种语义（澄清 vs 收尾确认）。

## 2. ask_user 提问卡片与弹窗交互（详见子报告 01）

> 本节结论以 `01-AskUser卡片交互重设计.md` 为准，以下为摘要。

### 2.1 现状

- 服务端：`ask_user` 工具（`server/agent.mjs:3891-4040`）支持 `question`、`options`、`fields`（text/select/radio/checkbox/file）、`previewFile`；单会话单槽位（并发第二个直接报错）；默认阻塞 **30 分钟**（`OAW_ASK_TIMEOUT_MS`），超时按假设继续；取消/新指令会结算旧提问。
- 事件与恢复：`ask_user` 事件 + `pending-asks.json` + SSE 握手补发 + `/api/agent/pending` 对账，刷新/切会话可恢复。
- 前端：消息流内卡片 `AskBlock` + 输入栏常驻 `PendingActionBar` + 审批条三处并存；已回答/超时折叠为一行回执；`previewFile` 自动打开草稿。

### 2.2 核心问题（P0/P1）

1. **提问预算缺失（最重要）**：43% 的提问是"接下来做什么/是否继续/要不要写回"，属于可默认执行的收尾确认；17% 超时说明"问了也白问"。提问应只用于**真正阻塞**的信息缺口。
2. **语义错位**：卡片标题固定"需要你确认"，但大量问题是开放提问；"跳过"与"跳过并继续"文案不一致；选项按钮没有描述/快捷键；`file` 字段只记录文件名、不上传内容。
3. **交互分层混乱**：卡片、待答条、审批条同时出现；无统一"当前待处理交互"焦点；多问题只能串行，没有"1/3"队列感；超时无倒计时，只有失效后的回执。
4. **状态机边界**：单槽位、30 分钟、取消/新指令、刷新恢复、历史水合去重、切线程清空等分支多，但没有一份可执行的交互状态表。
5. **可访问性与移动端**：无 `aria-live` 焦点转移策略、无数字键快捷选择、窄屏卡片过长。

### 2.3 重设计方向（摘要）

- **默认假设卡，不阻塞**：AI 先给 3–5 条假设并继续执行，用户可一键改；只有"文档类型/产物格式/必须包含的数据"这类真阻塞项才提问，且单次 ≤1 个、超时 ≤90s。
- **一张卡只做一件事**：澄清（选项/表单）、确认（允许/拒绝）、预览（草稿）三种卡片形态，标题与操作随语义变化。
- **浮层策略**：默认内联卡片 + 输入栏待答条；当用户不在消息流位置（滚动离屏/切会话回来）时用非模态浮层引导定位，不抢焦点、不打断输入。
- **统一状态机**：`asked → editing → submitting → answered | skipped | expired | cancelled`，输入草稿本地持久化，多问题排队显示"第 n/m 个"。
- **键盘与文案**：1–9 选择、Enter 提交、Esc 收起浮层；超时前 60s 显示倒计时与"按假设继续"。

## 3. Skills 发现/调用与依赖卡死（详见子报告 02）

### 3.1 PPT master 失败的六环主因链（每环均有证据）

1. **发现环**：`description: >` 块解析坏（10/66，`ultimate-ppt-master` 注入行就是 ``- `ultimate-ppt-master` [project]：>``），模型看不出它适合做 PPT。
2. **搜索环**：`searchLocalSkills` 仍是空格 AND 词面匹配（`server/agent.mjs:522-530`）；`PPT 演示`、`生成PPT`、`制作演示文稿`、`幻灯片` 等 17 个自然语言查询 **0 命中**；真实 Run `run_cd23bb40` 搜"ppt master 演示文稿" → 未找到。
3. **读取环**：`skills_read` 按 **16000 字符**截断（头 72% + 尾 28%，`agent.mjs:460/478`），PPT master SKILL.md 26007B/25213 字符，**正好切掉 Step 2–6**（含 MANDATORY 的 Strategist 与 Executor）。
4. **运行时环**：本机无 `python/python3/py`（只有 QGIS Python 3.9.5），技能要求 3.10+ 且用 POSIX `.venv/bin/python`（Windows 实际是 `Scripts/python.exe`）。
5. **依赖环**：pip SSL/直连失败，只能镜像逐包装；4 次 pip 触发 120s 后台化，但**返回坏 payload（ArrayBuffer 错误、无 jobId）**，模型只能重试（480s 白等）。
6. **闸门环（新发现 P0）**：`template/generate` 写作路由下，任何 `python *.py` / `node *.mjs` 都被判为"绕过管线生成 Office"而硬拦（`执行闸门.mjs:157-169`）；同一技能在 `read` 路由下能跑、在"生成 PPT"的自然路由下反而被拦。

### 3.2 依赖卡死的量化

- 14/146 个会话出现安装类命令；72 条命令中 ≥30s 12 条、≥60s 8 条、≥120s 4 条。
- 17/380 个 Run 含安装命令，合计 1352s；`run_dea3fb50` 单 Run 1015s 装依赖（69%）。
- 925 个后台 Job 中 56 个安装类、35 个 ≥60s；坏 payload 8 次/5 Run；纯 `sleep+tail` 等待约 387s；12 个 Run 因"静默 3 分钟"被强制收尾。

### 3.3 规则设计（摘要）

- **何时找技能**：确定性触发矩阵 T1–T7——显式点名必 preflight；任务命中且产品无同类能力才读；有产品能力不读；无命中不搜；同一 Run `skills_search` ≤2 次；闲聊/继续/停止类不搜。
- **找什么技能**：workspace > project > user；以 frontmatter `name` 为主键、目录名为别名；解析支持 `>`/`|` block scalar；搜索改 OR + 打分（名称 > 描述 > 别名 > 频次），返回命中理由；目录预算先保证所有名称出现，再补描述。
- **依赖治理**：技能 frontmatter 增加 `requires`（runtime/python/npm/network/platform/exec）；`skills_read` 前做**只读预检**，给出 `ready/degraded/blocked` 与人话原因；**禁止自动 pip/npm**，安装降级为用户点击确认的一次性 Job（复用 `.oaw/jobs` 并先修坏 payload）；优先复用 editorial_pipeline/officecli 等产品能力。
- **闸门分流**：正则收窄（不再把任意 `.py/.mjs` 当 Office 生成）+ 技能白名单通道（显式技能调用时放行其脚本，产物仍走 validate）+ 事件记录。
- **可观测性**：补 `skill_catalog_injected / skill_search / skill_selected / skill_preflight / skill_read / skill_exec_allowed` 事件，让"为什么没调用成功"可诊断到具体一环。

## 4. 对话框 `/ @ # &` 命令与引用（详见子报告 03）

> 本节结论以 `03-对话框命令与引用交互审查.md` 为准，以下为摘要。

### 4.1 现状

- 输入区实际有四套触发器：`/`（6 个客户端命令）、`@`（文件 + 智能体提及两套）、`#`（技能/插件/文件三组）、`&`（历史会话），另有 `#文件`、`@知识库` 等直写标记。
- `@` 与 `#` 的菜单同时受 `composerMenu` 与 `mentionState` 两个状态控制，**可能同时弹出两个浮层**；Enter 的处理顺序是"提及优先于命令"，同一按键有两种语义。
- `/` 命令只在整条消息完全匹配时才执行（`^/(compact|new|chat|agent|review|help)$` 或 `/goal …`）；插入后若继续补字就不再生效。
- 插入的是**纯文本标记**（`@文件[...]`、`#技能[...]`、`&会话[...]`）；发送后用户气泡按原样显示，服务端解析结果对用户不可见，失败也不提示。
- 设计规范（`DESIGN.md:296`）只定义 `#` 一组，代码实现了四种；`#` 菜单只读 `project.settings.skills`，而 7/7 个项目该值为 `[]`，所以**用户从输入框 `#` 看不到 66 个已装技能**。

### 4.2 根因

1. **符号语义未定义**：`/`=动作、`@`=引用对象、`#`=标签、`&`=会话，用户心智没有建立；同一 `@` 又承担"文件引用"和"智能体提及"两种含义。
2. **输入态 ≠ 气泡态 ≠ 解析态**：输入是文本、气泡是文本、服务端是 Reference 对象，三态没有统一渲染。
3. **键盘冲突**：两个弹层抢 Enter/Esc/上下键；中文输入法 composition 期间的 Enter 只在部分分支被拦截。
4. **静默失败**：解析不到、预检不通过、技能不存在，用户只看到"文字"，没有状态。

### 4.3 方向（摘要）

- **一个面板，两个分区**：输入 `/ @ # &` 任一符号打开同一候选面板（"动作" / "引用"两个 tab），不再出现两个浮层；`@` 默认引用分组，输入 `@智能体` 或面板 tab 切换。
- **chip 三态一致**：插入即渲染为可退格整体删除的 chip；发送后气泡渲染同样 chip；chip 上显示解析状态（已解析/待解析/未找到），失败可点击查看原因。
- **命令与消息分离**：`/` 命令改为"选中即执行"或"命令 chip + 参数"，不再依赖整条消息完全匹配；命令不进消息流。
- **键盘与 IME**：统一 keydown 分发（composition 期间全部放行），Esc 只关一层，Tab 补全，Enter 选中/发送按"是否有打开面板"决定。
- **失败兜底**：无法解析的标记在发送前提示，不静默丢弃；服务端返回的 `references` 在气泡上可见。

## 5. 文本写作流程：慢与机械（详见子报告 04）

### 5.1 实测基线

| 指标 | 写作类 Run（n=96） |
|---|---|
| 时长 p50 / p90 / 最长 | 3.1min / 15.5min / 49.4min |
| 模型回合 p50 / p90 / max | 9 / 44 / 440 |
| officecli 调用 p50 / p90 / max | 0 / 32 / 367 |
| ask_user 触发率 | 36% |
| 闸门拒绝命中率 | 22% |
| 首字 p50 / p95 | 8.07s / 56.2s（服务端准备 0.55s） |

### 5.2 慢的 top3

1. **一工具一回合 + 无回合上限**：49.4min 的 Run 里 430/440 个回合恰好只有 1 次工具；367 次 officecli 中 266 次是逐属性 `set`；`OAW_RUN_BUDGET_UNLIMITED` 默认 true 使 25/45 回合预算失效。
2. **上下文膨胀**：同一会话 prompt 在第 680 轮达 524K token，每轮 TTFT 从 1.9s 涨到 3.9s；压缩仅 3 次且远晚于窗口。
3. **仪式成本**：ask 阻塞 66min（13%）；每 6 轮进度 steer 543 次（单 Run 74 次）；流水线阶段 20min/4%。

### 5.3 机械感的 top3

1. **强制澄清 + 收尾确认**：41% 写作 Run 触发 `shouldAsk`；约 1/4～4/10 的提问是"是否继续/接下来/要不要写回"。
2. **高频逐步播报**：单 Run 223 条 assistant 文本、74% <80 字；用户看到的是执行日志而不是写作。
3. **模板优先 + 固定六步 + 收尾套话**：28/96 走模板路由，六步 playbook 无短任务分支；终稿 34% 出现"已完成"、16% "通过校验"、29% "建议"，仅 7% 用 `## 结论`。

### 5.4 方案（摘要）

- **默认假设卡不阻塞 + 一次成稿**：Markdown 即终稿，直转 docx/pptx（`sourceMarkdown` 直通，跳过 Planner/Writer）；预览即确认；大纲仅在用户要求或 >8000 字时可选。
- **砍回合**：officecli 一次 `batch`、恢复写作路由 60 回合硬上限、关闭每 6 轮播报、提问 ≤1 次且阻塞 ≤90s。
- **文风宪法 + 样例**：禁用套话清单、具体化要求、结构随文体、voice sample/few-shot；接入仓库已有 `humanizer` 与 `doc-coauthoring` 方法论，写作前自检（套话词表/重复句/段长方差/无数字段落比例）。
- **目标指标**：首字 p50 ≤4s / p95 ≤10s；单次 p50 ≤2min / p90 ≤6min；回合 p90 ≤20；officecli ≤40/文档；ask ≤1 次。
