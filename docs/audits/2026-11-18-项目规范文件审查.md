> 方法：全文通读 + 机械核对（链接 / 头部元信息 / 测试别名 / 索引）+ 实跑门禁（`verify`、`test:harness`、`test:known-failures`、`test:spec-index`、`CI全量复跑`、`test:ui-smoke`、`test:a11y`）+ 代码反证（grep / `wc -l`）

## 0. 结论摘要

**规范体系“写得很全”，但“能不能执行”与“有没有执行”是两套状态。** 13 份规范覆盖了文档、架构、代码、测试、Office、会话流、技能依赖、运行时验收等面，链接零失效、ADR 索引有门禁、`verify` 是绿的；但同一批规范里有 **6 处互相矛盾**、**9/13 份基线过期或缺失**，而真正守护规范的 CI 在 `develop` 上是**红的：64 步里 11 步失败**，`test:harness` 与 `test:spec-index` 也红。最重要的“失败可区分”机制（G2 已知失败基线）只登记了 4 个**不在 CI 里**的套件，CI 里红着的 11 个套件一个都没登记。

| 维度 | 评级 | 依据 |
|---|---|---|
| 结构完整性 | 中 | 13 份规范分层清楚；3 份头部元信息缺失（2 缺基线、1 缺版本） |
| 内部一致性 | 低 | 命名、版本、Office 闸门、技能依赖、字号、G1 触发条件等至少 6 处直接矛盾 |
| 与实现一致性 | 低 | 架构分层/HTTP/SSE 规则大面积未落地；Office 闸门语义与文档相反；测试假绿 |
| 引用有效性 | 中高 | 82 条本地链接 0 失效；88 个 `test:*` 引用中 3 个真实缺失（另 2 个为通配写法） |
| 门禁覆盖 | 低 | 架构、命名、Office 开关无任何自动检查；G1 白名单与规范不一致 |
| 执行证据 | 中 | `verify`、ADR 索引、G3 提交门禁真实可用；CI/契约/索引门禁红且未登记 |
| 可维护性 | 中 | 规范用行号锚定代码（已漂移）、基线长期不刷新、状态口径多头 |

一句话：**规范不缺“文本”，缺的是“唯一口径 + 绿灯门禁 + 定期复审”**。当前最该修的不是再写一份规范，而是把红的门禁变绿或如实登记，并把互相矛盾的条款收敛成一条。

## 2. 矛盾清单（按严重度）

### P0-1｜CI 与契约门禁在 develop 上是红的，且未登记

**证据**（2026-11-18 实跑）：

```text
node scripts/CI全量复跑.mjs
CI 声明测试步骤 64 个
通过 53 / 失败 11 / 脚本缺失 0
失败：任务结论事件流、AVA对话状态可信、AVA提及、AVA附件、工具元数据契约、
      规范索引守护、事件发射点守护、工作区面板与输入栏收敛、会话收敛与流水线状态、
      图标体系契约、Office写作闸门通电
```

- `npm run -s test:harness` → **exit 1**（`工具元数据契约测试`：`map_template.sideEffectScope` 实际 `workspace`、断言期望 `session`，`server/工具元数据.mjs:287` vs `scripts/工具元数据契约测试.mjs:65`）。
- `npm run test:spec-index` → **exit 1**（`会话流渲染通道清单.md`、`运行时验收与门禁规范.md` 缺基线）。
- `npm run verify` → **通过**（绿），但这只串了 `平台边界检查.mjs` + `验证脚本.mjs` 两个脚本，覆盖不到上述失败。

**冲突对象**：AGENTS §7.1「验证通过才允许提交」、§8 DoD「受影响 `test:*` 通过」；《开发收敛规范》§8「三条全绿才算完成」、§9「门禁绿：`verify`、`test:harness`、CI 全步骤均通过」。规范要求的状态与仓库实际状态相反。

**影响**：规范里“验证通过”已不可判定；任何人按规范跑一次自检都会失败，久而久之只能选择性执行——这正是《开发收敛规范》§0 复盘过的问题再次发生。

### P0-2｜G2 已知失败基线的覆盖是假的

**证据**：

- `scripts/门禁已知失败基线.json` 只登记 4 个套件：`test:ui-guard`、`test:component-spec`、`test:design-tokens`、`test:perf-budget`。
- 这 4 个套件**都不在 CI 的 64 步里**；CI 里红的 11 个套件**一个都没登记**。
- `test:a11y` 实跑 3 条失败（亮色缺 `--text`/`--panel-bg`、缺 `--dim`、缺 `@media (max-width: 520px)`），也不在基线；`变更日志.md:84` 自己写明「test:a11y 的 520px 断点失败为存量……未登记进 G2 基线」。

**冲突对象**：《运行时验收与门禁规范》§2.1「未登记的新失败一律视为回归」、§2.4「当前登记」表；AGENTS §7.2 关联快测第 3 条。

**影响**：G2 名义上是“既有失败必须登记、会过期”，实际只覆盖 4 个与 CI 无关的套件，CI 的红灯完全绕过它。这是“门禁存在但不守护”的典型。

### P0-3｜文件命名：两份规范互相打架，实践跟了第三套

**证据**：

- 《代码规范》§2（`代码规范.md:18,21`）：「**新增文件一律英文命名**（2026-11-10 起）」「新增测试脚本用 `<feature>.test.mjs` 英文 kebab-case」。
- 《文档管理规范》§3（`文档管理规范.md:41,46`）：「代码文件……**文件名部分优先中文**」「脚本文件名**必须是中文**」。
- 实践：2026-11-10 之后新增的代码/脚本几乎全是中文名——`server/模型标识.mjs`、`server/地图导出执行器.mjs`、`scripts/主题与外观持久化测试.mjs`、`scripts/已知失败校验.mjs` 等（`git log --diff-filter=A --since=2026-11-10`）。英文新增只有既有组件习惯（`VideoViewer.jsx`、`ProcessGroup.jsx`）。

**影响**：这是全仓最“显性”的一条规范失效——两份生效规范对同一件事给出相反命令，而代码两边都不完全遵守。新人/智能体无法判断该听谁的。

### P0-4｜Office 闸门：规范说“默认关、关=基线”，代码是“按路由默认开”

**证据**：

- 《Office 排版规范》`Office排版规范.md:13-14`：「强制闸门由 `OAW_OFFICE_FORMAT` 控制且**默认关闭**」；`:141-142`：「默认关；关闭时……不启用澄清闸门、封面、目录、页码与 QA」；`:151`：「生效条件：`OAW_OFFICE_FORMAT=1`、Work、`route=template|generate|edit`」；`:160`：「关闭 `OAW_OFFICE_FORMAT` 即完全放行」。
- 实现 `server/运行开关.mjs:356-366` `officeGateActiveFor()`：只要路由是 `template/generate` 且非 Chat/Review 就返回 true；`OAW_OFFICE_FORMAT` 只用于**显式退出**（`=off`）。
- 另一半：流水线的 `autoClarify/cover/toc/pageNumbers/qa` 仍按 `RUNTIME_FLAGS.officeFormat`（默认关）控制（`server/agent.mjs:5815-5825`）。

**影响**：默认用户体验是“**写作闸门通电、但封面/目录/页码/QA 不做**”——规范没有描述这个中间态，且与 ADR 0012「按路由自动启用」一致、与规范正文相反。按 AGENTS §2，规范效力高于 ADR，冲突时本应停下，但实际代码按 ADR 跑了很久。

## 5. 根因（为什么会出现这些矛盾）

1. **规范只加不改**：新规范落地时复制旧口径（如“默认关”），代码后来按 ADR 改了，规范没有回写；会话流、Office、版本口径都是这样分叉的。
2. **同一概念多头定义**：命名（文档管理 vs 代码规范）、版本（开发收敛 vs 版本管理计划）、字号（DESIGN vs 会话流规范）、闸门（排版规范 vs ADR 0012）都没有“谁是唯一事实源”的裁决句。
3. **门禁与规范脱节**：`verify` 只串两个脚本；`test:harness`/CI 红了没人修；G2 只登记“方便登记的”，红套件绕开基线。
4. **行号锚点会腐烂**：通道清单用 `:7537` 这类行号指向 9k 行的 `ChatPanel.jsx`，一周就漂；应改为“组件/函数/选择器”锚点。
5. **缺少定期复审**：基线 v0.11.55 的规范还在“生效”，没有人负责在版本推进时重签基线。
