## 1. 本项目是怎么编排的

### 1.1 三段式结构

```
① 事件层（唯一事实源）        server/事件注册表.mjs      167 种类型，147 落盘
        │  Pi 事件 → 项目事件（server/agent.mjs:4914-5289）
        ▼
② 归约层（两个纯函数归约器）   client/src/运行轨迹.js      reduceRunTrace(events)    → trace
                            client/src/会话流投影.js    buildRunTimeline({blocks, trace})
        ▼
③ 呈现层                     RunFoldBar / TimelineRow / ToolCard / SummaryBlock / ArtifactCard
```

关键设计：**实时流与历史回放共用同一套归约器**（`运行轨迹.js:134` 的事件 switch 与 `会话流投影.js:150` 的块归约），这是本项目做得比 DSH 更"可测"的地方——归约是纯函数，Node 可直接断言。

### 1.2 事件层：双维度 + 四道落盘门

- 单一事实源：`server/事件注册表.mjs:20-234`。`lifecycle` = 通道历史里不被增量挤出；`persist` = 落 `.oaw/events/事件流.jsonl` 可跨会话回放；测试强制"persist 必须 lifecycle"（`:239`）。
- **但"一条事件是否进 Run 记录 / 全局流"并不只看这张表**，实际有 4 道门：
  1. `registry.persist`
  2. `emit` 的硬编码白名单（`server/agent.mjs:4854`）
  3. `emitChannelSafe` 默认全记（`server/agent.mjs:6883-6885`）
  4. `recordRunFinalText` 单写特判（`server/runs.mjs:968-971`）
  
  后果举例：`run_admitted`、`file_changed`、`agent_summary` 只进全局流不进 Run；`tool_call_progress`、`context_usage` 两边都不落。审计口径因此分叉（详见 §5-P1-4）。

### 1.3 一轮 Run 的时序（精简）

```
run_admitting ──▶ beginRun/run_started(seq=1) ──▶ capability_plan ──▶ run_admitted
   └─▶ model_request_started ──▶ agent_started ──▶ turn_started
          ├─ thinking_boundary / thinking(delta)*        ← 仅 SSE，不落盘
          ├─ text_boundary / token(delta)*               ← 仅 SSE，不落盘
          ├─ tool_start {name, input}                    ← 落 Run + 全局流
          │    ├─ tool_output(delta)*                    ← 仅 SSE
          │    └─ tool_end {name, isError, result≤16K}   ← 落 Run + 全局流
          ├─ message_end / stats
          └─ turn_ended
        （多回合重复）
   └─▶ agent_settled ──▶ assistant_final（唯一终稿）──▶ run_finished（权威终态）
```

证据：`server/执行句柄.mjs:183-530`、`server/agent.mjs:4914-5289`、`server/runs.mjs:1254-1487`。

### 1.4 四类过程事件：边界在哪

| 维度 | 思考 | 工具调用 | 运行命令（bash） | 文件读取（read） |
|---|---|---|---|---|
| 事件 | `thinking` + `thinking_boundary`（`agent.mjs:4993-4995, 5002/5016`） | `tool_start` / `tool_output` / `tool_end` | 同左，另加 `write_*`、`tool_backgrounded`、`background_job_*` | 同左（**没有 read 专用事件**） |
| 是否落盘 | ❌ `lifecycle:false, persist:false`（`事件注册表.mjs:229`） | start/end 落 ✅，output ❌ | output 落 ❌；后台任务事件落 ✅ | 同工具 |
| 结果形态 | 无（靠 Pi 消息块回放） | `tool_end.result` 截 16K（`agent.mjs:452-476`） | 流式 `tool_output`；结果预算 `strategy: artifact` + 取尾部（`工具元数据.mjs:187-197`） | `strategy: truncate` 30KB 取头部（`工具元数据.mjs:59-62`） |
| 前端标签 | 「思考」+ N 字 | `toolPhrase` 手写 switch（18 个工具名，未知名回落「调用 X」） | 「执行命令」+ `$ 命令` | 「读取文件 {path}」 |
| 失败表达 | — | `isError` | `isError` + `write_rejected(BASH_FAILED)` | `isError` 文本 |

**两个要点**：

- 思考是**真流式**（Pi `thinking_delta` → SSE `thinking`），但**不落盘**。回放依赖 Pi 会话 JSONL 里的 assistant `thinking` 块（`server/index.mjs:4158-4189` 不剥离该块 → `App.jsx:248-251` 读取）。跨内核迁移会断（未验证 Pi 各版本的块结构）。
- "读取"与"命令"在事件层**完全同构**，只有 `name` 不同。区分完全靠前端标签表（`client/src/事件展示.js:345-373` + `ChatPanel.jsx:7730-7759`）。这意味着新增工具默认退化成「调用 xxx」，见 §5-P1-5。

### 1.5 "步骤"有三套口径（容易混）

| 口径 | 定义 | 来源 |
|---|---|---|
| 服务端 `run.steps` | **一步 = 一次工具调用**（`tool_start` 建步、`tool_end` 收口、`agent_error` 置失败） | `server/runs.mjs:691-714`（本次已核） |
| 前端折叠头 `N 步` | **`runTimeline.length`** = 时间流行数（含思考行、阶段小结行、系统提醒行） | `ChatPanel.jsx:6433` `steps={runTimeline.length}`；规范 §2.1 明文规定 |
| 模型回合数 | `entry.turnCount`（`turn_started` 自增），驱动 6 轮进度小结与预算 | `agent.mjs:4932`、`轮次预算.mjs:23-40` |

三者会互相"打架"：一次 5 工具 + 8 思考块 + 3 段小结的 Run，折叠头写「16 步」，而任务中心写「步骤 5/5」。建议收敛为**折叠头只报工具步数、chips 分别报工具/产物**（见 §6）。

### 1.6 结论怎么产生（本项目的核心资产）

```
模型最后一条 assistant 文本
   └─ agent_settled → assistant_final（agent.mjs:5254-5258）
        └─ recordRunFinalText 单写、幂等、文本修正则 version+1（runs.mjs:910-952）
             └─ run.finalText → run_finished.completion
                  └─ 前端：authoritativeFinalText（ChatPanel.jsx:5855-5864）
                       ├─ finalTextBlockIndex 在时间流里找到同一段 → 隐藏该文本块（去重，5989/5996）
                       ├─ splitCompletionSummary → { conclusion, detail }（会话流投影.js:272-312）
                       └─ SummaryBlock 合并为一篇连续 Markdown（无标签、无 cap）
```

三条保护性设计值得保留（DSH 都没有）：

1. **终态围栏**：`run_finished` 之后到达的增量事件直接丢弃（`ChatPanel.jsx:2432`），"假完成/复活"问题被结构性堵住。
2. **不拿进度文本当结论**：中间 `text` 块 cap 标注「进度」（`会话流投影.js:171`），只有 `assistant_final` 进结论区。
3. **终稿缺失显式化**：`final_text_missing{recovering}`（`agent.mjs:5950-5971`）+ 前端「本轮没有最终答复」+ 继续/重试动作。
4. **`complete_task` 已停用**：显式完成声明工具已移除，`completion.source` 一律 `inferred`（`运行轨迹.js:4-6`）。这正好避开了规范 §5 最担心的"工具摘要冒充结论"。

## 3. DSH 是怎么做的（对标）

### 3.1 事件模型：append-only typed log + surface 投影 + 双流

- **一份日志派生一切**：模型历史、对话、标题、遥测、投影、持久化全部由 `Session` 事件日志派生；原则是 *model-visible means logged*（`dsh-session/README.md:12,100`）。
- **层级**：`turn/start → step/start → (assistant/message | assistant/attempt) + (tool/call → tool/result) → step/end → turn/end`。`turn/end.reason` 是终止语义的唯一定义点（`completed / aborted / blocked / error / max-tokens / interrupted / forked`）。
- **surface 投影**：`append` 或 `replace{startSeq,endSeq}` 让"改写历史"不破坏 append-only；压缩只是隐藏不删。
- **双流**：durable 事件带 `seq`；**live 帧（`assistant-stream` 的 start/chunk/end）无游标、不进日志**，且"**先落 durable 再发 end 帧**"——live 永远只是展示，不是回放源（`dsh-api-session-controller/README.md:54`）。
- **传输**：unary RPC 走 HTTP POST，所有流走同一个 WebSocket `/api/remote.mux`（`dsh-api-gateway/README.md:39`）；SSE 只用于 HMR。

### 3.2 四类过程

| 过程 | DSH 做法 |
|---|---|
| 思考 | 流式 `reasoning-delta` → 装配为 `reasoning` 块；落盘时**同时**存整段 + 紧凑时间戳流 `{type:'reasoning-chunks', dt[], texts[]}`。即"过程流式、证据整段"（`dsh-llm/lib/types/assembler.js:46-53`、`api-catalog.js:4807-4808`） |
| 工具 | 五段管道：`pre-execute → guard（单调，不可翻案）→ execute → post-execute → finalizeContent → result`；同 step 内 exclusive barrier + 并行池 10，结果按模型序提交 |
| 命令 | 每次新进程；每流 64KB 截尾 + spill 文件（≤64MiB）；固定模板标记 `[output truncated; full output: <path>]`、`[exit code: N]`；**命令即 job**（超时转后台，ring buffer + 双游标供模型与前端） |
| 读取 | 固定信封：`<path>/<type>/<content>` + `N: 行文本` + **恰好一个脚注**（`(Output capped. Showing lines a-b. Use offset=…)` 三种之一）；2000 行 / 2000 字符 / 50KB 上限；结果作为 `tool/result` 进上下文，卡片由**原始参数**推导 |

### 3.3 进度呈现

- 持久层只记**边界**（turn/step 的 start/end），状态全部派生：`AgentStatus = idle | running`、`SessionSummary.running`、Tool 节点 `preparing → dispatched → result` 三阶段。
- UI 约定：状态点五态（idle/ongoing/warning/error/done）；运行中一律 `TextShimmer` 左→右高亮；**in-flight 不编造时长**；完成回合按四档 Work details 折叠，**但绝不隐藏 final answer**。
- 导航：`turnOutline` 投影，每 turn 只推 ≤3 次（boundary / prompt / settled response），prompt 预览 50 字符、response 120 字符。

### 3.4 结论交付：**DSH 没有 `assistant_final`**

- 终稿 = **最后一个非空 `assistant/message` 的文本** + `turn/end.reason`（`dsh-headless/README.md:100`）；子代理答复也是"子会话最后一条 assistant 文本"作为工具结果返回。
- 没有 `complete_task`/`summary` 工具产物参与结论；`present` 只写 `deliverables/presented`（log-only）。
- 失败尝试落 `assistant/attempt`（不进模型历史、可诊断）；取消时"已交付给用户的流式文本保留"。
- 前端靠五道隔离避免"把进度当结论"：事件类型隔离 / 提交点隔离 / 折叠隔离（承诺不藏终稿）/ 失败隔离 / 上限隔离。

### 3.5 对照表

| 机制 | DSH | 本项目 | 判断 |
|---|---|---|---|
| 唯一事实源 | 单一 typed log，派生一切 | 事件注册表为源，但"进 Run/全局流"有 4 道门 | 本项目**需收敛** |
| 事件信封 | 固定白名单 + surface replace | V2 信封 + streamId 代际 + 游标 | 同构；缺显式 shadow 语义 |
| turn/step 边界 | 有 `step/start|end` | 无模型 step 边界事件，靠 tool_* 推断 | 建议补 |
| 思考 | 流式 + 整段/时间戳落盘 | 流式 + **不落盘** | 差距明确（可接受，但要写进已知边界） |
| 工具流水线 | pre/guard/execute/post/finalize | 白名单 + 审批 + gate_denied | 同构 |
| 命令输出 | 64KB + spill + 固定标记 + 命令即 job | `tool_output` 流式 + 后台任务；外置**默认关** | 本项目需开外置 |
| 读取结果 | 行号 + 唯一脚注 + 字节上限 | 全文 `<pre>` | 本项目明显弱 |
| 传输 | WS 逻辑流 + durable/live 分离 | SSE，token/thinking 同流 | 语义可用，缺 live/durable 标记 |
| 进度 UI | shimmer + 五态 + 不编时长 + 折叠不藏终稿 | 状态点 + 用时，无"正在做什么" | 本项目需补 |
| 结论 | 最后一个 assistant 文本，无权威事件 | 显式 `assistant_final` 单写 + 缺失语义 | **本项目更强**（对齐风险：与最后一条 assistant 文本的一致性需断言） |
| 工具卡 | 按工具名注册 typed view（terminal/diff/read/search/image/generic） | 单一泛型 ToolCard + 裸 `<pre>` | **最大差距** |

### P1（对齐质量，约 1 周）

1. **工具卡结构化**（最大体验差距）：`ToolCard` 按工具类型分叉 —— bash 出终端卡（含 `[exit code]`）、`read` 出「N 行 / 首页行号 / 还有更多」、`write/edit` 出 diff 卡（9 行折叠）、`grep/glob` 出结果计数卡。参考 DSH `dsh-client-ui-tool/README.md:50-54,84`。
2. **折叠头补 chips**：接上已有但未引用的 `summarizeTimeline` → `工具 6 · 文件 2 · 验收通过`，正好补 R3:114 的缺口。
3. **补「正在做什么」**：`summarizeTimeline.runningLabel` 挂到 `.tl-elapsed` 后面；同时把 `waitingMs` 真正归约进 `createRunTrace`（现在 `ChatPanel.jsx:6027` 读的字段从不存在 → 「其中等待 X」是死代码）。

7. **token 显示**：R3 要求「每轮显示用时与 token」，但 token 指标块只在旧渲染路径（`ChatPanel.jsx:5618-5631`），`timelinePath` 下不显示。
8. **动效闸门补折叠过渡**：`.run-fold-body`/`.run-fold-chev` 未纳入（`styles.css:11228-11232`）。

### P2（整洁性）

1. 两套渲染路径（`timelinePath` 新时间线 / 旧 `<details>`）长期并存；旧路径的边框、背景、`›` 与规范冲突。建议要么把旧路径也对齐视觉，要么在无 `runId` 时也走新时间线。
2. 死代码清理：`ExecutionFlow` 非 embedded 分支（约 180 行）、`runTraceProgressText`/`runTraceElapsedText`、`outputPreview`、`summarizeTimeline`、`waitingNote`、`阶段条.jsx`（未接入会话流）。
3. `renderTimelineItem` 每行都 `reduce` 两次求 `lastTextIndex/lastThinkingIndex`（`ChatPanel.jsx:6124-6125`，O(n²)），应 `useMemo` 一次。
4. 概念命名四处不一：`阶段小结 / 小节结论 / 阶段结论 / 进度`。
5. `run_finished` 双形状：SSE 里 `artifacts` 是数组，落库是数字（`runs.mjs:1460`），而注册表 schema 要求 array（`事件注册表.mjs:34`）→ 开 schema 校验会每次收尾误告警。
6. 折叠头 `failed` 判定只看 `runCardView.lifecycle`，`interrupted` 却有 `runStatus` 兜底 → 缺 `runSummary` 的历史失败轮会显示「已完成」（`ChatPanel.jsx:6084-6089`）。
7. `completed` 折叠头文案里的"步"口径建议改为工具步数（与任务中心一致），时间流行数改叫「N 条过程」。
