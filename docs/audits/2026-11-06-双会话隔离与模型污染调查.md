# 双会话隔离与模型污染调查（2026-11-06）

> 现象（用户报告）：同时开两个会话、来回切换后，
> ① 两个会话的内容互相渲染到对方位置；② 明明已完成仍显示"正在执行"；③ 模型会自动切换；④ 默认推理档位偏低。
> 结论：**三个前端状态隔离缺陷叠加**，服务端按 `client::thread` 隔离本身是正确的。

---

## 1. 服务端隔离是正确的（已核对）

| 事实 | 证据 |
|---|---|
| runtime 键 = `client::thread`，每个 thread 独立 runtime/model/channel | `server/index.mjs:5413` `ensureRuntimeWithTimeout(agentKey(client, thread), …)` |
| 模型切换按 key 生效，不跨线程 | `server/agent.mjs:6653` `setModel(clientId, spec)`（`clientId` 即 `client::thread`） |
| 对话流按 thread 隔离，同键只留 1 条 | `server/index.mjs:5294`、`server/流连接.mjs:131` |

→ 串台不是服务端把事件发错线程，而是**前端把上一个会话的本地状态沿用到了新会话**。

---

## 2. 缺陷一：切会话时目标会话的历史不重新水合

`ChatPanel` 历史水合 effect 原依赖 `[historyMessages]`（现为 `[historyMessages, historyThreadId, threadId]`）。

缓存命中路径的时序（`App.jsx` `handleSelectSession`）：

```
setHistoryThreadId(B) → setHistoryMessages(cachedB)   // 此刻 threadId 仍是 A
   → 水合 effect 触发，guard: historyThreadId(B) !== threadId(A) → 早退
setCurrentSessionId(B) → setThreadId(B)               // 水合 effect 依赖未变 → 不再触发
```

结果：**B 从未被水合**，界面继续显示 A 的消息；直到服务端历史返回产生新的 `historyMessages` 引用才纠正；若请求失败/很慢，就是"完全污染"。

**修复**：依赖加入 `threadId`，切换即重新水合目标会话。

---

## 3. 缺陷二：水合分支不复位运行态 → 已完成仍显示"正在执行"

同一 effect 的 `if (!hydratingHistory) { … }` 分支只在该分支里复位
`messages / runState / todoItems / busy / executionEvents`。

当 `hydratingHistory === true` 时这些**全部沿用源会话 A 的值**：

- A 在跑 → `busy === true` → B 显示"正在执行/实时"，即使 B 早已完成；
- A 的时间流锚点、Todo、执行轨迹一起带到 B。

**修复**：水合以目标会话 Run 事实为准（`setBusy(isLiveRun)`、`setRunState({status: run.runStatus…})`、`replaceExecutionEvents(historyFlowEvents)`）；非水合路径回落到该 thread 缓存或 idle。

---

## 4. 缺陷三：模型是全局单值，被任意会话事件改写

模型相关写点原本全部是"全局"的：

| 位置 | 行为 |
|---|---|
| `case "connected"` | 服务端上报本会话模型 → `setModel` + `applyModel`（写 `localStorage.oaw_model`） |
| `agent_model_fallback` / 提示响应 | 同上 |
| `model_switched` | `applyModel` + `onModelChange`（写 App 级 `selectedModel`） |
| 初始化 effect（依赖 `threadId`） | 读 `oaw_model` → `setModel` + `onModelChange` |

于是：切到会话 B（模型 Y）→ `connected` 把全局写成 Y → 初始化 effect 在 A 上把 Y 推给 A →
`setAgentModel(client, Y, threadA)` **真的把 A 的模型改成了 Y**。这就是"模型自动切换"。

**修复**：

- 新增 `applyModelForSession()`：会话上报的模型**只更新本地显示**，不写全局偏好、不回推 `onModelChange`；
- App 级 `selectedModel` 只在「用户真的改了」（`lastSelectedModelRef` 前后值不同）时下发给当前会话；
- 模型随 `threadCacheRef` 按 thread 缓存，切回立即显示该会话自己的模型（`connected` 再到时以服务端为准）。

---

## 5. 缺陷四：默认推理档位

`THINKING_OPTIONS` 默认 `default`（跟随模型）。用户要求默认「高」。

**修复**：`DEFAULT_THINKING_EFFORT = "high"`；模型不支持时按 `high → medium → default` 降级，不再直接掉到「跟随默认」。

---

## 6. 验证与剩余项

- 新增/追加断言在 `scripts/流恢复冻结回归测试.mjs`（水合依赖、切换清理阶段文案、模型隔离、默认档位与降级链），并跑通
  `会话流排版 / 对话区布局 / 无障碍与窄屏 / 动效治理 / 组件交互规范 / 界面一致性守护 / 运行展示投影`。
- **未做浏览器端双会话实机回归**（本机无自动化 UI 环境）。建议手测：
  1. A、B 各启动一轮（不同模型、不同进度）；
  2. 在 A 运行中切到 B、再切回 A，检查消息、运行态、模型三处互不影响；
  3. 让 B 先完成，切到 B 确认不再显示"正在执行"；
  4. 在工具栏切换模型，确认只影响当前会话。
