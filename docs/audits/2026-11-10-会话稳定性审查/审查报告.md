## 2. 模型自动切换

### 2.1 证据链

会话 JSONL 的 `model_change`（UTC）：

| 时间（UTC） | 模型 | 说明 |
|---|---|---|
| 13:29:14 | `opencode-go/claude-haiku-5-5` | 会话创建 |
| 13:31:35 | `opencode-go/deepseek-v4.1-flash` | 第一次自动变化 |
| 13:50:34 | `deepseek/deepseek-flash` | 第二次 |
| 13:50:38 | `minimax-cn/MiniMax-M3.1-Flash` | 4 秒后再次变化（疑似回退链） |

- 当前 runtime：`minimax-cn/MiniMax-M3.1-Flash`；`localStorage.oaw_model = minimax-cn/MiniMax-M3.1-Flash`；`sessionStorage.oaw_thread_model_v1` 只缓存了另一个 thread，本 thread 无缓存。
- 运行 `run_c2bdbf09`（21:50 起）直接使用 minimax；UI 中出现“模型切换为 minimax”分割线。
- 服务端存在 `agent_model_fallback` / `model_switched` 事件与连接失败回退逻辑（`server/agent.mjs` `MODEL_FALLBACK_LIMIT=2`）；日志有 403/400/Request aborted 等上游错误。
- 计划 006 已记录客户端根因：全局 `oaw_model` 跨窗口共享 + 旧 effect 自动回推；当前工作树的 ChatPanel 已包含修复（删除自动回切 effect、sessionStorage 会话缓存），构建产物也包含该修复；但**旧标签页/旧窗口仍在运行旧 bundle**，或**服务端回退链**仍会自动改模型。

### 2.2 结论

- 自动切换是事实，不是用户操作；**不是数据丢失**。
- 触发源有两条，需按现场区分：
  1. 旧标签页（未刷新，旧 bundle）读取全局偏好后向服务端 `setAgentModel`；
  2. 服务端连接失败后的自动回退（`agent_model_fallback`），会写会话 model_change 并可能连续切换。
- 当前 UI 对回退的提示不够持久/不够显眼，用户容易误以为“自己变了”。

## 3. 结论区标题/段落顺序问题（可复现）

### 3.1 复现

对 `run_c9abf693` 的 `finalText` 调用 `splitCompletionSummary`：

- 结论 = `一是**前端没有刷新或没有展示子目录**……`（本应是正文第一段，不是结论）
- detail = `刚才那一轮我误输出成半截工具标记…… ## “没更新”最可能的原因 …… 二是…… 三是……`
- ChatPanel 渲染顺序是“结论 + detail”，于是页面先出现“一是…”，再出现开场白与 `## 一、…` 标题。

浏览器 DOM（历史回放，`.sum-body`）实际子节点顺序：

```
0 P: 一是前端没有刷新或没有展示子目录……
1 P: 刚才那一轮我误输出成半截工具标记……
2 H2: 一、“没更新”最可能的原因
3 P: 二是你可能在看旧文件……
4 P: 三是确实有一处我判断错了……
5 H2: 二、怎么确认文件是对的
```

源文本顺序本应为：开场白 → `## “没更新”…` → 一是 → 二是 → 三是 → `## 怎么确认…`。

### 3.2 根因

`client/src/会话流投影.js:392-397`：有分节但没有“结论”分节时，把**第一个分节的首段**提升为 conclusion，并从 detail 删除；`ChatPanel.jsx:6797` 又以 `[conclusion, detail]` 拼接渲染 → 首段被移到最前。

触发条件：模型终稿有 `##` 小标题、但标题不是“结论”（本次正是“没更新/怎么确认”这类内容词），且第一段不是总起句。

### 3.3 结论

- 不是模型写错，也不是标题 CSS；是历史结论区的文本重排缺陷。
- 无文字丢失（各段仍在，只是顺序改变）；同类结构（内容词小标题）会稳定复现。
- 另：`numberTopLevelSections` 自动补“一、二、”是既有设计，但叠加该重排后读者会看到“一、”标题出现在“一是…”之后，观感更差。

## 4. 列表读取失败/不稳定（补充）

- 144 次采样：`/api/runs?fields=summary&limit=50` 平均 1.09s、峰值 4.02s；`/api/sessions` 平均 0.73s、峰值 1.68s；全部 HTTP 200，无 500。
- 数据规模：`.oaw/runs` 412 文件/146.7MB，`.规聚会话` 155 文件/78.3MB；列表每次扫描成本高。
- 结论：用户看到的“读取失败”更可能是**客户端超时/竞态**（如 `apiControl` 8s、SSE 重连、并发 run），不是服务端稳定 500；需要按实际报错文案与时刻再确认。此项建议与 007 的“列表加载稳定性”一并处理。

## 5. 影响与建议

1. **先修结论渲染顺序**：只把标题以“结论”开头的分节当结论；无结论分节时保持原文顺序（不提升首段）。这是用户最直观的“标题坏了”。
2. **修产物归属/展示**：回答轮引用产物时，展示“本会话最近产物”兜底；cancelled Run 产物要明确标注并可选“重试归属”；materialize skip 要有可见提示与重试。
3. **模型治理**：落地 006；增加旧标签页构建版本检测与“请刷新”提示；服务端回退时持久横幅（从→到、原因、可一键切回），并记录来源（user/fallback/pending）。
4. **列表稳定性**：为 `/api/runs`、`/api/sessions` 增加分页/缓存/TTL，避免高负载下超时。
