## 1. 结论先行

- 本轮四项 UI 改动（同宽、图标、源码预览、图片粘贴）**主体可用**，新增的 4 个契约测试与相关 UI 回归均通过。
- 但提交 `2458d39f` 本身有一个 **P0 级样式语法问题**：`styles.css` 中一段 `transform`/`@media` 被插到了错误位置，导致提交版本的样式在浏览器中解析异常；修复目前只存在于工作区、尚未提交。提交、构建产物与验证时的代码不是同一份状态。
- 会话切换/历史加载仍有明确的稳定性缺口：历史展示被 Agent resume 阻塞（最长 20s）、`getSession` 没有超时、恢复失败后输入区仍可发送、切会话时旧会话内容不会先清空、运行列表一次拉取约 2.9MB。多条叠加会表现为“点会话没反应 / 历史加载失败 / 显示错会话”。
- 会话流的问题不是“没有折叠”，而是 **折叠的粒度不对、信息不完整、总结被隐藏**：一次运行可能拆成多个“执行过程”折叠行；折叠行没有“运行了多久 / 多少步”；`complete_task.summary`（809–1890 字）在存在最终答复时被直接隐藏，只显示更短的最终答复（156–734 字），与 PRD R3“summary 必须是完整结论”的意图不一致。
- 本轮只出审查与计划，不改代码。需要修改的需求、规范和代码位置见第 6 节与配套计划。

### 3.2 A-01（P0）：提交版样式语法损坏

提交版 `client/src/styles.css` 在 `.integration-body` 规则之后出现了：

```css
.integration-body { overflow-y: auto; padding: 24px 30px 48px; }
  /* .chat-body 用 scrollbar-gutter: stable ... */
  transform: translateX(-4px);
}
@media (max-width: 720px) {
  .center-chat-slot .chat-compose { transform: none; }
.integration-layout { ... }
```

问题：

- `transform` 成了规则外的裸声明，后面的 `}` 成了多余闭合；
- `@media` 没有在 `.chat-compose` 规则后闭合，后续规则被错误嵌套；
- 本应写在 `.center-chat-slot .chat-compose` 内的输入区补偿（`translateX(-4px)`）没有落在目标规则里。

实测（headless Edge，1400×900，加载提交版 CSS）：

```json
{
  "ready": "complete",
  "integrationDisplay": "block",
  "composeTransform": "none",
  "medias": [{ "media": "(max-width: 720px)", "children": 5 }]
}
```

预期 `.integration-layout` 在桌面宽度是 `grid`，`.chat-compose` 应有 `translateX(-4px)`；实际都没有生效。说明提交版本的桌面布局与文档声称的“1px 对齐”不一致。

当前工作区已经有修复（`git diff HEAD -- client/src/styles.css`）：把补偿声明移回 `.chat-compose`，并删除错误位置的块。**但该修复尚未提交**，所以：

- 构建产物、浏览器实测、提交内容三者不一致；
- 任何人从 `2458d39f` 重新拉取/构建，得到的是坏样式；
- 现有 `test:chat-layout` 只匹配 `--chat-content-w` 等字符串，无法拦截此类错误。

**修复方向**：把工作区中的 UI 修复单独 hunk 提交（不要夹带并行 GIS 样式）；新增 CSS 语法/CSSOM 冒烟测试（至少检查关键选择器在 1400px 下的 computed style，而不是只做正则）；把“样式改动必须在干净提交上构建并跑一次 CSS 解析”列入 DoD。

### 3.3 A-02（P1）：源码预览懒加载没有局部错误边界

`DocViewer.jsx:16` 用 `React.lazy` 加载 `CodeViewer`，`DocViewer` 外层只有 `Suspense`（`App.jsx:2254`），没有 `ModuleBoundary`。`AppErrorBoundary`（`App.jsx:144`）只在 `isStaleChunkError` 时自动刷新一次，否则整页显示“应用出错”。

这意味着：服务重新构建后旧页面打开源码文件，若 `CodeViewer` 的 chunk 404，用户看到的不是“预览加载失败”，而是整页错误——与 10-30 刚修过的地图懒加载崩溃同类问题，但这次新加的源码查看器没有接上防护。

**修复方向**：在 `DocViewer` 内部给 `CodeViewer` 包一层局部 `ModuleBoundary`（可复用 `App.jsx` 的组件或抽公共组件），提供“重新加载源码 / 用系统应用打开 / 关闭”三个动作；`isStaleChunkError` 的自动恢复保留为兜底。

### 3.4 A-03（P2）：2MB 截断影响预览，JSON 行为变化

`server/index.mjs` 对 `text`/`htmlfile`/`code` 三类都调用 `readTextPreview`（2MB 上限）：

- Markdown/HTML **预览**（`DocViewer.jsx:740/826` 使用 `doc.content`）现在只拿到前 2MB，不再是完整内容；
- 截断会切断 Markdown 结构或 HTML 标签，预览可能不完整；
- `.json` 之前走 `kind=text`（Markdown/文本视图），现在 `isTextExt` 不含 `json`、`isCodeExt(json)` 为真，变成只读源码，没有“预览”切换。

如果 2MB 截断是刻意保护传输/渲染，应该在 PRD/DESIGN 登记为“文本预览也受限”，并给出“打开完整文件/系统应用”的入口；如果只打算限制源码视图，则需要把预览与源码的读取策略分开。

### 3.5 A-04（P2）：编码兼容

`readTextPreview` 固定 `buffer.toString("utf8")`，且用“包含 NUL”判断二进制：

- UTF-16 LE/BE 文本天然含 NUL，会被误判为二进制并返回 415；
- GBK/GB18030 中文按 UTF-8 解码会出现替换字符；
- 在 2MB 边界截断可能切断一个多字节字符，末尾出现 `�`。

用户群体大量使用 Windows + 中文文档，这是可感知的预览质量问题。建议按 BOM/UTF-8 合法性检测，失败时回退 `TextDecoder("gb18030")`（Node 内置），并在截断时回退到最后一个完整字符边界。

### 3.6 A-05（P2）：图片粘贴的并发与去重

`ChatPanel.jsx:3730-3762`：

- `existingKeys` 与 `remaining` 来自 `imagesRef.current`，而 `imagesRef` 只在 `useEffect` 里随渲染更新（`ChatPanel.jsx:732-734`）。连续两次粘贴/拖入时，第一次还在 `await compressImage`，第二次调用读到的仍是旧 ref，两个批次都可能拿到 8 个名额，最终超过 8 张。
- 去重键是 `name|size|lastModified|type`（`图片处理.js:36-38`）。剪贴板 `getAsFile()` 生成的 `lastModified` 可能是每次粘贴的时间，同一张截图重复粘贴不一定命中；现有测试使用固定的 `lastModified`，无法覆盖真实行为。
- 非图片附件超过 6 个时仍然静默丢弃（`otherFiles.slice(0, 6)`），没有提示；这是既有行为，但与本轮“移除静默截断”的目标不一致。

建议：在 `handleFiles` 入口同步预留名额（先写 ref 再 await），压缩完成后再合并；去重用内容哈希（或至少 `size + type + 像素尺寸/字节采样`）替代 `lastModified`；对非图片超限补一条跳过提示。

## 4. 会话切换与历史加载稳定性

### 4.1 现有链路

点击历史会话（`App.jsx:1122` `handleSelectSession`）：

1. 清空右栏 run 范围，推进导航代际；
2. 如工作区不同，先 `switchWorkspace`；
3. 有缓存则先 `setHistoryMessages(cached)`，无缓存则置空；
4. 并行发起 `getSession(view=chat, limit=50)` + `listRuns(limit=50)` + `resumeAgentThread`（20s 超时）；
5. `await Promise.all([historyPromise, resumePromise])` 后才设置 `currentSessionId`、`threadId`、历史消息（`App.jsx:1179-1226`）；
6. `ChatPanel` 在 `historyMessages` 变化时水合消息（`ChatPanel.jsx:1282-1349`），在 `threadId` 变化时切换缓存（`ChatPanel.jsx:1351-1422`）。

### 4.2 发现

| ID | 严重度 | 问题 | 证据 |
|---|---|---|---|
| B-01 | **P1** | 历史展示被 resume 阻塞：即使 `getSession` 22ms 返回，也要等 resume（最长 20s）才显示 | `App.jsx:1164-1180`；`api.js:291`（getSession 用无超时 `api`）与 `api.js:203`（resume 20s） |
| B-02 | **P1** | 无缓存会话加载时旧会话消息不清空、没有 loading 态；用户会看到上一会话内容，随后突然替换 | `App.jsx:1152-1159`；`ChatPanel.jsx:1282-1289`（仅在 historyMessages 为真时水合） |
| B-03 | **P1** | 恢复失败后界面标“只读”，但输入区仍可发送；`frozen` 只取 `session.frozen`，没有与 resume 错误联动 | `App.jsx:1181-1182`、`App.jsx:1692`、`ChatPanel.jsx:3282` |
| B-04 | **P1** | 切会话时 `listRuns` 拉完整 Run（含最新事件），一次约 2.91MB；`fields=summary` 只需 0.08MB | 实测：`/api/runs?limit=50` 151ms/2.91MB；`&fields=summary` 22ms/0.08MB |
| B-05 | **P1** | 跨标签页只按“每标签页 3 条预算”控制，浏览器同源连接池仍是全局 6 条；3 个标签页各 2 条必需流即可占满，控制面请求排队/超时 | `长连接预算.js:16`；`ChatPanel.jsx:1846`、`App.jsx:744` 两条 essential；现场 24 条流/12 个 client（每个 2 条） |
| B-06 | P2 | 关闭流时先发 `/api/agent/stream/close` 再关本地 EventSource；池满时该请求排在自己要关闭的流后面，只能等 2s 兜底 | `长连接预算.js:206-230` |

| B-08 | P2 | 后台 Run 结束时只刷新会话列表，不失效历史缓存；切回缓存会话先显示旧内容，等新请求回来才更新 | `App.jsx:797-806`、`App.jsx:1226/1243` |
| B-09 | P2 | 冷启动/外部磁盘繁忙时，`/api/sessions` 内部要遍历全部 Run 元数据；实测热态 155–232ms，但多个标签页同时刷新会放大 | `/api/sessions` 实测；`server/index.mjs:3795`、`server/runs.mjs:1618` |

### 4.3 关键解释

- **不是服务端慢**：热态 `/api/sessions` 在 155–232ms，样本会话 `getSession` 22ms/80KB，`listRuns` 151ms；用户感知的“读取失败”更多来自浏览器端连接排队和前端等待策略。
- **最长的等待来自 resume**：正常 resume 很快，但遇到 20s 超时、另一个标签页的同会话占用（SESSION_BUSY）、工作区不匹配或冷启动时，历史会一起等。用户看到的就是“点了没反应”。
- **跨标签页是剩余的结构性风险**：008 已经把单标签页从 5 条流降到 2 条，但预算仍是“每标签页”而不是“每浏览器/每源”。在 3 个标签页同时打开时，2 条 essential × 3 = 6，控制面没有槽位；`apiControl` 的自动回收只能回收 optional 流，收不掉对话流/全局事件流。
- **关闭顺序会放大恢复时间**：`closeEventSourceQuietly` 先 POST 再本地 `close()`，连接池满时 POST 本身要排队；2s 兜底后才释放，切换会话会连续触发，形成“越切越慢”的体感。
- **缓存策略是“先旧后新”**：有缓存时先显示缓存，这对快速切换是优点；但后台 Run 完成后没有主动失效，用户可能先看到旧的一轮，再看到刷新，误以为“历史丢了”。

- `apiControl` 8s 超时 + 回收可放弃流 + 重试（`client/src/api.js:60`）；

### 5.3 目标形态（ZCode 式）

建议把“Run”作为会话流的一等单元，而不是把 Run 的碎片散在 assistant 消息里：

```text
[用户消息]

┌ 已完成 · 运行了 2 小时 13 分 · 45 步 · 3 个产物        [展开过程] ┐
│  （折叠时只显示这一行；展开后是按 turn 分组的时间线）              │
└──────────────────────────────────────────────────────────┘

本轮总结
  做了什么 / 关键结果（含数字）/ 产物路径 / 如何验证 / 未完成项或风险

本轮产物
  [📄 规划报告.docx]  [📊 OD矩阵.xlsx]  [🗺 图层.geojson]     查看全部 →

（如最终答复包含总结之外的内容，再显示“补充答复”；否则不重复）
```

状态文案建议：

- 运行中：`正在运行 · 已用 12 分 · 当前：写入文档`（用时每秒刷新，过程默认展开）
- 完成：`已完成 · 运行了 2 小时 13 分 · 45 步 · 3 个产物`（过程默认折叠）
- 部分完成：`部分完成 · 运行了 18 分 · 2 项未完成`（保留未完成项入口）
- 失败/取消：`失败 · 运行了 3 分` / `已取消 · 运行了 18 分`（原因与重试入口在同一行展开）

### 5.4 数据是否够用

- `run.startedAt` / `finishedAt`：够算总用时；终态缺失时需用最后一个事件时间兜底。
- `run.steps`：真实样本 1–45 步，可提供步数；`run.events` 可提供工具数。
- `run.completion.summary`：已有的详细总结来源；真实样本与 `run.summary` 相同。
- `run.finalText`：最终答复，可能比 summary 短。
- `run.artifacts`：产物路径/类型/确认状态，够做产物卡。
- 不足：`listRuns(fields=summary)` 当前不返回 `stepCount/toolCount/durationMs/artifactCount/compact artifacts`（`server/runs.mjs:1583`），历史首屏若想零事件渲染折叠行，需要补这些摘要字段；完整过程可按需 `getRun`。
- 不足：没有“总结来源/是否被展示”的显式字段，前端只能靠 `finalAnswer` 是否存在猜测；建议补 `summarySource` 或统一投影规则。

## 10. 补记（2026-10-30）：文件列表读取失败调查

### 10.1 现象

前端横幅“文件列表读取失败，已保留上一次可用数据”来自 `App.jsx:1001` 的统一加载失败提示；`files` 分区的错误由 `refreshFiles` 捕获（`App.jsx:675-704`）。文件列表 API 是 `apiControl("/api/files")`（`client/src/api.js:82`），超时 8s；服务端路由在 `server/index.mjs:969`。

### 10.2 复现与证据

1. **稳定态**：四个工作区的 `/api/files` 实测 3–36ms、200；`/api/files` 根目录 5.7ms。说明不是“目录大/服务端常态慢”。
2. **文件抖动下复现 500**：在临时目录创建 100 个文件 + 100 个子目录，用子进程持续删除/重建，同时向 `/api/files?workspace=<temp>` 发 60 次请求：
   - `200` 33 次，`500` **27 次**；500 响应是 Express 默认 HTML 错误页，前端 `api()` 只能得到 `HTTP 500`。
3. **隔离函数复现**：同样抖动下直接调用 `listWorkspace(dir)` 220 次，**78 次抛 `ENOENT`**。
4. **代码原因**：`server/workspace.mjs:183` 的 `listWorkspace` 先 `readdirSync`，随后对每个文件/目录直接 `statSync`，没有逐项 `try/catch`；条目在 `readdir` 与 `stat` 之间被删除/重命名就会抛 `ENOENT`。`/api/files` 路由（`server/index.mjs:969-982`）也没有包裹 `listWorkspace`，同步异常直接变成 500。对比 `searchWorkspace`（同文件后续函数）对 `readdirSync`/`statSync` 都有 try/catch，说明这是列表路径的遗漏，不是设计意图。

### 10.3 为什么是“偶发”

- Agent 写文件常用“临时文件 + 原子 rename”、OfficeCLI 运行时会创建/清理锁文件与临时目录；用户或 Agent 同时删除/重命名目录也会触发同样的窗口。
- `file_changed` 事件会合并 500ms 后刷新（`App.jsx:1429-1452`），刷新时后台写入可能仍在继续，正好撞上 `readdir`→`stat` 的窗口。
- `refreshFiles` 没有 in-flight 去重：一轮任务里多次 `file_changed` 可能排队多个列表请求；一旦控制面连接池也紧张（见 B-05），8s 超时会叠加成“失败 + 保留旧数据”。
- 当前目录被删除/改名时路由返回 404，但前端不会自动回到工作区根目录；横幅会一直保留到用户手动切换目录。

### 10.4 修复方向（纳入 W10）

1. `listWorkspace`：`readdirSync` 外层 try/catch；每个条目的 `statSync` 单独 try/catch，失败就跳过（文件消失不应让整页列表失败）；目录条目可不再强求 `stat`（列表按名称排序，mtime 只用于展示）。
2. `/api/files`：捕获 `ENOENT/EPERM/EBUSY/EIO`，返回 JSON 错误码（如 `FILES_TRANSIENT` / `FILES_NOT_FOUND`），不要落到 Express HTML 500；对临时性错误可做一次短重试。
3. `refreshFiles`：复用 `sessionsRefreshRef` 的 in-flight 合并/排队模式；失败后 300–500ms 重试一次；`404 currentDir` 自动回到根目录并提示“目录已不存在”。
4. 回归测试：文件/目录抖动下 60 次请求不出现 500；单个文件消失时列表仍返回其余条目；目录被删后前端能回到根目录；控制面超时不影响旧列表保留。
5. 观测：`/api/files` 错误按 code 计数（不记录文件名/用户内容），便于确认是否还有外部盘/权限问题。

### 10.5 结论

“文件列表读取失败”有一个可稳定复现、与 Agent 写文件高度相关的服务端缺陷（P1），不是单纯的浏览器连接池问题；连接池/超时是叠加因素。修复应优先于会话流改造，因为它直接发生在任务执行过程中，用户感知为“边跑边报错”。
