# 切回「运行中会话」后界面冻结的调查

> 日期：2026-11-06　范围：`client/src/App.jsx`、`client/src/components/ChatPanel.jsx`、`server/index.mjs`、`server/agent.mjs`、`server/流连接.mjs`
> 方法：三路只读静态调查（前端流生命周期 / 会话切换编排 / 服务端 SSE 回放）+ Lead 交叉复核；**未改动任何文件**，无浏览器实机复现
> 现象：刷新、或切到其他工作区/会话后再切回「之前正在运行」的会话 → 界面停住不再渲染、运行态动画消失

---

## 1. 结论：三个闸门串联，任一处失败即永久冻结

现象不是"渲染挂了"，而是 **`isTaskLive` 变成 false**：时间流从"直铺 + 动画"退回"折叠一行 + 静态"（`ChatPanel.jsx:6502-6513`；动画只在 `.tl-list.is-live` 上，`styles.css`）。而 `isTaskLive` 依赖三个**本地**来源：

```js
// ChatPanel.jsx:5945
isTaskLive = streaming || executionFlow?.running || LIVE_RUN_STATUSES.has(runSummary?.runStatus)
```

三个来源在切回后都可能为假，且**没有任何自动恢复路径**：

| 闸门 | 位置 | 一旦成立 | 自动恢复？ |
|---|---|---|---|
| **G1 `agentReady` 单点门闩** | `ChatPanel.jsx:2081` `if (!agentReady) return undefined;` | **SSE 根本不建立**，没有新事件进来 | ❌ 只有 resume 成功 / 手动点横幅 / `resumeAutoRetry`（默认关且仅 SESSION_BUSY） |
| **G2 自举死锁** | `ChatPanel.jsx:2306-2307` 对账要求 `busy \|\| live status`；而 `busy` 只由历史水合置真（`1408`） | 水合没判出 live → `busy=false` → 对账不跑 → `busy` 永远不可能变真 | ❌（探测本身还挂在 `replayRecover`，默认关） |
| **G3 无锚点即丢帧** | `ChatPanel.jsx:2480` `ensureAssistant` 在 `!busy && !live` 时返回 null | 回放/实时到达的 `token/thinking` 被**静默丢弃**，但游标照常前进（`2217-2221`） | ❌ 游标已越过，重连不再回放 |

叠加服务端三个"回放不可信"问题（§3），结果就是：**事件也许在到，但前端不消费；或者干脆没建连接**——两种都表现为"卡住、动画消失、像丢了一样"。

## 2. 前端证据链

### 2.1 切走/切回做了什么

- **切走**：App `setAgentReady(false)`（历史到达后，`App.jsx:1712`）→ ChatPanel SSE effect 清理（`2249-2261`：close EventSource、清 watchdog、`slot.release()`）。**不卸载 ChatPanel**（无 `key`，`App.jsx:2773`），`frozen` 与切换无关（它是人工冻结）。
- **切回**：`setThreadId` 后 SSE effect 重跑，游标来自 per-thread 表（`2117`），带 `stream=<已知代际>`（`2150-2156`）。

### 2.2 会永久停在 `agentReady=false` 的三条路径（都真实存在）

1. `resumeAgentThread` 失败：`SESSION_BUSY`（`server/agent.mjs:6408`）、`SESSION_WORKSPACE_MISMATCH`（`server/index.mjs:5262-5267`）、`apiControl` 20s 超时、5xx → `setAgentReady(false)`（`App.jsx:1792`）。当前只有"手动重试"能救，自动重试受 `resumeAutoRetry`（默认关，`App.jsx:1916`）限制且只认 `SESSION_BUSY`。
2. **静默卡死分支**：`await resumePromise` 前有 `if (loadSeq !== sessionLoadSeqRef.current) return;`（`App.jsx:1790`）——提前返回跳过了 `1791/1792`，`agentReady` 停在 false，且 `sessionResumeError` 仍为 null → **横幅不渲染**（`App.jsx:2723` 依赖它），用户既看不到原因也没有重试入口。
3. `1712 → 1792` 之间任何异常（`localStorage.setItem` 配额、`mergeMapContext`、`buildHistoryMessages` 等）只进 `catch`（`1806`）打日志，`agentReady` 同样停在 false。

### 2.3 即使 SSE 建了，也可能"事件在到、界面不动"

- `ensureAssistant` 的闸门（`2480`）只认 `busy` 或 `runState.status`；`busy` 的唯一来源是历史水合（`1408`）或 thread 缓存（`1578`）。
- 对账探测（唯一能主动发现"服务端还在跑"）的入口要求 `busy || live`（`2306`），**自己把自己锁死**。
- 游标按"收到"推进而非"已渲染"推进（`2217-2221`）→ 被丢弃的事件永久不可恢复。
- 锚点错位风险：历史最后一条 assistant 的 `runId` 与 live Run 不一致时，`assistantIdRef` 为 null，`executionAnchorId` 退化到**上一轮**气泡（`1445-1452`、`4526-4529`），表现为"实时动画挂在上一轮"。

### 2.4 另外两条真实存在的卸载/丢状态路径

- 打开「知识库 / 模板库」时整个主布局不渲染（`App.jsx:2484`）→ ChatPanel 卸载，游标/Generation 全丢；返回后从 `after=0` 重连。
- `slot === null` 时 `connect()` 仍会建连（`ChatPanel.jsx:2144-2242` 不检查 slot）→ 该流不进预算表，预算失真，更容易占满浏览器同源 6 槽 → 控制面请求（含 resume）排队超时 → 回到 2.2。

### 2.5 被排除的假设

- **不是** `frozen`：它是会话级人工冻结（`App.jsx:2307`），与切换无因果关系。
- **不是**跨标签页租约：租约只作用于全局事件流 `/api/agent/events`（`跨标签页流租约.js`），对话流按标签页保留；对话流是 `essential`，预算层不会拒绝。
- **不是**ChatPanel 被卸载：会话切换不重挂载（唯一例外是知识库/模板库）。

## 3. 服务端证据链：回放不可信

| # | 问题 | 位置 | 后果 |
|---|---|---|---|
| S1 | 首连（`after=0`）且通道历史 >300 条时**只回放最近 300 条**，但 `connected` 的 `earliest` 仍报整段历史头、`truncated` 仍为 false | `server/index.mjs:5500-5502`、`5431`、`5434`、`5466-5468` | 客户端拿到"看似连续"的半截回放，无法触发 Run 对账；运行中 Run 的 `run_admitted`/早期 `tool_start`/正文前段丢失 |
| S2 | `replayRecover`（从 `run_admitted` 整段回放）**默认关**，且分支只在 `lastId===0` 内 | `server/index.mjs:5506-5517`、`运行开关.mjs:146` | 刷新场景几乎必现缺头；带游标的切回重连永远不走该分支 |
| S3 | Runtime 健康判定为 failed 时，`ensureRuntime` 会**重建 Runtime**（新通道、空历史、seq 从 0）；若此刻 busy，则 `restartRuntime` 抛错 → 路由 `agent_error + res.end` | `server/agent.mjs:5441`、`6626`、`index.mjs:5524-5553` | 「上一轮失败过」的会话每次重连都可能拿到空通道或进入"连不上→重连→再失败"循环 |
| S4 | SSE 只在建立时挂一次 `channel.emitter.on`，Runtime 换代后旧 SSE 仍挂在死通道上，不主动发 `stream_resync` 也不断开 | `server/index.mjs:5447-5448` | "连接正常但永远无事件"，只能等 watchdog/重连 |
| S5 | `/api/agent/stream/close` 只按 `(client, thread)` 关"最旧一条"，没有 tab、没有 grace；客户端 `es.close()` 后异步 POST | `server/index.mjs:5281-5290`、`长连接预算.js:247-262` | 迟到的 close 可能关掉**刚建立的新流**，形成"被踢→重连"抖动 |

## 4. 快速自检（复现时按顺序做，能直接区分根因）

1. 控制台看是否有恢复失败横幅 / 输入框是否显示「正在恢复会话，请稍候…」（`ChatPanel.jsx:4996`）。有 → 命中 G1。
2. `GET /api/diagnostics/streams`：找不到该 `thread` 的 `/api/agent/stream` → G1；有流但 `ageMs` 极小、反复重建 → S5。
3. `GET /api/runs?session=<会话id>&fields=summary`：返回 `status:"running"` 而界面静止 → G2（服务端在跑、前端不消费）。
4. 控制台执行 `window.dispatchEvent(new CustomEvent("oaw:force-reconnect"))`：能恢复 → 游标/代际类（S1/S4）；`oaw:force-reconcile` 能恢复 → G2。
5. `window.__oawStreams` / `streamEvents(20)`（`长连接预算.js`）看 `open/close/evict/denied` 序列，区分"没建连"与"建了被杀"。

## 5. 修复方案（按优先级，**尚未实施**）

### P0（直接决定"能不能自己恢复"）

| # | 改动 | 位置 | 说明 |
|---|---|---|---|
| P0-1 | **`agentReady` 不再是单点闸门**：resume 失败/超时/异常/`loadSeq` 早退，全部必须落到 `sessionResumeError`（有横幅 + 重试按钮），`finally` 兜底；同时把"等待恢复"做成有上限的自动重试 | `App.jsx:1712-1818` | 消除 §2.2 的"静默卡死"三条路径 |
| P0-2 | **解除自举死锁**：切回/hydrate 后**无条件**对账一次 `listRuns(threadId, includeEvents:"all")`（不依赖 `replayRecover`），命中 live 就恢复 `busy/runState/activeRunIdRef/executionFlow`；对账完成前把无锚点的 `token/thinking` 缓冲（复用 `replayBufferRef`），完成后冲刷 | `ChatPanel.jsx:2303-2338`、`2427-2430`、`2480` | 解决"事件在到但被丢弃" |
| P0-3 | **服务端回放说真话**：走 `slice(-300)` 时把 `connected.earliest` 改为实际起点、`truncated=true`，并触发 `stream_resync` | `server/index.mjs:5431-5434`、`5489-5497`、`5500-5522` | 前端已有 resync 对账路径可用 |
| P0-4 | `ensureRuntime` 健康失败时，**busy 则不得重建**（返回现有 entry + 降级记录），避免把 SSE 打成 `agent_error` 循环 | `server/agent.mjs:5441`、`6626` | 消除 S3 的自毁循环 |

### P1（降低复发概率）

| # | 改动 | 说明 |
|---|---|---|
| P1-1 | SSE 与 agentReady 解耦：新增 observer 模式（`&observer=1` 时服务端**只 attach 现有 runtime，不创建**，无 entry 则回 `runtime_missing` 保持心跳） | 让"历史可读 + 运行中仍能看到实时进度"不再依赖 resume 成功；需要服务端配合，属中等改动 |
| P1-2 | 通道代际失效时主动下发 `stream_resync` 并 `end()` | 消除 S4 的"死通道订阅" |
| P1-3 | `/api/agent/stream/close` 加 `tab` 维度 + 只关 `probe()` 为真的最旧流 | 消除 S5 误杀 |
| P1-4 | `slot === null` 时不建连（或建连后标记"未计入预算"） | 避免预算失真引发控制面超时 |
| P1-5 | 知识库/模板库改为隐藏而非卸载 ChatPanel | 兑现"常驻"注释，避免游标全丢 |

### P2（可选）

- 评估把 `OAW_REPLAY_RECOVER` / `OAW_RESUME_AUTO_RETRY` 默认打开——**按 AGENTS §4.3 需用户确认**；本报告倾向用 P0-1/P0-2 的"无开关修复"替代。

## 6. 未验证项（如实声明）

1. **无实机复现**：以上为静态代码路径推导 + 三路交叉复核，触发概率未用真实流量统计。
2. **未验证**：`ensureAssistant` 丢弃后游标推进导致"永久丢失"的最终表现（依赖真实事件顺序）。
3. **未验证**：`session.id` 与 Run 记录 `sessionId` 在"服务端内存丢过 runtime、由 SSE 现场创建空会话"后是否漂移——若漂移，`listRuns({sessionId})` 会返回空，直接命中 G2。
4. 开关均按默认（关）判定：`resumeAutoRetry`、`replayRecover`、`streamQuota`、`qoderSseBackoff`。
5. 服务端诊断端点 `/api/diagnostics/streams` 仅用于人工核对，未纳入本次证据。
