# 0034 创作画布版本采用画布级时间线与内容寻址

- 状态：已采纳（随 2026-11-09 用户确认“全量修改”落地）
- 记录日期：2026-11-09
- 决策者：用户
- 基线：v0.13.24
- 关联：[004 计划](../plans/2026-11-09-004-创作画布多画板与版本时间线修改计划.md)、`REQUIREMENTS.md` R17、`DESIGN.md` §8.4、[0031](0031-创作画布采用可编辑画布文档与多画布标签.md)

## 1. 背景

0031 的版本历史是“每块板保存前留一份 JSONL 快照，最多 20 条”，只能列当前板历史并恢复单板；没有画布级版本、文件级变更清单、diff、删除恢复，也没有“Agent 一轮 = 一个版本”的语义。

## 2. 问题

如何用工作区文件承载可回溯的画布版本，让用户能看到“谁在什么时候改了哪些文件”，并支持整画布/单板恢复？

不解决的后果：Agent 连续生成多块板后无法一次回滚；删除的画板无法从版本恢复；版本只能按板看，无法理解一轮改动的全貌。

## 3. 备选方案

### 方案 A：继续每板 JSONL 快照

- 做法：把上限提高、补 UI。
- 优点：改动最小。
- 代价：没有跨板版本、没有 changes、恢复删除板困难；文件体积随板数线性增长。

### 方案 B：画布级版本索引 + 内容寻址（本决策）

- 做法：`designs/<slug>/.history/index.json` 记录版本（n/first/at/by/runId/summary/changes/restoredFrom）；文件内容按 sha256 存 `objects/`；一次保存批次/Agent 一轮合并为一条；恢复整画布或指定文件，恢复本身生成新版本。
- 优点：文件级 changes 与 diff 天然可得；内容去重；支持删除恢复；与 baoyu-design 的 history 模型同构。
- 代价：需要 GC 与保留策略；恢复整画布要处理“版本中不存在的板”（移入 `.trash`）。

### 方案 C：数据库/事件溯源

- 做法：引入 SQLite 或事件日志作为版本真源。
- 优点：查询与 diff 更强。
- 代价：违反“不引入数据库”的项目约束；与工作区文件真源冲突。

## 4. 决策

选择**方案 B**：画布级版本索引 + 内容寻址对象；Agent 同 `runId` 10 分钟内合并、UI 同 actor 2 秒内合并；最近 20 条不清理，最多 200 条/90 天；支持整画布/指定文件恢复与文件级 diff。

边界：不写回外部 `.dc.html`；不读取/修改 baoyu 自己的 `history/`；旧 `.history/*.jsonl` 保留只读兼容。

## 5. 理由

- 文件级 changes 足以支撑“版本时间线 + 恢复 + diff”，且实现不依赖数据库。
- 内容寻址让多板/多版本去重，256MB 画布配额下更可控。
- 与 0033 的 `runId` 事件字段对齐，Agent 一轮可自然合并成一条版本。

## 6. 影响

- 正面：画布级回滚、删除恢复、文件级 diff、actor/run 可追溯。
- 代价：版本存储与 GC 逻辑；恢复整画布会移动/删除当前多余板（软删到 `.trash`）。
- 迁移：新索引从首次写入开始；旧 JSONL 保留，旧板级历史接口继续可用。
- 回滚：关闭开关即无入口；`.history/index.json` 与 `objects/` 属于运行时数据，可保留。

## 7. 验证

- `test:canvas-model`：同 runId 合并、changes、diff、整画布/单板恢复、删除回滚、未知版本错误码。
- `test:canvas-ui`：版本时间线、恢复范围、diff 展示接线。
- 人工验收：Agent 一轮 5 板 = 1 条版本；恢复上一版内容/顺序正确。

## 8. 复审触发条件

- 版本存储超过配额或 GC 成本显著上升；
- 需要对象级 diff 或分支/合并；
- 外部画布格式要求复用同一 history 目录。
