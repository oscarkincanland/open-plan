# 0001 智能体内核采用 Pi Agent SDK

- 状态：已采纳（追溯确认）
- 记录日期：2026-10-25
- 决策者：项目负责人 / 架构评审
- 基线：v0.11.55
- 关联：[技术架构分析与内核迁移可行性报告](../2026-10-14-技术架构分析与内核迁移可行性报告.md)、[架构规范](../规范/架构规范.md)

## 1. 背景

项目当前形态是“内嵌 Pi Runtime + 自研 Harness 控制平面”。Pi（`@earendil-works/pi-coding-agent@1.1.0`）负责 Agent 循环、模型运行时、会话 JSONL 与工具执行；Run、事件、产物、工作区、权限、知识库、地图、Office 由本项目实现。

2026-10-14 的可行性报告对比了 Pi 与 DeepSeek Harness（DSH），结论是不建议整体替换，可先做内核适配 seam，再把第二个内核作为可选开关接入。

## 2. 问题

是否为了获得 subagent、plan mode、沙箱、调度等能力而更换或 fork 智能体内核？

## 3. 备选方案

### 方案 A：保留 Pi，强化自研控制平面

- 做法：Pi 仅作内核；能力缺口通过工具、工作流、子代理编排、审批与事件层补齐。
- 优点：改动面小、现有能力不丢、可回滚、无内核维护成本。
- 代价：受 Pi API 与能力边界约束；部分能力需要自研。

### 方案 B：整体替换为 DSH

- 做法：以 DSH 作为完整 Harness，重建 Office/知识库/地图/权限/产物能力。
- 优点：原生获得沙箱、调度、subagent、恢复等范式。
- 代价：等于重做控制平面；DSH 处于开发者预览，存在破坏性变更风险。

### 方案 C：自研内核

- 做法：自行实现 Agent 循环、模型适配、工具执行。
- 优点：完全可控。
- 代价：成本最高，且与业务价值无关。

### 方案 D：立即双内核

- 做法：同时维护 Pi 与 DSH 两个适配器并默认切换。
- 优点：可对比。
- 代价：当前阶段维护成本翻倍，收益未验证。

## 4. 决策

选择方案 A：**保留 Pi Agent SDK 作为默认且唯一的内核，不 fork、不修改 SDK 源码。**

- 只有 `server/agent.mjs`、`server/Pi运行时管理.mjs`、`server/项目信任.mjs` 可以直接 import Pi SDK。
- 未来若引入第二内核，必须先实现“内核适配器 + 规范化事件 + 能力描述符”，并以默认关闭的开关接入；该改造必须另写 ADR。

## 5. 理由

- 项目真正的短板在编排事实来源、权限/沙箱、任务恢复，而不是模型循环本身；这些可以在控制平面补齐。
- 替换内核会同时覆盖“内核”和“Harness”两层，风险与收益不匹配。
- 保留 Pi 可以继续复用其模型目录、会话、工具执行与现有 70+ 回归资产。

## 6. 影响

### 正面

- 现有功能、事件、测试基线保持稳定；升级路径可控。
- 业务能力沉淀在自研层，不被内核绑定。

### 负面 / 代价

- 受 Pi 事件模型与 API 约束；Pi 升级可能带来兼容工作。
- 官方不支持的 subagent/plan mode 只能模拟，不能宣称原生能力。

### 迁移与回滚

- 当前无迁移；内核升级按小版本推进，先跑 `verify` 与关键回归。
- 如需第二内核，采用开关 + 适配器，可回退到 Pi。

## 7. 验证

- 内核相关改动必须跑 `npm run verify`、`test:pi-config`、`test:pi-connectivity`、`test:capability-contract`。
- 事件转译改动必须跑 `test:event-registry`、`test:event-payload`、`test:sse-protocol`。

## 8. 复审触发条件

- Pi 出现破坏性升级或长期停止维护。
- 业务需要 Pi 无法通过控制平面补齐的关键能力（如强沙箱、原生调度）。
- 双内核对比数据证明第二内核在稳定性/成本上显著更优。
