# 0002 保持单仓单服务与 React SPA

- 状态：已采纳（追溯确认）
- 记录日期：2026-10-25
- 决策者：项目负责人 / 架构评审
- 基线：v0.11.55
- 关联：[架构规范](../规范/架构规范.md)、[README](../../README.md)

## 1. 背景

项目是一个本地优先的规划工作台：`client/` 为 React 18 + Vite 5 单页应用，`server/` 为 Node.js 22 + Express 5 单服务，默认监听 `127.0.0.1:3002`；数据落在工作区与 `.oaw/`。当前服务端约 74 个 `.mjs` 模块，前端约 47 个 `.jsx` 组件，`server/index.mjs` 与 `server/agent.mjs` 已成为超大文件。

## 2. 问题

是否拆分前后端仓库、拆微服务、或立即引入桌面壳（Electron/Tauri）？

## 3. 备选方案

### 方案 A：保持模块化单体

- 做法：单仓、单 Express 服务、React SPA；按层分模块，`index.mjs` 只做组合根。
- 优点：部署简单、调试链路短、契约变更可一次提交、现有测试体系无需重搭。
- 代价：无法独立伸缩；超大文件需要持续拆分。

### 方案 B：拆分为多个服务

- 做法：Agent、Office、地图、知识库各自独立服务。
- 优点：边界清晰、可独立发布。
- 代价：本地部署复杂、跨服务事件/事务/权限成本高，与单机定位不符。

### 方案 C：拆分前后端仓库

- 做法：`client` 与 `server` 独立仓库。
- 优点：权限与发布解耦。
- 代价：契约改动需要双提交、联调成本上升。

### 方案 D：立即桌面壳

- 做法：Electron/Tauri 包装现有服务与前端。
- 优点：安装与离线体验更好。
- 代价：壳层、自动更新、officecli 分发、签名都需要长期维护。

## 4. 决策

选择方案 A：**保持单仓、单 Express 服务、React SPA 的模块化单体。**

- `server/index.mjs` 只做路由注册、依赖装配、参数校验与错误映射；业务逻辑进入 L2 模块。
- 不新增独立后端服务、不拆仓、不引入桌面壳；确有需要时另写 ADR。
- 新增模块遵守 [架构规范](../规范/架构规范.md) 的分层与依赖方向。

## 5. 理由

- 产品是单机、单用户的本地工具，微服务的运维成本没有对应收益。
- 单仓能让 API/SSE/事件契约与前端消费在同一提交内演进，回归脚本也能直接 import 服务端模块。
- 桌面端是独立的产品化问题，不应与当前业务迭代捆绑。

## 6. 影响

### 正面

- 启动、部署、备份、排障路径最短；测试可直接跑真实服务。
- 前端与后端契约变更可以原子提交。

### 负面 / 代价

- 单进程故障影响全部能力；无法水平扩展。
- 超大文件（`index.mjs`、`agent.mjs`、`ChatPanel.jsx`、`App.jsx`）需要持续拆分，否则维护成本上升。

### 迁移与回滚

- 当前无迁移。
- 拆分服务/仓库时，先做契约层与模块边界，再迁移；保留单服务回退路径。

## 7. 验证

- 架构改动必须跑 `npm run verify` 与受影响关键回归；新增跨层依赖必须在评审中说明。
- 新增模块应能被 `node --check` 与至少一个契约/行为测试覆盖。

## 8. 复审触发条件

- 需要多用户远程部署或水平扩展。
- 单进程成为明确瓶颈（并发、内存、故障隔离）。
- 桌面端成为必须交付的独立产品，且壳层方案已验证。
