## 1. 背景

2026-10-29 事故中，一条 `Get-NetNeighbor` 让整轮 Agent 卡死 630 秒；虽然 B1–B4 已把超时/中断修好，但长命令仍同步占用当前回合，用户无法“让慢命令在后台跑、同时继续做别的”。用户明确提出需要前端可见的后台运行界面。

## 2. 问题

在不引入数据库、消息队列或新服务的前提下，如何让长命令脱离当前回合运行、可查询、可终止，并在前端可见？不解决则长扫描/大导出仍会阻塞对话，或只能被超时打断后重跑。

## 3. 备选方案

### 方案 A：进程内作业表 + 文件日志（采用）

- 做法：在现有 Express 进程内维护 job 表；复用 B1 受控执行器 spawn；输出追加到 `.oaw/jobs/<runId>/<jobId>.log`；元数据写 `<jobId>.json`；通过 SSE 推送 `bash_job_started/updated/finished`；提供工具与 REST 查询/终止。
- 优点：不新增进程/服务/依赖；复用已有的进程树终止与工作区边界；日志可回放；实现与运维成本最低。
- 代价/风险：服务重启会丢失运行中的 job（只能标记 interrupted）；job 与主进程共享 CPU/内存；日志需要上限与清理。

### 方案 B：独立 worker 进程 / 常驻 sidecar

- 做法：把 job 交给独立 Node 子进程或 DSH sidecar，通过 IPC/RPC 管理。
- 优点：崩溃隔离、可独立限流。
- 代价/风险：新增进程模型、IPC 契约、生命周期与部署复杂度；当前 Pi SDK RPC 不含 customTools，无法直接承载；违反“单服务、最小依赖”。

### 方案 C：shell `&` / `nohup` 直接丢后台

- 做法：在 bash 命令末尾加 `&`，不登记 job。
- 优点：零实现。
- 代价/风险：无法查询状态、无法可靠终止、输出丢失、跨平台差异大；用户与模型都看不到结果，等于不可用。

### 方案 D：保持同步，只靠超时

- 做法：继续使用 B1 的 120/600 秒硬超时。
- 优点：零新增面。
- 代价/风险：长任务被强制中断、必须重跑；用户明确要求后台运行，不满足。

## 4. 决策

选择**方案 A**，并限定边界：

1. 仅 Work 模式可用；Chat/Review 不提供后台命令。
2. 新工具：`bash_background`（启动）、`bash_status`（查询）、`bash_kill`（终止）。
3. REST：`GET /api/bash/jobs?client&thread&runId`、`POST /api/bash/jobs/:id/kill`，供前端读取与终止。
4. 事件：`bash_job_started` / `bash_job_finished` 落盘；`bash_job_updated` 作为增量事件、节流（≥2 秒）且不落盘，避免 Run JSON 膨胀。
5. 存储：`.oaw/jobs/<runId>/<jobId>.json` + `<jobId>.log`；日志单文件上限 10 MB，超出截断并标记 `truncated`。
6. 生命周期：并发上限 4；空闲超时 30 分钟；单 job 最长 6 小时；Run 取消、服务退出时统一终止；启动时把遗留 `running` job 标记为 `interrupted`。
7. 安全：沿用工作区边界与审批策略；破坏性命令（删除/覆盖/写入）启动前走 `requireToolApproval`；禁止交互式 stdin；命令文本只落前 500 字符，输出不写日志以外的位置。
8. 不引入数据库、消息队列、独立服务或常驻 worker。

## 5. 理由

- 关键权衡 1：崩溃隔离 vs 实现成本。当前规模（单机、单用户、并发 ≤4）下，进程内作业表的收益远大于独立 worker 的隔离收益。
- 关键权衡 2：可观测性。文件日志 + 事件流让模型、用户、审计都能看到同一份事实；不依赖内存态。
- 与项目约束的关系：本地优先（文件存储）、可回滚（删除 job 不影响主流程）、可测试（JobManager 可注入执行器）、单一事实来源（事件注册表 + job JSON）。

## 6. 影响

### 正面

- 长命令不再占用对话回合；用户可继续提问/操作。
- 终止路径与 B1 共用，进程树清理能力一致。
- 前端有明确的“后台运行”状态与日志入口。

### 负面 / 代价

- 服务重启会丢失运行中的 job（标记 interrupted，不伪装成功）。
- 日志占用磁盘，需要上限与清理策略。
- 新增工具与 REST/SSE 面，需要同步白名单、能力计划、事件注册表、测试与 DESIGN。

### 迁移与回滚

- 迁移：新增文件与工具；无数据迁移。旧会话不受影响。
- 回滚：从 `server/task.mjs` 白名单移除三个工具，删除 REST 路由与前端卡片；`.oaw/jobs` 可保留或手动清理。
- 兼容性：新增事件与 REST 为增量，不改变既有事件 payload；`bash` 工具行为不变。

## 7. 验证

- 新增 `scripts/后台命令测试.mjs`：启动/状态/终止/日志截断/并发上限/Run 取消清理/重启恢复标记。
- `test:event-registry`、`test:capability-contract`、`test:harness-api`、`npm run verify` 通过。
- E2E：启动 5 分钟命令后，同会话 2 秒内可继续对话；任务卡可见；终止按钮生效；服务重启后 job 标记 interrupted。

## 8. 复审触发条件

- 并发 job 需求持续 >4，或单 job 超过 6 小时。
- 日志总量超过 1 GB 或单文件频繁触顶。
- 需要跨进程崩溃隔离、跨机器执行，或需要持久化队列。
- 前端需要独立的终端页签/交互式 stdin（当前明确不做）。

## 9. 实施记录（2026-10-30）

- 新增 `server/后台命令.mjs`：进程内 JobManager（start/list/get/log/kill/killJobsForRun/killAll/recover），文件日志 10 MB 截断、并发 4、空闲 30 分钟、最长 6 小时；执行器注入便于测试。
- `server/命令执行器.mjs` 增加 `onSpawn({ pid, stop })`，作业表无需等待 Promise 即可拿到 PID 与终止句柄。
- `server/agent.mjs` 注册 `bash_background` / `bash_status` / `bash_kill`（仅 Work 白名单），复用 bash 的审批、执行闸门、全盘搜索与长期记忆保护、暂存物化；事件按作业自己的 Run 归属。
- `server/index.mjs`：`GET /api/bash/jobs`、`GET /api/bash/jobs/:id`（日志尾部）、`POST /api/bash/jobs/:id/kill`；Run 取消与对话栏中断统一终止该 Run 的作业；服务退出 `killAllBackgroundJobs`；启动 `recoverBackgroundJobs` 标记 interrupted。
- 事件注册表新增 `bash_job_started`（落盘）、`bash_job_updated`（高频不落盘）、`bash_job_finished`（落盘）。
- 前端：`BackgroundJobCard.jsx` 后台任务卡（状态徽记、时长、最后一行、日志尾部 200 行、终止二次确认）、对象栏“后台进程”组并入 job 条目、`api.js` 三个只读/终止接口。
- 测试：`npm run test:bash-jobs`（9 项）、`test:harness-api`（新增 3 项）、`test:tool-metadata`、`test:event-registry`、`test:capability-contract`、`test:bash-hang`、`test:exec-handle`、`npm run verify`。
- 未做：独立终端页签、交互式 stdin、后台任务历史独立页；对象栏只读汇总，不作消息流定位跳转（DESIGN §6.7 已同步）。
