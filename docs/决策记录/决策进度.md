## 1. 决策机制

### 1.1 参与角色

| 角色 | 职责 | 权限 |
|---|---|---|
| 产品负责人（用户） | 提出目标、拍板取舍、签字批准 | **唯一**有权批准：需求变更、默认开 flag、新增依赖、合并/发布、推翻既有决策 |
| 主控智能体（Leader） | 调研、起草方案、列代价与替代、记录决策、跟进落地 | 提案与执行，无最终签字权 |
| 代码审计智能体 | 独立审查方案与实现的风险 | 只读，给出阻断/建议 |
| 执行子代理（worker） | 按批准方案实施 | 仅在本轮范围内写，写操作需审批 |
| 验收智能体 | 验证决策落地效果 | 只读，给出通过/失败 |

### 1.2 决策流程（五步，不可跳）

```
① 提出：写清问题、现状、约束（谁提都行）
② 方案：至少 2 个可选方案 + 各自代价/放弃什么（主控智能体）
③ 评审：架构/安全/性能/可回滚性四项检查（代码审计智能体）
④ 签字：产品负责人明确同意，记录日期与参与人
⑤ 跟进：落地动作、验证方式、复查时间写入下表
```

### 1.3 状态取值

`已采纳` / `生效中` / `待定` / `已否决` / `已废弃（替代者：D-xxx）`。

### 1.4 硬规则

- 决策一旦记录，后续会话**不得无故推翻**；要推翻必须写"推翻条件"并经产品负责人确认。
- 只记"选了什么 + 为什么 + 代价"，不记讨论过程。
- 每轮收尾若有新的技术取舍，必须补一条；没有记录的决策视为未发生。
- 与代码实际行为冲突时，先核对代码，再更新决策状态。

## 4. 明确否决过的方案（防止反复重提）

| 被否决的方案 | 否决原因 | 什么情况下值得重新考虑 |
|---|---|---|
| 引入 Redis / 消息队列 | 单机数据量小，进程内事件足够 | 多实例部署或并发 >500 |
| PostgreSQL / MySQL | 违反"不做数据库服务"约束，本地文件 + JSONL 已满足审计 | 需要多人共享与事务 |
| WebSocket 替代 SSE | 单向事件流足够；自管心跳/重连收益低 | 需要双向高频交互（如协同编辑） |
| Next.js / SSR | 纯本地工作台，无 SEO/首屏服务端渲染需求 | 对外公开站点 |
| 新增 UI 组件库（AntD/MUI/shadcn） | 破坏既有冻结样式与令牌体系 | 全站视觉重构且产品负责人批准 |
| 新增图标库 | `Icon.jsx` 统一管理，`test:icons` 守护 | 图标规模超出维护能力且零新增依赖可解 |
| Qoder 皮肤引擎（多 Flavor × Swatch） | 需求是"对齐视觉语言"，不是复刻 | 产品定位变为可换肤的商业产品 |
| 全量重构 `agent.mjs` / `index.mjs` / `ChatPanel.jsx` | 破坏基线、无法回滚；与"最小侵入"冲突 | 有完整测试保护且单独立项（清理批次） |
| 移动端适配 | 用户是桌面办公场景 | 出现明确的移动端使用需求 |
| 多租户 / 公网部署 | 本地单机、数据不出本机 | 产品转为 SaaS |
| 把对话流改为手写 SSE 解析 | 原生 EventSource 已满足；手写易错 | 需要 EventSource 不支持的能力 |
| 修改 Pi 内核 / 假设官方 subagent | 官方不支持，改内核不可维护 | 官方提供对应能力 |
| 老格式 `.doc/.ppt/.xls` 转换队列 | 使用频率未知，先按 415 拒绝 | 用户明确需要且提供样本 |

## 7. 复查节奏

- **每轮收尾**：有新技术取舍就补一条；没有就保持沉默，不写"本轮无决策"。
- **每个版本发布前**：核对第 5 节"已记没做"的项；未落地的决策必须降级为 `待定` 或说明原因。
- **每月一次**：清理已废弃决策的引用；确认待定项没有变成"永久悬空"。
- **决策冲突时**：以编号更大、日期更新的决策为准，但必须在旧条目上标 `已废弃（替代者：D-xxx）`，不得直接删除。
