# 0029 输入区采用统一引用与命令面板

- 状态：已采纳
- 记录日期：2026-11-08
- 决策者：用户
- 基线：v0.13.24（`develop @ 7ef77f76`）
- 关联：计划 [2026-11-08-001-人机协作中枢与技能写作链路完整修改计划](../plans/2026-11-08-001-人机协作中枢与技能写作链路完整修改计划.md) §2.1/§5/D3、`REQUIREMENTS.md` R4/R16、`DESIGN.md` §3/§7、`client/src/components/ChatPanel.jsx`、`server/context.mjs`

## 1. 背景

审查（2026-11-07）显示输入区实际存在四套触发器（`/` 命令、`@` 文件、`@` 智能体提及、`#` 技能/插件/文件、`&` 会话）与两套浮层状态：`@` 可能同时打开两个菜单；插入的是纯文本标记，发送后气泡只渲染部分 chip，服务端解析结果对用户不可见，失败静默；`#` 菜单只读 `project.settings.skills`，而 7/7 个项目该值为空，用户从输入框看不到 66 个已装技能。`DESIGN.md` 只定义了 `#` 一组，与实现漂移。

## 2. 问题

输入区的符号语义未定义，同一个 `@` 承担"文件引用"与"智能体提及"两种含义；输入态、气泡态、服务端解析态不一致，导致"分不清、调用后还是文字、打字被干扰"。若不统一，引用失败无法诊断，技能/插件无法从输入框被发现。

## 3. 备选方案

### 方案 A：四套独立菜单 + 纯文本标记（现状，放弃）

- 做法：分别修 `/ @ # &` 的菜单与文案，保持各自状态机。
- 优点：改动最小。
- 代价/放弃原因：双弹层、键盘冲突、三态不一致的根因仍在；每新增一类引用就多一套菜单。

### 方案 B：只修 `@` 双弹层与 `#` 数据源（放弃）

- 做法：合并两个 `@` 菜单，`#` 改为读全部已装技能，chip 暂不统一。
- 优点：能解决最痛的两个点。
- 代价/放弃原因：仍是多套渲染层与多套状态机，服务端解析状态仍不可见；"删除 chip 同步删除文本"无法统一。

### 方案 C：统一引用模型 + 单一候选面板 + chip 三态（采纳）

- 做法：`/` 只做动作、`@` 默认引用组（`@智能体` 为子项）、`#` 技能与插件、`&` 会话组；四者共用同一候选面板与统一搜索；插入即 chip，输入栏与气泡渲染一致；服务端返回引用解析状态并回填 chip；客户端与服务端共用一组解析 fixture 做 parity 测试。
- 优点：一个面板、一套键盘规则、一套三态；失败可明示；技能/插件可发现。
- 代价/风险：需要从 8k 行的 `ChatPanel.jsx` 抽出 composer，回归风险高；需要保留旧路径一个版本周期。

## 4. 决策

选择**方案 C**：

1. 单一候选面板分四组：动作（`/`）、引用（`@`：文件/知识库/模板/会话/智能体）、技能与插件（`#`）、会话（`&`）；任一符号只打开**一个**面板，Tab 切组、统一搜索。
2. `/` 命令选中即执行，不进入消息流，不再依赖"整条消息完全匹配"；`/goal` 使用参数浮层；`/help` 打开帮助面板。
3. `@` 默认为引用组；`@智能体` 作为引用组子项，不再触发第二个弹层；删除 `mentionState` 独立状态与双弹层实现。
4. 引用类型统一为 file/knowledge/knowledge_dir/template/template_dir/skill/plugin/session/agent；服务端返回解析状态，前端回填 chip。
5. chip 三态一致：已解析 / 待解析 / 缺失。输入栏 chip 条可删，气泡渲染同样 chip（替代原始标记文本）；删除 chip 与删除文本标记双向同步；解析失败必须明示，不得静默降级为普通文字。
6. 键盘与 IME：统一 keydown 分发；中文输入法 composition 期间 Enter 不选中、不发送；Esc 只关一层；↑↓ 选择、Enter 选中。
7. 失败兜底：未识别标记在发送前提示；服务端预检失败 chip 标红并在消息流给原因。
8. 组件职责：`ChatPanel.jsx` 只做编排与事件转发；输入区抽为 `client/src/components/输入区/`（`Composer`、`ComposerPanel`、`useComposerState`）；解析器抽为 `client/src/引用标记.js`，与 `server/context.mjs` 用同一组 fixture 做 parity 测试。
9. 运行时开关 `composerUnified` 默认关；关闭时保留旧四菜单路径一个版本周期。

## 5. 理由

- 用户的真实心智是"我要插入一个东西"，符号只是入口；一个面板 + 四组比四套菜单更接近心智模型。
- 输入态、气泡态、解析态统一为 chip 后，"调用后还是文字"与"静默失败"从根上消失。
- 客户端/服务端共用 fixture 做 parity，避免两套解析器长期漂移。
- 先抽组件再改逻辑，可把 8k 行 ChatPanel 的改造风险降到可控，并保留开关回退。

## 6. 影响

### 正面

- `@` 只出现一个面板；`#` 菜单可见全部已装技能；引用/技能/插件/会话全部 chip 化并显示解析状态。
- 键盘与 IME 行为统一，中文输入不再被弹层打断；失败可诊断。
- ChatPanel 体积与职责下降，输入区可独立测试。

### 负面 / 代价

- 需要重构 `ChatPanel.jsx` 中 composer 相关逻辑，存在会话流回归风险，需要逐屏回归。
- 新增客户端解析器与服务端解析器的一致性维护成本（用 parity 测试兜底）。
- 旧四菜单路径保留一个版本周期，短期双路径并存。

### 迁移与回滚

- 迁移：无数据迁移；已发送的历史消息按旧文本渲染，不做回写；新消息走 chip 路径。
- 回滚：`OAW_COMPOSER_UNIFIED=0` 恢复旧四菜单路径。
- 兼容：服务端引用解析接口只增不改；旧标记语法继续被解析。

## 7. 实施约束

- 不新增设计令牌（字号/圆角/色值），沿用 `--radius-*`、`--success/--warning/--danger`、`--muted` 与 14/12 字号档；状态色不作为唯一载体，须附图标或文案。
- 不新增全局状态库；输入区状态用组件内状态机 + 既有持久化方式。
- 服务端与客户端解析器必须用同一组 fixture 做 parity；不允许两套规则各自演进。
- 旧路径保留一个版本周期，开关默认关；不得在未验收时删除旧实现。
- 不改变引用解析的安全边界（工作区路径校验、跨工作区拒绝）。

## 8. 验证与验收

- 新增 `scripts/输入区引用契约测试.mjs`（`test:composer-refs`）、`scripts/引用标记契约测试.mjs`（`test:ref-parser`）；修改 `test:ava-mention`、`test:ava-composer`、`test:chat-flow`。
- 验收口径见计划 §20：A-28～A-32（单面板、chip 三态、命令选中即执行、删除同步、IME）。
- 手工验收：中文输入法下输入/选中/发送；窄屏与键盘路径；刷新与切会话后引用状态。

## 9. 复审触发条件

- 输入法/键盘回归在真实中文输入场景持续出现。
- parity 测试频繁失败或两套解析器出现语义分叉。
- composer 抽取导致会话流/引用失败率上升，或旧路径在一个版本周期后仍需保留。
