# 0014 新增代码英文命名与存量冻结

- 状态：已采纳
- 记录日期：2026-10-30
- 决策者：用户
- 基线：v0.13.12
- 关联：[代码规范](../规范/代码规范.md) §2/§6、[文档管理规范](../规范/文档管理规范.md) §3、[计划](../plans/2026-10-30-001-分支合并与交付级规范化整改计划.md)

## 1. 背景

仓库既有代码大量使用中文文件名与中文标识符（`server/流连接.mjs`、`server/任务编排` 相关模块、`工作产物面板.jsx` 等），远程 v0.13.11 的《代码规范》v1.1 要求“新增文件必须中文命名”。用户在合并评审时明确要求：**代码规范中不要出现中文命名**。

若继续要求新增中文文件名，会与工程通用实践、外部工具链（ESLint/编辑器/CI 脚本）及远程既有英文文件形成双重标准；若全量重命名存量，则会产生巨大 diff、破坏 Git 历史与既有测试断言。

## 2. 问题

新增代码应使用英文还是中文命名？存量中文文件是否整改？不解决将导致：

- 规范与用户指令冲突，后续提交无法判定合规；
- 全量重命名引发合并冲突、测试断言大面积失败、历史追溯困难。

## 3. 备选方案

### 方案 A：新增英文 + 存量冻结（已选）

- 做法：新增代码文件/目录一律英文（模块 kebab-case、组件 PascalCase、脚本 `<name>-test.mjs`）；存量中文文件与标识符保持原名，不因规范重命名；注释、用户文案、日志仍用中文。
- 优点：规范唯一、diff 最小、Git 历史与测试稳定；新代码可直接对接通用工具链。
- 代价/风险：仓库长期处于“双语文件名”状态，检索时需知道两种形态。

### 方案 B：全量改为英文

- 做法：一次性重命名所有中文文件与标识符，并同步全部 import、测试断言、文档引用。
- 优点：命名彻底统一，长期检索成本最低。
- 代价/风险：超大 diff 与 16 个冲突文件的二次合并风险；远程主线后续提交必然冲突；违反“不做顺手重构”。

### 方案 C：新增继续中文

- 做法：维持远程规范 v1.1 原文。
- 优点：与远程主线一致，无需改规范。
- 代价/风险：直接违背用户明确指令；新增文件继续累积中文命名债。

## 4. 决策

选择**方案 A**。适用边界：

- 仅约束**新增**代码文件/目录与**新增**标识符；
- 存量中文文件、中文导出函数名（如 `按字节切分`）不整改；
- 文档仍按《文档管理规范》中文命名（`AGENTS.md` 等固定文件名除外）；
- 确需迁移存量文件时，必须独立提交、保留历史、经用户确认。

本轮已按此执行的改名：`供应商配置弹层.jsx → ProviderConfigDialog.jsx`；`活动摘要行测试.mjs → activity-summary-test.mjs`；`陈旧流停摆测试.mjs → stale-stream-test.mjs`；`预览懒加载测试.mjs → preview-lazy-test.mjs`。

## 5. 理由

- 用户指令优先于既有规范（AGENTS.md §2 解释顺序第 1 条）。
- 与“最小侵入、不做顺手重构、单一事实来源”约束一致。
- 新代码英文、注释中文，兼顾可维护性与团队可读性。

## 6. 影响

### 正面

- 新增代码命名有唯一、可机检的标准；测试脚本与 npm 别名一一对应，便于定位。

### 负面 / 代价

- 仓库存在中英混合文件名；新人需理解“存量冻结”边界。

### 迁移与回滚

- 迁移：新文件按本 ADR 命名；存量不动。
- 回滚：撤销本 ADR，恢复《代码规范》v1.1 §2 即可；已改名文件可保留（英文名同样合法）。
- 兼容性：只涉及文件名/导入路径，测试已同步。

## 7. 验证

- 需要新增/更新的测试：`test:preview-lazy`、`test:activity-summary`、`test:stale-stream` 断言新文件名；`test:cad` 注册断言兼容远程新增工具。
- 验收口径：`npm run verify` EXIT=0；上述定向测试全绿。
- 观察指标：新增提交中是否出现中文代码文件名（人工评审 + 提交前自检清单）。

## 8. 复审触发条件

- 远程主线再次修改命名规范并要求同步；
- 仓库新增自动化命名检查（可机检时改为强制门禁）；
- 存量文件迁移成本因工具链改善而显著下降。
