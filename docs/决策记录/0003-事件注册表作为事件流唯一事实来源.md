# 0003 事件注册表作为事件流唯一事实来源

- 状态：已采纳（追溯确认）
- 记录日期：2026-10-25
- 决策者：项目负责人 / 架构评审
- 基线：v0.11.55
- 关联：[架构规范](../规范/架构规范.md) §4–§5、`server/事件注册表.mjs`

## 1. 背景

事件流同时承担：SSE 实时展示、Run 审计、跨会话回放、前端投影、审批与终态语义。此前“是否算生命周期事件”（`事件协议.mjs`，决定通道历史能否被挤出）与“是否落盘”（`事件存储.mjs`，决定能否回放）是两张手写清单，实测出现 19 种事件“声明了但没落盘”、9 种“落盘但不受保护”的错位，重连后无法重建回合边界、审批、模型回退等语义。

## 2. 问题

如何保证事件类型、落盘语义、schema 与消费方始终一致，避免“只在某一处处理”的隐性缺陷？

## 3. 备选方案

### 方案 A：保留两张手写清单

- 做法：协议与存储各自维护事件集合。
- 优点：改动局部、无需新模块。
- 代价：已证明会错位；新增事件容易漏登记。

### 方案 B：每个模块自带事件定义

- 做法：事件在发射处声明 lifecycle/persist/schema。
- 优点：就近维护。
- 代价：同一事件多处发射时定义漂移，无法全局校验。

### 方案 C：中心化事件注册表

- 做法：一张表登记事件类型、`lifecycle`、`persist`、`schema`、备注；协议与存储从表派生。
- 优点：单一事实来源、可静态校验、可生成清单。
- 代价：新增事件必须改注册表；注册表需要维护纪律。

## 4. 决策

选择方案 C：**`server/事件注册表.mjs` 是事件流的唯一事实来源。**

- 新增/改名事件必须先登记；`persist: true` 必须同时 `lifecycle: true`。
- 事件负载 schema 在注册表声明；高频事件（token、进度等）默认不落盘。
- `事件协议.mjs`、`事件存储.mjs` 不得再维护第二份事件清单。
- 破坏性变更必须提升 `PROTOCOL_VERSION` 并写 ADR。

## 5. 理由

- 事件是前端展示、Run 审计与恢复的共同基础；两套清单必然漂移。
- 中心化后可以用测试强制“代码里出现的事件都已登记”，把运行时问题前移到提交前。
- schema 与 persist 语义放在一起，便于审查新增事件的影响面。

## 6. 影响

### 正面

- 事件新增/变更可被 `test:event-registry`、`test:event-payload` 自动拦截。
- 重连回放、审批、终态语义有稳定依据。

### 负面 / 代价

- 注册表会持续增长（当前约 115 种）；需要定期清理废弃事件。
- 高频事件误设 `persist: true` 会放大日志；需在评审中检查。

### 迁移与回滚

- 历史未登记事件已逐步补齐；新增事件从本 ADR 起强制登记。
- 若注册表设计不再适用，新建 ADR 替代，不直接删除历史登记。

## 7. 验证

- `npm run test:event-registry`：注册表一致性、代码发射点均已登记。
- `npm run test:event-payload`：schema 校验、必填/类型、发射点契约。
- `npm run test:sse-protocol`、`test:event-replay`、`test:event-archive`：协议、回放、归档。
- 新增事件必须在同一提交补测试与消费方投影。

## 8. 复审触发条件

- 事件数量增长到无法人工维护，或需要按模块拆分注册表。
- SSE 协议需要 v2 或不兼容字段变更。
- 出现跨进程/多实例事件总线需求。
