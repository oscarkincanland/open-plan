# 0026 人机协作中枢采用统一交互模型

- 状态：已采纳
- 记录日期：2026-11-08
- 决策者：用户
- 基线：v0.13.24（`develop @ 7ef77f76`）
- 关联：计划 [2026-11-08-001-人机协作中枢与技能写作链路完整修改计划](../plans/2026-11-08-001-人机协作中枢与技能写作链路完整修改计划.md) §2.1/§10/§11、`REQUIREMENTS.md` R2/R3、`DESIGN.md` §3/§6.4/§6.5/§7、[0010](0010-ask_user草稿预览契约.md)、[0014](0014-会话流折叠过程而不折叠答案与字号收敛.md)、`server/事件注册表.mjs`

## 1. 背景

审查（2026-11-07）显示：93 条 `ask_user` 中 17% 超时作废，43% 属于"是否继续/下一步"类收尾确认；ask 卡、输入栏待答条、审批条三处并存，缺少"当前待处理交互"的统一焦点；服务端单槽位、默认阻塞 30 分钟，回答耗时中位数 17.8 秒。写作 Run 中 ask 触发率 36%，阻塞占总时长 13%。产品需要把提问、确认、预览、审批收敛为人机协作的中枢，而不是各自为政的弹窗。

## 2. 问题

一切"需要人给一个输入"的交互由不同组件、不同状态机、不同存储分别实现：用户不知道现在该处理哪一个，模型把可默认执行的事项停下来提问，超时即作废且无法撤销。若继续让 ask 卡与审批卡各自为政，"提问预算"与"默认假设 + 可撤销"没有承载点。

## 3. 备选方案

### 方案 A：继续让 ask 卡与审批卡各自为政（放弃）

- 做法：只修文案与超时，保留单槽位、各自存储与渲染。
- 优点：改动最小，无迁移。
- 代价/放弃原因：无法统一优先级、幂等与刷新恢复；提问预算与假设回执无处承载；三处入口继续并存。

### 方案 B：前端聚合展示、服务端不改（放弃）

- 做法：前端订阅 ask/审批事件，统一渲染到同一个 Dock。
- 优点：服务端零改动。
- 代价/放弃原因：活动交互仍以两套文件为准，刷新恢复、多标签结算、幂等仍各自实现；无法统一状态机与优先级；跨会话归属校验无法单点收口。

### 方案 C：统一 Interaction 模型，服务端单一状态存储 + 前端 Dock/卡片/浮层（采纳）

- 做法：新增 `server/交互中枢.mjs`，将 `clarify/confirm/review/approval` 收敛为 `Interaction`；`.oaw/interactions.json` 作为活动状态单一存储；新增 `/api/interactions` 与 settle/assume；前端 `InteractionProvider` + Dock + 卡片 + 非模态浮层；legacy 事件与旧接口保留并双发兼容。
- 优点：单一事实源与状态机；优先级、幂等、恢复、多标签统一；假设可撤销、可追踪。
- 代价/风险：新增事件、存储、迁移与开关；双发期需断言不重复渲染。

## 4. 决策

选择**方案 C**：

1. `Interaction` 分四类：`clarify`（需要你补充）、`confirm`（请确认，高风险）、`review`（草稿已就绪/预览确认）、`approval`（工具审批）；提案过程中的超时/跳过产生假设回执，不新增第五类持久对象。
2. 状态机：`open → editing → submitting → settled(answered|skipped|assumed|denied|cancelled) | expired`。同一会话允许多个 `open`，优先级 `approval > confirm > clarify > review`；同一 `runId` 同时最多 1 个 clarify；`confirm` 不得 assumed。
3. 超时语义：`clarify`/`review` 默认 90 秒，超时按 `assumption` 继续并在消息流写回执；`confirm` 默认 30 分钟，超时不自动继续（取消并提示用户回来再处理）；`approval` 沿用现状 5 分钟视为拒绝。
4. 服务端以 `.oaw/interactions.json` 为单一活动存储（活动 + 最近 200 条历史）；中枢开关打开时启动迁移旧 `pending-asks.json`/`pending-approvals.json` 的 open 记录，迁移后旧文件只读兼容；开关关闭时继续写旧文件。
5. 前端以 `InteractionProvider` 为唯一事实源：Dock 位于输入框上方、队列坞之下，最多 3 条，显示"第 n/m 个"与主按钮；卡片三类形态，倒计时仅在最后 5 分钟出现；非模态浮层只在卡片离屏或会话不在前台时提醒，不打断输入。
6. 审批保留独立安全语义："允许一次/总是允许/拒绝"、拒绝红描边、自动批准不覆盖显式 deny；approval 的拒绝永远优先于自动批准。
7. 事件只增不改：新增 `interaction_open/updated/settled/expired/assumption`；`ask_user`、`tool_approval_request` 等 legacy 事件与旧接口继续保留；`GET /api/agent/pending` 作为 `/api/interactions` 的兼容投影。
8. 运行时开关 `interactionHub` 默认关；关闭时回到 ask 卡 + 审批卡原路径。默认值翻转由用户逐项确认。

## 5. 理由

- 提问、确认、预览、审批是同一件事的不同形态，统一对象后优先级、超时、假设、撤销、幂等只需要实现一次。
- 服务端持有活动事实，前端只做投影，符合项目"服务端事实以 API/SSE 为准、不新增全局状态库"的约束。
- 审批并入枢纽但保留独立安全语义，避免为了统一而降低安全边界。
- 假设与可撤销写入消息流回执，使"默认继续"成为可审计的交付事实，而不是隐藏行为。

## 6. 影响

### 正面

- 待处理交互常驻且可恢复，用户不再面对三处并存入口；写作 Run 的 ask 触发率目标 ≤15%、超时率 ≤3%。
- 提问预算、90 秒假设、可撤销有统一承载；审批与澄清共用 Dock，窄屏与键盘路径统一。
- 幂等与归属校验单点实现，避免多标签各答一次。

### 负面 / 代价

- 新增事件、JSON 存储、迁移与双发逻辑，实施与测试成本增加。
- 双发期存在重复渲染风险，需要专门去重断言。
- 前端 Dock/卡片/浮层增加复杂度；必须沿用既有设计令牌，不新增字号、圆角、色值。

### 迁移与回滚

- 迁移：开关打开时把旧 pending 文件的 open 记录迁入 `interactions.json`；旧接口内部转调 settle；历史交互不回放迁移。
- 回滚：`OAW_INTERACTION_HUB=0`（或关闭 `interactionHub`）恢复 ask 卡 + 审批卡路径，旧文件继续写入。
- 兼容：旧事件保留、旧接口保留；不迁移历史会话数据。

## 7. 实施约束

- 不改 Pi SDK，不新增 Agent 可调用工具；审批策略与安全文案不变。
- 新增事件必须登记 `server/事件注册表.mjs`，附 schema 与发射点守护测试。
- 交互结算必须校验 `clientId/threadId` 归属；同一 `interactionId` 重复 settle 返回第一次结果，不重复续跑。
- 事件与日志脱敏，不写用户文档内容；`.oaw/` 运行时文件不入 git。
- 所有新增行为受开关控制，默认关；默认值翻转需用户确认并记入变更日志。

## 8. 验证与验收

- 新增 `scripts/交互中枢测试.mjs`（`test:interaction-hub`，≥20 断言：状态机、优先级、幂等、迁移、双发去重、超时假设、撤销、刷新恢复、多标签）；修改 `test:ava-question`、`test:session-resume`、`test:event-*`。
- 验收口径见计划 §20：A-07（超时回执）、A-20～A-27（中枢模型、优先级、幂等、刷新/切会话、多标签、假设撤销、焦点、迁移）。
- 指标：ask 触发率 ≤15%、超时率 ≤3%、已回答耗时 p50 ≤15s。

## 9. 复审触发条件

- 出现任一次越权结算、跨会话答题或重复续跑。
- Dock 常驻导致输入区可用高度不足、窄屏不可用或焦点被反复抢占。
- 提案后 ask 触发率、超时率仍未达标，且调整超时参数无效。
