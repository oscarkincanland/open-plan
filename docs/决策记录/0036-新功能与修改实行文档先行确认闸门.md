# 0036 新功能与修改实行文档先行确认闸门

- 状态：已采纳
- 记录日期：2026-11-10
- 决策者：用户（直接指令）
- 基线：v0.13.25（develop，未打 tag）
- 关联：[AGENTS.md](../../AGENTS.md) §4.2/§4.3/§7、[文档管理规范](../规范/文档管理规范.md)、[0013 提交门禁](0013-提交门禁与未验证改动不提交.md)、[0020 分支创建需用户确认](0020-分支创建需用户确认且默认在develop开发.md)、[变更日志](../../变更日志.md)

## 1. 背景

项目已有较完备的事后防线：提交门禁（ADR 0013）约束**提交内容**，§7 工作流要求先读再改再测再记。但"动手写代码之前"这一环节缺少硬性闸门——智能体在接到新功能开发或修改请求后，可以基于自主判断直接进入代码修改，文档（需求 / 方案 / 设计说明）常常在实现完成甚至提交之后才补。这导致：

1. **方向性偏差在代码阶段才暴露**：边界、验收口径、不做清单未经用户确认就已固化进实现，返工成本高。
2. **文档沦为事后记录**：与 §3"代码是实现，不是事实来源"的定位冲突，文档长期落后于实现。
3. **用户对"改什么"的控制滞后**：类似 ADR 0020 对分支创建的处理——把决定权还给用户——代码修改这一更高频的动作反而没有对等控制点。

## 2. 问题

如何在不瘫痪日常协作的前提下，把"是否开始改代码"的决定权前移到文档确认环节，杜绝智能体自主判断后直接修改代码文件？

## 3. 备选方案

### 方案 A：维持现状（文档随实现后补，靠提交门禁兜底）

- 优点：零沟通成本，迭代最快。
- 代价：方向性偏差在代码阶段才暴露；文档事后化；用户失控点太靠后。

### 方案 B：文档先行 + 用户确认闸门（选择）

- 做法：任何新功能的开发或修改（含调整）必须先产出文档，文档经用户确认后才开始修改任何代码文件；未确认前禁止修改代码。纯文档改动、只读检查与测试运行不受限制。
- 优点：把偏差拦截在零代码成本阶段；文档天然先于实现存在，与 §3 定位一致；用户获得与分支创建同等级的控制权。
- 代价：每个新功能/修改多一轮"出文档 → 等确认"往返；小改动也被闸门覆盖，节奏变重。

### 方案 C：仅新功能适用，缺陷修复与小调整豁免

- 优点：节奏轻，闸门只挡高风险动作。
- 代价："新功能"与"调整"的边界模糊，豁免条款会被扩大解读成绕行通道；与用户指令"任何新功能的开发或者修改"不符。本次不采纳。

## 4. 决策

选择方案 B：**任何新功能的开发或修改（含调整），文档先行；文档经用户确认后才能修改任何代码文件。未获确认前，禁止基于自主判断修改任何代码文件。**

落点为三处：

1. `AGENTS.md` §7：工作流新增第 0 步"文档先行（硬性闸门）"，位于"读 / 计划 / 改"之前。
2. `AGENTS.md` §4.2：新增禁止项——方案文档未经用户确认前直接修改任何代码文件。
3. `AGENTS.md` §4.3：新增确认项——进入代码修改前方案文档须经用户确认。

补充约束：

- 文档定位遵循 §2、§3 与[文档管理规范](../规范/文档管理规范.md)（需求进 PRD / 设计进 DESIGN / 方案进计划或规范）。
- 文档可在确认前多轮修订；代码改动只能落在**已确认的意图范围**内，确需超出时回到文档更新并重新确认。
- 纯文档改动、只读检查与测试运行不受此闸门限制。

## 5. 理由

- **与既有治理链互补而非重复**：ADR 0013 管提交内容、ADR 0020 管分支创建、本闸门管代码修改的起点，三者构成"起点 — 落盘 — 提交"全链路的用户控制点。
- **与 §3 定位自洽**：文档先行使"代码是实现，不是事实来源"在时间维度上成立，而不是靠事后同步去追。
- **代价可接受且可回滚**：本决策不改代码、不改运行时、不改 API 契约，只改治理条款；若实践证明过重，回退只需撤回 `AGENTS.md` 三处措辞与本 ADR 的引用。

## 6. 影响

### 正面

- 方向性偏差在文档阶段被拦截，返工成本显著下降。
- PRD / DESIGN / 计划天然先于实现更新，文档不再长期落后。
- 用户对"改什么、改到哪"的控制前移到最低成本环节。

### 负面 / 代价

- 每个新功能或修改多一轮确认往返，小改动节奏变重。
- 智能体需要更严格地区分"文档轮"与"代码轮"，避免在文档未确认时顺手改代码。

### 迁移与回滚

- 迁移：本 ADR 生效即切换，无存量数据迁移。
- 回滚：撤回 `AGENTS.md` §4.2/§4.3/§7 三处措辞，并在本记录头部标注废弃即可，不影响代码与测试。

## 7. 验证

- 需要新增/更新的测试：无代码行为变化，不新增测试。
- 验收口径：智能体在收到新功能开发或修改请求后，第一步产出的是文档而非代码改动；文档未经确认前 `git diff` 中不出现代码文件变更。
- 观察指标：确认往返次数、返工（推倒重做）次数是否下降。

## 8. 复审触发条件

- 出现高频小改动被闸门严重拖慢、用户主动要求豁免某类改动时，复审是否引入分级闸门（需新的 ADR）。
- 与后续自动化审批机制（如结构化 Interaction 审批流）集成时，复审确认动作的承载形态。
