# 0004 优化开关统一且默认关闭

- 状态：已采纳（追溯确认）
- 记录日期：2026-10-25
- 决策者：项目负责人 / 架构评审
- 基线：v0.11.55
- 关联：[架构规范](../规范/架构规范.md)、`server/运行开关.mjs`

## 1. 背景

项目在快速迭代中引入了大量优化项（Qoder 对标、地图、浏览器、事件规范化等）。如果每个模块自行读取环境变量、或把新路径默认打开，会出现：开关语义分叉、默认行为漂移、出问题无法快速回退。

`server/运行开关.mjs` 已统一解析环境变量、提供只读快照，并经 `/api/status` 下发前端；约定“默认关 = 与历史基线行为一致”。

## 2. 问题

如何让优化项可预览、可对比、可回滚，同时保证默认路径稳定？

## 3. 备选方案

### 方案 A：各模块自行读取环境变量

- 做法：每个功能用 `process.env.XXX` 判断。
- 优点：实现快。
- 代价：命名/取值/默认值不一致；无法统一展示与审计。

### 方案 B：配置文件集中管理

- 做法：用 JSON/YAML 配置文件控制开关。
- 优点：可视化、可热更。
- 代价：引入配置加载/校验/热更复杂度；单机场景收益有限。

### 方案 C：中心化运行时开关 + 默认关

- 做法：所有优化项在 `运行开关.mjs` 注册，统一解析、只读快照、经 `/api/status` 下发；默认关，开启时走新路径，关闭时与基线逐字等价。
- 优点：语义一致、可回滚、可测试。
- 代价：开关增多需要清理；测试需覆盖开/关两条路径。

## 4. 决策

选择方案 C：**优化项统一走 `server/运行开关.mjs`，默认关闭，关闭时与基线行为等价。**

- 业务模块禁止自行解析 `OAW_*` 特性开关；路径/端口等启动参数除外。
- 开关必须支持“功能级 / 文件级 / 整站级”回滚，至少保证关闭即回退。
- 默认开启任何开关都需要 ADR 与用户确认。
- 开关稳定后应移除分支或登记为长期配置；不允许无限堆积。

## 5. 理由

- 单机产品最重要的是“默认路径可靠、出问题能一键回退”。
- 统一快照让前端、诊断、测试看到同一事实，避免“后端开了前端不知道”。
- 默认关使新路径可以灰度验证，不牺牲现有稳定性。

## 6. 影响

### 正面

- 优化项可独立预览与回退；默认行为稳定。
- 开关语义、命名、取值集中，便于测试与文档化。

### 负面 / 代价

- 双路径增加测试矩阵与代码分支。
- 开关长期存在会形成技术债，需要定期清理。

### 迁移与回滚

- 新优化项：先加开关（默认关）→ 双路径测试 → 灰度开启 → 稳定后移除开关或转为长期配置。
- 回滚：关闭开关即可；不得依赖回滚代码版本。

## 7. 验证

- 开关相关改动必须验证：关闭时基线与历史一致、开启时新行为生效、`/api/status` 快照正确。
- 涉及关键链路时跑对应 `test:*` 与 `npm run verify`。
- 不允许只测开启路径或只测关闭路径。

## 8. 复审触发条件

- 开关数量超过可维护范围，或出现长期常开的“僵尸开关”。
- 需要运行时热更新/多用户差异化配置。
- 开关关闭路径已无法与基线保持等价。
