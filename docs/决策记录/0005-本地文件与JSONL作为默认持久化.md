# 0005 本地文件与 JSONL 作为默认持久化

- 状态：已采纳（追溯确认）
- 记录日期：2026-10-25
- 决策者：项目负责人 / 架构评审
- 基线：v0.11.55
- 关联：[架构规范](../规范/架构规范.md) §7、`server/持久化工具.mjs`

## 1. 背景

项目定位为本地优先的单机工作台：用户文档在 `office-workspace/`，地图项目在 `office-workspace/maps/`，Run 与事件在 `.oaw/`，会话由 Pi 以 JSONL 管理。现有写入采用原子写（临时文件 + rename）与工作区写锁；事件流按体量归档，避免单文件无限增长。

## 2. 问题

是否需要引入数据库（SQLite/Postgres）来承载 Run、事件、产物与会话查询？

## 3. 备选方案

### 方案 A：本地文件 + JSONL

- 做法：工作区文件 + `.oaw/runs` JSON + `.oaw/events` JSONL + 会话 JSONL；原子写、锁、归档。
- 优点：零外部依赖、可直接查看/备份/迁移、与本地优先定位一致。
- 代价：复杂查询与并发能力有限；需要自己维护锁、归档、索引。

### 方案 B：SQLite

- 做法：嵌入式数据库承载 Run/事件/产物索引。
- 优点：查询与事务强；单文件部署。
- 代价：引入 schema/迁移/并发锁；现有 JSONL 回放与人工可读性需迁移。

### 方案 C：Postgres/服务端数据库

- 做法：独立数据库服务。
- 优点：多用户、强并发、成熟运维。
- 代价：与单机定位冲突，部署与备份复杂。

### 方案 D：事件溯源数据库

- 做法：专门的事件存储/流平台。
- 优点：回放与审计强。
- 代价：过重，超出当前规模。

## 4. 决策

选择方案 A：**默认使用本地文件 + JSONL，不引入数据库。**

- 关键状态写入必须使用 `server/持久化工具.mjs` 的原子写。
- 工作区写入必须经 `server/写入协调.mjs` 的锁；禁止并发绕过。
- 事件流必须归档并维护索引/游标；Run 快照必须有文件数与字节上限。
- 引入数据库必须先证明本地文件在查询/并发/可靠性上无法满足，并另写 ADR。

## 5. 理由

- 用户需要能直接打开、备份、迁移自己的工作区与运行记录；数据库会降低可解释性。
- 当前是单机单用户场景，本地文件的并发压力可控。
- 原子写 + 锁 + 归档已经能覆盖现有故障模式；引入数据库的收益不足以抵消迁移成本。

## 6. 影响

### 正面

- 零外部依赖、离线可用、备份简单、审计可读。
- 与“产物写工作区、运行记录可回放”的产品语义一致。

### 负面 / 代价

- 不支持多用户并发与复杂聚合查询。
- 需要自行维护锁、归档、损坏恢复与索引一致性。
- 大工作区快照有性能上限，必须显式标记 `truncated`。

### 迁移与回滚

- 当前无迁移。
- 若引入 SQLite，应先做双写/导出工具与回放校验，保留 JSONL 作为事实来源或可回退副本。

## 7. 验证

- 写入相关改动跑 `test:write-lock`、`test:workspace-isolation`、`test:run-budget`、`test:event-archive`、`test:event-replay`。
- 原子写/损坏恢复改动必须有故障注入或等价测试。
- 事件归档后必须验证游标与回放仍正确。

## 8. 复审触发条件

- 需要多用户/远程并发访问。
- 事件或 Run 数据量导致启动/回放明显变慢。
- 本地文件损坏/丢失成为高频故障，且原子写 + 归档无法解决。
- 业务需要跨 Run 的复杂查询与统计。
