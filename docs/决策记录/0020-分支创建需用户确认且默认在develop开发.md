# 0020 分支创建需用户确认且默认在 develop 开发

- 状态：已采纳
- 记录日期：2026-11-02
- 决策者：项目负责人
- 基线：v0.13.3（main @ be113d38）
- 关联：[AGENTS.md](../../AGENTS.md) §4.1/§4.3/§7/§7.1、[版本管理计划](../../版本管理计划.md) §二、[0013 提交门禁](0013-提交门禁与未验证改动不提交.md)、[变更日志](../../变更日志.md)

## 1. 背景

仓库历史里长期并存三类分支：`feature/*`（功能）、`fix/*`（修复）、`wip/*`（未验证进度暂存），另有两类"backup/*"归档分支与多台 worktree 长期挂载的工作分支。截至 2026-11-02，本地可见分支 12 个，其中至少 5 个处于"已合并但未删除"或"长期不再推进"状态：

| 分支 | 状态 | 问题 |
|---|---|---|
| `feature/2026-11-02-002-分支收敛与冲突消解` | 已合并进 develop，指向同一 commit | 合并后未删，重复来源 |
| `fix/session-file-flow` | 领先 develop 9 个提交 | 与 `feature/workspace-canvas` 等多分支长期分叉 |
| `fix/session-load-and-pref` | 已合并 | 同上 |
| `backup/develop-before-v0.11.11` / `...v0.13.11` | 归档 | 快照分支长期占用分支列表 |
| `feature/office-writing-capability` | 独立 worktree，`@477be500` 未合并 | 长期挂着，易被遗忘 |

同时，`AGENTS.md` §4.1 把"创建 `feature/*` / `fix/*` 分支"列为智能体**可以自主执行**的动作，§7 的固定流程第 1 步就是"从 develop 拉新分支"——等于制度化地要求每轮改动开分支。这带来三个具体成本：

1. **分支噪声掩盖真实状态**：一个功能一个分支，合并后忘删，分支列表无法反映"当前在做什么"。
2. **合并成本被低估**：`fix/session-file-flow` 与 `fix/session-load-and-pref` 各自领先 develop 9 个提交且相互分叉，2026-11-02 的收敛工作（27 个冲突块、6 项语义冲突裁决）正是多分支分叉的偿还账单。
3. **决策权外溢**：分支策略本属工程治理范畴，但按现行规则智能体可自行决定何时开线，用户失去对"主线是否干净"的控制。

## 2. 问题

在保证交付质量与可回滚的前提下，如何既降低分支噪声，又不让"禁止分支"退化成"所有改动堆在一个 commit 里"？

## 3. 备选方案

### 方案 A：维持现状（每轮改动开分支）

- 优点：每项改动物理隔离，回滚粒度最细。
- 代价：分支长期累积；合并冲突与语义裁决成本随分支数增长（2026-11-02 收敛已付一次账单）；智能体自主决定开线，用户失控。

### 方案 B：一律禁止分支，所有改动直接进 develop

- 优点：分支列表永远干净；主线历史线性。
- 代价：单个 commit 承载过多意图，直接违反 ADR 0013 §7.1「范围单一」；一个失败的实验改动会污染主线，需要 `git reset` 才能清理（而 §4.2 禁止 `git reset --hard`）；无法并行两个互相阻塞的任务。

### 方案 C：默认在 develop 开发 + 分支创建需用户明确确认（选择）

- 做法：日常改动、缺陷修复、文档同步一律在 `develop` 落地；任何分支（含 `wip/*`）的创建必须先说明理由并取得用户明确确认；分支只作临时隔离手段，合并即删。
- 优点：分支数量与真实并行度对齐，不再由流程强制产生；用户保留"何时分叉"的决定权；保留 ADR 0013 的提交门禁（门禁约束的是**提交内容**，不依赖分支存在）。
- 代价：单个 develop 上可能出现"多个意图连续提交"，需要靠提交信息与 ADR 0013 的范围单一要求维持可读性；智能体在真正需要隔离时必须先停下来问一次。

### 方案 D：Git 钩子 / CI 强制拦截分支创建

- 优点：机械强制，不可绕过。
- 代价：钩子可被 `--no-verify` 绕过，不构成真约束；且"用户确认"这一状态无法被 CI 机械判定（CI 不知道用户是否口头批准过）。作为方案 C 的补充手段，不作为本次决策。

## 4. 决策

选择方案 C：**默认在 `develop` 上直接开发；创建任何分支必须先经用户明确确认。**

落点为三处：

1. `AGENTS.md` §7「分支与提交」：改写为默认在 `develop` 开发、分支创建需用户确认、分支合并即删、发布 tag 前须经用户确认。
2. `AGENTS.md` §4.1：把"创建分支"从**可自主执行**移出，改为"在用户明确确认后创建"。
3. `AGENTS.md` §4.3：把"创建长期分支或发布 tag"收紧为"创建**任何**分支或发布 tag"，消除"只有长期分支才需确认"的解读空间。
4. `版本管理计划.md` §二：分支表补齐 `wip/*` 行与"创建约束"列，流程第 1 步改为"在 `develop` 上直接修改"。

补充约束：

- 需要分支时，**先说明三件事再创建**：为什么需要分支、隔离什么、预计存活多久。
- 仅在四类情形建议分支：高风险大范围改动、跨多轮的长周期任务、需与主干隔离的实验性改动、并行任务互相阻塞。
- `wip/*` 不再是自动可用的逃生舱：保存未验证进度同样需用户确认（ADR 0013 的"留在工作区"仍是首选）。

## 5. 理由

- **不削弱既有质量门禁**。ADR 0013 的七条约束全部作用在**提交内容**上（功能明确、验证通过、范围单一、禁入内容零容忍等），与分支是否存在无关。取消"每轮开分支"不会降低提交质量，只改变改动落在哪个引用上。
- **与仓库实际形态吻合**。当前 `develop` 已是唯一活跃分支，74 个提交领先 `main` 且 `main` 是其祖先（可快进）；工作区还有一批未提交的在途改动。现状事实上已经是"develop 单线 + 少量临时分支"，规则只是把既成事实写清楚。
- **成本可回滚**。本决策不改代码、不改运行时、不改 API，只改治理条款。若实践证明 develop 上堆积过多，回退只需撤回这四处措辞。

## 6. 影响

### 正面

- 分支列表重新反映"当前在做什么"，不再有已合并未删的僵尸分支。
- 智能体在需要分叉时会先说明理由，用户对"主线是否干净"保持控制权。
- 合并冲突与语义裁决成本下降——2026-11-02 那种 27 冲突块的收敛不再由流程主动制造。

### 负面

- 真正需要隔离时多一次沟通往返（提出理由 → 等待确认）。
- develop 上连续提交多个意图时，历史可读性依赖提交信息质量与 ADR 0013 的范围单一自律。

### 不做

- 不新增 Git 钩子或 CI 门禁去机械拦截分支创建（方案 D）。
- 本决策**不涉及**冻结发布、`v0.14.x` 版本号启用、桌面端路线选型；这些是独立事项。
- 本决策**不裁决** `v0.13.14` 分叉线上的 `AGENTS.md` v3.0 / `docs/规范/GIT工作流规范.md` v1.1 治理模型——该线主张"`develop` 未启用、分支从 `main` 拉出且合并即删"，与本决策口径不同，已在 [版本管理计划 §二](../../版本管理计划.md) 标注为**待裁决**，合并前须由用户裁定以哪套为准。

## 7. 落地与回滚

- 落地：`AGENTS.md` v2.1 → v2.2（顶部基线日期更新为 2026-11-02）；`版本管理计划.md` §二 重写；本 ADR 与 `docs/决策记录/决策记录索引.md` 同步；`变更日志.md` 记一条 `docs`。
- 生效范围：仓库内全部人机协作。
- 回滚：撤回 `AGENTS.md` §4.1/§4.3/§7 与 `版本管理计划.md` §二的对应措辞即可，不影响代码、测试与运行时行为。
