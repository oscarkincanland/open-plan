# 0035 创作画布选中引用采用 kind=canvas 结构化引用

- 状态：已采纳（随 2026-11-09 用户确认“全量修改”落地）
- 记录日期：2026-11-09
- 决策者：用户
- 基线：v0.13.24
- 关联：[004 计划](../plans/2026-11-09-004-创作画布多画板与版本时间线修改计划.md)、`REQUIREMENTS.md` R17、`DESIGN.md` §8.4、[0029 输入区采用统一引用与命令面板](0029-输入区采用统一引用与命令面板.md)

## 1. 背景

0031 的“添加到对话”只把整画布 `@designs/<slug>/project/canvas.json` 插入输入框；Agent 拿不到“当前板/选中元素”，只能读整包后猜。用户要求“选中画布中的某一页，然后加入对话，让 Agent 来修改”。

## 2. 问题

如何把画布的板/元素选区作为可解析、可回链的引用送进对话，并让 Agent 只改引用范围？

不解决的后果：用户说“把标题改大”时 Agent 可能改错板；整画布 JSON 进入上下文，token 成本高且定位弱。

## 3. 备选方案

### 方案 A：继续插入整画布文件引用

- 做法：`@designs/<slug>/project/canvas.json`。
- 优点：零新契约。
- 代价：无法表达板/元素范围；Agent 需要自己扫描；用户无法确认改了哪块。

### 方案 B：新增 `kind=canvas`，复用 references 管线（本决策）

- 做法：标记 `@画布[designs/<slug>/project/<boardPath>#element=<id>]`；客户端/服务端解析器 parity；服务端 `resolveReference/readReference` 生成 ≤4000 字符的结构化上下文（画布/板/页/选中元素 JSON + 修改约束）；消息 references 持久化，chip 可读（点击定位列为后续增强）。
- 优点：不新造消息通道；与 `@文件` 同一套 chip/三态/lint；服务端可校验路径与元素是否存在。
- 代价：引用类型从 9 种增到 10 种，需要同步客户端/服务端 parity 测试与 `REFERENCE_KINDS`。

### 方案 C：独立“画布选区”附件通道

- 做法：消息 payload 增加 `canvasRefs` 字段。
- 优点：结构最干净。
- 代价：绕过现有 references 的 chip/持久化/回链；需要改发送 API 与历史消息格式。

## 4. 决策

选择**方案 B**：新增 `kind=canvas`，复用 `references` 管线；V1 支持当前板与选中元素，整画布引用保留兼容。

## 5. 理由

- 现有 `references` 已具备解析、去重、chip 三态、消息持久化与 `context_read`，扩展成本最低。
- 服务端可把引用解析为明确的范围上下文，Agent 只改目标板/元素，符合用户预期。
- 与 ADR-0029 的“统一引用”方向一致，不引入第二套引用体系。

## 6. 影响

- 正面：选中即可对话；Agent 定位准确；chip 可读（板名/元素 id）。
- 代价：`REFERENCE_KINDS` 与解析器需要双端同步；画布引用解析失败要给出明确 missing，不静默降级为文件。
- 迁移：旧 `@designs/.../canvas.json` 文件引用仍按 file 解析；新引用只在双端升级后出现。
- 回滚：关闭开关即无画布入口；旧消息不受影响。

## 7. 验证

- `test:ref-parser`：`@画布[...]` 客户端/服务端 parity、`#element` range、chip 标签。
- `test:canvas-model`：画布/板路径校验。
- 人工验收：选中板 3 改标题只改板 3；选中元素只改该元素。

## 8. 复审触发条件

- 需要多选元素/区域选区；
- 需要评论线程锚定到画布对象（届时复用同一 range 模型）。
