# 0033 创作画布事件扩展为板级增量刷新

- 状态：已采纳（随 2026-11-09 用户确认“全量修改”落地）
- 记录日期：2026-11-09
- 决策者：用户
- 基线：v0.13.24
- 关联：[004 计划](../plans/2026-11-09-004-创作画布多画板与版本时间线修改计划.md)、`REQUIREMENTS.md` R17、`DESIGN.md` §8.4、[0031](0031-创作画布采用可编辑画布文档与多画布标签.md)

## 1. 背景

0031 落地后，`canvas_changed` 只在 Agent 工具路径发射；前端收到事件后丢弃 payload，把全局 `canvasRevision` 加一，所有 `design` 标签一起整画布重读。HTTP 保存（UI 直接编辑）完全不发事件，其他标签页看不到。

## 2. 问题

如何让 Agent 与 UI 的每次写板都能同步到所有打开的标签页，并且只刷新受影响的画板，而不是整画布重读？

不解决的后果：多画布同时打开时改一张闪一片；用户编辑无法跨标签同步；大画布每次全量重读，丢失当前板/选中/撤销栈。

## 3. 备选方案

### 方案 A：保持全局 revision

- 做法：任何写路径都递增一个全局令牌。
- 优点：实现最省。
- 代价：无法按画布/板定位，误刷新与状态丢失不可控；不满足“板级增量”。

### 方案 B：扩展既有 `canvas_changed`（本决策）

- 做法：事件增加 `scope`（canvas/board/list）、`boardPath`、`pageId`、`changedPaths[]`、`actor`、`runId`；Agent 与 HTTP 写路径统一发射；HTTP 走 `appendEvent` + `/api/agent/events` 全局流；App 按 `slug` 累积 changedPaths，画布组件只增量拉变化的板。
- 优点：不新增事件名；复用现有 seq/cursor 与跨标签页 leader 机制；兼容旧消费方。
- 代价：payload 语义要约定 `scope=board` 时 `revision` 为板 rev、`scope=canvas` 时为画布 rev；消费方必须按 scope 解释。

### 方案 C：新增 `canvas_board_patched` 等细分事件

- 做法：每种写操作一个事件类型。
- 优点：语义最直白。
- 代价：事件注册表膨胀；审批/回放/测试面扩大；与“开发收敛规范”的事件收敛方向冲突。

## 4. 决策

选择**方案 B**：保留 `canvas_changed` 一个事件，扩展可选字段；HTTP 写路由统一 `appendEvent` 到全局流；前端只按 `slug + changedPaths` 增量刷新，事件合并窗口 100–300ms。

## 5. 理由

- 一个事件名覆盖所有画布写入，注册表只增字段不增类型。
- 全局流已有 seq/cursor、跨标签页 leader/BroadcastChannel，天然适合“用户编辑也要广播”。
- 画布组件可保留当前板、选中与撤销栈；脏状态只提示，不覆盖。

## 6. 影响

- 正面：多标签/多窗口同步；增量刷新；新画布自动开标签；导出完成可通知产物面板。
- 代价：事件 payload 变大；HTTP 路由需要统一的 `canvasEvent` 发射点；消费方必须尊重 `scope` 语义。
- 迁移：旧事件字段全部保留，新增字段可选；旧前端忽略新字段不受影响。
- 回滚：关闭 `OAW_CREATIVE_CANVAS` 即无入口/工具/API；事件字段保留无副作用。

## 7. 验证

- `test:canvas-model`：写路径版本/事件前置条件。
- `test:canvas-ui`：App 全局流消费、changedPaths 合并、脏状态不覆盖。
- `test:event-payload`：`canvas_changed` 新字段类型校验。
- `test:event-emission`：HTTP 与 Agent 路径都有发射点。

## 8. 复审触发条件

- 事件量导致全局流压力显著上升（需要独立画布频道或按工作区过滤）；
- 需要对象级流式 patch（当前只做板级增量）。
