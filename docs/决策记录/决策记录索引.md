## 1. 什么是决策记录（ADR）

决策记录只回答一件事：**在若干可选方案中，我们为什么选了这一个，代价是什么。**

它不是计划、不是教程、不是变更日志。计划描述“这次怎么做”，ADR 描述“以后为什么这样做”。已采纳的 ADR 是对后续开发的约束。

## 2. 何时必须写

出现以下任一情况，必须先有 ADR（或与实现同一提交）：

- 更换/新增智能体内核，或修改 Pi SDK。
- 拆分/合并服务，引入数据库、消息队列、微服务、桌面壳。
- 破坏性修改 API/SSE 协议、事件语义、Run 终态、审批模型。
- 新增默认开启的运行时开关，或改变默认工具白名单。
- 改变工作区根、产物发布/回滚模型、长期记忆准入规则。
- 新增跨层依赖、引入新框架/构建工具/全局状态库。
- 推翻既有规范或既有 ADR。

普通功能、样式、文案、缺陷修复不需要 ADR；写进计划、变更日志与测试即可。

## 3. 命名与状态

- 文件名：`NNNN-<中文标题>.md`，编号四位、递增，不复用。
- 标题用决策句，不用疑问句，如 `0003-事件注册表作为事件流唯一事实来源.md`。
- 状态：`提议` → `已采纳` → `已废弃` / `被 NNNN 替代`。
- 已采纳的 ADR 不修改“决策”结论；变更时新建 ADR，并在旧记录头部标注替代关系。
- 追溯确认的既有决策，状态写“已采纳”，并在正文注明“追溯确认，记录日期晚于实施日期”。

## 4. 流程

1. **提案**：复制 [模板](模板.md)，写背景、问题、备选方案、影响。
2. **分析**：至少两个备选方案；写清成本、风险、回滚方式。
3. **评审**：涉及架构/契约的，由用户或负责人确认；必要时先做小原型验证。
4. **落库**：ADR 与实现同一提交或更早提交；更新本索引。
5. **执行**：代码、规范、测试、变更日志同步引用该 ADR。
6. **复审**：触发条件出现时（规模、依赖、故障率变化）新建 ADR 复审，不静默失效。

## 6. 与其他文档的关系

```text
AGENTS.md（宪法）
  ├─ REQUIREMENTS.md（PRD）
  ├─ DESIGN.md（设计与体验）
  ├─ docs/规范/（长期约束）
  ├─ docs/决策记录/（为什么这样约束）
  ├─ docs/plans/（这次怎么改）
  └─ 变更日志.md（实际改了什么）
```

- 规范可以直接引用 ADR，但不得复制 ADR 的论证过程。
- 计划若违反已采纳 ADR，必须在计划开头写明冲突与新的 ADR 编号。
- 变更日志只记录结果，不替代 ADR。
