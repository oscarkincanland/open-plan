# 0012 Office 写作闸门按路由自动启用

- 状态：已采纳
- 记录日期：2026-10-31
- 决策者：项目负责人 / 架构评审
- 基线：v0.11.56
- 关联：[0004 优化开关统一且默认关闭](0004-优化开关统一且默认关闭.md)、[执行闸门](../规范/Office排版规范.md)、`server/运行开关.mjs`、`server/office规范/执行闸门.mjs`
- 前序计划：`docs/plans/2026-10-31-003-Office写作预设流程与防线启动计划.md`

## 1. 背景

Office 写作能力（模板路由 / 场景参数 / 版式令牌 / 9 项规则闸门 / 澄清闸门 / 执行闸门）在 2026-10-27～28 已随 `00b5c2a0` 合并进 `main`，代码完整可用。但其启用条件是全局环境变量 `OAW_OFFICE_FORMAT`，按 0004 号决策的"默认关"原则出厂即关。

实测 run_05198175（2026-10-31，"写一个100页左右的规划文本"）证实：防线断电时，模型完全不知道存在编辑流水线与澄清闸门，改用 `officecli` 裸命令 + 手写 `styles.xml` XPath 试探，88 次工具调用中 20 次失败（23%），55 个模型回合，0 产物登记，模板要求的 12 张图一张未插。

问题本质不是"能力缺失"，而是"能力在位但不可达"：同一套代码，开关关时模型以极低成功率绕路。

## 2. 问题

如何在不推翻 0004 号决策（默认关 = 基线等价）的前提下，让写作场景能真正用上既有防线？

## 3. 备选方案

### 方案 A：保持默认关，由用户手动设 `OAW_OFFICE_FORMAT=1`

- 优点：完全不动 0004 语义，默认路径零风险。
- 代价：普通用户在应用内无法感知该开关（`/api/status` 之外无入口），实测中被系统性绕过；防线形同虚设。

### 方案 B：全局默认打开 `OAW_OFFICE_FORMAT`

- 优点：实现最简单。
- 代价：直接违反 0004「默认开启任何开关都需要 ADR 与用户确认」，且把闸门施加到非写作路由（编辑既有文档、Chat、Review），越界。

### 方案 C：按路由自动启用（路由即开 + env 可退出）

- 做法：闸门启用条件不再是全局开关，而是「任务路由 ∈ {template, generate} 且 mode=agent」；`OAW_OFFICE_FORMAT=off` 显式退出。判定收敛到 `运行开关.mjs` 的单一函数 `officeGateActiveFor(route, mode)`。
- 优点：只在"真的要写文档"的场景通电，非写作路由零影响；退出路径清晰（一行 env）；符合 0004 "关闭即回退"的实质要求。
- 代价：默认行为在写作路由上与 0004 时代不一致，需要 ADR 明确收窄。

## 4. 决策

选择方案 C：**Office 写作闸门按路由自动启用，`OAW_OFFICE_FORMAT=off` 可显式退出。**

- 判定唯一事实来源：`server/运行开关.mjs` 的 `officeGateActiveFor(route, mode)`；`server/agent.mjs` 与 `server/task.mjs` 不得各自再写一份条件。
- 启用范围严格限定：`route ∈ {template, generate}` 且 `mode = agent`。Chat / Review / 编辑既有文档（route=edit）行为与基线逐字一致。
- 本决策只收窄 0004 的适用范围（从"全局默认关"到"写作路由默认开、其余默认关"），不推翻 0004 的开关集中管理、可回退、需 ADR 三条原则。
- 退出路径：`OAW_OFFICE_FORMAT=off` 立即还原旧行为，无需改代码、无需回滚版本。

## 5. 理由

- 0004 的立意是"默认路径可靠、出问题能一键回退"，而非"任何新路径一律不得默认"。写作路由上旧路径已被实测证明是失败率 23% 的野路子，让它继续当默认值不构成"可靠"。
- 收窄到路由维度后，闸门只影响用户明确要求写文档的场景，属于产品承诺范围内的行为，不是"实验性优化"。
- 决策记录 0004 第 4 节已写明"默认开启任何开关都需要 ADR 与用户确认"，本文件即为该确认。

## 6. 影响

### 正面

- 写作路由自动获得澄清首问、10 回合流水线提醒、执行闸门（拦截绕过管线的 bash 生成脚本与 CLI 变更操作）。
- 旧路径保留一键退出，运维风险可控。

### 负面 / 代价

- 写作路由的默认行为与 2026-10-27 之前的版本不一致，需要回归覆盖。
- 闸门误拦风险由 `server/office规范/执行闸门.mjs` 的 `--allow-manual` 逃逸阀与只读放行规则兜底。

### 迁移与回滚

- 迁移：本次改动含双路径实现与测试，`OAW_OFFICE_FORMAT=off` 下必须与基线逐字等价。
- 回滚：设 `OAW_OFFICE_FORMAT=off`；或单独 revert 引入 `officeGateActiveFor` 的提交。

## 7. 验证

- 必须同时覆盖开启路径与退出路径：未设 env 时写作路由闸门生效；`OAW_OFFICE_FORMAT=off` 时闸门全放行（不允许只测一条）。
- 非写作路由（route=edit/read、mode=chat/review）闸门不生效。
- 关键链路跑 `test:office-gate-auto`、`test:capability-contract` 与 `npm run verify`。

## 8. 复审触发条件

- 闸门在写作路由上出现高频误拦（用户需要反复 `--allow-manual`）。
- 写作路由的默认行为引发其他模块的兼容问题。
- 编辑既有文档（route=edit）也需要纳入闸门时，须重新评估范围。
