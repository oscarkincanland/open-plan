# 0038 地图创建即绑定交付与 map_export 工具

- 状态：已采纳
- 记录日期：2026-11-11
- 决策者：用户（[计划 2026-11-11-004](../plans/2026-11-11-004-Agent地图OD工作流与画布导航联动修改计划.md) §8 逐项确认 + `/goal 开启全量落地`）
- 基线：v0.13.25（`develop @ f433b852`）
- 关联：`REQUIREMENTS.md` R10、`DESIGN.md` §9.3、`server/agent.mjs`、`server/地图导出执行器.mjs`、`server/批量导出.mjs`、`client/src/地图/预览策略.js`

## 1. 背景

Agent 已能新建地图项目（`map_project_create`）与生成草稿层（`map_draft_layer`），地图预览标签已能只读回放草稿；但创建后不绑定会话、无截图工具，"对话一句话 → OD demo → 交付预览 → 截图归档 → 继续编辑"链路断在两处。服务端 G7 批量导出已有完整截图管线（内置浏览器渲染 → PNG/printToPDF），但执行器内联在 `server/index.mjs` 未导出，agent 无法复用。

## 2. 问题

Agent 生成的地图 demo 无法自动交付到会话的地图预览，也无法自主产出截图产物；不解决则 Work 对话的地图工作流需要用户手动切项目、手动导出，闭环断裂。

## 3. 备选方案

### 方案 A：agent 发事件、前端完成会话绑定 + 抽取执行器供工具复用（采纳）

- 做法：`map_project_create` 成功后 emit `map_action{action:"project_created"}`（复用既有无 schema、persist:false 事件）；前端 `onMapAction` 匹配当前会话后 POST 既有 `/api/sessions/:id/map-context` 绑定并走 `resolveMapPreviewAction` 被动打开预览。G7 执行器原样抽取为 `server/地图导出执行器.mjs`，agent 新工具 `map_export` 与 G7 路由共用。
- 优点：与"前端拥有会话状态"现状一致；事件与端点全部复用，契约面最小；G7 行为零变更。
- 代价/风险：绑定依赖前端在线（后台无人值守 Run 不落地绑定）；多会话并行需 sessionId 匹配防误绑。

### 方案 B：服务端在 agent 工具内直接写会话 header

- 做法：agent.mjs 直接改会话存储并广播会话更新事件。
- 优点：无人值守 Run 也能绑定。
- 代价/风险：`server/agent.mjs` 现无会话头写权限，需要新增跨层依赖与会话更新事件；前端会话状态需双源同步，违反单一事实来源；改动面大。

### 方案 C：不自动绑定，提示用户手动切换（现状）

- 做法：保持现状，仅加 `map_export`。
- 优点：零契约风险。
- 代价/风险：工作流闭环仍断裂，用户每次都要手动切项目开预览。

## 4. 决策

选择**方案 A**，边界：

- `map_action{project_created}` 只在 `map_project_create` 审批通过并创建成功后发出；前端仅当事件 sessionId 匹配当前会话时绑定。
- `map_export` 仅 Work 模式可用、审批 ask；沿用 `OAW_MAP_EXPORT` 运行开关（默认不变），关闭时工具返回明确错误；产物落 `maps/{project}/agent/exports/` 并写 `appendAgentManifest`，不改变 G7 产物位置（`地图导出/{批次}/`）。
- agent 导出与用户导出共用单飞闸门（同一浏览器会话串行），冲突返回明确提示。

## 5. 理由

- 关键权衡 1：会话状态单一事实来源（服务端 API + 前端刷新）优先于"无人值守也能绑定"——本地优先工作台的主场景是用户在线交互；无人值守绑定可作为后续增量（服务端直写 + 会话更新事件）再立 ADR。
- 关键权衡 2：抽取执行器而非复制代码——G7 与 agent 工具必须共用同一条截图管线与单飞闸门，否则浏览器会话互相竞争。
- 与项目约束的关系：本地优先（产物落工作区）、可回滚（开关默认值不变、G7 行为零变更）、可测试（执行器纯逻辑可测）、单一事实来源（事件/端点全部复用，无新契约）。

## 6. 影响

### 正面

- Work 对话地图工作流端到端闭环：创建 → 绑定 → 预览交付 → 截图归档 → 继续编辑。
- G7 与 agent 共享一条截图管线，后续地图导出类能力只有一条实现。

### 负面 / 代价

- 前端新增一个 map_action 分支（约 30 行）与一次 fetch 绑定。
- `map_export` 增加一条审批 ask，auto 模式下按现有审批策略处理。

### 迁移与回滚

- 迁移步骤：无数据迁移；会话 header 结构不变（仍 mapProject/mapView）。
- 回滚方式：移除工具白名单条目与前端分支即回到基线；执行器抽取可独立回退（index.mjs 恢复内联）。
- 数据/契约兼容性：`map_action` 无 schema，新增 action 取值不破坏既有消费方；`/api/map/export/batch` 契约不变。

## 7. 验证

- 需要新增/更新的测试：`test:capability-contract`（map_export 白名单↔能力计划↔元数据一致）、`test:map-export-executor`（执行器 URL 拼接/单飞闸门/越界拒绝/非法任务报错；既有 `test:map-export` 继续作为 G7 批量导出回归）、`npm run verify`。
- 验收口径：`REQUIREMENTS.md` R10 验收"创建即绑定交付（2026-11-11-004）"与"地图截图导出（2026-11-11-004）"两条。
- 观察指标：审批通过到预览标签打开无报错；导出冲突提示出现率；G7 导出回归通过。

## 8. 复审触发条件

- 出现无人值守批量 Run（服务端无头环境）需要绑定时，重新评估方案 B。
- 地图导出需求超出"单项目单尺寸单格式"（如多视图书签式导出）时，重新评估 `planExportJobs` 复用边界。
