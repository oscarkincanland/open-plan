# 0039 开发工作流按改动规模分级与方案对抗审查

- 状态：已采纳
- 记录日期：2026-11-18
- 决策者：用户（本轮对话直接指令：「改文案和调样式的小改动两三句话就能改完的就跑完一次关联快测；常规单功能开发，在最终计划里用直白的话把界面和操作怎么变、复用现在的什么组件、这次明确不做什么、需要哪些拍板讲清楚；跨多个模块的大改动，写成方案文档或者分文件树来推进；对于常规和跨模块的方案，在确认给我看之前先安排一个独立的子 agent 来挑一遍漏洞」，并要求在 `AGENTS.md` 明确「别重复造轮子」）
- 基线：v0.13.25（`develop @ 8fc02209`）
- 关联：`AGENTS.md` v2.8 §4.2/§7.0/§7.2/§7.3/§8/§11、[全仓缺陷复盘](../audits/2026-11-17-全仓缺陷复盘/00-复盘报告.md) §3.1/§5、`docs/规范/运行时验收与门禁规范.md`

## 1. 背景

复盘结论：会话流一个模块吃掉 31% 的 fix，根因之一是"形态未冻结就动代码"与"计划深度与实际规模不匹配"——小改动被文档流程拖住（于是绕过），大改动一张纸糊过去（于是返工）；同时「同一信息多通道渲染」「新增前不查既有实现」导致第二份事实源反复出现。

用户据此拍板：**按改动规模分级定计划深度**，并对"常规/跨模块"方案强制**独立子代理对抗审查**，同时在宪法层面明确**禁止重复造轮子**。

## 2. 决策

### 2.1 分级（AGENTS.md §7.2）

| 级别 | 判定 | 计划要求 | 验证 |
|---|---|---|---|
| **S1 微改动** | 改文案/调样式/死链；**单文件**；三句话能说清 | 写清「改哪里 / 改成什么 / 影响谁」，落变更日志或交付说明，**不单独写方案文档** | 关联快测 + `npm run verify` |
| **S2 常规单功能** | **≥3 文件，或 2 文件且新增交互状态** | 最终计划写清四件事：界面与操作怎么变、复用哪些组件（复用 X / 新增 Y / 不新增 Z）、明确不做什么、需要拍板的点 | 新增行为有测试 + 受影响 `test:*` + `verify` + `test:ui-smoke` |
| **S3 跨模块大改动** | 跨 2+ 模块，或改事件/API/白名单/存储 | 方案文档，或分文件树/分阶段推进：模块边界、契约、迁移回滚、阶段验收、风险与不做清单 | 分阶段验收 + `verify` + `ui-smoke` + 关键链路 CI 同款 |

### 2.2 三条防规避规则

1. 按**同一次用户请求 + 同一批提交**的并集定级，禁止拆小降级；
2. S1 一旦触碰契约/白名单/事件/数据/新增交互状态，立即升级并重新确认；
3. 用户当轮明示「直接做 / 不用出方案」视为已完成 §7.0 确认，S2/S3 的对抗审查可后置到交付前回填；**不得默认豁免**。

### 2.3 方案对抗审查（AGENTS.md §7.3）

S2/S3 方案在提交用户确认前，必须由**独立子代理**（与方案作者不共享上下文）对抗审查六项：重复造轮子、遗漏边界、冲突（PRD/DESIGN/规范/ADR）、不可行假设、测试缺口、范围与不做清单。

- 审查者须直读原文并给至少 1 条证据（`路径:行号`）；
- 结论原文回填方案文档「对抗审查」小节；实质修订须重审；
- 子代理不可用时须用户明示豁免并留痕，否则方案不得提交确认。

### 2.4 别重复造轮子（AGENTS.md §4.2 + §7 第 1 步）

- 新增前必须列出候选既有实现及「它为什么不满足」的差异；
- 工作流第 1 步改为「读 + 查复用」，检索留痕，计划写「复用 X，新增 Y，不新增 Z」；
- 新增可复用组件须先在 `DESIGN.md` 登记，避免第二份事实源。

## 3. 备选与取舍

- **方案 A（采纳）**：宪法内分级 + 独立子代理审查 + 复用登记。代价：S2/S3 多一轮审查往返；收益：把"返工成本"前移到"方案评审"。
- 方案 B：只写"尽量少造轮子、方案要清楚"的原则，不设分级与审查。代价：不可判定、不可执行（复盘已证明"写下结论 ≠ 建立机制"）。
- 方案 C：所有改动一律走完整文档 + 审查。代价：S1 被拖死，实际必然绕过，闸门失真。
