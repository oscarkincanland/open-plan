# 0028 写作采用一次成稿与预览即终稿

- 状态：已采纳
- 记录日期：2026-11-08
- 决策者：用户
- 基线：v0.13.24（`develop @ 7ef77f76`）
- 关联：计划 [2026-11-08-001-人机协作中枢与技能写作链路完整修改计划](../plans/2026-11-08-001-人机协作中枢与技能写作链路完整修改计划.md) §2.1/§12、`REQUIREMENTS.md` R13、`DESIGN.md` §6.1/§7、[写作规范](../规范/写作规范.md)、[0007](0007-编辑流水线blocks契约v2.md)、[0012](0012-Office写作闸门按路由自动启用.md)

## 1. 背景

审查（2026-11-07）显示写作类 Run（n=96）p50 3.1 分钟 / p90 15.5 分钟 / 最长 49.4 分钟；回合 p90 44 / max 440；officecli 调用 p90 32 / max 367（其中 266 次是逐属性 `set`）；ask 触发率 36%，阻塞占总时长 13%；首字 p50 8.07s / p95 56.2s。慢的主因是一工具一回合、回合无上限与上下文膨胀；机械感的主因是强制澄清、每 6 轮播报与固定六步 playbook，而不是文风模板。

## 2. 问题

写作流程把"大纲轮、草稿确认轮、多轮修订"当作默认路径，用户必须陪跑一串仪式才能拿到成稿；每多一轮确认就多一次往返与一组工具回合，质量却未因此提升。若不收敛成"一次成稿 + 预览即终稿"，写作时长、回合数与 ask 触发率无法达标。

## 3. 备选方案

### 方案 A：保留 Planner/Writer 多段模型调用与草稿确认（现状，放弃）

- 做法：先出大纲，用户确认；再写草稿，用户确认；再逐轮修订。
- 优点：中间态可控，长文用户可早期纠偏。
- 代价/放弃原因：多段模型调用与多轮确认叠加，回合与时长不可控；审查数据表明多数写作任务不需要大纲轮。

### 方案 B：只提高回合预算、关闭进度播报（放弃）

- 做法：保留六步 playbook 与草稿确认，仅放宽预算、减少旁白。
- 优点：改动小。
- 代价/放弃原因：治标不治本，强制确认与模板固定仍制造回合；首字与总时长改善有限。

### 方案 C：提示词要求"一次成稿"但保留六步 playbook（放弃）

- 做法：不改流水线，仅改提示词措辞。
- 优点：实现成本最低。
- 代价/放弃原因：playbook 与闸门仍引导多阶段；同一目标两套指令相互矛盾，模型行为不可预期。

### 方案 D：一次成稿 + 预览即终稿 + 一次验收（采纳）

- 做法：Markdown 正文即终稿，直通 docx/pptx；取消独立大纲/草稿确认轮；预览自动打开即视为确认入口；排版一次 batch、验收一次 validate；多阶段流水线仅作 fallback；配套文风宪法与交付自检。
- 优点：回合与时长显著下降；用户看到的就是终稿；与写作质量自检、语音样例（voice sample）配合提升"人味"。
- 代价/风险：超长/高复杂度文档质量风险；中间态不可见，需要预览与自检弥补；fallback 路径需维护。

## 4. 决策

选择**方案 D**：

1. 写作默认一次成稿：直接写 Markdown 正文作为终稿，不先出大纲；仅当用户显式要求或预计正文 >8000 字时，附可选大纲。
2. Markdown 直通排版：同一份 Markdown 进入 `editorial_pipeline` 的 `sourceMarkdown` 路径生成 docx/pptx；默认跳过 Planner/Writer，多阶段保留为长文/用户要求/开关回退。
3. 预览即终稿：自动打开预览即视为确认入口；用户修改后重排一次，不重走流程。写回原文件仍需确认（不可逆动作）。
4. 取消"草稿后必须 ask 确认"的强制；保留"写回原文件确认"。删除固定六步 playbook，改为"一次成稿 → 批处理排版 → 一次验收"。
5. 版式精修使用 officecli 一次 `batch`；`batch` 不覆盖的属性按每批 ≤5 条合并，禁止逐属性 `set`。验收为一次 `validate` + 规则闸门，失败自动修一次，不再多轮 revise。
6. 写作路由默认受回合预算约束（软 30 / 硬 60），命中后先收尾并如实记录；关闭每 6 轮进度播报（写作路由）。
7. 写作默认 `thinking=medium`（用户可改，受 `OAW_WRITING_THINKING` 开关控制）。
8. 文风宪法落到 `docs/规范/写作规范.md` 并注入提示词：禁用套话/意义拔高/重复结论/空序列/无主语承诺；每 500 字 ≥3 个可核验事实；结构随文体；voice sample 来自用户旧文；交付前自检。
9. 运行时开关 `writingOneShot`、`OAW_WRITING_BUDGET`、`OAW_WRITING_THINKING` 默认关（或维持基线行为）；默认值翻转由用户逐项确认。

## 5. 理由

- 审查数据表明写作慢在"回合"而非"思考"：减少仪式直接减少回合与首字等待。
- Markdown 即终稿让内容与排版解耦，排版变成确定性后处理，预览所见即交付物。
- 保留多阶段 fallback 与"写回确认"，把质量与不可逆风险留在可控一侧。
- 文风宪法与自检解决"一次成稿会不会更机械"的顾虑，用可测规则替代多轮确认。

## 6. 影响

### 正面

- 写作回合 p90 目标 ≤20（现 44）、Run p50 ≤2 分钟 / p90 ≤6 分钟（现 3.1 / 15.5 分钟）、首字 p50 ≤4s（现 8.07s）。
- 用户确认次数显著减少；预览即终稿，改稿只需重排一次。
- officecli 调用/文档 p90 目标 ≤40，减少逐属性写样式。

### 负面 / 代价

- 超长或高约束文档一次成稿质量可能下降，需要 fallback、自检与人工样例验收。
- 中间过程可见性降低，用户对"怎么写的"感知变弱；需要用假设回执与文风说明弥补。
- 保留双路径（一次成稿 vs 多阶段）增加测试矩阵与维护成本。

### 迁移与回滚

- 迁移：无数据迁移；旧会话按历史事件回放；写作设置新增默认值仅在开关打开时生效。
- 回滚：`OAW_WRITING_ONESHOT=0` 回到多阶段流水线；`OAW_WRITING_BUDGET=0` 回到基线预算行为；`OAW_WRITING_THINKING` 关闭恢复原思考档位。
- 兼容：`editorial_pipeline` blocks 契约 v2 不变；保留"写回原文件确认"。

## 7. 实施约束

- 不改 officecli 调用契约与编辑流水线 blocks v2；不新增数据库或队列。
- 只对写作路由生效，不影响 Chat/Review 与普通 Work 任务。
- 回合预算命中后必须如实写入 Run 轨迹，不得伪装完成。
- 写作产物的验收仍走规则闸门（9 项）与 `validate`；未通过不得报"已完成"。
- 不允许一次性删除多阶段流水线；`sourceMarkdown` 直通与多阶段 fallback 并存。

## 8. 验证与验收

- 新增 `scripts/写作一次成稿测试.mjs`（`test:writing-oneshot`）、`scripts/文风自检测试.mjs`（`test:writing-style`）；修改 `test:editorial-pipeline`、`test:office-generate`、`test:office-qa`、`test:office-contract`、`test:run-budget`。
- 验收口径见计划 §20：A-33～A-38（一次成稿、预览终稿、提问预算、batch 排版、文风自检、写作指标）。
- 验收方式：真实写作 10 例重放 + 3 例真实执行（用户参与）；文风人工盲评 ≥4/5。

## 9. 复审触发条件

- 10 例重放或用户真实反馈显示质量/返工率明显上升，盲评 <4/5。
- 回合硬预算频繁截断长文档，或写作时长指标未达标。
- 用户明确要求恢复独立大纲/草稿确认，或出现"写回原文件"未经确认的事件。
