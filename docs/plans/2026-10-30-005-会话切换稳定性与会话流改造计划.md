## 零、量化目标与总体策略

### 0.1 量化目标

“减少文件列表读取失败次数”不能靠隐藏横幅，必须同时降低服务端失败率和错误提示的敏感度。验收口径如下：

| 指标 | 现状基线 | 目标 | 测量方式 |
|---|---|---|---|
| `/api/files` 在文件抖动下的 500 率 | 60 次请求 27 次 500（45%） | **0 次 500** | `test:file-list-churn`：100 文件 + 100 目录持续删除/重建，2 秒 60 请求 |
| 文件列表失败横幅 | 任务执行中偶发 | **30 分钟真实任务 0 次**；持续故障最多提示 1 次，恢复后自动消失 | L4 跑一个多文件写作任务，统计横幅出现次数；客户端记录 `files` 分区失败事件 |
| 单个文件/目录消失 | 可能导致整表 500 | 跳过该条目，其余列表正常返回 | 抖动测试断言返回条数 >0 |
| 当前目录被删除 | 404 后横幅常驻 | 自动回工作区根目录并提示一次 | L4 删除当前子目录 |
| `file_changed` 刷新风暴 | 每个事件批可能各发一次请求 | 同一时刻最多 1 个在途 + 1 个排队；5 秒内 ≤3 次请求 | 客户端埋点/测试断言 |
| 会话历史首屏 | 最长等 resume 20s | 缓存会话 <100ms；无缓存 <1s，且不依赖 resume | L4 人为延迟 resume 20s |
| 会话切换失败横幅 | 偶发 | 3 标签页 × 每页切 10 次 = 0 次 | L4 + `test:stream-budget` |
| 控制面 p95 | 受连接池影响可达 8s | `GET /api/sessions`/`/api/files` p95 <1s | 3 标签页压测 |
| 每浏览器 SSE 总数 | 3 标签页可达 6 | ≤4（阶段 A：1 leader 全局 + 每标签页对话流） | `/api/diagnostics/streams` + L4 |
| 会话流结构 | 一轮多个“执行过程”折叠 | 一轮 1 个折叠行，行内含用时/步数；summary 可见 | 5-turn 样本 L4 |

### 0.2 总体策略：三层同时收口

1. **服务端容错**：`listWorkspace` 逐项 try/catch；`/api/files` 返回结构化错误码而不是 HTML 500；临时性错误短重试；目录消失可区分。
2. **客户端降噪**：`refreshFiles` 合并/排队、失败重试一次、**连续失败才显示横幅**、成功自动清除；404 自动回根目录；会话历史与 resume 解耦；运行列表只传摘要。
3. **结构性治理**：跨标签页连接租约（阶段 A）、轮询 leader 化、会话流 Run 级折叠。

原则：**先降低真实失败率，再降低提示敏感度**；不允许只改前端文案或吞掉错误。

### 0.3 已采纳的决策（按用户 2026-10-30 要求）

| 决策 | 采用方案 | 理由 |
|---|---|---|
| 跨标签页 SSE | 阶段 A：BroadcastChannel/localStorage 租约 + 全局事件流 leader；对话流按标签页保留；阶段 B（SharedWorker/多路复用）暂缓并走 ADR | 3 标签页可从 6 条降到 4 条；改动小、可回滚；避免一次性架构改造 |
| 总结与最终答复 | `completion.summary` 作为“本轮总结”主内容；final 只在有新增信息时作“补充答复”；中间小节结论随过程折叠、展开可见 | summary 是结构化完整结论（样本 809–1890 字），final 更短（156–734 字） |
| 2MB 截断 | 源码视图 2MB；Markdown/HTML 预览保留完整内容（10MB 安全上限），超限提供系统打开；JSON 只读源码 + 打开完整文件 | 预览是阅读主路径，截断在段落/标签中间不可接受；源码视图有性能边界 |

## 一、目标与边界

### 1.1 目标

1. **先恢复“提交可信”**：把本轮已验证但未提交的样式修复收口，并补上能拦住 CSS 语法错误的门禁。
2. **降低文件列表失败与提示次数**：任务执行中文件抖动不再产生 500；客户端只对“重试后仍失败”的持续错误提示，并在恢复后自动清除。
3. **让切会话稳定**：历史展示不再等待 Agent resume；任何一步失败都有明确、可重试、不误导的界面；运行列表只传摘要；跨标签页不会再因 SSE 占满 6 个同源连接而“整站卡死”。
4. **把会话流改成“一轮一块”**：完成后过程折叠为一行“运行了 X 小时 X 分”；随后是本轮工作总结；再接本轮产物。纯问答、失败、取消、部分完成都有稳定形态。
5. **把需要改的需求先写清楚**：PRD/DESIGN 的验收口径与实现对齐，不靠代码猜。

### 1.2 不做清单

- 不改 Pi SDK、不 fork 内核、不伪装内核能力；
- 不新增数据库、消息队列、微服务或桌面壳；
- 不默认开启任何运行时开关；新增开关默认关；
- 不改变 Chat/Work/Review 三种产品模式，不恢复 Office 独立模式；
- 不删除或重写历史决策记录、审计报告、已完成计划；
- 不在本轮修改代码（本文档只定义改什么、怎么验收）；
- 不把用户会话正文、日志、密钥写入文档或提交。

### 1.3 实施原则

- **先证据后改动**：每个工作包先有复现/测量，再改代码；改完用同一口径复测。
- **最小侵入**：优先复用 `RunSummary`、`运行轨迹.js`、`产物类型.js`、`文件类型图标.jsx`，不重写消息模型。
- **一次只解决一类问题**：P0 样式、会话加载、连接预算、会话流分别提交，便于回滚与验收。
- **文档同步**：每个用户可见行为变化同步 PRD/DESIGN/变更日志；跨标签页方案补 ADR。

## 四、W2（P0）：会话历史加载与 resume 解耦

### 4.1 问题

`App.handleSelectSession` 把 `getSession`、`listRuns`、`resumeAgentThread` 放进 `Promise.all` 一起等（`App.jsx:1164-1180`）；resume 超时 20s，`getSession` 没有超时；无缓存时旧会话消息不清空；恢复失败后输入区仍可发送。

### 4.2 改动

**加载顺序**

- [ ] 拆成两段：
  1. **历史段**：`getSession(view=chat, limit=50)` + `listRuns(fields="summary")`，用 `Promise.allSettled` 分别处理；历史先展示，运行摘要失败只降级运行卡，不阻塞消息。
  2. **恢复段**：`resumeAgentThread` 后台执行；成功后才把 `agentReady=true`，允许发送与连接 SSE。
- [ ] `currentSessionId` / `historyThreadId` 在历史段完成后即可设置；`threadId` 仍等 resume 成功再切换（避免 SSE 先创建新 runtime）。
- [ ] `ChatPanel` 增加 `agentReady` / `sessionReadOnly` 两个显式状态：
  - `agentReady=false`：输入禁用、发送禁用、SSE 不连接（或连接但不发消息），显示“正在恢复会话…”；
  - `sessionReadOnly=true`：显示只读原因与“重试恢复”，输入与发送禁用。
- [ ] 无缓存会话加载时：先清空旧会话消息并显示骨架/标题，不允许旧内容停留；缓存会话可以继续“先旧后新”，但要显示刷新中的轻提示。

**超时与错误**

- [ ] `getSession` 改走 `apiControl`（8s，可配置）或 `AbortSignal.timeout`；超时显示“历史读取超时，重试”，不清空已成功的历史。
- [ ] 切会话请求带 `AbortController`/请求序号；A→B 快速切换时取消 A 的历史请求，B 的结果不得被 A 覆盖（保留现有 `loadSeq` 语义）。
- [ ] resume 失败时不要设置 `threadId` 到未恢复的会话，不建立 SSE；只展示历史 + 只读横幅。

**缓存**

- [ ] `run_finished` 事件对对应 `sessionId` 失效 `sessionHistoryCacheRef`；若该会话是当前会话，由 SSE 增量更新；不是当前会话则下次切回时拉新。
- [ ] 缓存淘汰时同时清理 `sessionHistoryCursorRef` 与 `sessionHistoryMetaRef`，避免半套缓存。

### 4.3 验收

- 缓存会话：点击后 100ms 内出现历史；无缓存会话：历史首屏不受 resume 影响。
- 人为让 `/api/agent/resume` 延迟 20s：历史仍先显示；界面有“正在恢复”而不是空白/旧内容。
- resume 失败：只读横幅 + 输入禁用 + 重试可用；不会向未恢复的会话发送消息。
- 连续快速切换 A/B/C：最终只显示 C 的历史，A/B 的迟到响应不写入。
- 断网/接口 500：历史区显示错误与重试，不把旧会话内容留在新会话位置。

### 4.4 风险

- 设置 `threadId` 的时机变化会影响 ChatPanel 的 SSE、草稿/队列缓存 key、任务中心过滤；需要同时检查 `previousThreadRef`、`queueCache`、`draft` 的会话键。
- 若产品选择“历史也必须在 resume 后显示”，需要明确写出理由，否则不要回退到 `Promise.all`。

## 五、W3（P0/P1）：跨标签页连接预算与关闭顺序

### 5.1 问题

`长连接预算.js` 的 `MAX_STREAMS=3` 是**每页面**预算；浏览器同源 HTTP/1.1 只有 6 个连接。每个页面的对话流 + 全局事件流都是 essential（2 条），3 个标签页就是 6 条，控制面请求没有槽位。`closeEventSourceQuietly` 先 POST 再关本地连接，池满时只能等 2s 兜底。

### 5.2 方案（需要 ADR）

建议分两步，先低风险止血，再做结构性收敛：

**阶段 A：跨标签页租约（推荐先做）**

- [ ] 用 `BroadcastChannel` + `localStorage` 心跳选举“流 leader”；同一 origin 同一时刻只有一个标签页持有**全局事件流**，其余标签页通过 BroadcastChannel 接收事件。
- [ ] 对话流仍按标签页保留（它绑定当前 thread）；当总流数将超过预算（建议 ≤3）时，非 leader 标签页降级为轮询/按需拉取，并显示“实时连接由其他标签页持有”的轻提示。
- [ ] 统一租约释放：`beforeunload`/心跳超时/页面隐藏超时；避免标签页崩溃后永久占位。
- [ ] 服务端增加 per-client（不区分 tab）总流上限作为兜底；超过时返回 503 + `Retry-After`，不静默踢掉活跃流。

**阶段 B：单连接多路复用（ADR 后做）**

- [ ] 评估 SharedWorker 持有唯一 SSE，各标签页通过 MessagePort 订阅 thread/全局事件；
- [ ] 或服务端提供 `/api/stream/multiplex`，一个连接承载 events + 当前 thread 事件，前端按 `thread` 过滤；
- [ ] 目标：一个浏览器最多 1–2 条 SSE，无论开多少标签页。

**关闭顺序（无论选哪个方案都要修）**

- [ ] `closeEventSourceQuietly` 先 `es.close()` 释放本地 socket，再 `fetch("/api/agent/stream/close", { keepalive: true, signal: AbortSignal.timeout(1500) })` 做服务端收尾；或使用 `navigator.sendBeacon`。
- [ ] 关闭请求失败不得阻塞重连；重连按现有退避执行。

**轮询治理**

- [ ] 会话列表刷新从固定 15s 改为：SSE 事件驱动 + 可见/聚焦时刷新 + 指数退避 + 抖动；隐藏标签页停止轮询。
- [ ] 多标签页只让 leader 轮询一次，其余通过 BroadcastChannel 复用结果（与阶段 A 同一套租约）。

### 5.3 验收

- 3 个标签页同时打开、每页连续切会话 10 次：不出现“会话列表读取失败/本地服务 8 秒未响应”；浏览器同源 SSE 总数 ≤4（阶段 A）或 ≤2（阶段 B）。
- 断网/恢复、页面隐藏/显示、关闭一个标签页后，剩余标签页仍能收到事件并正常切会话。

- 控制面 `/api/sessions` p95 < 1s（本机、3 标签页场景）。

### 5.4 风险

- BroadcastChannel 在旧浏览器/隐私模式不可用，需要回退到 localStorage 心跳或单页模式；
- leader 标签页崩溃会导致事件短暂中断，需要租约超时与重新选举；
- 阶段 B 是架构变更，必须走 ADR，不得夹带在普通 UI 提交中。

## 六点五、W4B（P1）：文件列表读取健壮性

### 6.5.1 问题与证据

前端“文件列表读取失败，已保留上一次可用数据”来自 `App.jsx:1001`；文件 API 为 `apiControl("/api/files")`（`client/src/api.js:82`）。服务端 `server/workspace.mjs:183` 的 `listWorkspace` 在 `readdirSync` 之后对每个文件/目录直接 `statSync`，没有逐项 try/catch；`/api/files`（`server/index.mjs:969`）也没有包裹它。

用临时目录做文件抖动（100 文件 + 100 目录持续删除/重建），2 秒内向 `/api/files` 发 60 次请求：**27 次 500**；隔离调用 `listWorkspace` 220 次：**78 次 `ENOENT`**。Express 返回 HTML 500，前端只能显示“HTTP 500”。Agent 的“临时文件 + rename”、OfficeCLI 锁文件清理、用户/Agent 删目录都会命中 `readdir→stat` 的窗口；`file_changed` 合并 500ms 后刷新时写入可能仍在继续，因此是偶发而非必现。

### 6.5.2 改动

- [ ] `listWorkspace`：`readdirSync` 外层 try/catch；每个条目的 `statSync` 单独 try/catch，失败跳过；目录条目不再强求 `stat`（列表按名称排序），减少一次竞态窗口。
- [ ] `/api/files`：捕获 `ENOENT/EPERM/EBUSY/EIO`，返回 JSON 错误码（`FILES_TRANSIENT` / `FILES_NOT_FOUND`），不要落到 Express HTML 500；临时性错误在服务端短重试一次（约 50ms），仍失败才返回。
- [ ] `refreshFiles`：复用 `sessionsRefreshRef` 的 in-flight 合并/排队模式（同一时刻 1 个在途 + 1 个待执行）；失败后 300–500ms 重试一次。
- [ ] **横幅节流**：第一次瞬时失败只保留旧列表、不显示横幅；重试仍失败才显示；成功后立即清除。连续失败 3 次或持续 30 秒才升级为带错误码/重试按钮的持久提示。这样“横幅次数”下降来自真实失败率下降 + 提示只针对持续故障。
- [ ] `404 currentDir`：自动回到工作区根目录并提示“目录已不存在”，不要一直保留错误横幅。
- [ ] 观测：服务端按 `/api/files` 错误码计数（不记录文件名/用户内容）；客户端记录 `files` 分区失败次数/重试结果，供 L4 断言横幅次数。
- [ ] 测试：新增 `test:file-list-churn`（文件/目录抖动下 60 次请求无 500；单文件消失不拖垮整表；目录删除后前端回根目录；连续失败才显示横幅）。

### 6.5.3 验收

- 文件/目录抖动场景下 `/api/files` 不再返回 500；列表最多跳过瞬时消失的条目。
- 任务运行中 `file_changed` 连续到达：请求合并，不出现并发风暴/8s 超时横幅。
- 30 分钟真实多文件任务：文件列表失败横幅 **0 次**；人为制造持续 500 时最多显示 1 次，恢复后自动消失。
- 当前目录被删除：界面回到根目录并提示一次，不持续报错。

### 10.1 目标形态


### 10.2 分阶段实现

**阶段 1：最小改造（复用现有结构，1–1.5 天）**

- [ ] 在 `ChatPanel` 的单条 assistant 消息内，把所有过程块合并到**一个** `message-process-fold`（当前每遇到文本就切段，导致多个折叠）；中间的小节结论是否一并收进过程，需要先按 PRD R3 确认（折叠是展示层收起，不删除内容；默认建议：仅最终答复留在主阅读流，小节结论可在过程展开后看到）。
- [ ] 折叠行使用 Run 级文案：完成 `已完成 · 运行了 2 小时 13 分 · 45 步`；运行中 `正在运行 · 已用 12 分 · 当前：…`；失败/取消带状态与原因入口。
- [ ] 时长取 `run.startedAt/finishedAt`，终态缺失用最后一个事件时间兜底；步数取 `run.steps.length` 或工具数；运行中每秒刷新。

- [ ] 产物卡改用扁平图标；最多 6 个 + “查看全部”入口；保留交付/待确认徽标。

- 一个多 turn 的真实样本（5 turns / 59 events / 4 steps）：完成后**只有一行**过程折叠；行内含总用时/步数；展开可见按 turn 分组的过程。
