## 2. 与计划的偏差

1. **提交拆分**：计划为 2 个 perf 提交（T1 / T2+T3），实际合并为 1 个。原因：T1 与 T3 的改动交错在同一文件（`内置浏览器面板.jsx`）相邻 hunk，拆开需要 hunk 级暂存两个中间态，收益（独立回退）低于风险（中间态易出错）。单一意图"帧流负载治理"不变。
2. **T6 实现路径**：计划预计"包装 14 个工具的 execute 签名"，实际改为**注册点统一包装**（`wrapBrowserStepTool(kind, tool)`，一处调用），工具内部实现零改动；`browser_progress` 事件已登记契约（不落盘）但等待进度经 T5 的 `state.phase` 承载，前端等待文案已可见——该事件现阶段备用，未在 UI 消费（后续如需更细粒度等待进度可直接启用）。
3. **验证口径**：本会话工作树同时包含另一并行会话（CAD 专项）的未提交改动；`npm run verify` 与 `test:browser` 运行于两者的合并状态并通过（exit 0）。三个代码提交均已按 hunk 隔离只含本批次文件；并行会话未通过全部验证前不视为其改动已验收。
