## 2. A：导出任务跨重启可见（止血）

`GET /api/canvas/exports/:jobId` 内存未命中时回落画布目录 `.jobs.json`
（`listExportJobs(workspace, null, { jobId })`），按前端已识别形状返回
`status/files/errors` 并标 `recoveredAfterRestart: true`；确实找不到才 404。

现场依据：用户那次导出产物其实已生成（17.4MB / 50 页 / 2 个视频 base64 完整），
只是任务号在内存里、服务被重启后轮询 404 → 前端显示「导不出来」。

## 3. B：消除周期性同步阻塞（根因）

实测数据（本机、USB 工作区）：

| 操作 | 改造前 | 改造后 |
|---|---|---|
| 回收候选查询（50~460 条 Run） | `listRuns({limit:50, includeEvents:"latest"})` 同步 **1976ms**；冷启动首轮 **3485ms** | 异步分批：冷扫总耗时 816ms / 单次事件循环滞后 **76ms**；带 180s 预筛 256ms / **21ms** |
| `copyAfterBlobs` | 只有单文件 4MB 上限，无总量上限（100+ 产物 Run 可连续同步拷几百 MB） | 复用 `MAX_BLOB_TOTAL` 预算，超预算停止复制 |
| 回收器重入 | 无保护，慢扫描可能叠加 | `reaperRunning` 门闸 + `void` 调度 |

关键实现：`listRunStallCandidates({ limit, olderThanMs, chunkSize })`
- `statSync` 按 mtime 先筛掉「刚写过」的 Run（活跃 Run 必然刚写过）；
- 对剩余文件只 `readSync` 头 4KB + 尾 16KB，正则取 `status` 与最后一个 `"at":"…"`，**不 JSON.parse**；
- 每 40 个文件 `await setImmediate` 让出事件循环；只有真停滞的候选（通常 0~2 条）才 `getRun()` 复核。

## 4. C：可观测

`/api/status` 返回 `eventLoopLagMs`（2s 采样，带衰减保留峰值）。健康检查超时时可直接区分
「进程卡死」与「事件循环被同步工作占满」。
