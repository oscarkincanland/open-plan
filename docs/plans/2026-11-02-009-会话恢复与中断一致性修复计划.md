> 状态：已实施（P0-1～P0-5 + P1-2，2026-11-03）；`steer`（P1-1）未做，待契约确认
> 日期：2026-11-02（实施记录 2026-11-03）
> 基线：`develop` @ `1f1dcb2e`（v0.13.22 之后）
> 适用范围：`server/agent.mjs`、`server/index.mjs`、`server/执行句柄.mjs`、`client/src/App.jsx`、`client/src/components/ChatPanel.jsx`、`client/src/api.js`、`scripts/`、`REQUIREMENTS.md`、`变更日志.md`
> 关联：[AGENTS.md](../../AGENTS.md) §5/§7、[REQUIREMENTS.md](../../REQUIREMENTS.md) R5（含第 160 行“运行中会话恢复有等待/重试保护”）、[决策记录 0013](../../docs/决策记录/0013-提交门禁与未验证改动不提交.md)

## 0. 结论先行

用户报告的“两个会话并行后切回运行中的会话恢复不了、运行中插入指令卡死、中断 10 秒不确认”，不是网络或模型故障，而是服务端会话运行时的状态机缺陷，叠加客户端恢复策略。共 6 个问题，按依赖顺序修复：

| 编号 | 问题 | 性质 | 方案 |
|---|---|---|---|
| P0-1 | 切回运行中会话必然 `SESSION_BUSY` | 确定缺陷：`resume` 非幂等，把“附着到活运行时”当成错误 | 同 key + 同 sessionId 直接复用活运行时，返回 `reused:true` |
| P0-2 | 中断后 agent 仍挂在 `ask_user` 上 5 分钟 | 确定缺陷：`abort` 不结算 `pendingAsks`，看门狗却提前把 Run 收尾 | 中断/新指令到达时结算 ask，持久化状态 `cancelled` |
| P0-3 | 新指令静默排在幽灵回合后，界面无反馈 | 确定缺陷：占用判定只看 `busy/queuedCount`，不看 promptChain 是否仍有活 | 引入 `chainDepth`，链上有活时照常发 `agent_queued` |
| P0-4 | 中断 10 秒提示“服务端未确认” | 确定缺陷：客户端窗口 10s < 服务端看门狗 15s，且终态事件可能先于窗口到达 | 服务端返回结算期限；客户端按期限计时，`run_finished` 也终止计时 |
| P0-5 | 切回后提问卡退化成普通工具卡，无法回答 | 确定缺陷：`ask_user` 只由实时 SSE 创建，`listPendingQuestions` 从未被调用 | SSE 握手补发待答问题；客户端恢复时主动拉取并合成提问卡 |
| P1 | 多会话下 `abort` 可能命中错误 entry；“立即执行”是死路径 | 设计隐患 | 精确化 `resolveLiveEntry`；`steer` 走显式投递通道（需契约确认） |

**核心判断：运行时本来就是活的，切回时不应该重建它。** 当前 `resumeThread` 在同一个 `client::thread` 上发现 `busy` 就抛错（`server/agent.mjs:5376-5391`），客户端把任何 resume 失败都当作“历史只读”，于是输入禁用（`client/src/App.jsx:1527`、`:1607`）。同时，中断路径把 Run 收尾与 agent 真正停止解耦：Run 在 15 秒后被看门狗标成 `cancelled`，但 agent 仍停在最长 5 分钟的 `ask_user` 上，后续指令被 `promptChain` 无声阻塞。

## 2. 根因定位

### 2.1 P0-1：`resume` 非幂等

- `server/agent.mjs:5376-5391` `resumeThread`：`old = this.sessions.get(clientId)`，只要 `old.busy || old.compacting || old.queuedCount > 0` 就抛 `_sessionBusyError`（`:5362`）。
- 切走时不会删除或挂起该 entry；切回时 `handleSelectSession` 无条件再次 resume（`client/src/App.jsx:1499`）。
- 失败后 `setAgentReady(false)`（`App.jsx:1527`、`:1607`），发送入口被 `if (!agentReady)` 拦截（`ChatPanel.jsx` 发送前置判断）。
- `resumeAutoRetry` 默认关闭（`server/运行开关.mjs:123`），任务结束后不会自动恢复。
- 即使空闲也会 dispose+重建（PROBE3），造成每次切换冷启动、通道内事件丢失。

### 2.2 P0-2：中断不结算 ask，看门狗提前收尾

- `ask_user` 是阻塞 Promise，最长 5 分钟（`server/agent.mjs:3278-3410`；`ASK_TIMEOUT_MS = 300_000`，`:681`）。
- `abort()`（`server/agent.mjs:5272-5295`）只做：打 `cancelRequested`、`piRuntimeManager.abort`、`emitAbortedOnce`；**不 resolve `pendingAsks`**。
- 取消看门狗（`server/index.mjs:6362-6405`，`CANCEL_STALL_MS=15000`）15 秒后 `finishRun(cancelled)`，并把 `entry.busy=false`、`entry.cancelRequested=false`。
- 因此出现“Run 已终态、agent 仍在跑”的双写状态；日志 10:13:15 与 10:17:35 的间隔就是证据。

### 2.3 P0-3：新指令被幽灵回合静默阻塞

- `_enqueuePrompt`（`server/agent.mjs:4578-4598`）的 `wasOccupied = busy || compacting || queuedCount > 0`。
- 看门狗把 `busy` 清零后，链上仍有未完成的 prompt，但 `wasOccupied` 为 false：
  - 不发 `agent_queued`，客户端不知道已排队；
  - 新操作挂在 `entry.promptChain` 后面，等旧的 ask 超时才轮到。
- 这解释了“插入新指令又卡死”且没有任何“排队第 N 项”提示。

### 2.4 P0-4：中断确认窗口与服务端结算期限不匹配

- 客户端固定 10 秒（`ChatPanel.jsx:3693-3701`）；服务端看门狗 15 秒（`index.mjs:6362`）。
- `aborted` 由 `emitChannelSafe` 只写入通道内存与 Run 事件（`agent.mjs:5899-5917`），不进入根级事件流；页面未订阅或正在重连时收不到。
- `run_finished` 到达时只 `setStopping(false)`，不调用 `finalizeStopped()`，10 秒计时器仍可能先触发提示。

### 2.5 P0-5：待答问题没有恢复通道

- 提问卡只由实时 `ask_user` SSE 创建（`ChatPanel.jsx:2654-2690`）。
- `listPendingQuestions` 只有定义（`client/src/api.js:392`），全仓库无调用。
- resume 重建 Runtime 后 `streamId` 变化，客户端游标清零，新通道没有历史事件；JSONL 里只有 `tool_start`，于是渲染成普通工具卡。
- 服务端 `pending-asks.json` 仍保存着待答记录，但没有接口/事件把它推给重连后的页面。

### 2.6 P1：多会话下的兜底匹配与 steer 死路径

- `resolveLiveEntry`（`server/agent.mjs:5297-5310`）：精确 key 不存在时按 `client::` 前缀返回第一个 busy entry；同一 client 有两个活会话时可能命中错对象（中断/诊断串台）。
- `_enqueuePrompt` 串行化所有 prompt；`_promptEntry` 里的 `isStreaming = entry.busy`（`:4994-4998`）在轮到执行时必为 false，`streamingBehavior:"steer"` 分支不可达。前端“立即执行”实际等于“排队”。
- `clientId` 存 `localStorage`（`client/src/api.js:394-404`），两个标签页共享同一 agent 命名空间；`oaw_thread_id`、`oaw_event_cursor` 也是全局键（`App.jsx:684`）。不同 thread 由 key 隔离，但兜底匹配与全局游标是隐患。

## 3. 修复方案

### 3.1 P0-1 `resume` 幂等（`server/agent.mjs`、`server/index.mjs`、`client/src/App.jsx`）

**规则**：

1. `old = sessions.get(key)` 存在，且 `old.session.sessionId === expectedSessionId`：
   - 无论 `busy/compacting/queuedCount` 如何，直接返回
     `{ ok: true, reused: true, threadId, sessionId: old.session.sessionId, runtimeId: old.runtimeId, cwd: old.workspace }`；
   - 不 dispose、不 `_create`、不改 `workspace`。
2. `old` 存在但 sessionId 不一致：
   - `busy || compacting || queuedCount > 0` → 保留 `SESSION_BUSY`（真正的冲突）；
   - 否则 dispose 后重建（保持现状）。
3. `old` 不存在 → 现状 `_create`。

**实现要点**：

- `/api/agent/resume`（`server/index.mjs:5051`）把 `found` 解析出的 sessionId 一并传入 `resumeThread`（新增第 5 个参数），或由 `resumeThread` 用 `path.basename(sessionPath, path.extname(sessionPath))` 推导；优先显式参数，避免扩展名差异。
- `SESSION_BUSY` 的 `detail` 保留，供横幅继续显示 `busyForMs/activeRunId`。
- 客户端：`resume` 成功即 `agentReady=true`；`reused` 仅用于诊断，不改变 UI。

**为什么复用是安全的**：SSE 通道按 `client::thread` 订阅，多个订阅者会同时收到事件；prompt 仍由 `promptChain` 串行化。同一会话在两个标签页打开时共享一个运行时，避免两个 Runtime 同时写同一 JSONL。

**验收**：切走再切回运行中会话，历史正常显示、输入可用、无黄色横幅；切换空闲会话不再冷启动（可通过 `runtimeId` 未变化确认）。

### 3.2 P0-2 中断/新指令结算 `ask_user`（`server/agent.mjs`、`server/index.mjs`）

**已确认语义**：用户中断或插入新指令时，待答问题视为取消，并继续执行新指令。

**实现**：

1. 抽出 `settlePendingAsk(key, { status, answer })`：
   - 取 `this.pendingAsks.get(key)`，存在则删除并调用 resolver；
   - 同步 `resolvePendingAsk(key, answer, status)` 持久化，状态用 `cancelled`（新增合法值）。
2. `abort()` 在发出 `aborted` 之前调用：
   `settlePendingAsk(key, { status: "cancelled", answer: "[系统提醒] 本轮任务已被用户取消，请立即停止执行，不要再调用工具，直接在正文里说明本轮已取消。" })`
   - 与 `submitAnswer` 现有的“取消后回填”文案保持一致，避免模型继续扩大任务。
3. 新指令到达时（`promptWithContext` / `/api/agent/prompt` 入口）：若该 key 有 pending ask，先结算为
   `"[系统提醒] 用户已插入新指令，原提问作废；请结束当前回合，等待并执行新指令。"`，再入队/投递新指令。
4. 取消看门狗（`server/index.mjs:6362-6405`）在 `finishRun` 前再兜底结算一次，防止其他路径漏掉。
5. `pending-asks.json` 的 `cancelled` 记录由现有读取方忽略；`/api/agent/pending` 只返回 `pending`。

**效果**：ask 立即返回 → `promptChain` 立即排空 → Run 正常收尾，不再依赖 15 秒看门狗；日志里不会再出现“run_finished 在 10:13、agent_error 在 10:17”的错位。

**验收**：ask 待答时点中断，2 秒内 Run 进入 `cancelled`；ask 待答时插入新指令，旧提问消失、新指令在下一回合执行。

### 3.3 P0-3 排队可见性（`server/agent.mjs`）

- 新增 `entry.chainDepth = 0`：
  - `_enqueuePrompt` 入口：`const chainBusy = entry.busy || entry.compacting || entry.chainDepth > 0;`
  - `chainBusy` 时发 `agent_queued`（position 用 `entry.queuedCount + 1`）；
  - `entry.chainDepth += 1`，在 operation 的 `finally` 里 `Math.max(0, chainDepth - 1)`。
- `queuedCount` 继续表示“等待中的条数”，`chainDepth` 表示“链上是否有活（含正在执行的一条）”。
- 响应里的 `queued` 与 `queuePosition` 逻辑不变，但会覆盖“幽灵回合”场景。
- 注意不要在 `_promptEntry` 的 `finally` 里减，必须在 `_enqueuePrompt` 包装的 operation 里减，确保异常路径也归零。

**验收**：人为制造“链上有活但 busy=false”的状态，第二次入队必须产生 `agent_queued`，客户端显示“任务排队（第 N 项）”。

### 3.4 P0-4 中断确认（`server/index.mjs`、`client/src/components/ChatPanel.jsx`）

- 服务端 `/api/agent/abort` 响应增加 `settleDeadlineMs`（建议 `CANCEL_STALL_MS + 5000 = 20000`），不新增事件。
- 客户端 `stop()`：
  - 计时器使用 `settleDeadlineMs || 20000`；
  - `run_finished` 且状态为 `completed/failed/cancelled/aborted` 时，若 `stoppingRef.current` 为真，调用 `finalizeStopped()` 并清除计时器；
  - 文案从“服务端未在 10 秒内确认收尾”改为“已受理中断，服务端仍在收尾（可能卡在不响应中断的工具里）”，超时时间动态展示。
- 保留“没有找到正在运行的任务”分支。

**验收**：走看门狗路径时不再出现 10 秒误报；正常中断在 2 秒内收尾。

### 3.5 P0-5 待答问题恢复（`server/index.mjs`、`client/src/components/ChatPanel.jsx`、`client/src/api.js`）

- 服务端 SSE 握手：`/api/agent/stream` 在发送 `connected` 之后，检查该 key 是否有 pending ask（内存 `pendingAsks` 或 `pending-asks.json` 中 `status=pending` 且未过期），有则补发一条同 `askId` 的 `ask_user` 事件（带 `recovered: true`、`expiresAt`）。同一 askId 客户端去重。
- 客户端：
  - 历史加载完成后调用 `listPendingQuestions(clientId, conversationId)`；
  - 若未收到同 askId 的实时事件，合成 `type:"ask"` 块（复用 `ChatPanel.jsx:2673` 的结构）；
  - `expiresAt` 已过的显示“已超时”，不再允许回答。
- 服务端把 `pendingAsks` 的查询做成只读方法 `getPendingAsk(key)`，避免暴露 Map。

**验收**：有待答问题时刷新页面/切走再切回，提问卡仍在且可回答；回答后 ask 状态变 `answered`。

### 3.6 P1-1 真正的“立即执行”（需契约确认，不在本次默认范围）

- `/api/agent/prompt` 增加显式 `delivery: "steer"`（或复用客户端已有的 `channel` 字段），仅在 `chainDepth > 0` 且当前 prompt 已派发到 Pi 时走 `session.steer`，不排到 `promptChain` 后面。
- 若有 pending ask，先按 3.2 的语义结算，再 steer。
- 返回 `{ accepted: true, merged: true, queued: false }`；`steer` 事件 `source:"user"`。
- 风险：Pi 的 steer 只在回合边界生效，不能打断正在执行的工具；文档与 UI 必须说清楚“插话在下一个回合边界生效”。
- 这是公开 API 契约变更，按 AGENTS §4.3 需单独确认并补决策记录。

### 3.7 P1-2 `resolveLiveEntry` 精确化（`server/agent.mjs`、`server/index.mjs`）

- 顺序：精确 key → 按 `runId === entry.activeRunId` 找 → 前缀候选**仅当唯一**时返回；多候选返回 `null` 并 `console.warn` 诊断。
- `/api/agent/abort` 已有 `runId`，调用 `resolveLiveEntry(key, { runId })`。
- 取消看门狗按 `run.threadId` 精确 key，不走前缀。
- 验收：同一 client 两个活会话时，中断 A 不会影响 B。

### 3.8 P2 观测与不变式

- `/api/agent/diagnostics` 增加：最近一次 resume 结果（`reused/created/busy`）、`pendingAsk` 是否被中断结算、`chainDepth`、`busy` 与 `activeRunId`。
- 增加不变式检查：同一 entry 在 `run_finished` 之后不得再产生该 Run 的 `agent_error`；违反时写一条诊断。
- 事件流健康巡检（`scripts/事件流健康巡检.mjs`）增加对应计数。

## 4. 测试计划

### 4.1 新增 `scripts/会话恢复与中断一致性测试.mjs`

用与本次探针相同的方式直接驱动 `AgentManager`，不依赖真实模型：

| 用例 | 断言 |
|---|---|
| busy + 同 sessionId resume | 返回 `reused:true`；不抛 `SESSION_BUSY`；`dispose` 未被调用 |
| idle + 同 sessionId resume | 复用；`create` 未被调用 |
| 不同 sessionId + busy | 抛 `SESSION_BUSY`，`detail.activeRunId` 正确 |
| abort 且有 pendingAsk | resolver 被调用一次；`pending-asks.json` 状态为 `cancelled` |
| 新指令到达且有 pendingAsk | 先结算 ask，再入队；ask 状态为 `cancelled` |
| 幽灵回合 + 第二次入队 | 发出 `agent_queued`，position 正确；旧链结束后新指令执行 |
| 两活会话 + 前缀兜底 | 精确 key 缺失时返回 `null`，不误命中另一个 thread |

### 4.4 手工验收

1. 两个标签页各开一个会话，同时运行。
2. 在 A 标签页切走再切回运行中的会话：历史正常、输入可用、无横幅。
3. A 会话出现 ask 时切到 B，再切回 A：提问卡仍在、可回答。
4. ask 待答时点中断：2 秒内进入“本轮已中断”，不再出现 10 秒误报。
5. ask 待答时插入新指令：旧提问作废，新指令执行。
6. 中断后立刻插入新指令：新指令正常开始，不再静默等待。
7. 两个会话同时运行时，中断 A 不影响 B。

## 5. 风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| 复用活运行时导致两个标签页共享同一 session | 两个标签页的 prompt 串行、事件同时可见 | 这是期望行为；`promptChain` 已串行；禁止两个 Runtime 写同一 JSONL 的风险反而更低 |
| 结算 ask 后模型仍继续输出 | 取消后多一条收尾正文 | 文案明确“立即停止”；`isRunStopping` 继续抑制工具提醒；Run 终态仍为 `cancelled` |
| `chainDepth` 计数泄漏 | 永远显示“排队” | 在 operation 的 `finally` 减；新增单测覆盖异常路径 |
| `run_finished` 直接 finalize | 迟到的 `assistant_final` 被丢弃 | 已有终态围栏（`ChatPanel.jsx:1009`、`:2232`）会丢弃迟到增量；本轮终稿以 `run_finished.finalText` 兜底 |
| SSE 补发 ask 与实时事件重复 | 两张提问卡 | 按 `askId` 去重（现有 `patch` 已按 id 判重） |
| 复用后 session 文件被外部修改 | 内存与磁盘不一致 | 既有约束：外部修改会话文件不受支持；恢复仍以 Pi 内存会话为准 |

回滚：四个 P0 可按提交拆分单独 revert；P0-1 回滚后恢复 `SESSION_BUSY` 行为，不影响数据；P0-2 回滚后 ask 仍可正常回答，只是中断延迟回到 5 分钟。

## 6. 不做清单

- 不修改 Pi SDK，不新增任务模式、数据库、微服务或桌面壳。
- 不默认开启任何运行时开关（`OAW_RESUME_AUTO_RETRY`、`OAW_BUSY_WATCHDOG` 保持默认关闭）。
- 不在 P0 阶段改 `/api/agent/prompt` 的公开契约；`steer` 单独立项。
- 不把 `clientId` 改成“每标签页独立”（会让同一会话被两个 Runtime 同时写，风险更大）；跨标签页身份另议。
- 不重构 ChatPanel 的消息流/SSE/执行流，只改恢复与提问卡补全所需的入口。
- 不创建分支、不提交、不推送，直到实现完成并通过提交门禁。

### 10.2 与计划的偏差

- 客户端额外增加“历史水合后主动调用 `/api/agent/pending` 对账”的第二道保险；计划只要求 SSE 补发。原因是历史水合会整体替换 `messages`，仅靠握手补发在特定时序下仍可能被覆盖。
- `_enqueuePrompt` 在所有新指令入队时都结算旧提问（含任务恢复/继续路径），比计划中“仅用户插话”更宽；理由是新指令到达即表示旧提问已过期，且可避免恢复路径再次被阻塞。
