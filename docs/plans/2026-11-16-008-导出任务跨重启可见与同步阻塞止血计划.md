# 2026-11-16-008 导出任务跨重启可见 + 服务端同步阻塞止血计划

> 状态：待用户确认（2026-11-16）　基线：v0.13.25（develop @ 487b5d37 + 未提交 010/011/012/005/006/007 改动）
> 需求来源：用户反馈「导不出来呢？然后把我这个本地的服务都带崩溃了」

## 1. 现场结论（已实测取证）

### 1.1 HTML 其实导出成功了

`designs/open-plan-tech-sharing/exports/Open Plan 规聚 技术分享-20261116-085455.html`：

| 项 | 值 |
|---|---|
| 大小 | 17.4 MB |
| 页面 | 50 个 `.slide` |
| 视频 | 2 个 `<video>`，base64 完整性通过（2,299,482 / 4,496,376 字节，与源文件一致） |
| 图片 | 10 个 base64 内嵌 |
| 结构 | `<!doctype html>` 起始、`</html>` 收尾、翻页脚本与 `id="stage"/bar/counter` 齐全 |
| 导出任务记录 | `.jobs.json` 里 `format=html, status=completed, 763ms` |

**所以“导不出来”是显示问题，不是产物问题。**

### 1.2 显示失败的直接原因：任务号只存在内存

- `server/index.mjs` 的 `canvasExportJobs` 是进程内 `Map`，`GET /api/canvas/exports/:jobId` 只查它。
- 服务在 00:54:06 被监督器重启（见 1.3）→ 前端轮询该 jobId 得到 **404** → 前端把它当失败/超时。
- 而落盘的 `.jobs.json` 里有完整结果，接口没有用它兜底。

### 1.3 服务为何被重启：健康检查连续 3 次超时（10s/次）

`运行日志/服务监督.log`：

```
[2026-11-16T00:53:37] 健康检查失败（1/3）
[2026-11-16T00:53:50] 健康检查失败（2/3）
[2026-11-16T00:54:05] 健康检查失败（3/3）
[2026-11-16T00:54:06] 健康检查连续失败，正在重启服务：/api/status 不可用或服务版本不匹配（端口仍在监听，疑似卡住）
[2026-11-16T00:54:06] 服务异常退出（signal SIGTERM，运行 43097 秒）
```

`/api/status` 本身只返回 2KB（实测 13ms），它超时只能说明**事件循环被同步工作占满**。实测到的同步开销：

| 操作 | 实测 | 位置/触发 |
|---|---|---|
| `listRuns({limit:50, includeEvents:"latest"})` | **1976 ms**（同步） | `server/index.mjs` 静默回收器，**每 30 秒一次** |
| 工作区快照 `snapshotWorkspace` | 冷 586 ms / 热 257 ms（3000 文件、1450MB 被截断） | `beginRun` / `finishRun` / 回收器 |
| 会话 JSONL 读取+解析+序列化 | 25.1MB 文件：91+10+29+71 ≈ **200 ms** | 会话恢复/历史 |
| `copyAfterBlobs` | 同步 `copyFileSync`，单文件上限 4MB | `finishRun` |

叠加起来：一次 17.4MB HTML 导出（in-process 实测 226ms、峰值堆 +110MB）与上面这些周期任务撞在同一时间窗，就足以让 `/api/status` 连续 3 次在 10s 内拿不到响应。

### 1.4 内存现状

服务进程 PID 426148：**私有内存 745MB / 工作集 586MB**，已跑 41 分钟。HTML 导出每轮峰值 +110MB 堆（GC 后回落到 10MB，无泄漏），但 `.jobs.json`（34 条、94KB）、50 块板的画布、3000 文件快照常驻，基线本身就高。

## 2. 方案

### A. 导出任务跨重启可见（止血，必做）

1. `GET /api/canvas/exports/:jobId`：内存没有时**回落 `.jobs.json`**（`listExportJobs(workspace, null, { jobId })`），把落盘的 `status/files/errors` 按前端已识别的形状返回，并标 `recoveredAfterRestart: true`。
2. 前端 `执行导出` 轮询：404 不再当作失败——改为「任务在服务重启前提交，结果见产物面板」，并触发一次产物刷新；已完成的落盘任务直接显示文件名。

### B. 消除周期性同步阻塞（根因，必做）

1. `listRuns` 的 `includeEvents:"latest"` 之所以贵，是给 50 条 Run 各解析完整 events。回收器只需要「最后一条事件时间 + 状态」，改为：
   - 新增轻量查询 `listRunStallCandidates({ limit })`：只读 Run JSON 的 `status/startedAt/events[-1].at`，**不构造完整对象**；或
   - 回收器改用 `fs.statSync` 的 mtime 做第一道筛选（mtime 新于阈值的直接跳过，不解析），只对候选做完整读。
2. `snapshotWorkspace` 的 walk 改成分批让出（`for await` + `await new Promise(setImmediate)` 每 N 个目录），避免 586ms 独占；或把回收器触发的快照去掉（回收器不需要快照）。
3. `copyAfterBlobs` 的 `copyFileSync` 改 `await fsp.copyFile`（与 `copyBeforeBlobs` 已有的做法一致）。

### C. 中文说明与可观测

- 导出对话框在 `recoveredAfterRestart` 时显示「服务重启前已完成，文件：xxx」。
- `/api/status` 增加 `eventLoopLagMs`（每 2s 采样一次 `performance.now()` 偏差），健康检查失败时日志能直接指向阻塞而非“疑似卡住”。
