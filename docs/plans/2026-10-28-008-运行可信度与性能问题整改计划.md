## 三、WP-R1：运行恢复判定修复（P0）

### 3.1 问题与证据

- 失败分布：`completed 62 / failed 16 / cancelled 14`。16 个 failed 中 **10 个** 的错误是“服务重启两次后未被恢复，任务已终止”，其中 **7 个已有产物**（最多 32 个）、2 个已有终稿。
- 案例 `run_2555f48c`（10-27 21:51）：
  - `13:58:37` `assistant_final` + `agent_end`（44 回合、54 次工具）
  - `13:59:13` `run_recovered`
  - `13:59:50` `run_finished status=failed`，`completion=null`，`finalText` 仍在，`artifacts` 被清空
- 案例 `run_a305cc77`：`finishedAt=14:46:09`，但事件持续到 `14:49:44`（先判失败、任务还在跑）。
- 另有 2 个 Run 从 09-28 挂到 10-09（11 天）才被下一次重启“清理”。

### 3.2 根因

1. `server/index.mjs:129` 在模块加载阶段、`app.listen()`（`:5999`）之前无条件执行 `recoverActiveRuns()`。任何第二次启动（哪怕端口被占、最终启动失败）都会改写 Run 状态。
2. `server/runs.mjs` 的 `recoverActiveRuns()`：
   - 第一次调用把 `running` 改成 `recovering`；
   - 第二次调用直接 `finishRun(failed)`，**不检查 `finalText`、`agent_end`、`artifacts`**。
3. `finishRun(failed)` 会按 before/after 重算产物，导致已存在的 `artifacts` 归零（最小复现中 1 → 0）。
4. 收尾路径 `waitForFlush → diffWorkspace` 历史上抛过 `TypeError: object is not iterable`，异常时跳过 `finishRun`，Run 留在 `running`，正好落进上面的恢复逻辑（当前代码已用 `snapshotPathSet` 修复，但缺少“异常也必须收口”的兜底）。

### 3.3 最小复现（已跑通）

在临时目录造一个“已产出终稿 + 1 个产物、仍为 running”的 Run，调用两次 `recoverActiveRuns()`：

```
0-initial    running     finalText=有  artifacts=1
recover#1 →  recovering  finalText=有  artifacts=1
recover#2 →  failed      finalText=有  artifacts=0
error="服务重启两次后未被恢复，任务已终止"，completion=null
```

### 3.4 修复设计

1. **终态优先**：`recoverActiveRuns` 判 failed 前先检查客观完成证据：
   - `run.finalText` 非空，或事件里存在 `agent_end` / `assistant_final`，或 `artifacts.length > 0` → 按 `completed` 收尾，`error` 记为 `recovered_after_restart`，**不清空 artifacts**；`completion.source` 标记 `recovered`。
   - 只有确实没有终稿和产物、且超过静默阈值时才按 failed。
2. **调用时机**：把 `recoverActiveRuns()` 移到 `httpServer.listen` 成功回调之后；或在执行前加“单实例锁”（`.oaw/runs/恢复锁`），端口被占时直接跳过；两种都做。
3. **异常兜底**：`执行回合` 的 `finally` 保证“即使 `waitForFlush`/`diffWorkspace` 抛错，也必须调用 `finishRun`”，错误写进 `run.error`，不要留 running。
4. **悬挂超时**：`running` 超过可配置阈值（建议 6 小时，`OAW_RUN_STALE_MS`）且无活跃 runtime → 自动收口（优先 completed-if-finalText，否则 failed），消除 11 天悬挂。
5. **失败收尾保留产物**：`finishRun(failed/cancelled)` 不再清空既有 `artifacts`，改为保留并标 `unverified`/`recovered`，由产物面板展示“未验收”。

### 3.5 改动文件

- `server/runs.mjs`（`recoverActiveRuns`、`finishRun` 产物保护、悬挂超时）
- `server/index.mjs`（调用时机 / 恢复锁）
- `server/执行句柄.mjs`（收尾异常兜底）
- `server/事件注册表.mjs`（如需新增 `run_recovered_completed`，必须先登记；否则复用 `run_recovered` + data.status）

### 3.6 测试

- 新增 `scripts/运行恢复判定测试.mjs`：
  - 有 finalText + artifacts → 两次恢复后仍 completed，artifacts 保留；
  - 无 finalText 无 artifacts → 第二次恢复 failed；
  - 端口占用导致的二次启动不改变 Run 状态；
  - 悬挂超时收口。
- 回归：`test:startup`、`test:main-flow`、`test:conclusion`、`npm run verify`。

### 3.7 验收

- 已产出终稿的 Run 经历 2 次恢复后仍为 completed，产物数量不变。
- 二次启动（含启动失败）不再改写任何 Run。
- 不再出现“finishedAt 早于最后事件”的记录。
- 无 Run 悬挂超过阈值。

### 3.8 风险与回滚

- 风险：把真正失败的 Run 误判成 completed。对策：只有 `finalText`/`agent_end`/`artifacts` 三者之一存在才升级，并保留 `recovered` 标记供审计。
- 回滚：单次 revert；恢复逻辑无数据迁移。

## 四、WP-S1：长连接预算与泄漏修复（P0）

### 4.1 问题与证据

- 服务端 `/api/sessions` 实测 65–171ms，`/api/status` 1.5ms；UI 却出现“会话列表读取失败，已保留上一次可用数据”（`client/src/App.jsx:910`）。
- 前端控制面超时 8s（`client/src/api.js:35`），失败后才会回收可选长连接。
- 现场 `/api/diagnostics/streams`：**5 条 SSE / 浏览器 6 槽**
  - `/api/agent/stream` age=48.7 分钟（泄漏）
  - `/api/agent/stream` 同一 thread 两条（1.4s / 0.4s）
  - `/api/agent/events` 两条
  - 全部来自同一个 `clientId`（`localStorage` 跨标签页共享）
- 服务端 `MAX_PER_CLIENT=8`（`server/流连接.mjs:25`）> 浏览器同源 6；`MAX_SAME_KEY=2`（`:23`）；`/api/agent/stream` keep=2、graceMs=60s。

### 4.2 根因

1. 服务端允许的流条数大于浏览器连接池，配额没有意义。
2. 两个标签页共享 `clientId`，服务端无法区分，只能“保留 2 条”，于是重复流长期并存。
3. 页面重载/切会话时旧连接在 60s grace 内不被判旧，叠加 48 分钟泄漏流，池子长期 5/6。
4. 控制面请求没有预留连接，`/api/sessions` 与 SSE 抢同一个池。

### 4.3 修复设计

1. **服务端配额**：`MAX_PER_CLIENT` 降到 4；`/api/agent/stream` 改 `keep:1`、`graceMs` 降到 5–10s（组件切换的竞态用客户端重连解决）。
2. **客户端预算**：全局最多 3 条 SSE（`agent-events` + 当前 `chat` + 1 条可选）；页面隐藏（`visibilitychange`）时释放可选流（浏览器帧/记忆流），回到前台再连。
3. **标签页身份**：`clientId` 改为 `localStorage 基础 id + sessionStorage tabId` 组成，服务端按 tab 维度限流；或至少让 `streamKey` 包含 `tabId`，避免两标签页互踢/重复。
4. **服务端主动清扫**：15s heartbeat + 连续 2 个周期写失败即注销；`sweepServerStreams` 增加“超 10 分钟无写入强制关闭”。
5. **控制面兜底**：`apiControl` 超时时优先回收**本标签页**的可选流；仍失败时提示“关闭其他标签页/刷新页面”，而不是只报超时。

### 4.4 改动文件

- `server/流连接.mjs`（配额、清扫）
- `server/index.mjs`（SSE 注册、tab 维度、diagnostics 展示）
- `client/src/长连接预算.js`、`client/src/api.js`、`client/src/App.jsx`、`client/src/components/ChatPanel.jsx`、`内置浏览器面板.jsx`、`MemoryTab.jsx`

### 4.5 测试

- 新增 `scripts/长连接预算测试.mjs`：
  - 配额上限（`MAX_PER_CLIENT`）与同键淘汰；
  - 泄漏流（无写入 > 10 分钟）被清扫；
  - 两标签页场景模拟不同 tabId，不产生重复流。
- Playwright 场景（L4）：两个标签页同会话，连续切换 10 次，`/api/sessions` p95 < 1s，不出现读取失败横幅。
- 回归：`test:a11y`、`test:perf-budget`、`npm run verify`。

### 4.6 验收

- 两标签页 + 浏览器面板打开时，SSE 总数 ≤ 4，控制面请求 p95 < 1s。
- 48 分钟泄漏流不再出现；`/api/diagnostics/streams` 的 `age` 超过 10 分钟的条目为 0。
- 会话列表读取失败横幅在 30 分钟压测中不出现。

### 4.7 风险与回滚

- 风险：限流过紧导致“切会话断流/重连抖动”。对策：先降 `MAX_PER_CLIENT=4`、`keep=1` 并在测试环境压测；保留诊断接口便于回滚观测。
- 回滚：配额是常量，revert 即恢复。

## 五、WP-T1：首字延迟治理（P1）

### 5.1 问题与证据

- 热机（隔离实例）：admission 81–286ms → dispatch 49–134ms → provider 首事件 16–60ms，**合计 160–480ms**。
- 冷启动：`npm start` → 就绪 **41 秒**（12:23:33 → 12:24:14）。
- 历史 87 个 Run：Run 开始 → 模型请求 p50 763ms / p90 **14.1s** / max 617s；模型请求 → 首字 p50 5.4s / p90 11.9s；合计 p50 6.4s / p90 **31.5s**。
- 同会话 `promptChain` 串行，`queueWaitMs` 直接叠加到首字（`server/agent.mjs` 注释明确）；全局 `agentLimiter` 并发 2。
- 前端 `POST /api/agent/prompt` 无超时；连接池满时请求排在 SSE 后面（与 WP-S1 同根因）。
- 收尾：`agent_end → run_finished` p50 3.3s / p90 5.5s（`waitForFlush` 固定 1.5s×6）。

### 5.2 修复设计

1. **启动不阻塞**：`recoverActiveRuns`（45MB 解析）、事件流 `loadStore`（15MB）、Run 索引改为“listen 后再跑”或分片异步；`/api/status` 在启动期先返回 `{ok:true, starting:true}`。
2. **排队可见**：`/api/agent/timing` 已有 `queueWait` span，前端在 `agent_queued` 时显示“排队中（第 N 位）”；长任务允许插话（已有 steer）。
3. **首字观测**：把 `serverReceivedAt / admissionReadyAt / sdkDispatch / firstProviderEvent` 四段做成前端可见的“本轮耗时”明细（已有数据，只差展示）。
4. **超时文案**：45s 首事件、120s 流空闲已有；错误文案统一说明“模型未响应/网络/排队”，避免用户误以为卡死。
5. **`waitForFlush` 快路径**：先比较签名，无变化立即返回；有变化才进入 1.5s 轮询（最多 3 次）。

### 5.3 测试

- `test:first-token-latency` 扩展：热机首事件基线 < 1s；排队场景 `queueWait` 正确；
- 新增启动基线脚本：`npm start` → 就绪 < 15s（在清理后的事件目录上）。
- 回归：`test:chat-flow`、`test:perf-budget`、`npm run verify`。

### 5.4 验收

- 热机首字 p50 < 1s、p95 < 3s（不含模型思考）。
- 冷启动就绪 < 15s。
- 排队时界面明确显示“排队中”，不再无反馈等待。
- `agent_end → run_finished` p50 < 2s。

## 六、WP-M1：监督器容错与可观测（P1）

### 6.1 问题与证据

- 52 次健康检查失败、4 次因此重启（10-25 两次、10-27 一次、10-28 一次）。
- 12:47:50 系统唤醒 → 12:48:55 / 49:09 / 49:24 连续三次失败 → 12:49:24 重启（唤醒后服务尚未恢复，被当成故障）。
- 20:11–20:16 服务与监督器**同时消失**，日志停在“健康检查失败 2/3”，没有 `收到 SIGINT`、没有退出记录；20:23 手动 `npm start` 后 41s 恢复。

### 6.2 修复设计

1. **唤醒宽限**：健康检查失败前检查系统最近 resume（或进程启动时长/单调时钟跳变）；唤醒后 120s 内不计失败。
2. **失败策略**：连续 3 次失败改为“端口探测 + 1 次重试 + 指数退避（15s/30s/60s）”，仍失败才重启；重启前先请求 `/api/status` 两次确认。
3. **崩溃可观测**：子进程 stderr 单独落 `运行日志/服务错误.log`；退出码非 0 时记录最后 50 行；`-1/4294967295` 这类退出码单独告警。
4. **监督器存活**：写 PID 文件 + `npm run service:status`；可选 Windows 计划任务/服务化（需用户决策，属部署方式变更）。
5. **前端提示**：`/api/status` 连续失败时，界面显示“本地服务已停止”，提供“重试/重启”按钮，而不是只显示读取失败。

### 6.3 测试

- 单元：`restartDelayFor`、唤醒宽限状态机、退避序列。
- 模拟：临时把 `/api/status` 路由挂起（测试实例）验证不误杀；正常停止不重启。
- 回归：`npm run verify`（该脚本无 npm 别名，需新增 `test:supervisor`）。

### 6.4 验收

- 睡眠唤醒后 2 分钟内不发生重启。
- 服务真实崩溃时 1 次重试内恢复；连续崩溃进入 30s 冷却。
- 监督器消失后可通过 `service:status` 发现，前端有明确提示。

## 七、WP-P2：写放大与收尾等待（P2）

### 7.1 证据

- `saveRun` 每个 Run 事件对整份 Run 做 `JSON.stringify(..., null, 2)` + 原子写。实测 1.2MB / 647 事件的 Run：**22.2ms/事件**；一轮几十个工具事件会持续占用事件循环。
- `appendJsonLine` 每个事件 `fsyncSync`。
- `waitForFlush` 固定 6×1.5s。

### 7.2 修复设计

1. Run 事件增量落盘：事件追加到 `run.events.jsonl`，主 JSON 只存摘要；或按 200ms 合并写 + 退出前 flush。
2. `fsync` 改为批量/延迟（例如每 5 个事件或 100ms 一次），崩溃时最多丢最后一小段事件。
3. `waitForFlush` 快路径（同 T1-5）。

### 7.3 验收

- `recordRunEvent` p95 < 5ms（1MB Run）。
- `agent_end → run_finished` p50 < 2s。
- 崩溃后事件缺失 ≤ 1 个批次。

### 13.7 已知限制

- 多标签页总连接数仍受浏览器 6 槽限制：每标签页预算 3 条，两标签页理论最大 6 条；本次通过 tab 去重、每 tab 配额 4、2 小时寿命回收把重复/泄漏流清掉，但“两标签页同时开满可选流（浏览器帧流 + 记忆流）”仍可能占满池。根治需要共享 Worker 或 HTTP/2，属后续架构项。
- 被强杀的浏览器进程可能留下半开连接，最长要等到 2 小时寿命上限才回收；正常重连与关闭不受影响。
- fsync 合并窗口为 250ms：进程被强杀/掉电时最多丢失最后 250ms 的 JSONL 追加；正常关闭会 flush。
