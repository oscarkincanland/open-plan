## 0. 计划摘要

**目标**：把 Open Plan 从"能用但每个不确定点都停下来问/等/重试"的工作台，改成**以人机协作中枢为核心、模型自主判断技能、依赖可治理、写作一次成稿**的工作台。

**五项已定决策**

| # | 决策点 | 用户决定 | 本计划落点 |
|---|---|---|---|
| 1 | ask_user 定位 | **人机协作的中枢** | §11：统一 Interaction 模型（澄清/确认/预览/审批/假设），Dock + 卡片 + 非模态浮层 |
| 2 | 提问预算 | **默认假设 + 可撤销**，不保留长时间空等 | §10：提问预算清单、90s 假设卡、假设回执、可撤销 |
| 3 | 技能策略 | **由模型判断是否需要**（不做服务端强制选择器） | §13：收敛为单一策略，只补目录质量/搜索/预检 |
| 4 | 依赖策略 | **可以往工作区装依赖，但规范统一** | §9：`.oaw/skill-deps/` 隔离安装 + 声明式 `requires` + 用户点击触发 |
| 5 | 写作流程 | **接受一次成稿 + 预览最终稿** | §12：Markdown 直通、预览即终稿、砍回合/砍仪式 |

**里程碑**（可并行项已标注）

| 阶段 | 内容 | 预计人日 | 依赖 |
|---|---|---|---|
| D0 | 基线硬缺陷修复（技能解析/搜索/截断、后台化坏 payload、写作默认刹车、ask 90s） | 2 | 无 |
| D1 | 技能策略收敛 + 依赖预检/安装规范 | 4–5 | D0 |
| D2 | 人机协作中枢（服务端 Interaction 模型 + 前端 Dock/卡片/浮层） | 6–8 | D0；与 D3 可部分并行 |
| D3 | 输入区统一面板 + 引用 chip 三态 | 4–5 | D0；与 D2 共用 ChatPanel，需**串行**改同一文件 |
| D4 | 写作一次成稿 + 文风宪法 | 5–7 | D0；与 D2/D3 无文件冲突 |
| D5 | 写作性能与上下文（回合预算、batch、压缩前移） | 3–4 | D4 |
| D6 | 观测、回归、文档与决策记录收敛 | 2 | 全部 |
| **合计** | | **26–33 人日**（串行约 5–7 周；D2/D3 串行后与 D4 并行可压到 3–4 周） | |

**实施原则**

1. **全部行为变更走运行时开关**（`server/运行开关.mjs`，`/api/status.runtimeFlags` 下发），默认关；验收通过后按 §15 逐项翻转，翻转前需用户确认。
2. **不改 Pi SDK、不新增数据库/微服务、不新增 Agent 可调用的安装工具**（安装只从 UI 触发）。
3. 事件只增不改语义；新增事件必须登记 `server/事件注册表.mjs` + schema + 发射点守护测试。
4. 每个阶段独立可回退：开关关掉即回到基线行为。

### 4.2 PRD 需新增/修改的验收口径（建议文本）

**R2 新增需求条目**

> - 人机协作中枢：提问、确认、预览、审批统一为可追踪的交互；同一会话允许多个待处理交互按优先级展示；未决交互在消息流折叠体外常驻。
> - 提问预算：仅当关键信息缺失且不猜会做错时提问；篇幅/受众/风格等非阻塞项一律给默认假设并注明；禁止"是否继续/下一步/是否写回"类收尾提问。
> - 默认假设 + 可撤销：澄清类交互超时（默认 90 秒）按假设继续，回执必须写明假设；用户可点击"改一下"撤销假设并发起修正；高风险确认类不得自动继续。

**R4 新增验收**

> - `@文件/@知识库/@模板/&会话/@智能体/#技能/#插件` 在发送前、发送后、服务端解析后三态一致；解析失败必须明示，不得静默显示为普通文字。
> - 引用 chip 可点击查看解析状态与来源；删除 chip 与删除文本标记双向同步。

**R6 新增需求/验收**

> - 技能 frontmatter 支持 `description: >`/`|` 块标量；所有本地技能的名称与描述必须完整出现在 `/api/skills` 与每轮目录注入中（预算不足时截断描述而不是删除条目）。
> - 技能策略只有"开/关"两档：开启时每轮注入目录，由模型按任务与 description 自行判断是否 `skills_read`/`skills_search`；关闭时不注入目录。
> - 技能依赖必须声明（`requires`）：缺失时返回 `ready/degraded/blocked` 与可执行替代方案；未获用户确认不得执行任何安装命令；确认后只允许安装到当前工作区 `.oaw/skill-deps/`。

**R13 新增验收**

> - 写作 Run 默认受回合预算约束（软 30 / 硬 60）；命中后先收尾并如实记录。
> - 写作默认一次成稿：Markdown 正文直接生成 docx/pptx；预览即终稿；仅在用户显式要求或预计超长时提供可选大纲。
> - 版式精修使用 officecli 批处理（一次 `batch`），禁止逐属性 `set`。

在 `REQUIREMENTS.md` §需求追踪表对应行补充：`server/交互中枢.mjs`、`server/技能依赖.mjs`、`client/src/components/交互/*`、`client/src/components/输入区/*`、`server/写作约束.mjs`（如新增）与对应测试脚本。

## 6. 契约变更清单

> 原则：**只增不改**。旧事件/旧接口保留，客户端按开关选择新路径；新增事件必须登记 + schema + 发射点守护测试。

### 6.1 新增事件（`server/事件注册表.mjs`）

| 事件 | 触发 | 必填字段 | schema 类型 |
|---|---|---|---|
| `interaction_open` | 任意交互创建（clarify/confirm/review/approval） | `interactionId, kind` | string/string；可选 `runId, threadId, question, options, fields, expiresAt, owner, previewFile` |
| `interaction_updated` | 用户填写中/状态变化（节流） | `interactionId, status` | status 枚举 |
| `interaction_settled` | 已答/跳过/假设/取消/拒绝 | `interactionId, status` | 可选 `answer, values, assumption` |
| `interaction_expired` | 超时 | `interactionId` | 可选 `assumed` |
| `interaction_assumption` | 用户撤销/修改假设 | `interactionId, assumption` | string |
| `skill_catalog_injected` | 每轮目录注入 | `count, included, truncated` | number/bool；可选 `bytes, policy` |
| `skill_search` | 每次搜索 | `query, hits` | number；可选 `topNames, empty, stopAutoSearch, durationMs` |
| `skill_selected` | 服务端预检/模型选择记录 | `name, reason` | 可选 `score, sourceScope` |
| `skill_preflight` | 读取/调用前 | `name, status` | 可选 `missing[], platform` |
| `skill_read` | `skills_read`（**无论 flag 开关都记**） | `name, bytes` | 可选 `fullBytes, truncated, hash` |
| `skill_exec_allowed` / `skill_exec_blocked` | 闸门判定 | `name, script, route, code` | string |
| `skill_dep_install` | 用户确认安装 | `name, jobId, status` | 可选 `durationMs, exitCode` |

> 现有 `ask_user` / `tool_approval_request` / `skill_injected` 保留。中枢模式下两者作为 legacy 事件继续发出（保证旧客户端/回放），新客户端按 `interaction_open` 渲染；双发期间需在测试中断言不重复渲染。

### 6.2 HTTP / SSE 接口

| 接口 | 变更 |
|---|---|
| `GET /api/interactions?client&thread` | **新增**：返回活动交互（含 ask/审批/预览），字段同 `interaction_open` + `status/createdAt` |
| `POST /api/interactions/:id/settle` | **新增**：`{answer?, values?, skip?, decision?}`；幂等（同 id 重复提交返回第一次结果） |
| `POST /api/interactions/:id/assume` | **新增**：`{assumption}`；用户修改/撤销假设，触发修正 |
| `GET /api/agent/pending` | 保留；中枢模式下作为 `/api/interactions` 的兼容投影 |
| `POST /api/agent/answer` / `/api/agent/approval` | 保留；内部转调交互中枢 settle |

### D2 人机协作中枢（6–8 人日）

**目标**：决策 1 + 决策 2 落地。

**D2-1 服务端模型**（新增 `server/交互中枢.mjs`）

- 发 `interaction_open/updated/settled/expired/assumption`；legacy `ask_user`/`tool_approval_request` 双发（开关控制）。

**D2-2 前端模型与组件**（新增 `client/src/components/交互/`）
- `交互模型.js`：纯函数状态机 + 优先级排序（approval > confirm > clarify > review）+ 去重。

- `InteractionCard.jsx`：三类形态（澄清/确认/预览），表单/选项/自由输入/跳过（按默认假设继续）；自动聚焦规则（空闲时）；无倒计时噪声。

**D2-3 提问预算与假设**（服务端 + 提示词）

## 9. 依赖安装规范（决策 4 落地）

### 9.1 声明（SKILL.md frontmatter）

```yaml
---
name: ultimate-ppt-master
description: >-
  终极融合PPT大师 …
requires:
  runtime: [{ kind: python, version: ">=3.10" }]   # 或 node >= 20
  python: [python-pptx, cairosvg, PyMuPDF, mammoth, markdownify, ebooklib, nbconvert, Pillow, numpy, requests, beautifulsoup4, curl_cffi, google-genai, openai, PyYAML]
  npm: []                                          # 例：pptxgenjs
  exec: [python]                                   # 需要可执行的解释器/二进制
  network: true
  platform: [win32, darwin, linux]
install:
  python: requirements.txt                         # 仅提示，不自动执行
  npm: package.json
---
```

### 9.2 目录与隔离

```
<workspace>/.oaw/skill-deps/
├─ manifest.json                 # 安装台账（技能名/版本/来源/sha256/时间/解释器路径）
└─ <skill-name>/
   ├─ .venv/                     # Windows: .venv/Scripts/python.exe；POSIX: .venv/bin/python
   ├─ node_modules/              # npm 安装（--ignore-scripts）
   └─ requirements.lock          # 实际解析版本（pip freeze）
```

- **禁止**写系统 Python、全局 npm、用户 home；**禁止**改项目目录。
- 同一技能同一时刻只允许一个安装 job；安装完成前技能状态为 `installing`。

### 9.3 安装流程（只从 UI 触发）

```
技能广场/设置 显示依赖状态（ready / degraded / blocked / installing）
  ↓ 用户点击「安装到当前工作区（需确认）」
  ↓ 二次确认：目标目录 + 包清单 + 预计来源 + 不写系统目录
  ↓ POST /api/skills/:name/deps/install {confirm:true}
  ↓ 后台 job：创建 venv → pip install（逐包，失败重试≤1，120s 超时，超时转后台并返回 jobId）
  ↓ 进度事件（字节/包/状态）→ UI 可取消
  ↓ 完成：写 manifest + 复检 → 状态变 ready
  ↓ 失败：记录原因（网络/SSL/解析/平台），给出替代方案（editorial_pipeline 等）
```

### 9.4 Agent 侧硬规则（提示词 + 闸门双层）

1. Agent **不得**自行执行 `pip/pip3/uv/conda/npm/pnpm/yarn/apt/brew/winget/choco/git clone`；尝试即返回结构化错误并提示"请用户到技能广场安装"。
2. 只允许使用已 `ready` 的依赖；`blocked` 时改用产品能力（editorial_pipeline/officecli/内置 ECharts/地图工具）。
3. 安装命令不进入模型工具循环：仅 UI 触发的 server job 执行，Agent 通过 `skill_preflight` 感知状态。
4. 镜像：默认不配置；用户可在设置填写镜像源；不在代码硬编码第三方镜像。
5. 卸载：设置中"清理依赖"→ 删除目录 + manifest 记录（需确认；不删除用户文档）。

### 9.5 错误码（人话 + 可执行）

| code | 场景 | 提示 |
|---|---|---|
| `SKILL_DEP_RUNTIME_MISSING` | 无 Python/Node 或版本低 | "需要 Python ≥3.10（当前未安装）；可改用工具体内能力或在此安装" |
| `SKILL_DEP_PACKAGE_MISSING` | 包缺失 | "缺少 N 个包；点击安装（工作区隔离）" |
| `SKILL_DEP_PLATFORM_UNSUPPORTED` | POSIX-only | "该技能仅支持 macOS/Linux；当前 Windows 不建议使用" |
| `SKILL_DEP_NETWORK_BLOCKED` | SSL/代理 | "网络不可达（SSL）；可配置镜像或改用内置能力" |
| `SKILL_DEP_INSTALL_TIMEOUT` | 安装超时 | "安装超时已转后台（jobId），可在任务中心查看" |
| `SKILL_DEP_INSTALL_DENIED` | 未确认安装 | "未获用户确认，已停止安装" |

## 10. 提问预算与假设卡规范（决策 2 落地）

### 10.1 允许/禁止清单

| 情况 | 处理 |
|---|---|
| 文档类型/产物格式/必须包含的数据/覆盖范围缺失，且不猜会做错 | **允许**提问 1 张卡，合并字段（≤3 必填） |
| 篇幅/受众/风格/章节顺序/语气 | **禁止**提问；给默认假设并标注 |
| 收尾确认（是否继续/下一步/是否写回） | **禁止**提问；默认执行或给"可撤销"说明 |
| 高风险不可逆（覆盖原文件/批量删除/对外发布） | **允许** confirm 卡（不得自动继续，30 分钟超时则取消） |
| 同一主题本会话已问过 | 不再问，复用假设（工作区记忆） |

### 10.2 时间语义

| kind | 默认超时 | 超时行为 |
|---|---|---|
| clarify（澄清） | **90s** | 按 `assumption` 继续；回执写明假设；可撤销 |
| review（预览确认） | 90s | 视为"未反对"，按假设继续；保留预览入口 |
| confirm（高风险确认） | 30min | **不自动继续**；取消并提示"回来后可重试" |
| approval（工具审批） | 5min（现状） | 视为拒绝（不变） |

### 10.3 假设与可撤销

- 服务端为每个 clarify 生成 `assumption`（模型必须随提问给出；缺失时服务端用"按专业判断继续"兜底）。
- 运行中撤销：点击回执"改一下" → 打开输入，发送修正 → 作为 steer 注入当前 Run（若仍在跑）或排下一轮。
- 已完成撤销：点击"改一下" → 新建一轮修正任务（带上原假设与修正），不改历史。
- 事件：`interaction_assumption`、`interaction_settled(status=assumed)`。
- 指标：`assumed_rate`、`assumption_override_rate`（撤销率），用于调默认值。

### 10.4 提示词约束（写入写作/通用提示）

> - 只在"不猜会做错"时提问；一次只问一张卡，最多 3 个必填字段。
> - 必须随提问给出 `assumption`（默认怎么做）。篇幅、受众、风格、章节顺序不得提问。
> - 禁止提问"是否继续/下一步/是否写回"；直接执行默认动作并说明可撤销。
> - 高风险不可逆动作才用 confirm，且必须写清影响面。

## 11. 人机协作中枢模型（决策 1 落地）

### 11.1 概念

**Interaction** 是产品中一切"需要人给一个输入"的统一对象：

| kind | 来源 | 形态 |
|---|---|---|
| `clarify` | `ask_user(intent=clarify)` | 需要你补充（字段/选项/自由输入） |
| `confirm` | `ask_user(intent=confirm)`、写回原文确认 | 请确认（动作/目标/影响） |
| `review` | `ask_user(previewFile)`、草稿预览 | 草稿已就绪（预览 + 确认/改/暂不） |
| `approval` | `tool_approval_request` | 需要审批（允许一次/总是允许/拒绝） |
| `assumption` | 超时/跳过产生的假设 | 回执行（可展开/改一下） |

### 11.2 服务端数据与状态机

```json
{
  "id": "itx_...",
  "kind": "clarify",
  "status": "open",
  "clientId": "...", "threadId": "...", "runId": "...",
  "priority": 20,
  "payload": { "question": "...", "options": [], "fields": [], "previewFile": "..." },
  "createdAt": "...", "expiresAt": "...",
  "answer": null, "values": null, "assumption": "...", "settledAt": null
}
```

状态：`open → editing → submitting → settled(answered|skipped|assumed|denied|cancelled) | expired`。
约束：同一会话可多个 `open`（优先级 approval 30 > confirm 20 > clarify 10 > review 5）；同一 `runId` 同时最多 1 个 clarify；`confirm` 不得 assumed。

### 11.3 前端交互模型

- **唯一事实源**：`InteractionProvider` 维护 `interactions[]`；消息流卡片只是 detail 视图。
- **Dock**（输入框上方、队列坞之下）：最多 3 条摘要；显示"第 n/m 个"、倒计时（仅最后 5 分钟）、主按钮；点击定位卡片。
- **卡片**：三种形态；自动聚焦规则（用户空闲时聚焦问题，正在输入时不抢焦点只显示角标）；Esc 只收浮层；表单校验内联。
- **浮层**：仅当卡片离屏/会话不在前台时出现右下角非模态提醒；不打断输入。
- **审批**：并入 Dock/Card，但保留"允许一次/总是允许/拒绝"与安全文案；auto 审批策略不变。
- **恢复**：`GET /api/interactions` 对账 + SSE 补发；刷新/切会话不丢、不重复。
- **多标签**：沿用现有跨标签流租约；交互结算广播（避免两个标签各答一次）。

### 11.4 与消息流的关系

- 未决交互卡留在折叠体外常驻（ADR 0014 已定）。
- 已决交互折叠为一行回执：`已回答：…` / `已按假设继续：…（改一下）` / `已超时（confirm 未继续）`。
- 假设回执与"本轮产物/结论"并列，属于交付事实。

### 11.5 安全不变式

1. 审批类 `approval` 的拒绝永远优先于自动批准（沿用现状）。
2. `confirm` 高风险不得超时自动继续。
3. 交互结算必须校验 `clientId/threadId` 归属，防跨会话答题。
4. 幂等：同一 `interactionId` 的重复 settle 返回第一次结果，不重复续跑。
5. 事件与存储均脱敏，不写用户文档内容（只写问题/选项/答案的摘要或哈希？答案需原样回传模型；存储保留原文但沿用现有权限，不入 git）。

## 12. 写作一次成稿流程（决策 5 落地）

### 12.1 新流程

```
用户提出写作需求（含引用/材料）
  ↓ 预检（并行 <1s）：读当前文档/引用、选模板骨架、项目偏好；确定文体与产物格式
  ↓ 假设卡（不阻塞）：一次给 3–5 条默认假设（类型/篇幅/受众/风格/来源），可在正文上方一键改
  ↓ 一次成稿：直接写 Markdown 正文（不先出大纲；>8000 字或用户要求时才附可选大纲）
  ↓ 直通排版：同一份 Markdown 进 editorial_pipeline（sourceMarkdown）→ docx/pptx
  ↓ 预览即终稿：自动打开预览；用户改就重排一次，不重走流程
  ↓ 一次验收：officecli validate + 规则闸门；失败自动修一次
  ↓ 交付：3 句（做了什么/产物路径/假设与未完成项）
```

### 12.2 提示词与工具改动

- 删除 `officeWritingPlaybook` 的固定六步；改为"一次成稿 + 批处理排版 + 一次验收"。
- 禁止逐属性 `officecli set`；样式统一用一次 `batch`（先验证 batch 覆盖范围；不支持的属性按 ≤5 条/批合并）。
- 删除"草稿确认"强制 ask；保留"写回原文件确认"（不可逆）。
- 写作路由默认 thinking=medium（flag）。
- 写作路由回合预算：软 30 / 硬 60（D5）。

### 12.3 文风宪法（写入 `docs/规范/写作规范.md` 并注入提示词）

- 禁用清单：空转套话、意义拔高、重复结论、空序列（首先/其次/最后）、无主语承诺。
- 具体化：每 500 字 ≥3 个可核验事实；引用到文件与章节；无来源写"待核实"。
- 结构随文体；段落长度与信息量匹配；至少一处来自用户材料的细节。
- voice sample：`memory/style-{project}.md`（200–500 字用户旧文）；有则匹配句长/用词/开头。
- 交付自检：套话词表、重复句、段长方差、无数字段落比例；不通过重写该段。

### 12.4 验收口径

见 §20 A-33～A-38；以真实写作 10 例重放 + 3 例真实执行（用户参与）验收。

## 13. 技能策略（决策 3 落地）

### 13.1 唯一策略

- `skillsPolicy = on|off`（默认 on）：**on = 每轮注入目录，模型自行判断是否 `skills_read`/`skills_search`**；off = 不注入目录（显式 `@技能` 仍可 preflight）。
- 删除 `auto/always` 概念与设置项；旧值迁移为 on。
- **不做服务端意图分类器/强制选择器**（用户决策），但保留两类确定性能力：
  - 显式点名 → preflight（存在性/可读性/依赖状态）；
  - 依赖预检（只读）→ 给模型可用性提示与替代方案。

### 13.2 目录质量

- frontmatter 解析支持 block scalar；解析失败回退正文前 200 字。
- 预算算法：先保证所有名称（name-only），再按剩余预算补描述；`truncated` 只影响描述。
- 排序：workspace > project > user；同级按使用频次/名称；不再整条丢弃。

### 13.3 搜索质量

- OR + 打分：名称完全匹配 > 名称包含 > 名称 2-gram > 描述命中 > 别名 > 频次。
- 中文别名表（`server/技能别名.mjs`）：演示文稿/幻灯片/PPT→pptx/slide/deck；柱状图/图表→chart/echarts；审查→review/qa；公文/报告→docx/report；飞书→lark 等。
- 返回 `hitReason`；空查询返回分类清单；连续空搜返回 `stopAutoSearch`；同一 Run ≤2 次。

### 13.4 提示词规则

> - 用户点名技能 → 先 `skills_read` 全文再动手；缺失则说明原因并给替代方案。
> - 任务明显匹配某条 description → 先 `skills_read`；不确定时 `skills_search`，命中后读 1–2 个最相关技能。
> - 无命中或目录已完整且无匹配 → 直接执行主任务，不要换词反复空搜（同一轮最多 2 次）。
> - 技能需要依赖且状态 blocked → 不得自行安装，改用产品能力并说明。

## 19. 待确认的细节（不阻塞 D0）

1. **审批是否并入中枢**：本计划建议并入（同一 Dock/状态机），但保留安全语义；若希望审批保持独立，可只做"统一展示、独立逻辑"。

6. **是否保留"草稿确认"作为可选**：默认关闭；高风险/长文可由用户手动开启？
