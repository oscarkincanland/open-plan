## 1. 背景与结论

用户提供了一份「让 Review 模型按四个目标检查并汇报」的规则，原文四条 + 一句流程要求：

1. **业务是否真的跑通**：功能有没有真正跑通、有没有对应测试、有没有端到端测试（模拟用户从输入操作到最终看到导出结果的完整业务流程）去验收；
2. **代码实现是否足够优雅**：有没有多余冗余代码、有没有自己维护的很绕且后续维护成本很高的算法；
3. **有没有写完全没用的测试**：没有实际意义的测试会白白浪费后续跑测试的时间；
4. **有没有充分复用项目已有的基建**：通用组件、工具函数等有没有拿来复用，而不是自己重复写一套；
5. 审查发现问题就直接打回继续修改，全部通过后再合入分支。

结论：**可以放，但不能四条原样塞进 `npm run verify`。** 四条里 ①③ 可机器判定，进测试路径；②④ 是判断项，进评审路径；第 5 条要改写成提交门禁——本项目默认在 `develop` 直提，没有「合入分支」这个动作。

| 图中要求 | 项目现状（证据） | 判断 | 落点 |
|---|---|---|---|
| ① 业务真跑通 + 端到端 | 有 L2 分层，但真正端到端只有 GIS（HTTP 层）与 Review 修复（`:live`）；浏览器里「输入 → 导出」没有 | 可落地，最大缺口 | **G4 业务流验收**（§3.3） |
| ② 代码优雅 / 无冗余 | 已管「第二份事实源」，`代码规范` §15 有 9 条自检；「优雅」无判定口径 | 不能做成测试 | 改写成可判定三问，进评审清单（§3.4） |
| ③ 没有无用的测试 | `功能验证测试规范` §13 已列反模式，但无机器检查 | 可落地，须先基线 | **`test:test-quality`**（§3.2） |
| ④ 复用已有基建 | 契约层有强守护（能力契约 / 规范索引 / 白名单派生）；UI 与工具函数层无「能力索引」 | 部分可机器化 | 评审项 + 二期扫描（§3.4、§8） |
| ⑤ 打回再合入 | `develop` 直提，已有 §7.1 提交门禁、§8 DoD、`check:commit-gate` | 需改写 | 「评审未过 = 不得提交、不得标完成」（§3.5） |

**两条硬约束**（贯穿全计划）：

- **不新开《代码评审规范》**：四条并入现有三处规范 + PR 模板，避免第二份事实源与孤儿文档（`文档管理规范` §2/§8）；
- **不把「优雅」做成 CI 硬门禁**：主观项只进评审，机器门禁只收可判定规则。

### 1.1 统计口径（数字可复算）

```bash
grep -c '^      - name:' .github/workflows/ci.yml          # CI 步数：67
ls scripts/*测试.mjs | wc -l                               # 测试脚本：229
node -e "const s=require('./package.json').scripts;console.log(Object.keys(s).filter(k=>k.startsWith('test:')).length)"  # test:* 别名：235
grep -l 'readFileSync' scripts/*测试.mjs | wc -l           # 读源码的脚本：172
grep -l 'includes(' scripts/*测试.mjs | wc -l              # 用 includes 的脚本：123
grep -l 'assert' scripts/*测试.mjs | wc -l                 # 含 assert 的脚本：225
```

`test()` 总数 2544、`assert.*` 总数 9834（按上列脚本聚合）；无 `assert` 的 4 个脚本中，`CI运行测试.mjs` 是包装器、`界面一致性守护测试.mjs` 用 ok/fail 计数器——这两类正是「测试质量」规则必须带白名单与基线的原因。

### 1.2 一处更正

上一轮口头说明中「Review 模式工具只有 read/grep/find/ls + `review_copy`」不准确：`REVIEW_TOOLS` 还包含 `write`/`edit`（写审查报告与副本）与团队只读工具，但没有 `bash`、联网搜索、地图、记忆（`server/task.mjs`）。这不改变结论——Review 的产品定位是「依据本地规范审查材料」，不是代码评审。

### 3.2 测试路径层：`test:test-quality`

**文件**：`scripts/测试质量检查.mjs`；**别名**：`npm run test:test-quality`；**零依赖**。

| 规则 | 判定 | 默认级别 | 误伤处理 |
|---|---|---|---|
| R1 零断言用例 | `test()` 块内既无 `assert.*` 也无 `ok/fail` 调用 | 新增 → 退出 1 | 存量进基线 |
| R2 纯源码断言 | 文件内 ≥5 条断言，且读源码 / `includes(` 占比 >80% | 警告清单 | 标注「结构断言」，不判红 |
| R3 恒真断言 | `assert.ok(true)`、`assert.equal(true, true)`、`assert.equal(1, 1)` | 退出 1 | 无（明确无意义） |
| R4 重复用例名 | 跨文件同名 `test("...")` ≥2 次 | 警告 | 可能是合理复用，人工判断 |
| R5 空套件 | 0 用例且 0 断言，且不在包装器白名单 | 警告 | 白名单：`CI运行测试.mjs` |

**基线模型**（复用 G2 已验证的「签名 + 过期」思路）：`scripts/测试质量基线.json`，每条含 `id / file / signature / owner / reason / expires`。

- `--report`：只出清单，不判红（首次审计用）；
- `--update`：人工复核后写基线，**不得用来掩盖新违规**；
- 默认：新增违规 → 退出 1；已修复 → 提示从基线移除（不阻塞）；过期未清 → 退出 1。

**自测（这条是「测试的测试」，必须自己能失败）**：`node scripts/测试质量检查.mjs --self-test` 在临时目录生成 6 个夹具（零断言 / 恒真 / 源码断言为主 / 正常 / 重复名 / 空套件），断言检出与不误报，输出 `6/6`。

**接线**：

- CI 新增一步（无网络、<5s、稳定）；
- `npm run verify:flow` 加一条；
- 不进 `npm run verify`：保持 verify 的「语法 + 构建 + 冒烟」职责边界，避免继续膨胀。

**已知误伤（写进实施记录，不拍脑袋）**：`界面一致性守护测试.mjs` 无 `assert` 但用 `ok/fail` 计数器；`CI运行测试.mjs` 是包装器；部分 `:live` 脚本以退出码而非断言表达结果——全部走白名单 + 基线。

### 3.3 业务流验收层：G4

**文件**：`scripts/业务流端到端测试.mjs`；**别名**：`npm run test:e2e:live -- --flow=chat|work|review|map|canvas`。

**为什么是 `:live`**：第 ① 条要求「用户输入 → 看到导出结果」，必须有真实模型驱动工具与产物；确定性单测替代不了。按 `功能验证测试规范` §9，`:live` 默认不进 CI，发布前与触及对应模块时跑。

| 流 | 用户动作 | 断言（用户可观察） | 依赖 | 批次 |
|---|---|---|---|---|
| F1 Chat 只读 | 新建会话 → 输入只读检索 → 发送 | 终稿出现；无 `write`/`officecli` 工具卡；工作区无新增文件 | 模型 | 一 |
| F2 Work 文档 | 输入「生成一份周报 docx」→ 发送 → 打开产物面板 | Run 终态 success；产物面板出现 docx；工作区文件可打开；`artifacts_validated` 通过 | 模型 + officecli | 一 |
| F3 Review 审查 | 工作区放 fixture docx → 输入「按规范审查」→ 生成报告 | 报告与副本存在；原文内容/mtime 不变；`reviewEvidence` 含本地规范路径 | 模型 + 知识库 | 一 |
| F4 地图草稿 → 固化 | Work 地图项目 → 草稿层 → 固化 | 草稿不落正式库；固化需审批；图层可见 | 模型 + 地图数据 | 二 |
| F5 画布导出 | Work 画布 → 添加元素 → 导出 | `designs/<slug>/exports/` 有产物；预览可打开 | 模型 + 画布 | 二 |

**实现模板**：

- 浏览器交互（新建会话、输入、发送、读产物面板）：复用 `scripts/聊天界面冒烟检查.mjs` 的 Playwright 启动与选择器；
- Run 驱动与事件断言：复用 `scripts/Review修复端到端验证.mjs` 的「POST `/api/agent/prompt` → 轮询 `/api/runs` → 读事件」模式；
- 临时工作区 + `finally` 清理，不写真实工作区。

**证据**：`docs/audits/2026-11-17-四目标评审/` 记录命令、模型、耗时、断言结果；截图与日志放本地 `.oaw/`，不入库。

**失败判定**：区分「产品缺陷」与「环境不可用」——服务不可达 / 无模型凭据 → 退出码 2（跳过），**不得写成通过**（沿用 G1 约定）。

**二期可选**：本地 fake provider（OpenAI 兼容桩，只改 provider baseURL，不动 Pi 内核）把 F1–F3 变成确定性、可进 CI；需单独评估成本与收益。

### 3.4 评审层：四问 + PR 模板 + reviewer 子代理

1. **代码规范 §15 四问**：见 §3.1.2，作为人与 agent 共用的判断口径。
2. **PR 模板**：新建 `.github/pull_request_template.md`，合并复盘 §7.2 的 8 条 + 四问 + 证据段：

   ```markdown
   ## 改了什么
   ## 业务流证据（命令 / 事件 / 截图）
   ## 四问
   - [ ] 业务真的跑通（输入 → 产物）
   - [ ] 无第二事实源 / 重复实现 / 职责越界
   - [ ] 测试删掉实现会红，无零断言 / 恒真断言
   - [ ] 复用了既有组件与工具函数（列出复用了什么）
   ## 验证
   - 命令：
   - 结果：
   - 未验证：
   ```

3. **reviewer 子代理**：在 `server/子代理编排器.mjs` 的 `SUBAGENT_ROLES.reviewer.prompt` 增加输出格式要求：

   ```text
   - 业务流证据：通过/缺失
   - 第二事实源与重复实现：通过/缺失
   - 测试有效性：通过/缺失
   - 既有基建复用：通过/缺失
   判定：pass/revise/fail
   ```

   `parseVerdict` 已支持 `- 项：通过/缺失` 解析，无需改解析器；补一条单测断言四行能进 `checklist`，且 `revise` 会触发带反馈重交付（现有 `SUBAGENT_REVISE_ROUNDS = 1`）。

4. **不改产品 Review 模式**：它是「审材料」，工具含 `write`/`edit`（报告与副本）但没有 `bash`/联网/地图/记忆；把代码评审四问写进它的系统提示属于产品行为变更，需 PRD + ADR，另立计划。

### 3.5 流程层：把「打回再合入」改写成提交门禁

- 本项目默认 `develop` 直提（ADR 0020），没有「合入分支」动作；「打回」映射为：**评审 `revise`/`fail` → 不得提交、不得标记完成**；
- 已有依据：`AGENTS.md` §7.1「验证通过才允许提交」、§8 DoD、`npm run check:commit-gate`；
- 复跑顺序：目标测试 → `npm run verify` → G1（触及渲染）→ G2 → G3 → G4（发布前 / 触及业务流）；
- 本计划不建分支；如需隔离，按 §7 说明理由并取得确认后建 `wip/*`。
