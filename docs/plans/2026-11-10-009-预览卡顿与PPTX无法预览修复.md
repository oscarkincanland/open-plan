# 2026-11-10-009 预览卡顿与 PPTX 无法预览修复

> 状态：已实施（用户直接指令"尝试优化一下预览卡顿和卡死"）　基线：v0.13.25（develop）
> 关联：[偶发读取失败排查](../audits/2026-11-10-偶发读取失败排查/排查报告.md)、`DESIGN.md` §6、`会话流前端规范.md`

## 1. 现象与定位

| 用户现象 | 实测证据 | 根因 |
|---|---|---|
| 点击任何 PPTX 都"预览不了" | 打开后工具条显示 `OfficeCLI 高保真渲染（Invalid render input）`；服务端 `/api/doc/<pptx>/html` 首次转换 2.7–7.8 秒 | `PptxViewer` 的 `releaseViewer()` 把 `canvas.width/height` 归零，而 `applyCanvasSize()` 只改 CSS 尺寸 → pptxviewjs 校验 "Canvas must have positive dimensions" 失败 → 全部回退高保真 |
| 页面非常卡、有时卡死 | 空闲 5 秒内 48 个 long task、累计 4450ms 主线程占用；3 秒内 1441 次 DOM 变动，集中在两段结论的 `.markdown-body`（`<code>`/`<table>` 反复移除再添加）；服务端事件流 3 秒零增长 | `MarkdownBody` 每次渲染新建 `components={{…}}` 映射 → react-markdown 把自定义节点整体卸载重建；父级（run 卡计时等）高频重渲染时反复触发 |
| 会话列表/产物偶发"读取失败" | 6 条同源 SSE 下 `/api/sessions`、`/api/status` 12 秒超时；日志有多轮"健康检查连续失败→重启" | 浏览器同源 6 连接被长连接占满 + 服务端卡顿重启窗口（见排查报告，本次未改） |

## 2. 修改

### 块 A：Markdown 重渲染治理（`client/src/components/MarkdownBody.jsx`）

- `components` 映射改为 `useMemo`（仅依赖 `artifactIndex`），回调统一经 `handlersRef` 取最新值（`onTagClick` / `onWikilinkHover` / `onOpenFile`），避免 memo 后点击失效。
- `artifactIndex` 依赖由 `onOpenFile` 改为 `hasOpenFile`（布尔），不再因回调身份变化重算。
- 组件改为 `memo(MarkdownBody, sameMarkdownProps)`：正文、className、withToc、numberSections、artifacts 引用与"是否有打开回调"不变时不重渲染。

### 块 B：PPTX 浏览器内渲染修复（`client/src/components/PptxViewer.jsx`）

- `applyCanvasSize()` 同时设置 `canvas.width/height`（缓冲区）与 CSS 尺寸：既修掉归零导致的校验失败，也让画面不再被拉伸发虚。
- 新增 `renderSlideCompat()`：pptxviewjs 公开类与内层渲染器的 `renderSlide` 参数顺序不一致，先按文档签名调用，遇 `Invalid render input` 再按另一种顺序重试。

### 未改动（另案）

- 连接池饥饿（必需流占满 6 槽）与"超时后释放可放弃流再重试一次"：`apiControl` 已有该重试，但无可释放流时不生效；治本方案（合并必需流 / 必需流全局硬上限 + 降级轮询）需单独计划与确认。
- 服务端卡顿重启：仅有日志时间线证据，需事件循环延迟埋点定位。

## 4. 后续可选

1. 连接池治本：必需流合并或全局硬上限 + 轮询降级（需确认）。
2. 服务端事件循环延迟采样，定位"疑似卡住"的单点。
3. PPTX 首屏缓存（`首屏缓存`）在 canvas 修复后已能生效，可考虑把首帧写入 `localStorage` 以加速二次打开（需评估体积）。
