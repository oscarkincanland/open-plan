# 并发写锁与跨实例恢复修复计划

> 状态：已实施（2026-10-31，分支 `fix/concurrency-recovery`，提交 `32c039e1`）
> 日期：2026-10-31
> 来源：[多任务并发与会话切换压力测试报告](../audits/2026-10-31-多任务并发与会话切换压力测试/审查报告.md)
> 分支：`fix/session-file-flow`（从 `develop` 拉出修复分支，建议 `fix/concurrency-recovery`）
> 目标版本：下一补丁版本
> 关联需求：PRD R2/R3/R5；非功能要求中的并发可靠性、可恢复性与测试证据

## 1. 背景与目标

压力测试已验证：单任务、3 任务并发、同 client 多 thread、2 标签页 40 次切换均可完成；但暴露两个 P1 风险：

1. **跨实例恢复污染**：主服务运行期间，第二个 server 实例（如 `npm run verify` 的 3199 实例）扫描同一个 `.oaw/runs`，会把活动 Run 标记为 `recovering` 并写入 `run_recovered`。
2. **并发写冲突未真正退避**：`write`/`edit` 的 `stageWrite()` 使用立即取锁 `acquireWriteLock()`，没有走 `acquireWriteLockWithRetry()`；另一任务的 `bash` 持有工作区根锁时，文件写入会立即得到 `WRITE_CONFLICT`，只能依赖模型自己重试。

本计划要达成的结果：

- 活动 Run 不会被非 owner 的 server 实例标记为 recovering；测试/验证实例不读写生产 `.oaw/runs`。
- 同一工作区的并发任务在常见场景下不再因一次写锁冲突而失败；冲突要么被有限等待吸收，要么返回结构化、可重试的错误。
- 只读 bash 不再无谓占用工作区写锁，减少 Word/PPT/文件任务之间的互相阻挡。
- 新增可重复的回归测试，将本次压力测试的错误类型固化为验收项。

### 非目标

- 不尝试解析任意 bash 命令的写入路径；无法可靠推断时继续使用工作区根锁。
- 不改变 `WRITE_CONFLICT` 的安全语义，不允许两个任务同时改同一文件。
- 不新增公开 SSE/HTTP 事件；不改变现有 `write_started`/`write_locked`/`write_rejected` 的语义。
- 不修改 PRD/DESIGN 的产品范围；不改画布/GIS 功能。
- 不引入数据库、队列、锁服务或新依赖。

## 3. 分步修改计划

### Step 0：基线与复现（0.5 天）

**目的**：在改代码前把两个问题各复现一次，确认根因，避免修错层。

**修改内容**

1. 不修改生产代码；使用现有 API 和临时脚本：
   - 启动主服务，创建一个**长任务**（可用低 effort 的真实 Agent 任务，或直接构造一条 `status: running` 的 Run 记录）。
   - 在另一个终端启动第二个 server：`PORT=3199 node server/index.mjs`（暂不隔离 `.oaw`）。
   - 查询 `/api/runs/<id>`，记录是否出现 `run_recovered`、`status=recovering`。
2. 并发写复现：
   - Run A 执行一个会持锁的 bash 命令（例如 `node -e "setTimeout(()=>{},15000)"`，或一个真实 mutating 命令）。
   - Run B 同时调用 `write`，记录 `write_rejected` 是否**立即**出现，以及是否等待。
3. 记录命令、Run ID、事件时间线到本计划“证据”小节；不提交临时脚本或日志。

**验收**

- 能明确回答：
  - 第二个 server 是否写入了 `run_recovered`；主服务 uptime 是否稳定；
  - `write` 冲突是否发生在 `stageWrite` 的立即取锁，而不是模型层；
  - 冲突时 `error.code`、`ownerRunId`、`lockedAt` 是否可读。
- 若某一项无法复现，记录为“未证实”，后续步骤仍按防御性修复推进。

**回滚**：无代码改动。

### Step 1：Run owner 与跨实例恢复隔离（1 天）

**修改内容**

1. `server/runs.mjs`
   - 定义进程实例标识：`const RUN_OWNER = { pid: process.pid, instanceId: crypto.randomUUID() }`。
   - `beginRun()` 的 run 对象增加：
     ```js
     owner: { pid: process.pid, instanceId: RUN_OWNER.instanceId, startedAt: new Date().toISOString() }
     ```
     旧 Run 没有 `owner` 字段时保持兼容。
   - `recoverActiveRuns()` 扫描每个活动 Run 时，先判断：
     ```js
     const ownerPid = Number(run.owner?.pid || 0);
     if (ownerPid && ownerPid !== process.pid && processAlive(ownerPid)) {
       // 另一个活着的实例仍拥有该 Run，不标记 recovering
       continue;
     }
     ```
     `processAlive` 复用现有实现（`server/写入协调.mjs` 或抽到共享工具，避免重复）。
   - 恢复日志输出 owner 信息，便于诊断；**不新增事件类型**。
   - 注意：`ownerPid` 为空的旧 Run 维持当前恢复行为，保证服务重启后的恢复能力。
2. `server/index.mjs`
   - listen 后：
     ```js
     if (process.env.OAW_DISABLE_RECOVERY === "1") {
       console.warn("[runs] recovery disabled by OAW_DISABLE_RECOVERY");
     } else {
       recoverActiveRuns();
     }
     ```
     开关默认关闭；仅测试/CI 使用。
3. `scripts/验证脚本.mjs`
   - 在 `spawn` 前创建临时运行时目录：
     ```js
     const verifyRuntime = fs.mkdtempSync(path.join(os.tmpdir(), "oaw-verify-"));
     ```
   - `env` 增加：
     ```js
     OAW_RUNS_DIR: path.join(verifyRuntime, "runs"),
     OAW_WRITE_LOCK_DIR: path.join(verifyRuntime, "locks"),
     OAW_EVENT_DIR: path.join(verifyRuntime, "events"),
     OAW_DISABLE_RECOVERY: "1",
     ```
   - `finally` 中 kill server 并 `fs.rmSync(verifyRuntime, { recursive: true, force: true })`。
   - 这样 `verify` 不再读取/改写生产 `.oaw/runs`，也不会触发恢复。

**验收**

- 单元/集成：
  - 构造一个 `status: running`、`owner.pid = 当前存活 PID` 的 Run；在另一个实例语境调用 `recoverActiveRuns()`，Run 保持 running，无 `run_recovered`。
  - 构造 `owner.pid` 不存在（或旧 Run 无 owner）的 Run；恢复逻辑仍按原行为标记 recovering。
  - 主服务执行任务时运行 `npm run verify`；主 Run 不新增 `run_recovered`，`status` 不变；verify 不向生产 `.oaw/runs` 写入测试 Run。
- 命令：
  ```bash
  npm run verify
  npm run test:phase1
  node scripts/恢复隔离测试.mjs   # Step 3 新增
  ```
- 日志：第二个实例输出“跳过 owner 仍存活的 Run”，主服务 uptime 不因 verify 变化。

**风险与回滚**

- PID 复用可能把已死 Run 误判为存活；概率低，日志可见。若需更强保证，后续可增加进程启动时间或实例租约，但不在本次范围。
- 若不设置 `owner` 的旧 Run 在服务重启后被恢复，属于预期；回滚只需移除 owner 判断与 verify env。

### Step 2：写锁退避与只读 bash 分类（1.5 天）

**修改内容**

1. `server/写入协调.mjs`
   - 保留 `stageWrite` 的同步 API（兼容现有调用），内部拆出：
     ```js
     function stageWriteLocked({ token, ...args }) { /* 现有 stageWrite 主体，使用传入 token */ }
     ```
   - 新增异步：
     ```js
     export async function stageWriteWithRetry(options, { timeoutMs = 20000, intervalMs = 350, onWait } = {}) {
       const token = await acquireWriteLockWithRetry(options, { timeoutMs, intervalMs, onWait });
       try { return stageWriteLocked({ ...options, token }); }
       finally { releaseWriteLock(token); }
     }
     ```
   - `acquireWriteLockWithRetry` 增加：
     - `attempts`、`waitedMs` 统计；
     - 超时抛出的 `WriteConflictError.details` 增加 `retryable: true`、`attempts`、`waitedMs`、`ownerRunId`、`ownerThreadId`、`ownerKind`、`lockedAt`；
     - 可选 `OAW_WRITE_LOCK_TIMEOUT_MS` 读取，默认仍为 20000，避免无确认改变默认行为。
   - `stageWrite` 与 `stageWriteLocked` 的锁释放必须成对；异常路径不得留下锁文件。
2. `server/agent.mjs`
   - `managedWriteTool.writeFile`、`managedEditTool.writeFile`、子 Agent 的 `writeFile` 全部改为 `await stageWriteWithRetry(...)`。
   - 捕获 `WriteConflictError` 时保持错误抛出；确保工具错误文本含 `WRITE_CONFLICT` 和 owner 信息（模型可据此等待或改路径），不吞错。
   - `withWorkspaceWriteLock` 保持对 mutating bash 的工作区锁；不改成无锁。
3. `server/office规范/执行闸门.mjs`
   - 在 `READONLY_BASH` 增加**明确只读**命令：
     `diff`、`cmp`、`stat`、`file`、`sha256sum`、`md5sum`、`sort`、`uniq`、`cut`、`tr`、`jq`、`realpath`、`basename`、`dirname`。
   - 继续先检查 `WRITE_INDICATORS`（`>`、`>>`、`writeFile` 等），确保带重定向的命令仍视为写操作。
   - 不加入 `sed`/`awk`/`python`/`node` 的宽泛匹配；这些默认仍占工作区锁。
   - `isReadonlyBash` 仍只用于“是否占工作区写锁”，不影响审批/Office 闸门的写入判断。
4. `server/agent.mjs` bash 路径
   - 维持 `if (isReadonlyBash(effectiveCommand)) return runBash();`；新增分类后 `diff`/`wc` 等校验命令不再锁工作区。
   - 对 `bash` 工具错误保留现有 `write_rejected` 事件，不新增事件。

**验收**

- `npm run test:write-lock`：
  - 现有 5 个用例全部通过；
  - 新增：A 持有工作区锁，B 调 `stageWriteWithRetry`，A 在 600ms 后释放，B 成功且等待 ≥500ms；
  - 新增：超时后错误含 `WRITE_CONFLICT`、`retryable=true`、`attempts>1`、`waitedMs`。
- `npm run test:office-exec-gate`：
  - `isReadonlyBash("diff a.csv b.csv") === true`；
  - `isReadonlyBash("diff a.csv b.csv > out.txt") === false`；
  - `isReadonlyBash("node -e \"fs.writeFileSync(...)\"") === false`；
  - 现有 docx 生成拦截用例不回归。
- 并发场景：
  - Run A 执行只读 `diff`/`wc` 校验，Run B 同时 `write`，B 不再因 A 的工作区锁立即失败；
  - Run A 执行 mutating bash，Run B `write` 等待后成功；若超时，错误文本与 details 可读。
- `npm run verify` 通过；`npm run build` 通过。

**风险与回滚**

- 只读分类误判会让本应加锁的命令跳过锁；通过保守白名单 + `WRITE_INDICATORS` 优先 + 单测控制。回滚只需恢复 `READONLY_BASH` 原列表和 `stageWrite` 调用。
- 延长等待可能让工具调用变慢；默认仍 20s，仅通过环境变量调整，不改变默认产品行为。
- 不改变 `WRITE_CONFLICT` 的最终失败语义，避免两个任务同时写同一文件。

### Step 3：回归测试与压力脚本（1 天）

## 5. 风险与待确认决策

| 风险 | 影响 | 处理 |
|---|---|---|
| PID 复用导致误判 owner 存活 | 已死 Run 不被恢复 | 记录日志；后续可加进程启动时间/租约；本次接受 |
| 只读 bash 白名单漏项 | 少数读取命令仍占锁 | 先覆盖本次 `diff/wc` 场景；后续按实际冲突补充 |
| 延长等待导致工具慢 | 用户感知延迟 | 默认 20s 不变；仅环境变量调优 |
| 测试 server 仍可能写事件目录 | 生产事件流被污染 | verify env 隔离 `OAW_EVENT_DIR` |
| 真实模型并发测试耗时/波动 | CI 不稳定 | `test:multi-task-load` 不纳入默认 verify，发布前手工跑 |

**需要用户确认的点**

1. 是否接受默认写锁等待仍为 20 秒（通过 `OAW_WRITE_LOCK_TIMEOUT_MS` 可调），还是希望提高到 45–60 秒。
2. 是否同意新增 `test:recovery-isolation` / `test:multi-task-load` 两个测试入口（不纳入 `npm run verify` 默认路径）。
3. 修复分支命名：`fix/concurrency-recovery`（推荐）还是继续在 `fix/session-file-flow` 上叠加。
