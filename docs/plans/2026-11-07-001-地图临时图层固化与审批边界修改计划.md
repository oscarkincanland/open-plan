## 2. 目标 / 非目标 / 成功标准

### 2.1 目标

1. 地图模块成为 **Work 专属工作台**：查、画、改、固化全部在 Work 完成；Chat/Review 不再持有地图写能力。
2. 建立 **草稿图层（临时层）**：Agent 生成点/线/面 GeoJSON 后，先进入草稿区，不写 `layers/`、不改 `style.json`、不重建瓦片。
3. 建立 **用户确认固化**：用户在地图面板逐条或批量确认，填写名称/分组后转正式图层；固化为审批边界内操作，有审计。
4. 建立 **审批边界矩阵**：读、草稿、固化、导入、改样式、删层、重置、共享数据、演示数据、auto 模式各自规则明确，工具/服务端/UI/审计一致。
5. 刷新语义从"1 秒 SLA"改为"事件驱动刷新 + 手动刷新兜底"。
6. 工作区不再混入演示数据；演示数据只能作为草稿（带 demo 标记）存在，不得静默固化。

### 2.2 非目标

- 不做多用户实时协同编辑（仍是单用户本地工作台；锁/CAS 只解决单机并发）。
- 不承诺任何刷新时长 SLA；不改动 MapLibre 渲染栈；不引入数据库/消息队列。
- 不删除基础共享图层、真实数据成果（`highways.geojson` 的真实 `flow_avg/flow_max/flow_min` 保留；判断依据见 §8.3）。
- 不保留 Chat 地图能力；不为历史 Chat 地图会话恢复写能力。
- 不做"Agent 自动固化"：固化必须由用户确认（Agent 可以发起请求，但不能自动完成）。

### 2.3 成功标准

- 地图模块内看不到 Chat；Chat 会话无法调用任何地图工具（`chat` 能力计划 `routing.map = not_needed`）。
- Agent 生成一个点/线/面草稿后，地图出现草稿层、图层树"草稿层"出现条目；此时 `layers/`、`style.json`、`tiles/`、`map.config.json` 无变化。
- 用户点"确认固化"并填写名称/分组后，正式图层出现、草稿消失、`operations.jsonl` 有记录、产物面板/文件树可追溯。
- 所有写操作在审批矩阵中有明确规则；auto 模式不能绕过固化/导入/删除/重置等显式确认。
- 刷新页面或重启服务后，未确认草稿可恢复；正式文件变更后地图可通过事件或手动刷新更新（无时长承诺）。
- 工作区中没有未标注的演示数据；演示草稿固化后名称/元数据仍带"演示数据"标记。

## 4. 新交互流程（草稿层 → 用户确认固化）

### 4.1 角色与边界

- **Agent（Work）**：生成/更新/删除草稿图层；不得直接固化（只能发起固化请求，由用户审批/点击确认）。
- **用户（Work）**：查看草稿、调整显隐/定位/名称、确认固化、丢弃、全清。
- **系统**：草稿持久化到项目 `agent/drafts/`（运行时目录，非正式层）；固化走统一服务端写入函数。

### 4.2 状态机

```
                 ┌──────────────┐
   agent 生成 →  │  draft.pending│ → 用户确认固化 → formal layer（layers/ + tiles/ + config/style + operations + manifest）
                 └──────┬───────┘
                        │ 用户丢弃 / Agent 删除 / TTL 过期
                        ▼
                   draft.removed（不落正式库）
```

- 草稿只允许 `pending` 状态；固化成功后删除草稿文件；固化失败保留草稿并给出错误（可重试）。
- 同一草稿可被 Agent 更新（GeoJSON/样式/名称/可见性）；更新不改变 status。
- 固化是幂等操作：按 `draftId + revision` 防止重复固化；固化中锁住草稿。

### 4.3 端到端步骤（推荐交互）

1. 用户（Work）在地图模块，对 Agent 说："把 `data/物流点.csv` 生成点图层" / "把这段分析生成线图层" / "画一个面图层"。
2. Agent 读取数据 → 构造 GeoJSON（点/线/面）→ 调用 `map_draft_layer`（create/update）→ 服务端校验（几何类型一致、非空、中国范围内）→ 写 `agent/drafts/{draftId}.json` → 发 `map_draft_changed` 事件（摘要）。
3. 前端收到事件 → 地图渲染草稿层（临时 MapLibre layer，id 前缀 `draft-`，随 style 重载重放）；图层树"草稿层"出现条目（名称、几何类型、要素数、来源、demo 徽标、未保存角标）。
4. 用户操作：
   - 显隐/定位/删除：只影响草稿；删除需确认（轻量）。
   - "确认固化"：打开固化对话框（名称/分组/目标项目/来源/要素数/demo 提示）→ 确认 → `POST .../drafts/{id}/confirm` → 服务端复用 `importLayer`（校验 + 写 layers + 重建瓦片 + 更新 config/style + operations + manifest）→ 删除草稿 → 发 `file_changed` + `map_draft_changed(remove)`。
   - 用户也可以让 Agent 发起固化：`map_fixate_layer` → 审批卡片（显示草稿名、几何、要素数、目标项目、demo 标记）→ 用户批准 → 同一固化服务。
5. 刷新/重启：前端打开项目时 `GET .../drafts` 恢复草稿列表与地图渲染；正式文件变更按事件刷新（无 SLA）。
6. Agent 分析（heatmap/OD/等时圈/空间分析）也统一转为草稿层（保留 `source/provenance/demo`），不再依赖 `map_action` 运行时内存。

### 4.4 边界与失败处理

| 场景 | 行为 |
|---|---|
| 草稿 GeoJSON 为空 / 几何类型混用 | 拒绝创建/更新，返回可读错误 |
| 坐标越界（全球 ±180/±90 或中国 73–135E/18–54N） | 拒绝；发 `geo_out_of_range`（见 §9.8） |
| 记录数声明与实际不一致 | 拒绝；发 `data_integrity_failed` |
| 草稿体积/要素数超限 | 拒绝并提示上限（建议 20MB / 5 万要素，可配置） |
| 固化时目标图层已存在且锁定 | 拒绝；提示解除锁定 |
| 固化时目标在共享数据集 | 拒绝（除非显式新 layerId 且落在 workspace 归属） |
| 固化失败（瓦片构建/写盘错误） | 保留草稿，返回错误，不破坏现有项目；支持重试 |
| 页面刷新/服务重启 | 草稿恢复；固化中断后草稿仍在，可重试 |
| 项目删除/归档 | 草稿随项目目录归档/清理；提示用户 |
| 演示数据 | 草稿可生成；固化必须保留 demo 标记；UI 警告；导出/报告带"演示数据" |

## 5. 审批边界（D2 核心）

### 5.1 原则

1. **只读不问**：查数据、看地图、读注册表不需要审批。
2. **草稿不问**：草稿层不进入正式库、可丢弃、可重建，Agent 生成/更新/删除草稿不需要审批。
3. **正式写必问**：固化、导入、改正式图层样式/数据、删除、重置、项目生命周期变更，必须审批或用户显式确认。
4. **破坏性双确认**：覆盖/替换/删除/恢复基线/删除项目，除审批外还要 UI 二次确认（必要时输入项目名）。
5. **共享数据默认拒绝写入**：共享数据集只读；Agent 不得导入/固化/覆盖共享层；样式修改至少 ask。
6. **锁定即拒绝**：任何路径（工具/直写/REST/固化）都不得修改锁定图层。
7. **auto 不放行显式确认**：自动批准模式只能自动放行低风险、可逆、非共享的 workspace 写；固化/导入/替换/删除/重置/项目变更永远需要显式确认。
8. **UI 用户操作 = 用户已确认**：用户亲手点击的文件选择/保存/删除视为其授权；Agent 调用工具必须走审批。但 UI 的破坏性操作仍要二次确认，且服务端要求 `confirmed:true`，防止误调用/脚本调用。
9. **审计可追溯**：每次正式写记录 `operations.jsonl` / agent manifest / 事件；审批决策记录 `permissionAudit`（如开启）；审批卡片展示目标、图层、要素数、来源、demo、共享/锁定状态。

### 5.2 审批矩阵

### 5.3 auto（自动批准）模式的约束

现状：`.oaw/permissions.json` 的 `mode:"auto"` 会把所有 ask 提升为 allow（`审批策略.mjs:152-163`）。这会让 D2 形同虚设。

建议规则：

- `matchToolDecision` 增加 `toolMetadata.forceConfirm` / `destructive` / `scope` 判断：

  - 固化/导入/替换/删除/重置/项目变更/共享数据：**即使 auto 也保持 ask 或 deny**。
- `requireToolApproval` 的审批卡片字段扩展：`project, layerId, layerName, geometryType, features, source, demo, shared, locked, reason`。

## 9. 技术设计

### 9.1 草稿层数据模型（`MapDraft` v1）

```json
{
  "v": 1,
  "id": "draft-01J...",
  "project": "zhejiang-map",
  "name": "义乌物流点（草稿）",
  "geometryType": "point",
  "geojson": { "type": "FeatureCollection", "features": [] },
  "style": { "circle-color": "#2d9cdb", "circle-radius": 6 },
  "stats": { "features": 36, "bbox": [119.9, 29.2, 120.3, 29.5] },
  "provenance": {
    "source": "agent-data",
    "demo": false,
    "runId": "",
    "sessionId": "",
    "threadId": "",
    "createdAt": "2026-11-07T13:00:00.000Z",
    "updatedAt": "2026-11-07T13:00:00.000Z"
  },
  "status": "pending",
  "visible": true,
  "revision": 1
}
```

约束：

- `geometryType` ∈ `point|line|polygon`；同一草稿内所有要素几何族必须一致（Point/MultiPoint、LineString/MultiLineString、Polygon/MultiPolygon）。
- `geojson` 必须是非空 FeatureCollection；坐标 WGS84。
- 校验：全球范围 + 中国范围（经度 73–135、纬度 18–54）；越界拒绝并发 `geo_out_of_range`（若实现领域约束）。
- 记录数：若调用方提供 `expectedCount`，必须一致，否则拒绝并发 `data_integrity_failed`。
- 体积：建议上限 20MB / 5 万要素（可配置 `OAW_MAP_DRAFT_MAX_BYTES` / `MAX_FEATURES`；默认值需用户确认）。
- `demo=true` 的草稿：固化后图层名自动加"（演示数据）"或 metadata 保留 `demo:true`；UI/导出带标记。

### 9.2 存储位置与生命周期

- 目录：`office-workspace/maps/{project}/agent/drafts/`
  - `{draftId}.json`（完整草稿）
  - `manifest.jsonl`（可选：create/update/confirm/discard 审计）
- 理由：`maps/*/agent/` 已被 `.gitignore`；与"agent 生成内容归档"一致；不进入 `layers/`、不参与瓦片构建、不被 `map.config.json` 注册。
- 生命周期：
  - create → pending；update → pending；confirm → 删除草稿文件 + 正式层；discard → 删除草稿文件。
  - 服务重启：启动/打开项目时扫描 pending 草稿恢复。
  - TTL：建议 7 天未操作由后台清理（可配置）；项目归档/删除时随项目目录处理。
  - 并发：草稿文件写入使用项目级写锁（复用 `写入协调.mjs`）+ `revision` CAS；固化时锁住草稿。
- 文件树：`listProjectFiles` 需排除 `agent/drafts/`（或标记为运行时，不可 `@`），避免用户把草稿 JSON 当正式数据引用。

| 事件 | lifecycle | persist | runEvent | payload（核心） | 说明 |
|---|---|---|---|---|---|
| `map_draft_changed` | true | false | false | `{project, draftId, action:"create"\|"update"\|"remove", name, geometryType, features, demo, source, revision, updatedAt}` | 实时刷新草稿列表/图层；不落盘；前端收到后按需 GET 详情 |
| `map_draft_confirmed` | true | true | false | `{project, draftId, layerId, layerName, features, demo, runId}` | 固化成功审计；正式写另有 `file_changed` |
| `map_draft_discarded` | true | true | false | `{project, draftId, reason:"user"\|"agent"\|"ttl"}` | 丢弃审计 |
| `file_changed` | 不变 | 不变 | 不变 | 既有 | 正式文件变更刷新 |
| `write_started/write_locked` | 不变 | 不变 | 不变 | 既有 | 固化/导入写盘 |
| `geo_out_of_range` / `data_integrity_failed` | 沿用登记 | true | — | 既有 | **本次必须接入地图草稿/导入链路**（当前无发射点） |
| `map_action` | 保留 | false | false | 旧 payload | 过渡期兼容；Phase 3 后新分析走草稿，`map_action` 仅用于旧会话回放 |

- 事件注册：`server/事件注册表.mjs` 增加 3 个新事件并登记 schema（至少校验 `project/draftId/action/geometryType/features`）。
- 事件 payload 不携带完整 GeoJSON（避免大帧）；前端收到后 `GET .../drafts/:id`。
- `map_draft_changed` 不持久化（persist:false），但草稿本身持久化；刷新时可从 API 恢复。
- 写事件必须成对（现有审查发现 `map_import` N:1），固化按文件逐个 `write_started` 并在完成后 `file_changed`。

### 9.4 REST API（新增）

按现有 `/api/map/project/:name/...` 风格：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/map/project/:name/drafts` | 列表（摘要：id/name/geometryType/features/demo/status/updatedAt/visible） |
| GET | `/api/map/project/:name/drafts/:id` | 详情（完整 geojson/style/provenance） |
| POST | `/api/map/project/:name/drafts` | 创建草稿（body: name/geometryType/geojson/style/provenance/visible；校验） |
| PATCH | `/api/map/project/:name/drafts/:id` | 更新草稿（name/style/geojson/visible；revision CAS） |
| DELETE | `/api/map/project/:name/drafts/:id` | 丢弃草稿（可选 body reason） |
| POST | `/api/map/project/:name/drafts/:id/confirm` | 固化（body: name/group/visible/confirmed:true；服务端复用 `importLayer` + 审批边界；返回 layerId/features） |
| POST | `/api/map/project/:name/drafts/cleanup` | 可选：清理过期草稿（后台任务也可调用） |

- 所有写接口校验项目存在、路径合法、草稿存在、锁定/共享/坐标/记录数；错误码建议：
  - `MAP_DRAFT_NOT_FOUND`、`MAP_DRAFT_INVALID`、`MAP_DRAFT_CONFLICT`（revision）
  - `MAP_CONFIRM_REQUIRED`（缺少 `confirmed:true`）
  - `MAP_LAYER_LOCKED`、`MAP_SHARED_DENIED`、`GEO_OUT_OF_RANGE`、`DATA_INTEGRITY_FAILED`
- 响应保持 `{ok:true,...}` / `{ok:false,error,code}` 统一风格。

### 9.9 审批实现细节（伪代码）

```js
// 审批策略：新增规则（示意）
{ tool: "map_save_analysis", pattern: "*", action: "ask" },
{ tool: "map_fixate_layer", pattern: "*", action: "ask" },
{ tool: "map_fixate_layer", pattern: "shared/*", action: "deny" },
{ tool: "map_template", pattern: "*", action: "ask" },
// map_import / map_edit / map_reset / map_project_create 保持 ask；shared deny/ask

// auto 提升条件（示意）
function canAutoApprove(decision, metadata) {
  if (decision.action !== "ask") return false;
  if (metadata.forceConfirm) return false;       // 固化/导入/替换/删除/重置
  if (metadata.destructive) return false;
  if (metadata.sideEffectScope === "shared") return false;
  return true;                                    // 仅 workspace 低风险可逆写
}
```

- 工具元数据新增 `forceConfirm: true`（fixate/import/save_analysis/reset/project_create/template/replace/delete）与 `scope: "draft" | "workspace" | "shared" | "project"`。
- 审批请求 payload 增加 `detail` 字段；前端审批卡片展示。
- 服务端 `POST .../drafts/:id/confirm` 要求 `confirmed:true`，并在 body 中包含用户确认的名称/分组；Agent 工具走审批后调用同一函数（内部传 `confirmedBy:"agent-approval"`）。
- 固化函数内部再校验：锁定、共享、坐标、记录数、目标是否已存在（存在则要求 `overwrite:true` + 回收站备份）。

## 11. 验收标准

### 11.1 功能

1. Work + 地图：Agent 生成点/线/面草稿 → 地图出现草稿层、图层树"草稿层"出现条目；`layers/`、`style.json`、`tiles/`、`map.config.json` 无变化。
2. 用户确认固化 → 正式图层出现、草稿消失、`operations.jsonl` 有 `layer.import/confirm` 记录、`agent/manifest.jsonl` 有来源、`file_changed` 发出。
3. 刷新/重启 → 未确认草稿恢复；已固化图层正常显示。
4. 丢弃草稿 → 草稿文件删除、地图草稿层消失，正式层不变。
5. 演示草稿 → UI 显示"演示数据"；固化后图层名/元数据仍带 demo 标记。

### 11.2 边界

6. Chat 模式无任何地图工具；Chat 会话不能打开地图编辑模块；Review 同样不可写。
7. `map_fixate_layer`/`map_import`/`map_save_analysis`/`map_template` 必须弹审批；auto 模式不自动批准固化/导入/替换/删除/重置。
8. 共享数据集不可被导入/固化覆盖；锁定图层任何路径写入被拒。
9. 破坏性 UI 操作（覆盖/替换/删除/重置/删除项目）有二次确认；REST 缺 `confirmed:true` 返回 409。
10. 坐标越界/记录数不一致被阻断并产生对应事件。

### 11.3 刷新

11. 正式文件/草稿事件到达后前端刷新；无"1 秒"断言；手动刷新可恢复。
12. 跨会话/初始页预览不保证实时，但手动刷新后可见。

### 11.4 数据/审计

13. 工作区不再出现未标注演示数据；默认项目被跟踪文件不因运行期演示自动变化。
14. 每次固化/导入/删除/重置有操作日志与事件；审批决策可追溯。

### 11.5 回归

15. `test:map-readonly`（改写）、`test:map-project`、`test:map-import`、`test:map-canvas`、`test:map-visual`、`test:map-chat`、`test:gis-chain`、`test:gis-flags` 通过；新增 `test:map-drafts`、`test:map-approval` 通过。
16. `npm run verify` 通过；无新增失败；未跑项在交付中说明。

## 附录 D：ADR-0025 草案（待审核）

```markdown
# 0025 地图采用草稿层与显式固化审批边界

- 状态：提议
- 记录日期：2026-11-07
- 决策者：用户 / 项目负责人
- 基线：v0.13.24
- 关联：计划 2026-11-07-001、REQUIREMENTS R10、DESIGN §9.3

## 1. 背景
地图模块当前用 map_action 临时层 + map_save_analysis 保存分析结果；Chat/Work 双模式边界只在工具层成立，审批缺失，演示数据混入默认项目。

## 2. 问题
Agent 生成的临时结果无法可靠地"先预览、再确认固化"，且正式写缺少统一审批边界，存在未审批写入、共享数据污染与失败破坏项目风险。

## 3. 备选方案
- A：保留 Chat 常驻 + 在现有 map_save_analysis 上补审批（改动小，但模式边界仍分裂、临时层依赖内存态）。
- B：地图模块收敛为 Work 专属，引入草稿层 + 用户确认固化 + 审批矩阵（推荐）。
- C：全部写入都要求审批（最安全但草稿生成频繁打断，体验差）。

## 4. 决策
选择 B：地图仅 Work；Agent 生成草稿层不落正式库、免审批；固化/导入/正式写必须审批或用户显式确认；auto 模式不得自动批准固化与破坏性操作；无刷新时长承诺。

## 5. 理由
草稿层把"生成"与"采纳"分离，既保留 Agent 效率又给用户最终控制权；审批边界按可逆性/作用域分级，避免"每次生成都打断"；Work 专属消除双模式实现分叉。

## 6. 影响
- API/SSE：新增 draft 事件与 REST；map_action 过渡兼容；事件注册表更新。
- 白名单/审批：Chat 移除地图工具；新增 map_draft_layer/map_fixate_layer；审批策略与元数据更新。
- 数据：默认项目不再混入演示数据；草稿存 agent/drafts（gitignored）。
- 文档：REQUIREMENTS/DESIGN/AGENTS 同步；变更日志记录。

## 7. 不适用
不做多用户实时协同；不做刷新 SLA；不允许 Agent 自动固化；不改 MapLibre/数据管线。
```
