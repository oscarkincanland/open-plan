## 2. 问题 1：三栏宽度、对齐与 ask 卡片

### 2.1 现状（实测修正）

> 本节结论以浏览器实测为准（1280×720 视口，服务 v0.13.3）。初稿曾误判"中间对话栏固定 460px"，实测证明该令牌在当前布局下**不生效**。

真实结构（`App.jsx:1875-2077`）：

```
.app (flex, overflow hidden)
  ├─ .sidebar          274px（可拖 180–400）
  ├─ .center-area      flex: 1  ← 对话面板在这里
  │    └─ .center-chat-slot → ChatPanel
  └─ .app-canvas-slot  280–680（预览/文件/对象/工作流）
```

实测值：视口 1280 → sidebar **274** + center-area **1001**。对话区**已经是 `flex: 1` 自适应**，左右栏拖动时会自动让出/吸收空间。

| 栏 | 宽度变量 | 实测/默认 | 可拖范围 | 参与伸缩 |
|---|---|---|---|---|
| 左：会话栏 `.sidebar` | `--sidebar-w` | 274 | 180–400（`App.jsx:1872`） | `flex-shrink: 0` |
| 中：对话区 `.center-area` | — | **1001（flex: 1）** | 不可手动拖 | `flex: 1`（styles.css:432） |
| 右：画布 `.app-canvas-slot` | `--preview-w` 等 | 未打开 | 280–680（`App.jsx:2078`） | `flex: 0 0` |

**`--chat-w: 460px` 与 `.app-chat-slot` 是残留路径**：`App.jsx` 里 `.app-chat-slot` 只出现一次、且带 `.map` 类（地图模式的固定定位侧栏，宽度用 `--map-chat-w: 360px`）。正常对话路径完全不使用 `--chat-w` / `--chat-min` / `--chat-max` 这三个令牌——它们只影响地图模式与已废弃的独立列布局。

**内容宽度实测**：`.chat-body` 客户端宽 991px，左右 padding 各 64px（`--chat-gutter` 在 1280 视口下取 `5vw=64px`）→ 可用 863px；`--msg-content-max: min(100%, 720px)` 生效，消息列与输入框均 720px 居中。**也就是说大屏留白来自"内容上限 720px"这一设计选择，而不是容器被固定**。

**右栏矛盾（仍成立）**：`App.jsx:2078` 允许拖到 680px，但 `.app-preview-slot { max-width: 520px }`（styles.css:5479）——拖过 520 后手柄继续移动而栏宽不变。

### 2.2 对齐：四档左右留白并存

| 元素 | 左右留白 | 位置 |
|---|---|---|
| 消息列（`.msg-main`） | `max-width: 720px` 居中 | styles.css:8539-8545 |
| 输入框（`.chat-compose`） | 同 720px 居中，扣 `scrollbar-w` | styles.css:8593-8602 |
| 时间流 `.tl-list` | 额外 `margin-left: 5px` + `padding-left: 12px` = **17px 缩进** | styles.css:10382 |
| ask 卡片（未决） | 在 `.tl-detail` 内 → **30px 缩进** | styles.css:10427 |
| ask 事件行（已决） | 随 `.tl-list` → **17px 缩进** | styles.css:10382 |
| 本轮总结 `.sum-block` | `padding: 0 2px` | styles.css:10452 |

**结论**：消息列与输入框在宽度上是对齐的（实测输入框左缘 420、消息列内容左缘约 414，差值即滚动条补偿），但**时间流条目、未决 ask、已决 ask、总结块四者相对消息列左缘各有 17px / 30px / 17px / 2px 的偏移**。用户说的"没对齐""ask 卡片比会话窄"，就是这四档缩进造成的视觉错位。

### 2.3 ask 卡片

**结构**：`.ask-block`（styles.css:7147）本身已是卡片——`width:100%`、`border:1px solid var(--warning)`、圆角 8px、内边距 10×12。问题不在卡片，而在容器。

**渲染路径（已核实）**：未决 ask 从时间流里筛出来，单独渲染在 `.tl-list` **之外**：

- `ChatPanel.jsx:5448-5455`：`timelineInteractionItems = runTimeline.filter(item => item.kind === "ask" && !block.answer && !block.expired)`；
- `ChatPanel.jsx:5760-5762`：`.tl-elapsed` → `.tl-list` → `timelineInteractionItems.map(renderTimelineInteraction)`；
- `ChatPanel.jsx:5460`：包在 `<TimelineRow ... locked>` 里；而 `.tl-detail { margin-left: 30px }`（styles.css:10427）。

**所以 ask 卡片宽度 = 消息列宽度 − 30px**——比输入框窄 30px。这就是用户说的"宽度要跟会话宽度一致"。

**另一条路径**：已回答/已过期的 ask 会作为 `kind:"ask"` 条目留在 `runTimeline` 内、随 `.tl-list`（17px 缩进）渲染为一行事件。两条路径缩进不同（30px vs 17px），需要一并收敛。

**交互缺口**：选项按钮 `.ask-opt` 11px、输入框 `.ask-input` 12px 与规范 §4 字号表一致；但缺少"提交中"按钮态，`.ask-error` 只有 10px 单行，错误反馈偏弱。

### 2.4 方案

**方案 A（推荐）：统一四档缩进 + 内容上限可选**

1. **消除横向滚动**（最高优先，见 §5.6）：`.efn-item { min-width: 0 }` + `.chat-body { overflow-x: hidden }`。这是用户截图里横向滚动条的直接原因。
2. **收敛缩进**：
   - `.tl-list` 的 `margin-left` 归零，只保留竖线 `padding-left`（≈12px）；
   - 未决 ask 的 `.tl-detail` 在 locked 态 `margin-left: 0`，让 ask 卡片与输入框同宽；
   - `.sum-block` 的 `padding: 0 2px` 改为 0。
3. **内容上限**：把 `--msg-content-max` 从固定 720px 改为 `min(100%, 760px)` 并允许设置项覆盖（13/15/18 三档字号已有先例）。若用户希望"大屏更宽"，这一档是唯一需要调整的参数。
4. **右栏对齐**：`.app-preview-slot` 的 `max-width` 与 Resizer 的 680 对齐。

**方案 B：只做 1+2（不动内容上限）**——改动最小，解决"错位"与"横向滚动"，但大屏留白仍是 720px 上限。

**不做**：不给中间区加拖拽手柄——它已经是 `flex: 1`，再加手柄会与左右栏手柄产生三处拖拽，交互复杂度上升而收益有限。

## 3. 问题 2：「已运行 xx」

### 3.1 现状（已实现的部分）

`ChatPanel.jsx:5410-5421`：

```js
const runElapsedText = (() => {
  if (!timelinePath) return "";
  const startedMs = Date.parse(runTraceForTimeline?.startedAt || "") || 0;
  const traceDuration = Number(runTraceForTimeline?.durationMs || 0);
  const elapsed = isTaskLive
    ? (startedMs ? Math.max(0, clockNow - startedMs) : 0)
    : (traceDuration || (startedMs && runTraceForTimeline?.endedAt ? ... : 0));
  return elapsed > 0 ? `已运行 ${formatDuration(elapsed)}` : "";
})();
```

渲染（`ChatPanel.jsx:5760`）：`{runElapsedText && <div className="tl-elapsed">{runElapsedText}</div>}`，样式 `.tl-elapsed { font-size: 11px; color: var(--muted); margin: 2px 0 2px 5px; }`（styles.css:10420）。

**即：无框、一行小字、运行中实时累加 —— 用户要的"去框留字"已经做到了。**

### 3.2 三个真实缺口

**缺口 1：整条不渲染——历史轮必然触发。**
`runTraceForTimeline` 在 `timelineEventsSource.length === 0` 时为 `null`（ChatPanel.jsx:5398-5400），而 `timelineEventsSource` 在历史轮上取 `runSummary.events`。

服务端 `listRuns` 默认 `includeEvents: "latest"`（runs.mjs:1642），**只有活跃 Run 和列表第一条带 events**：

```js
const include = includeEvents === "all"
  || (includeEvents !== "none" && (ACTIVE_STATUSES.has(run.status) || index < 1));
```

→ 历史轮（非第一条、非活跃）`events` 为空 → `runTraceForTimeline = null` → `runElapsedText = ""` → **切回历史会话时「已运行」整条消失**。这正是用户说的"全部消失"。

注意此时 `m.startedAt` / `m.finishedAt` 是有的（App.jsx:1187-1188 已从 run 写入消息），只是没被使用。

**缺口 2：结束后不折叠。**
`isTaskLive` 为 false 时仍渲染同一行小字，位置在时间流最上方，**永久占位**。用户要的是"形成结论后自动折叠"。

**缺口 3：时长口径不标注。**
`formatDuration`（运行轨迹.js:617）输出"45 秒 / 3 分 12 秒 / 1 小时 2 分"，但**不区分"本轮执行时长"与"挂起等待时长"**。一个会话若跑了 2 小时但其中 1 小时在等审批，用户看到的仍是 2 小时。

### 3.3 方案

1. **兜底时长**：当 `runSummary.events` 为空但 Run 有 `startedAt`/`finishedAt` 时，直接用二者差值渲染（不依赖 trace）。一行改动，消掉"整条消失"。
2. **结束后折叠**：运行结束且本轮总结已生成时，把 `.tl-elapsed` 收进总结卡的 `本轮总结` cap 行（作为副文本，如「本轮总结 · 3 分 12 秒」），不再在时间流上方单独占行；无总结（失败/取消）时保留独立一行。这样"信息还在、框不占位"。
3. **口径标注**：若 Run 的等待时长（`waitingMs`，服务端 `budgetSnapshot` 已提供）超过总时长 30%，文案改为「已运行 2 小时（其中等待 1 小时 12 分）」。
4. **不做**：不恢复运行框、不加重试按钮、不把它做成可折叠面板——与规范 §2「没有运行框」一致。

## 4. 问题 3：会话间切换

### 4.1 现状流程（`App.jsx:1082-1220`）

```
点击会话
  ├─ 清空右栏改动/产物范围（1085-1087）
  ├─ 若工作区不同 → 先 switchWorkspace（1094-1110，含清空 tabs/文件）
  ├─ 缓存命中 → 立即 setHistoryMessages(缓存)   ← 快
  ├─ 缓存未命中 → setHistoryMessages(null)      ← 白屏
  ├─ 并行：getSession(limit 50) + listRuns(50) + resumeAgentThread
  └─ 三者回来后才 setThreadId + setHistoryMessages(新数据)
```

### 4.2 四个体验问题

| # | 问题 | 证据 |
|---|---|---|
| 1 | **白屏**：缓存未命中时 `setHistoryMessages(null)`（App.jsx:1118-1120），直到网络返回才有内容；无骨架屏、无进度提示 | App.jsx:1118-1120；全局搜索无 history skeleton |
| 2 | **缓存容量小**：LRU 只保留 8 个会话（App.jsx:1211-1215），长会话列表里第 9 个开始必然白屏 | App.jsx:1211 |
| 3 | **滚动位置不恢复**：切换后只按"是否在底部"决定是否 `scrollTo(bottom)`，没有"回到上次阅读位置" | ChatPanel.jsx:3911-3942 |
| 4 | **切换无过渡**：消息列表整块替换，无淡入/位移；动效只作用于时间流入场（styles.css:10383），切换瞬间是硬切 | 无 transition |

补充一个一致性风险：切换时先 `switchWorkspace` 再 `setThreadId`，若工作区切换失败会继续用旧工作区加载历史（App.jsx:1107-1110），可能显示"会话 A 的历史 + 会话 B 的工作区文件树"。

### 4.3 方案

1. **骨架屏**：缓存未命中时渲染 3–5 条 `.oaw-skeleton-block`（项目已有该组件，styles.css:181），替换 `null` 白屏；`aria-busy="true"` + `aria-live="polite"` 播报"正在载入会话"。
2. **缓存扩容 + 预取**：LRU 由 8 提到 24；侧栏 hover/聚焦 200ms 时预取该会话首页历史（复用 `getSession(limit:20)`，节流 1 次/会话/分钟）。
3. **滚动锚点**：按 `sessionId` 记录 `scrollTop`（只在"用户手动滚离底部"时记录），切回时恢复；随后若该会话仍在运行则继续跟随底部。
4. **切换过渡**：消息容器加 `opacity` 120ms 淡入（`--dur-fast`、`--ease-out`），纳入 `data-reduce-motion` 闸门。
5. **工作区不一致保护**：`switchWorkspace` 失败时**不继续加载历史**，改为提示"该会话的工作区不可用"并提供重试——避免"历史与文件树错配"。

### 4.4 补充：「加载更早的 50 条历史」为什么像没反应

用户反馈点这个按钮"加载不出来"。分三部分核查（服务端 → 前端 → 反馈）：

**① 服务端分页正常（已实测）**

用真实会话（`historyTotal: 147`）逐页验证：

| 请求 | 返回条数 | historyStart | historyEnd | hasMore |
|---|---|---|---|---|
| `?view=chat&limit=50` | 50 | 97 | 147 | true |
| `?limit=50&before=97` | 50 | 47 | 97 | true |
| `?limit=50&before=47` | 47 | 0 | 47 | false |
| `?limit=50&before=0` | 0 | 0 | 0 | false |

分页、游标推进、`hasMore` 全部正确（`server/index.mjs:4016-4025`）。**不是后端问题。**

**② 前端有三处隐患**

- **单一事实源分裂**：`loadOlderSessionHistory`（`App.jsx:1237`）把结果 `return` 给 ChatPanel，ChatPanel 只 `setMessages`（本地 state），**没有回写 App 的 `historyMessages`**。App 仍认为"这个会话只有首屏那一页"。一旦任何路径重新触发 `setHistoryMessages`，`useEffect([historyMessages])`（`ChatPanel.jsx:1351`）就会 `setMessages(normalizedHistory)` 把已加载的旧消息全部覆盖掉，并把 `messageWindowSize` 重置回 120。
- **旧页缺 run 摘要**：`loadOlderSessionHistory` 只做 `buildHistoryMessages`，**没有像首屏那样 `mergeRunSummaries`**（对比 `App.jsx:1193`）。加载出来的旧消息因此缺 `runSummary`，`associateRunMessages` 找不到本轮 Run → `runId` 缺失 → 这些轮次退回旧渲染，与首屏形态不一致。
- **静默失败/静默结束**：`handleLoadOlder`（`ChatPanel.jsx:4034-4061`）在 `!historyWindow?.hasMore` 时直接 `return`（无提示）；请求异常只弹 3.2 秒 toast；`result.messages` 为空时什么都不显示，只把按钮隐藏（`exhausted`）。用户无法区分"没有更早的历史了"和"加载失败了"。

**③ 一个可测的边界**：`before=0` 返回空 + `hasMore:false`。若游标与 `historyWindow.hasMore` 不同步（前者来自 `sessionHistoryCursorRef`，后者来自 App state），就会出现"按钮还在、点下去拿到空页、内容无变化"。

**方案**

1. **回写单一事实源**：`loadOlderSessionHistory` 成功后同时 `setHistoryMessages`（与缓存 ref 一起更新），保证 App 与 ChatPanel 对"已加载范围"认知一致。
2. **补 run 摘要**：旧页也走 `mergeRunSummaries`，与首屏同一份规则。
3. **明确反馈**：加载完成/无更多/失败三种状态都要有可见文案（例如按钮下方一行 11px 灰字"已加载 100 / 147 条"），失败提供重试。
4. **游标单一来源**：`hasMore` 只读 `historyWindow`（App state），`handleLoadOlder` 不再各自判断。

## 5. 问题 4：字体与结论排版

### 5.1 根因一：只有 400 字重，600/700 全是合成加粗

- 字体资产：`client/src/assets/fonts/misans/` 共 56 个 `@font-face`，**全部 `font-weight: 400`**（`MiSans-Regular.min.css` 逐条核对），无 Medium/Semibold/Bold 文件。
- 用量：`styles.css` 中 `font-weight: 600` **164 处**、`font-weight: 700` **70 处**。
- 后果：浏览器对中文字符做几何拉伸/描边（synthetic bold），笔画粘连、字面发糊——**这就是"字体太怪"的直接来源**。截图二里表头、截图三里"结论"二字尤其明显。

### 5.2 根因二：结论不解析 Markdown

`SummaryBlock.jsx:36`：

```jsx
<div className="sum-conclusion">{conclusion}</div>
```

纯文本插值。模型终稿的"结论"段若含 `` `PowerShell` ``、`**加粗**`、`[链接]`、路径，会**原样显示标记符**。截图三的结论里出现行内路径与英文专名，正是这个问题的表现（详细展开区走 `MarkdownBody`，结论区不走）。

### 5.3 根因三：同一屏里并存三套正文字号

| 元素 | 现值 | 位置 | 问题 |
|---|---|---|---|
| 回复正文（普通回复） | **13px** / 1.62 | styles.css:8578-8580 | 与 DESIGN 令牌 `--font-base 13` 一致 ✅ |
| 总结「详细展开」正文 | **12.5px** / 1.7 | styles.css:10460 | 不在 DESIGN 令牌内，且比回复正文小 0.5px |
| 表格 | **12px** | styles.css:1125 | 比回复正文小 1px、比总结正文小 0.5px |
| 表头 | 12px + `font-weight:600` | styles.css:1132 | 字号不足 + 合成加粗 |
| 表格布局（总结区内） | `display:block; overflow-x:auto` | styles.css:10461 | 表格脱离表格布局，不再按内容分配列宽，横向滚动条常驻 |
| 行内代码 | 等宽栈 | styles.css:1103 | 栈正确，但与中文混排时基线与字重不匹配 |

**同一轮对话里，正文可能先出现 13px，再出现 12.5px，表格又变成 12px**——阅读时字高不断跳变，"格式奇怪"由此而来。图二的表格尤其明显：表格字比上方正文小、表头又糊（合成加粗）。

### 5.4 根因四：`--msg-content-max` 与字号令牌双轨

- DESIGN §5.6 令牌：`--font-base 13 / --font-sm 12 / --font-xs 11 / --font-micro 10`。
- 会话流规范 §4 另立：14（结论）/ 12.5（正文）/ 12（条目）/ 11（元数据）。
- 代码里两套都在用，且 12.5px、14px 不在 DESIGN 令牌内 → `test:design-tokens` 目前不拦（它只查颜色），但属于"字号散值"。

### 5.5 方案

**第一步（必做）：补齐 600 字重**
- 引入 MiSans Medium/Semibold（按 `unicode-range` 分片，与现有 56 片同构），`@font-face` 声明 `font-weight: 500/600`。
- 若不便扩充字体资产：把会话流内所有 `font-weight: 600` 降为 `500`（同样会合成，效果有限）**或**改用系统栈的 `font-weight: 600`（`"Microsoft YaHei UI"` 有真 Semibold 时效果更好）。推荐前者（扩字体），因为 DESIGN §7 明确"层级只靠字号 + 字重"。

**第二步：结论渲染 Markdown（受限）**
- `.sum-conclusion` 改为渲染**行内 Markdown 子集**（粗体、行内代码、链接），**不支持块级元素**（标题/列表/表格）——结论是一段话，不是一篇文档。
- 若出现块级语法，降级为纯文本并保留首段，避免破坏版式。

**第三步：统一字号层级**
- 表格字号与正文一致（12.5px），表头用 `600`（补齐字重后不再合成）。
- 总结区表格改回 `display: table`，外层加 `overflow-x: auto` 容器（保留横向滚动但不破坏列宽）。
- 把 12.5/14 登记进 DESIGN §5.6 的字号令牌表（或改用 13/12 两档），消除双轨——**需用户裁定见 §6**。

**第四步：表格可读性**
- 表格 `line-height: 1.5`；单元格垂直居中；数字列 `font-variant-numeric: tabular-nums`。
- 行内代码在表格内降一档字号（0.92em），避免与中文正文抢视觉。

### 5.6 补充：横向滚动条根因（实测确诊）

用户反馈"恢复之后的内容还是有左右的滑轮"。用浏览器在运行中的应用里做了 DOM 注入实测（1280×720 视口）：

**测量结果**

| 元素 | 宽度 | 说明 |
|---|---|---|
| `.chat-body` clientWidth | 991 | 消息区可视宽 |
| 注入的 `.efn-item` | **1459** | 超出容器 468px |
| 注入的 `.efn-text` | **1459** | `text-overflow: ellipsis` **完全未生效** |
| `.chat-body` scrollWidth | **1523** | 出现横向滚动 |

**三个叠加成因**

1. **`.efn-item` 是 grid item 且 `min-width: auto`**。父级 `.execution-flow-embedded-notes { display: grid }`（styles.css:849）的隐式列宽由 item 的 `min-content` 决定，而 item 未声明 `min-width: 0`，于是被 `.efn-text` 的 `white-space: nowrap` 内容撑到 1459px。`.efn-text` 自己虽有 `min-width: 0`，但在被撑开的列里拿到了 1459px 宽，省略号自然不触发。

2. **`.chat-body` 只写了 `overflow-y: auto`，没写 `overflow-x`**（styles.css:695、8524）。按 CSS 规范，`overflow-x` 的 `visible` 会在另一轴为 `auto/hidden/scroll` 时被计算为 `auto` → **横向溢出直接变成可滚动**，而不是被裁剪。实测计算值确为 `overflowX: "auto"`。

3. **内容来源是常态事件**：`file_changed` 的"文件已更新：a、b、c…"（`ChatPanel.jsx:2993`）在有多个长路径时就是一条超长 nowrap 文本；历史恢复后这类条目更多，所以"恢复之后"尤其明显。

**两种修复的实测对比**

| 方案 | `.efn-text` 实测宽 | `scrollWidth` | 是否解决 |
|---|---|---|---|
| A. `.efn-item { min-width: 0 }` | 863 | 991 | ✅ 省略号生效，无溢出 |
| B. `.efn-notes { grid-template-columns: minmax(0, 1fr) }` | 863 | 991 | ✅ 同样有效 |
| C. 仅 `.chat-body { overflow-x: hidden }` | 1459 | 1523 | ❌ 只是裁剪，内容仍被切掉 |

**建议**：A + C 同时做——A 修根因（省略号正常工作），C 作兜底（其它未知溢出不再出滚动条，但不会再"切掉"可见内容，因为根因已修）。

**同类风险点**（应一并自查，均为「grid/flex 容器 + 子项 nowrap」组合）：
- `.efn-item`（本次确诊）
- `.tl-row-head` 内的 `.tl-obj`（已有 `min-width: 0` ✓）
- `.ac-files` 文件名行
- `.ask-options` 长选项
- 表格（`.sum-detail` 里 `display:block` 已自带 `overflow-x:auto`，属预期）

## 10. 风险与回滚

| 风险 | 缓解 |
|---|---|
| `.efn-item` 加 `min-width: 0` 后，某些短文本条目被压缩得过窄 | 省略号本就只在超长时触发；短文本不会低于 min-content（`min-width: 0` 只放开下限，不强制收缩） |
| `.chat-body` 加 `overflow-x: hidden` 掩盖其它未发现的溢出 | 必须与 L-01 的根因修复同做；并在验收里明确"内容不得被裁切" |
| 补字体增加包体（当前 2.1MB） | 按 `unicode-range` 分片，只补常用字 + 600 一档，预计 +1.2MB；`font-display: swap` 保留 |
| 结论渲染 Markdown 引入 XSS | 复用现有 `MarkdownBody`（已做 HTML 清洗），只开行内子集 |
| 历史分页回写 `historyMessages` 触发 effect 重置 | 回写时必须同时保持 `messageWindowSize`（不要在回写路径调用 `setMessageWindowSize(MAX_VISIBLE_MESSAGES)`） |
| 缓存扩容增加内存 | 24 个会话 × 首页 50 条，实测单会话 < 2MB；超出仍按 LRU 淘汰 |
| 字号归一导致层级感变弱 | 先在 `docs/baseline/` 存改前截图，改后逐屏对比，必要时只归一衰减过小的 12.5→12 |
| 清理死令牌影响地图模式 | `--chat-w` 系列仅 `.app-chat-slot.map` 之外的规则使用；删除前先全局搜索确认，地图模式单独回归 |

回滚：所有改动集中在 `styles.css` + 4 个组件，逐任务独立提交，可单条 revert；字体资产为新增文件，回滚时删除 `@font-face` 引用即可。

### 12.4 过程中修正的实现问题

1. **`.tl-row.locked > .tl-detail` 选择器无效**：`.tl-detail` 在 `.tl-detail-wrap` 内，必须用后代选择器。实测 ask 仍差 30px 才发现。
2. **ChatPanel 已有同名 `historyLoading` state**（历史面板切换态），新 prop 改名 `historyHydrating` 避免冲突。
3. **`updateScrollFollowState` 的 TDZ**：它定义在 3945 行，滚动恢复 effect 在 944 行，直接调用会 ReferenceError，改为内联更新 ref。
4. **App 回写 `historyMessages` 会触发 hydration effect 重置窗口/跳底部**：新增 `historyAppendPendingRef` 区分"分页追加"与"切换会话"。
5. **`.msg` 淡入动画违反动效规范 §8**（历史回放不得重播入场动画），放弃该方案，由骨架屏承担过渡。
6. **行内 Markdown 解析抽成 `.js` 纯函数**（`client/src/会话流排版.js`），否则 Node 测试无法 import `.jsx`。
