## 2. 根因拆解

### 2.1 问题 1：旧“运行结果”卡与工具过程

被中断的 Run 跨越了多条 user 消息（其中一条是 office-pipeline 的 steer 提示）。`associateRunMessages` 从摘要卡向前扫描时，把这条提示当成真实用户边界停下，摘要卡之前的 assistant（含工具过程）没有拿到该 Run 的 `runId`：

- `timelinePath` 为 false → 该 assistant 走旧 `msg-blocks`；
- 摘要卡不在 `assistantRunIds` 里 → 旧 `RunSummary` 不被抑制，图一的“运行结果”卡出现；
- 新 `ArtifactCard` 只在 `timelinePath` 分支渲染 → 该 Run 的“本轮产物”新卡不出现；
- `fields:"summary"` 让历史 Run 没有 events，旧卡即使展开也看不到工具细节，用户感知为“工具过程完全丢失”。

即：不是数据丢了，是**归属（runId）断了**，前端选错了渲染分支。

### 2.2 问题 1b：产物卡图标

`ArtifactCard` 用通用 `Icon` + `item.icon`，而 `item.icon` 是产物类型层的“语义名”（doc/xls/ppt/…），不是 `Icon.jsx` 的注册名。`doc` 未注册 → `<svg>` 不渲染，只剩 CSS 的灰底方块。文件树与旧 `RunSummary` 都用 `文件类型图标`（有 doc/xls/ppt 的彩色字形），所以看起来"文件树有图标、本轮产物没有"。

### 2.3 问题 2：会话栏/项目卡动画

运行状态只有一个来源：`/api/sessions` 返回的 `runStatus`（每个会话最新 Run 的 status）。

- 服务端 5s 缓存，且 Run 开始/结束不失效缓存；
- 客户端只在 Run 结束时刷新，开始时不刷新；
- `refreshSessions()` 无参数 → 命中缓存；
- 多个任务并行时，开始/切换/排队都不会触发列表更新，项目卡与会话行的 `runStatus` 停在旧值（绿色 completed），动画自然不跟；
- 项目卡行只有静态 `data-status` 圆点（`styles.css:5771`），没有 running 脉冲/旋转；会话列表项的脉冲又依赖 `.session-item.is-running`/marquee（`:9971`），两套表现不一致。

### 2.4 问题 4：中断仍停不下来

四条独立路径叠加：

1. **任务中心取消不 abort agent**：`/api/runs/:id/cancel` 只在 `live?.busy` 时 abort；key 不匹配（多标签页/切会话/entry 被重建）或 `busy=false`（幽灵回合、chainDepth>0、刚被 watchdog 清零）时直接 `finishRun(cancelled)`。界面显示“已取消”，agent/工具继续跑。
2. **abort 过早宣告结束**：`abort()` 在 `session.abort()` 返回后立即发 `aborted`、`busy=false`；如果当前工具不响应中断，UI 已经显示“已中断”，后台还在写文件。
3. **工具不接收 AbortSignal**：bash/officecli 的 execute 忽略了 Pi 传入的 `signal`，子进程只能等自身 timeout（bash 默认 120s、最长 600s；officecli 默认 120s）。中断后子进程继续持有写锁、继续产出文件；下一次任务可能撞锁或看到"中断后还出现了产物"。
4. **刷新后 `busy` 可能为 false**：`busy` 由历史里的最新摘要卡推导；归属失败/摘要卡缺失时 `busy=false`，停止按钮不渲染，`stop()` 直接 return，用户点了也发不出 abort。

## 3. 修改方案

### P0-1 修复 Run 归属与旧卡抑制（问题 1）

1. **internal harness 识别补齐**（`client/src/运行展示投影.js`）
   - 在 `INTERNAL_HARNESS_PREFIX` 增加 office-pipeline / 编辑流水线 / 轮次预算等实际写入文本的前缀，例如：
     - `^\s*本轮尚未使用\s*editorial_pipeline`
     - `^\s*请立即改用编辑流水线`
     - `^\s*本轮已经进行\s*\d+\s*个模型回合`
   - 更稳的长期方案：服务端注入这些提示时写入一个可识别的自定义条目/前缀（如 `[系统提醒][office-pipeline]`），历史消息按前缀识别；已有会话靠补齐正则兼容。
2. **归属边界改为 Run 时间窗**（`associateRunMessages`）
   - 从摘要卡向前扫描时，不再在第一条真实 user 消息处硬停；以摘要卡的 `startedAt`（`buildRunSummaryMessages` 已带）为下界，扫描到 `createdAt < startedAt` 或上一张摘要卡为止。
   - 容差：时间戳缺失/漂移时回退当前"最近 user 边界"逻辑；两张 Run 的时间窗重叠时以较晚的 `startedAt` 为准，避免抢消息。
   - 给 assistant 归属时同时检查它是否已被更晚的 Run 占用，避免同一消息反复改 runId。
3. **旧卡抑制与新式兜底**（`ChatPanel.jsx`）
   - Work 模式下，若摘要卡的 `runId` 已存在于 `assistantRunIds`，保持现有 `return null`；
   - 若该 Run **没有** assistant 消息（取消/失败得很早），不要退回旧 `RunSummary`，改为渲染新式紧凑摘要：`RunFoldBar` 风格头部（状态/用时/步数）+ `SummaryBlock`（结论/未完成项）+ `ArtifactCard`（产物）；Review 轮次保留旧 `RunSummary`（依据页签）。
   - 对 `cancelled/failed` 且有 timeline 的 Run，默认展开过程折叠（或至少提供“查看过程”按钮），避免"过程被折叠 = 丢失"的误判。
4. **历史过程还原**
   - 历史 `listRuns(fields:"summary")` 没有 events 是设计（省传输）；新 timeline 依赖 JSONL 的 toolCall/toolResult block。归属修好后，工具卡应出现在新的 fold 中。补一条回归：刷新一条多 user 指令的 cancelled Run，断言 `.run-fold` 内包含工具卡、页面无 `.run-summary-bubble`。
   - 若某些历史 block 缺失（旧 JSONL 只有 toolResult 没有 toolCall），在 timeline 中按 toolResult 生成“结果卡”兜底，不让过程完全消失。

### P0-2 产物图标统一（问题 1b）

- `client/src/components/会话流/ArtifactCard.jsx`：把
  `<span className="product-card-icon ..."><Icon name={item.icon} .../></span>`
  改为 `文件类型图标 file={item.path} size={15}`（与 `ChatPanel.jsx:5487` 的 RunSummary 产物行、文件树一致）。
- 保留 `artifact-kind-*` 类做背景；图标颜色/字形由 `文件类型图标` 的 `--file-*` 令牌控制，明暗主题一致。
- 备选（不推荐）：给 `Icon.jsx` 补 `doc` 字形；这会让“语义名→Icon 名”两套映射继续分叉，后续还会出现别的空白图标。
- 回归：docx/doc/xlsx/pptx/pdf/md 六类在文件树与“本轮产物”卡中的图标一致。

### P0-3 运行状态实时化（问题 2）

1. **服务端缓存失效**
   - `beginRun`（Run 开始）、`finishRun`（终态）、`requestRunCancellation`（进入取消）后调用 `invalidateSessionsListCache()`；`beginRun` 在 `runs.mjs`，由 `index.mjs`/`执行句柄` 的调用点统一包一层，或在 `listRuns` 写入后由路由失效。
   - 或者给 `/api/sessions` 增加 `live=1`（或 `fields=status`）分支，绕过缓存只返回 id/runStatus/runId；前端在运行态用轻量轮询。
2. **客户端事件触发**
   - `App.jsx` 的全局事件处理把 `run_admitted`、`run_started`、`agent_started`、`agent_queued` 纳入节流刷新（现有 `eventRefreshTimerRef` 180ms 可复用）。
   - `refreshSessions` 单飞时记录 `dirty`：当前请求在飞时又收到事件，结束后再跑一次，避免 3 个任务共用一份旧快照。
3. **本地乐观 overlay**
   - 发送受理拿到 `runId` 后，前端立即把该 thread 的 `runStatus` 置为 `running`/`queued`；`run_finished` 时置终态。
   - App 维护 `activeRunsByThread`（来自全局事件），`SessionSidebar` 合并 `sessions` 与 overlay，作为唯一显示状态；列表刷新失败也不影响动画。
4. **项目卡动画**
   - `.project-session-row.is-running` 增加与 `.session-item.is-running` 一致的脉冲/旋转图标（`session-pulse`/`icon-loading`），不只换圆点颜色；`queued/waiting_user/recovering` 也要有明确状态文案。
   - 统一走 `prefers-reduced-motion`/`data-motion-level` 闸门。

### P0-4 中断可靠性（问题 4）

1. **统一取消入口**
   - `/api/runs/:id/cancel` 改为调用 `执行句柄.中断(run.id, reason, { client: run.clientId, thread: run.threadId })`；
   - `执行句柄.中断` 内部：`requestRunCancellation` → `manager.abort(key, {runId})`（`resolveLiveEntry` 优先 exact、再按 runId）→ 结算 pending ask；
   - 只有 `manager.abort` 明确 `cancelled:false` 且 Run 已无活 entry 时才 `finishRun(cancelled)`；有 live entry/`chainDepth>0` 时保持 `cancel_requested`，让 agent 实际收尾或 watchdog 超时；
   - 返回值带 `stillRunning`/`chainDepth`，任务中心据此显示“收尾中”，不要立刻显示绿色已取消。
2. **abort 语义改为“请求中断 → 等真实收尾”**
   - `abort()` 不再立即 `busy=false`/发 `aborted`；改为设置 `entry.stopping=true`，先发 `abort_requested`（或复用 `run_draining`），结算 ask，调 runtime abort；
   - 等 `_promptEntry` 的 `finally`（promptChain 真正排空）后再 `busy=false` + `aborted`；若超过服务端上限（如 20s）仍未收尾，走 watchdog 强制收尾，同时记录 `forced`；
   - 客户端“中断中”保持到 `aborted`/`run_finished`，期间不允许把状态显示为“已中断”；若 20s 未确认，提示“后台工具仍在收尾”，而不是“已中断”。
3. **把 AbortSignal 传到工具**
   - bash：`execute: async (toolCallId, params, signal)`，`localBash.exec(..., { ...normalizeBashOptions(options), signal })`；Pi 的 `BashOperations` 已支持 signal。
   - officecli：`execute` 接收 signal，`runOfficecli(args, { signal, ... })`；`runOfficecliOnce` 监听 `signal.abort` → `child.kill('SIGTERM')`，宽限期后 `SIGKILL`；`runNativeOfficeCommand` 同样传 signal。
   - 浏览器工具/子代理已有 signal 的继续透传；`run_subagent` 的父 signal 要确保取消时终止子会话。
   - 工具 abort 后释放工作区写锁（`withWorkspaceWriteLock` 的 finally），避免下一次任务撞“文件正在被其他任务修改”。
4. **runId → entry 精确映射**
   - AgentManager 在 `_promptEntry` 开始时记录 `runEntryKeys.set(runId, key)`，finally 删除；`resolveLiveEntry(key,{runId})` 先查该映射，再查 `activeRunId`；这样切会话/entry 重建后仍能按 Run 找到正确 entry。
5. **客户端停止按钮按 live run 渲染**
   - `Message`/`ChatPanel` 的 `busy` 不再只由摘要卡推导：用 `isTaskLive`（runStatus/activeRuns overlay）驱动停止按钮和 `stop()` 守卫；
   - 刷新/切回运行中会话时，如果 Run 仍 active，停止按钮必须出现；`stop()` 不应因为本地 `busy=false` 直接 return；
   - 失败提示区分“没有找到任务”“已受理，收尾中”“已中断”。

### P1 观测与防回归

## 5. 风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| 旧卡抑制后某些 Run 没有可读摘要 | 用户看不到结论 | 纯摘要 Run 用新式紧凑卡兜底；Review 保留旧卡 |
| 时间窗归属在时间戳缺失/漂移时误判 | 消息挂到错误的 Run | 缺失时回退现有 user 边界；重叠时以较晚 startedAt 为准；补单测 |
| abort 延后到 agent_end，UI 感觉“停不下来” | 用户重复点击 | 显示“收尾中”+ 倒计时/后台工具说明；20s 后 watchdog 强制收尾 |
| kill 子进程导致半写文件 | 文档损坏 | 现有暂存/原子写；kill 前尽量 SIGTERM；在 UI 标注“已中断，部分内容可能未完成” |
| 会话缓存失效频率上升 | `/api/sessions` 解析变多 | 只失效不重建；或提供 live=1 轻量接口 + 200ms 节流 |
| 项目卡新增动画违反动效闸门 | a11y/动效测试失败 | 复用 `session-pulse`/`prefers-reduced-motion`，登记动效令牌 |

回滚：渲染与图标改动可按文件单独 revert；缓存/事件刷新与取消路由分提交；abort signal 改动独立提交，回滚后恢复“立即标中断”的现状。
