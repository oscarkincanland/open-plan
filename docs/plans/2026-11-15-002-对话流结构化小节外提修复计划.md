# 2026-11-15-002 对话流「结构化小节外提」把过程文本渲染到消息底部修复计划

> 状态：待用户确认（提出于 2026-11-15）　基线：v0.13.25（develop @ 487b5d37 + 未提交 010/011/012 改动）　需求来源：用户反馈「前端 SSE 对话流容易把一些思考的过程渲染到下面去」

## 1. 现象与证据

用户在当前进行中的会话里看到：模型在回合中途写的长段过程文本（读起来像「思考过程」）不会出现在它发生的位置，而是被搬到整条消息的**最底部**（折叠体之后）；运行中尤其明显（内容一出现就沉底）。

现场取证（浏览器实测当前进行中的 Run，DOM 顺序）：

- 运行中的 assistant 消息结构：`.tl-list.is-live`（时间流，含 `.tl-row` 思考行、`.tool-card`、`.textblock` 阶段小结）→ 其后才是 `.tl-lifted-sections`。
- `.tl-lifted-sections` 里的内容全部是**回合中段的过程文本**，例如：
  - 「现在用 editorial_pipeline 生成 PPTX。sourceMarkdown 传上面内容。参数会很长，可能截断…」（536 字）
  - 「4 个板建好。现在写内容，每页 7-9 元素。P3 章节页…」（869 字）
  - 「继续 P5、P6。P5 四类问题…」（278 字）
  - 英文过程旁白「The file is fixed. So the traceback is stale?? …」（865 字）等
- 已结束（取消）的相邻消息同样有 6 个 `.tl-lifted-sections` 块，内容也是中段进度文本，位置全部落在折叠体之后。

结论：不是模型顺序错，而是前端把「非播报的文本」一律外提（lift）出折叠体，再统一渲染到消息末尾，造成过程文本沉底。

## 2. 根因

`client/src/components/ChatPanel.jsx`（未提交改动）：

```js
const { foldTimelineItems, liftedTimelineItems } = useMemo(() => {
  ...
  for (const item of runTimelineView) {
    if (item?.kind === "text" && !isNarrationText(item.text)) lifted.push(item);
    else fold.push(item);
  }
```

- `isNarrationText()`（`client/src/会话流投影.js`）把「带标题/表格/列表/引用/代码块」或「≥2 行且 >200 字」「>240 字」的文本判为**结论**。模型在回合中段的长进度文本几乎都命中这几条 → 被判成「结构化结论」。
- 这些条目被 `lifted` 后，渲染在 `.tl-lifted-sections`，位置固定在时间流/折叠体之后（`ChatPanel.jsx` 渲染段），既丢失时间顺序，也在运行中造成「刚写出来的过程文本立刻跳到最底部」。
- 运行中也没有豁免：`isTaskLive` 分支只渲染 `foldTimelineItems`，外提块仍然追加在底部。

设计意图（2026-11-12）：结构化小节属于结论，不能被折进「执行过程」吞掉。问题在于判定范围过宽且位置被统一搬到末尾：**只有收尾阶段的结论小节**才该外提；回合中段的结构化文本仍属过程，应留在时间流原位。

## 3. 修复方案（最小侵入）

### 3.1 把二分逻辑提成纯函数（`client/src/会话流投影.js`）

新增 `splitRunTimelineSections(items, { live = false } = {})`：

- `live === true`：全部条目进 `fold`，`lifted` 为空——运行中整条时间流按原顺序直铺，不再有任何外提（修复「过程文本沉底」的直接观感）。
- `live === false`（收尾后）：
  - 计算 `lastProcessIndex` = 最后一个 `tool` / `subagent` / `pipeline` / `ask` / `approval` 条目；
  - 只有位于它**之后**、且 `isNarrationText(text) === false` 的 `text` 条目外提（收尾结论小节）；
  - 其余全部留在 `fold`（过程原位）。
- 保持既有返回形状 `{ foldTimelineItems, liftedTimelineItems }` 与渲染容器 `.tl-lifted-sections` 不变。

### 3.2 ChatPanel 接入

`ChatPanel.jsx` 的 `useMemo` 改为调用该纯函数（依赖加 `isTaskLive`），渲染分支不变（`.tl-list` + `.tl-lifted-sections`）。

### 3.3 测试

- `scripts/结构化回复折叠回归测试.mjs`：
  - 保留「折叠判定接入 `isNarrationText`」「`.tl-lifted-sections` 渲染」两条契约（断言改为指向新纯函数 + ChatPanel 调用点）；
  - 新增行为用例：①运行中（`live: true`）不外提任何文本；②中段结构化文本（最后工具之前）留在 fold；③收尾结论小节（最后工具之后的结构化文本）外提且保持原顺序。
- `scripts/会话流排版回归测试.mjs`：把两处「`foldTimelineItems` / `liftedTimelineItems` 映射」断言更新为「ChatPanel 调用 `splitRunTimelineSections`」+ 渲染容器仍在。
- `scripts/会话流时间线测试.mjs` 如受同类断言影响同步更新（以实际失败为准）。

## 4. 影响面

- 只影响 run 消息（有时间流）的折叠/外提位置；普通问答、Review 旧路径、结论卡、执行过程事件流、历史 hydration 的块顺序均不动。
- 修复后：运行中过程文本回到时间流原位；收尾后中段结构化文本随过程收进「执行过程」，只有结尾结论小节留在折叠体外。

## 5. 不做清单

- 不改 `isNarrationText` 判定阈值（避免影响「结论不被吞」的既有修复）。
- 不改折叠头/折叠体形态、结论卡（SummaryBlock）与产物卡。
- 不改服务端事件与 SSE 契约。
- 不动历史消息的 blocks 构造顺序（hydration）。
- 不提交 git（工作区仍有并行未提交改动）。
