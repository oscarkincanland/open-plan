## 3. 必须处理的四类硬冲突

### 3.1 治理模型冲突（最高优先级）

`v0.13.14` 的 `AGENTS.md` 是 **v3.0**（develop 是 v2.1），且新增 `docs/规范/GIT工作流规范.md` v1.1，声称是「分支、提交、评审、合并、打标、发布、冲突处理、仓库权限」的**唯一事实源**。两套模型核心分歧：

| 维度 | develop（本轮已按 ADR 0020 收紧） | v0.13.14 v3.0 + GIT工作流规范 v1.1 |
|---|---|---|
| 集成分支 | `develop` 启用，是默认工作面 | **`develop` 未启用**（单主线开发），当前集成线是 `integrate/v0.13.14` |
| 工作分支来源 | `develop` 拉出 | **`main` 拉出**，合并后立即删除 |
| 分支创建 | **须用户明确确认**（ADR 0020） | 未含"用户确认"要求 |
| 提交规范 | `类型(范围): 描述` | `<类型>(<范围>): <中文描述>` + 首行 ≤72 字符 + `Refs:` 脚注 |
| Git 铁律 | §7.1 提交门禁 7 条 | G-01 一次提交=一条工作流 / G-02 红灯不提交不合并不发布 / G-03 禁改写已推送历史 |

**冲突性质**：不是文字差异，是**流程模型互斥**。两者同时宣称自己权威，必须二选一。

**建议**：保留 develop 的 ADR 0020（用户刚确认的"分支需用户确认"），把 `GIT工作流规范.md` 的**可复用部分**（提交信息格式、G-01/G-03 铁律、冲突处理章节）吸收进 develop 的 `docs/规范/`，但**不采纳**其"`develop` 未启用"与"分支从 main 拉出"两条——这两条与用户"main = v0.14.x 发布线、develop = 默认工作面"的意图冲突。

## 5. 建议结论：**拆包取件，不整线合并**

整线合并要处理 27 个冲突文件，其中会话流（7）、package.json（2）、变更日志、AGENTS.md 都可以直接丢一边，但 `server/{agent,index,task,运行开关}.mjs` 这类核心文件的语义合并会反复返工。

建议改为：

1. **CAD 能力单独取件**：`server/CAD解析.mjs` + `server/CAD修改.mjs` + `CadViewer.jsx` + `CAD解析测试.mjs` + `scripts/服务监督.mjs` 的 `.env` 加载 + `server/{index,task,运行开关}.mjs` 里的 CAD 路由与开关——按 v0.13.14 的形态移植到 develop 的当前实现上。
2. **治理资产取件**：`GIT工作流规范.md`（择其可复用章节）、`当前开发进度.md`、`决策进度.md`、ADR 0014→0021、0015 直接占用。
3. **丢弃**：`ChatPanelLegacy.jsx`、会话流改名提交及其配套测试、旧 `chat-flow-layout.js` / `RunFold.jsx` / `RunFoldBar.jsx`。
