## 1. 规约的适用范围与生效方式

- 适用于本仓库全部功能开发、缺陷修复、文档与决策记录。
- 规约本身写入 `docs/规范/` 成为长期约束（见 §7 步骤 S-7），本计划在实施完 §2 后归档为实施记录。
- 冲突处理：本计划与 `AGENTS.md` 一致；与既有规范冲突时以 `AGENTS.md` 为准，并按 §7 开一份 ADR 记录本次变更理由。

### 1.1 四条线的定义

| 线 | 唯一事实来源 | 其他地方的正确角色 |
|---|---|---|
| **能力**（有哪些工具/模式可用） | `server/task.mjs` | 其他文件只能**引用**，不得复制 |
| **契约**（工具属性、事件类型） | `server/工具元数据.mjs`、`server/事件注册表.mjs` | 契约变更必须同提交同步 |
| **行为**（功能是否实现、测试是否守护） | 代码 + `scripts/` 下的测试脚本 | 文档只能描述，不得替代 |
| **状态**（做到哪、什么版本） | `版本管理计划.md` | 变更日志只描述不裁决 |

**判定规则**：任何一处文档/代码写了与另一处不一致的内容，都算缺陷；修复方向永远是"让副本回到事实源"，而不是"给副本加一段说明"。

## 3. 开发规约 R：能力线

### R-1 工具白名单只有一个事实来源

- 静态白名单只写在 `server/task.mjs`（AGENTS.md §5 已如此规定）。
- `server/agent.mjs` **不得**再出现工具名数组字面量；需要集合时从 `task.mjs` 导入或由 `toolPolicyForMode()` 派生。
- 内部工具（浏览器、编辑流水线）可以不在能力计划里，但**必须在白名单或动态注入里可追溯**（AGENTS.md §5）。

### R-2 加一个工具的完整清单（缺一不可）

新增或改名任何工具时，同一个提交内必须完成：

1. `server/agent.mjs`（或对应工具模块）定义实现；
2. `server/task.mjs` 加入需要它的模式白名单；
3. `server/工具元数据.mjs` 补 `meta(...)` 条目，含 `readOnly`/`destructive`/`sideEffectScope`/`riskLevel`/`needsApproval`/`resultBudget`；
4. 若产生新事件 → `server/事件注册表.mjs` 登记（含 payload schema）**并**在同一处发射；
5. 契约测试转绿（`scripts/工具元数据契约测试.mjs`、`scripts/能力契约测试.mjs`）。

> 本条正是 P0-1 的成因。把它写成清单，是这份规约最核心的一条。

### R-3 工具改名/删除 = 契约变更

- 改名会影响权限规则 id、事件载荷、测试断言、前端图标映射——**按架构级变更处理**，走 ADR。
- 删除工具必须同步清理：白名单、元数据表、事件注册表、图标映射（`client/src/产物类型.js` 或对应映射表）、测试断言。

## 4. 开发规约 T：测试线

### T-1 分层

| 层 | 位置 | 目的 | 要求 |
|---|---|---|---|
| 单元 | `scripts/*测试.mjs` | 纯函数/模块行为 | 覆盖边界与异常分支 |
| 契约 | `scripts/能力契约测试.mjs`、`scripts/工具元数据契约测试.mjs`、`scripts/事件注册表测试.mjs` | 跨文件事实源一致性 | **双向**：既查"该有的有没有"，也查"多出来的有没有" |
| 集成 | `scripts/Office*测试.mjs`、`scripts/写入锁并发测试.mjs` | 多模块协作 | 必须真并发或真进程，不能只断言源码字符串 |
| 端到端 | `scripts/*端到端测试.mjs`、`scripts/GIS*测试.mjs` | 用户可见路径 | 需要真实数据样本 |

### T-2 契约测试必须双向

- 只做正向覆盖会漏掉"后加的工具没登记"这类问题——P0-1 就是只做了正向的结果。
- **要求**：契约测试同时断言
  - 正向：白名单 ⊆ 元数据表；
  - 反向：元数据表 ⊆ 白名单 ∪ 显式内部工具集。

### T-3 不接受"只读源码正则"作为主要守护

- 正则断言无法发现 CSS 语法错误、懒加载 chunk 失效、真实粘贴/布局问题（这是 `docs/audits/2026-10-30-本体UI与会话负载审查/审查报告.md` A-09 的结论，至今未闭环）。
- **要求**：涉及布局/交互的验收，要么用 `getBoundingClientRect()` 之类真实测量，要么明确标注为"结构断言"并在文档里承认它不验证视觉结果。

### T-4 门禁分层（本次要落地）

| 门禁 | 内容 | 本次是否新增 |
|---|---|---|
| `npm run verify` | 语法 + 构建 + css-syntax + **契约层测试** + 关键回归 | 是：把契约层（能力/工具元数据/事件注册表）与本周新增的关键回归（写锁、恢复隔离、Office 闸门、并发回归）纳入 |
| CI | 33 步现有 + **契约层与并发回归** | 是：补 `test:harness`、写锁、恢复隔离、多任务并发回归 |
| 手动 | 浏览器视觉、L4、真实模型并发 | 保持手动，但**每次发版前跑并留证据**（`docs/audits/`） |

> 门禁薄弱的直接后果：本周 7 个 CI 红项无人发现，直到这次审计才暴露。
