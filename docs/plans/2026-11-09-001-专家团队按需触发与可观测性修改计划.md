# 专家团队按需触发与可观测性修改计划

> 文档类型：实施计划（**待批准，尚未实施**）
> 日期：2026-11-09　计划号：2026-11-09-001
> 基线：`develop @ 8a7361e9`（v0.13.24 工作线；AGENTS 2.4、ADR 0030 已入库）
> 关联：[计划 2026-11-04-014（Agent Teams 与子代理能力适配，已实施）](2026-11-04-014-AgentTeams与subagent能力适配计划.md)、[ADR-0023 专家团队采用 Team Lite 边界](../决策记录/0023-专家团队采用TeamLite边界.md)、`REQUIREMENTS.md` R2、`DESIGN.md` §7、`docs/规范/写作规范.md`（写作类团队场景）
> 本计划回答：**专家团队目前如何工作、为什么"能判断却很少主动用"，以及如何在不破坏 Team Lite 边界的前提下，让它在该用的时候更可靠地用起来。**

---

## 0. 结论先行

### 0.1 现状一句话

**当前专家团队 = "模式白名单 + 一段系统提示词 + 模型自觉"。** 工具只在 Work/Review 暴露，是否组队完全由模型判断；服务端没有建议器、没有显式入口、没有硬触发，也没有"建议但未采用"的观测。实测 555 个 Run 中仅 8 次创建团队（约 1.4%），且 7 次是用户明确点名/测试，说明**实际行为是"用户驱动"而不是"模型自主"**。

### 0.2 本计划的方案组合（推荐）

不做服务端强制组队，保留"模型决策权"，补四层使能：

| 层 | 内容 | 解决的问题 | 默认 |
|---|---|---|---|
| **A. 决策表** | 系统提示词增加"团队 vs 子代理 vs 单干"的明确判定表，替换现在一句模糊的"多角色" | 模型不知道怎么选、倾向单干 | 开（随 P0 一起） |
| **B. 建议器** | 能力计划根据任务特征给出 `team.status="suggested"` + 一行建议与原因；模型仍可拒绝 | 合适任务没有"被想起来" | 开关 `OAW_TEAM_SUGGEST`，默认关 |
| **C. 显式入口** | 输入区 `/team` 命令：`teamIntent="required"`，本轮必须使用团队；Chat 拒绝并提示切 Work | 用户想用却只能靠自然语言祈祷 | 开关 `OAW_TEAM_REQUIRED_ENTRY`，默认关 |
| **D. 可观测** | `team_started` 增加 `trigger`；新增 `team_suggested` / `team_spawn_blocked` 事件；`/api/metrics/summary` 增加团队指标 | 无法判断"建议是否被采用""团队是否空转" | 随功能一起 |

**非目标（明确不做）**：不服务端强制创建团队、不新增持久 child session、不改变 Team Lite 的 3 人/20 任务/不嵌套边界、不引入数据库/消息队列、不默认开启任何开关。

### 0.3 预期的行为变化

| 场景 | 现在 | 本计划完成后（开关开启时） |
|---|---|---|
| 用户输入 `/team` + 任务 | 无此命令；模型可能不用团队 | 本轮 `teamIntent=required`：必须先建 ≥2 个任务再 `team_spawn`，否则工具报可执行错误 |
| 多材料/批量审阅/多章节写作 | 模型通常单干 | 能力计划 `team.suggested` + 提示词一行建议；模型可采纳或说明不采纳理由 |
| 单文件修改/单步检索 | 模型可能偶发组队 | 建议器不触发；决策表明确"不用团队"；护栏阻止无任务的 `team_spawn` |
| Chat 模式 `/team` | 不适用 | 明确提示"团队只在 Work/Review 可用，请切换 Work" |
| 团队创建 | 无来源记录 | `team_started.trigger = user|suggested|model`；面板显示来源徽标 |
| 建议但未采用 | 不可见 | `team_suggested` 事件 + 指标（采纳率） |

## 1. 现状与证据

### 1.1 机制（代码事实）

| 环节 | 现状 | 证据 |
|---|---|---|
| 模式边界 | 只有 Work/Review 暴露 `team_*`；Chat 无工具、只读查看历史团队 | `server/task.mjs:36/53`；`agent.mjs:4971-4973`（`teamModeAllowed`） |
| 能力计划 | `team` 只是 `status:"available"`（可用、非必需），不带建议 | `server/task.mjs:458-470` |
| 系统提示词 | 仅 Work/Review 注入一段 `TEAM_TOOL_RULE`，要求"多角色并行/交接才用；简单任务不要" | `server/agent.mjs:61-62`，注入点 `:1452` |
| 工具 | `team_spawn/team_send/team_wait/team_list/team_task`；角色 scout/planner/reviewer/verifier 只读，worker 仅 Work；Review 降级 scout | `agent.mjs:5102-5220`；`团队编排器.mjs:25-33、317-322` |
| 生命周期 | 第一次 `team_spawn` 懒创建；绑定当前 Run，Run 结束/取消 `team_closed`；不跨 Run 恢复 | `agent.mjs` `ensureTeamService`；`团队编排器.mjs:209-222` |
| 限制 | 最多 3 人（Lead+2）、20 任务、消息 16KB、wait 默认 30s/上限 60s、不嵌套 | `团队编排器.mjs:17-33` |
| 观测 | 9 个 `team_*` 事件；`team_started` 载荷含 teamId/lead/mode/members/counts，**无 trigger/建议信息** | `事件注册表.mjs:94-102`；`团队编排器.mjs:209-220` |
| UI | 团队面板只读；不提供 spawn/中断/认领按钮 | `client/src/components/TeamPanel.jsx:139-142` |

| 决策依据 | 无"团队 vs 子代理"决策表；无服务端建议；无显式入口 | 全仓 grep `团队建议|teamIntent|/team` 无实现 |

### 1.2 真实使用证据（`.oaw/events`，截至 2026-11-09）

- 事件流共 555 个 Run；`team_started` 仅 **8 次**（约 1.4%）；`team_member_spawned` 14 次、`team_task_updated` 35 次、`team_closed` 7 次。
- 8 次中有 7 次的用户原话是显式指令或测试：
  - "请使用专家团队完成一个很小的只读验证……"
  - "严格按顺序使用专家团队做只读验证，不要写文件、不要用 run_subagent……"（多条）
  - "测试一下专家团功能"
  - "用智能体团队来做一个简单的任务吧"
- 另 1 次是用户追问："刚刚你没有采用这个团队来做分析吗？还是用 subagent？"——恰好证明用户感知到"没被用"。
- 结论：**模型具备使用能力，但自主触发率极低；当前团队能力实际上是"用户驱动"的。**

### 1.3 为什么会这样（根因）

| ID | 根因 | 影响 |
|---|---|---|
| T-01 | 提示词只有一句"多角色才用"，没有可执行的判定表（团队 vs 子代理 vs 单干） | 模型缺少选择依据，默认单干 |
| T-02 | 能力计划里 `team=available`，没有"本轮建议"信号 | 合适任务不会被提醒 |
| T-03 | 没有用户显式入口（无 `/team`、面板无创建按钮） | 用户想用只能靠自然语言，成功率不稳定 |
| T-04 | 团队创建无来源/建议记录，无法衡量"该用没用"或"不该用却用了" | 无法迭代提示词与阈值 |
| T-05 | 无"必须先有任务再组队"的护栏 | 可能为组队而组队，产生空团队/成本浪费 |
| T-06 | 子代理与团队的工具描述各自存在，但没有互斥指引 | 模型常常用 `run_subagent` 替代团队（用户已观察到） |

## 2. 决策落定

> 本计划实施前需新增 **ADR-0032「专家团队按需触发采用建议与显式入口」**（0031 已被创作画布占用）；以下 D1–D6 为建议决策，待用户确认后写入 ADR。

| # | 决策 | 内容 | 放弃的方案 |
|---|---|---|---|
| D1 | 保留模型决策权 | 系统只建议/提供入口，不服务端强制创建团队 | 服务端按关键词直接建团队（不可控成本） |
| D2 | `teamIntent` 三态 | `auto`（默认，模型判断）/ `suggested`（服务端建议，模型可拒绝）/ `required`（用户 `/team`，必须用） | 只有布尔“用/不用” |
| D3 | 建议器只做"轻量规则" | 依据现有任务文本/引用/附件/复杂度，纯函数、无模型调用；输出建议+原因+最少任务数 | 训练/调用模型做分类（成本与不确定性） |
| D4 | 决策表写入提示词 | 明确"≥2 个可独立认领子任务 → 团队；单次并行只读准备 → 子代理；单步 → 单干" | 继续用模糊措辞 |
| D5 | 护栏默认开 | 非 `required` 模式下，`team_spawn` 前必须已有 ≥2 个可认领任务（`team_task create` 或显式任务清单）；不满足返回可执行错误 | 硬性禁止组队（过度限制） |
| D6 | 观测最小集 | `team_started.trigger`（新增可选字段）；新增 `team_suggested`、`team_spawn_blocked` 事件；`/api/metrics/summary` 增加团队计数 | 只靠人工看会话（不可运营） |

**用户已确认项**：本会话中用户询问"是否需要提示词 / 大模型能否自己判断"，本计划按"保留判断权 + 补建议/入口"推进；具体开关默认值仍需用户在实施前确认（AGENTS §4.3）。

## 3. 目标、成功指标与非目标

### 3.1 成功指标

| 指标 | 当前基线 | 目标（P1 验收） | 数据源 |
|---|---|---|---|
| 复杂任务团队使用率（多材料/批量审阅/多章节写作） | 约 8/555（且几乎全为用户点名） | 建议开启后 ≥40%，且用户未点名场景 ≥20% | `team_suggested` / `team_started` 事件 |
| 建议采纳率 | 不可测 | ≥50%（suggested 后 1 个 Run 内出现 team_started） | 事件关联 runId |
| 简单任务误组队率 | 不可测 | ≤5%（单文件/单步任务出现团队） | `team_started` + 任务分类 |
| 空团队率（创建后无任务推进） | 不可测 | ≤10% | team_started 后无 team_task_updated |
| 用户 `/team` 成功率 | 无入口 | ≥95%（required 模式真的建团队并推进） | 验收用例 |
| 团队失败可见性 | 仅通用错误 | 100% 记录 `team_spawn_blocked` 原因 | 事件 |

### 3.2 非目标

- 不改变 Team Lite 边界（ADR-0023）：仍为 Lead+2、20 任务、不嵌套、不跨 Run。
- 不引入持久 child session / durable inbox / 跨进程；不复制 DSH 全量 Teams。
- 不做"团队自动创建"（服务端替模型决策）。
- 不默认开启任何开关；不改 Chat 只读边界（Chat 仍无团队工具）。
- 不把团队能力写进 Review 的写路径（worker 继续降级只读）。

### 4.1 PRD R2 建议追加文本（需用户确认）

**需求追加**

> - 团队按需触发：能力计划可对复杂任务给出"建议使用专家团队"（含原因与最少任务数）；建议不强制，模型可拒绝并说明理由。
> - 显式入口：Work/Review 输入区支持 `/team`，本轮 `teamIntent=required`，Agent 必须先建立 ≥2 个可认领任务再创建队友；Chat 输入 `/team` 时提示切换 Work。
> - 团队护栏：非必需模式下，创建队友前必须已有 ≥2 个可认领任务，否则返回可执行错误并记录事件。
> - 团队来源可追溯：团队创建事件记录 `trigger=user|suggested|model` 与建议原因；历史回放与团队面板显示来源。

**验收追加**

> - `/team` 后本轮必然出现团队与 ≥2 个任务；Chat 中 `/team` 被拒绝且提示切换模式。
> - 多材料/批量审阅/多章节写作任务在建议开启时出现 `team_suggested`，采纳后 `team_started.trigger=suggested`。
> - 单文件/单步任务不出现建议；强行 `team_spawn` 且无任务时被阻断并记 `team_spawn_blocked`。
> - 团队面板显示"用户指定 / 系统建议 / 模型自选"标签；关闭标签不终止团队（沿用现状）。

## 5. 设计

### 5.1 `teamIntent` 三态与数据流

```
用户输入（可选 /team）
  ↓
task payload: { teamIntent: "auto" | "required" }        ← 客户端
  ↓
planTaskCapabilities:
  teamIntent=required → capabilityPlan.team = { status:"required", minTasks:2, reasons:[...] }
  teamIntent=auto     → shouldSuggestTeam(...) ? { status:"suggested", reasons, minTasks } : { status:"available" }
  ↓
Run 上下文（entry.task.capabilityPlan.team）
  ↓
[P0] 系统提示注入一行建议/要求（含原因与最少任务数）
[P0] team_started 事件带 trigger（user/suggested/model）
[P1] /team 命令置 required；Chat 拒绝
  ↓
团队工具执行：team_task create ≥2 → team_spawn（护栏检查）
```

**说明**：`teamIntent` 不是"要不要创建"，而是"本轮对模型的约束强度"；`required` 仍由 Agent 自己调用工具创建（保留工具链与审计），只是要求必然发生且可验证。

### 5.2 建议器（纯函数）

新增 `server/团队建议.mjs`：

```js
/**
 * 是否建议本轮使用专家团队。
 * 输入全部来自已有任务字段，不调用模型、不读网络。
 * @returns {{suggested:boolean, score:number, reasons:string[], minTasks:number, signals:string[]}}
 */
export function shouldSuggestTeam({
  text = "", mode = "agent", route = "", references = [], attachments = [],
  complexity = null, hasCurrentFile = false,
} = {}) { ... }
```

**正向信号（命中累计 ≥2 才建议）**

| 信号 | 规则示例 | 理由文案 |
|---|---|---|
| 多材料 | `references.length + attachments.length ≥ 2`，或文本含"这三份/多份/批量材料" | 多份材料需要并行阅读与汇总 |
| 多章节/长文 | 文本含"多章节/分章/逐章/整本/长文/上万字" | 章节可并行起草再统一审校 |
| 撰写—审阅闭环 | 同时命中写作词与审查词（"审阅/复核/核验/校对"） | 需要独立审阅角色 |
| 批量审阅 | 文本含"批量审阅/逐条审查/全量检查"，且引用/附件 ≥1 | 批量问题适合分工 |
| 复杂任务 | `estimateTaskComplexity().level === "complex"` 且 reasons ≥2 | 任务本身复杂 |
| Review 模式 + 长材料 | `mode==="review"` 且引用/当前文件为长文档类 | Review 适合 Lead+审阅分工 |

**负向（直接不建议）**

- 单文件修改、单步检索、"读一下/看一下/解释一下"类；
- 纯问答/咨询/闲聊；
- Chat 模式（无团队工具）；
- 任务文本 <30 字且无引用/附件；
- 已显式点名 `run_subagent` 且未提团队。

**输出**：`suggested`、`score`、`reasons`（≤2 条，进提示词）、`minTasks = 2`（suggested）/`2`（required）、`signals`（进事件，便于评估）。

### 5.3 提示词决策表（替换 `TEAM_TOOL_RULE`）

**新规则草案（中文，逐条进系统提示）**

> - **专家团队与子代理的选择**：
>   1. **单干**：单文件修改、单步检索、纯问答、一次生成——直接做，不组队、不派子代理。
>   2. **子代理（`run_subagent`）**：只需一次性并行/隔离的只读准备（多份资料同时读、多个文件同时审），没有交接与共享任务板需求。
>   3. **专家团队（`team_*`）**：存在 ≥2 个可独立认领的子任务，且需要"分工 → 交接 → 汇总/审阅"（多章节写作、批量审阅、撰写—审阅—核验闭环、跨角色核验）。
> - 本轮若收到"建议使用专家团队"：先 `team_task create` ≥2 个可认领任务，再 `team_spawn` 1–2 名队友；若判断不需要，必须在正文说明原因（一句话），不要沉默跳过。
> - 本轮若用户用 `/team` 指定团队模式：必须使用团队且至少 2 个任务；不得用 `run_subagent` 替代。
> - 团队总人数最多 3（含 Lead）；不嵌套；创建后 `team_wait` 一次，不轮询；写文件仍按角色与审批。

**建议注入文案（仅当 suggested）**

> `[团队建议] 本轮任务特征适合使用专家团队：{reasons[0]}；{reasons[1]}。若采用，请先创建 ≥2 个可认领任务再 team_spawn；若判断不需要，请在最终答复中用一句话说明原因。`

**required 注入文案（`/team`）**

> `[团队要求] 用户已指定本轮必须使用专家团队（teamIntent=required）：必须先 team_task create ≥2 个可认领任务，再 team_spawn 1–2 名队友；不得用 run_subagent 替代。`

### 5.4 显式入口 `/team`

  ```js
  { insert: "/team ", label: "团队模式", hint: "要求本轮必须使用专家团队（Work/Review）" }
  ```

  - 若文本以 `/team` 开头：去掉命令文本，置本轮 `teamIntent="required"`，在输入栏上方显示可移除 chip「团队模式：必须使用」；
  - 无其它内容时仅切换状态，不发送空消息；
  - Chat 模式：提示"专家团队只在 Work/Review 可用，请切换 Work"并清空命令，不发送；
  - Review 模式允许（worker 仍降级只读）。
- 消息落库：用户消息保留 `/team` 文本？建议**不保留**（命令只作状态），但需要在消息流显示系统提示"已开启团队模式"（`pushSystem` 风格），与现有 `/chat` 命令一致。
- 统一输入面板（`composerUnified`）与旧路径都要支持：`COMPOSER_COMMANDS` 是共享常量，旧 send 命令分支需加 `/team` 处理。

### 5.5 护栏（`team_spawn` 前置检查）

新增开关 `OAW_TEAM_GUARD`（默认关；验收后建议开）：

- 在 `team_spawn` 执行前检查 `service.snapshot().tasks.length`（或可认领任务数）：
  - `teamIntent=required`：任务数 <2 → 返回错误 `TEAM_TASKS_REQUIRED`，附"先 team_task create 两个可认领任务"；
  - `teamIntent=suggested` 或 `auto`：任务数 0 → 返回错误 `TEAM_TASKS_REQUIRED`（有任务但只有 1 个时警告性放行，避免过度限制）；
  - 记录 `team_spawn_blocked` 事件（含 runId/teamIntent/taskCount/原因）。
- 不修改 `TeamService` 本身的 API；护栏只在工具层，保持编排器纯净。

### 5.6 可观测

| 变更 | 内容 |
|---|---|
| `team_started` 载荷扩展 | 新增可选 `trigger: "user"|"suggested"|"model"`、`suggestReasons: string[]`、`teamIntent`；schema 把 trigger 列入 types（仍必填 teamId/leadId/mode） |
| 新事件 `team_suggested` | Run 开始时发出：`runId, reasons[], score, minTasks, mode`，用于计算采纳率 |

### 5.7 事件契约与白名单影响

- `team_suggested` / `team_spawn_blocked` 必须登记到 `server/事件注册表.mjs` 并有真实发射点（发射点守护测试）。
- `team_started` schema 增加可选字段类型（向后兼容，不改旧回放）。
- 工具白名单不变（仍 5 个 `team_*`），不新增工具；`teamIntent` 是 task 字段而非工具字段。
- 公开 API/SSE 契约只增不改；新增事件属契约变更，需 ADR-0031 记录。

## 15. 决策（用户 2026-11-09 已拍板）

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 建议阈值 | 正向信号命中 **≥2** 才建议 |
| 2 | 命令名 | `/team` |
| 3 | required 模式与子代理 | 允许用 `run_subagent` 做并行只读准备，但团队必须 ≥2 个可认领任务，不得用子代理替代团队 |
| 4 | 护栏强度 | 非 required 模式下仅当任务数为 **0** 时阻断 `team_spawn` |
| 5 | 默认值 | `teamSuggest` / `teamGuard` / `teamRequiredEntry` **默认打开**（用户已按 AGENTS §4.3 确认；`OAW_TEAM_*=0` 回退） |
| 6 | “建议未采纳”提示 | 只在 Run 收尾给一句可操作提示，不进入过程流 |
| 7 | 指标持久化 | `.oaw/team-metrics.json` |
