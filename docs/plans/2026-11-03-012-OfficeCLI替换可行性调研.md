## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 能否把 OfficeCLI **完全**替换掉？ | **不建议，也不现实。** 它覆盖 docx/pptx/xlsx 的图表、透视表、条件格式、修订跟踪、批注、Morph/SmartArt/OLE/音视频、高保真 HTML/PNG/PDF 渲染等长尾；1:1 复刻是数年工程量，且渲染器无法用 Node 现有库等价替代。 |
| 能否用「内部编排 + 原生 OOXML」替换**大部分文本编辑**？ | **可行。** 当前已经原生覆盖 `create`（三种格式）、`view text/outline/stats`、docx 全文替换；再把高频的 `get/query/set/add`（段落、run、样式、表格、图片、批注、页眉页脚、目录、查找替换、合并）做进内部编排，可覆盖日常写作的绝大多数调用。 |
| 「很多情况卡住是 OfficeCLI 的问题」有证据吗？ | **目前日志不足以证明是超时/卡死。** 真实记录里没有 `OFFICECLI_TIMEOUT`；已观测的平均耗时约 1.1s、最大 17.7s；失败主要是参数误用（`.xls` 不支持、`--prop find:` 格式、`--compact` 与 `--json` 混用、`--before` 被忽略）。但单并发（`officeLimiter=1`）、冷启动、文件锁、`watch` 长驻命令确实可能造成“卡住”的体感，需要先补埋点再下结论。 |
| 推荐路线 | **B：内部编排优先 + OfficeCLI 长尾兜底**，不是“删掉 OfficeCLI”。先做 P0（可观测性与卡点治理），再做 P1（文本编辑原生层），最后按调用量决定 P2/P3。 |

## 1. OfficeCLI 当前职责

### 1.1 调用面

`server/office.mjs:9-12` 的文件参数命令：

```
view get set batch query watch open close save validate refresh dump
create add remove move swap delete import export
```

`.claude/skills/officecli/SKILL.md` 的完整能力包括：

- L1：`create` / `view`（outline/stats/issues/text/annotated/html/screenshot/svg/pdf/forms）/ `get` / `query` / `validate`；
- L2：`set`（属性/样式/查找替换）、`add`（段落/表格/图片/批注/图表等）、`remove/move/swap/delete`、`import/export`；
- L3：`batch`（原子多操作）、`dump`（可回放脚本）、`raw/raw-set/add-part`（XML 逃生舱）、`refresh`（目录/页码域）、`merge`（模板合并）；
- 预览/交互：`watch`（常驻预览服务器）、`unwatch`、`goto`、`mark/unmark/get-marks`、`get selected`；
- 长尾：图表、透视表、条件格式、迷你图、公式、修订跟踪、批注、表单域、保护、Morph/SmartArt/OLE/媒体、PDF 导出。

### 1.2 真实调用频次（`.oaw/events/事件流.jsonl`，33 次 officecli 调用）

| 命令 | 次数 |
|---|---:|
| `view` | 15 |
| `add` | 8 |
| `validate` | 4 |
| `query` | 3 |
| `set` | 2 |
| `create` | 1 |

结论：**读（view/query）与写（add/set）是绝对主力**；`validate` 是质量闸门；`create` 已原生。把 `view/query/add/set/validate` 做进原生层，能覆盖绝大多数文本编辑场景。

### 1.3 当前原生覆盖（`server/文档引擎.mjs`）

| 格式 | 已原生 | 仍必须 CLI |
|---|---|---|
| docx | `create`、`view text/outline/stats`、`set --find --replace`（全文替换，run 感知） | `get/query/batch/add/remove/move/swap/delete/import/export/open/close/save/validate/refresh/dump/watch`、`view html/svg/screenshot/annotated/issues/forms`、`set` 样式/属性、图表/修订/批注/表单/保护/PDF |
| xlsx | `create`、`view text/outline/stats` | `get/query/batch/add/remove/...`、`set`、图表/透视表/公式/条件格式/迷你图/PDF |
| pptx | `create`、`view text/outline/stats` | `get/query/batch/add/remove/...`、`set`、图表/Morph/SmartArt/OLE/媒体/PDF |

原生路由在 `server/office.mjs:93-103`：先跑 `runNativeOfficeCommand`，未命中或异常回退 CLI；原生路径不占 `officeLimiter`。

## 2. 「卡住」的候选根因

### 2.1 已观测的失败（不是超时）

| 时间 | 命令 | 结果 |
|---|---|---|
| 2026-11-03 09:21 | `query ... .xls table --json` | `Unsupported file type: .xls`（只支持 docx/xlsx/pptx） |
| 09:25 | `add ... --type image --prop image=.work/fig1.svg` | `'src' property is required for picture type`（参数名错误） |
| 09:26 | `add ... /body/p[@paraId=...] --type paragraph` | 段落不能嵌套在段落里 |
| 09:26 | `add ... --prop find:...` | `Invalid --prop ... expected key=value` |
| 09:26 | `add ... --before` | `officecli_failed / OFFICECLI_OPTION_IGNORED`（选项被剥离） |
| 14:53 | `query ... --compact` 与 `--json` 同用 | 参数冲突 |

这些是**参数/格式错误**，不是卡死；但模型会按“失败→改参数→再试”循环，消耗回合，体感就是“卡住”。

### 2.2 可能的真实卡点

| 候选 | 证据 | 状态 |
|---|---|---|
| 单并发排队 | `server/Pi运行时管理.mjs:43` `DEFAULT_OFFICE_CONCURRENCY = 1`；所有 CLI 调用串行 | **确定存在**；多会话/多文档时会排队 |
| 冷启动 | 每条命令 spawn 一次二进制；实测 33 次平均 1.1s，最大 17.7s | 确定存在；大文档更明显 |
| 命令超时 | `server/office.mjs:106-150` 默认 120s；超时发 `OFFICECLI_TIMEOUT` | 机制存在；当前日志 0 次 |
| 文件锁 | 检测 `being used by another process` / `sharing violation`；自动 `close` 后重试一次 | 机制存在；用户开着 WPS/Word 时必现 |
| 长驻命令 | `watch` 是预览服务器，不是一次性命令；`FILE_ARGUMENT_COMMANDS` 包含 `watch`，若模型调用会挂到 120s 超时 | **高风险**；当前没有专门拦截 |
| `open` / `save` / `refresh` 等交互命令 | 依赖 Office/WPS 进程，可能等待 | 未量化 |
| 输出过大 | `view html`/`screenshot`/`dump` 可能返回大载荷 | 未量化 |

**诚实结论**：现有日志没有抓到 OfficeCLI 超时；但单并发 + 冷启动 + 长驻 `watch` + 参数重试足以造成“很卡”的体验。需要先补 P0 埋点（每条命令的排队时长、执行时长、退出码、超时、锁等待、重试次数、输出字节），否则替换决策会建立在体感而不是数据上。

## 3. 替换选项

### 选项 A：完全内部替换（不推荐）

- 需要重写：OOXML 读写、样式继承、表格/图片/批注/页眉页脚/目录域、图表/透视表/条件格式/修订/Morph/SmartArt/OLE/媒体、渲染器（HTML/PNG/PDF）、表单/保护/签名。
- 风险：文件损坏、版式偏差、长尾能力缺失；与现有 Office 规范层/模板/验收规则全部要重做。
- 结论：**不可行**，至少不是本轮或今年内的事。

### 选项 B：内部编排优先 + CLI 长尾兜底（推荐）

- 新增 `server/文档编辑编排器.mjs`（纯 Node，不 spawn）：
  - 解包/重打包 OOXML（jszip）；
  - 解析 `document.xml` / `styles.xml` / `numbering.xml` / `header*.xml` / `footer*.xml` / `comments.xml` / `slide*.xml` / `sheet*.xml`；
  - 提供结构化编辑 API：段落、run、样式、表格、图片、批注、页眉页脚、目录、查找替换、合并；
  - 原子写：临时文件 + 校验 + rename；失败自动回滚；保留原文件备份；
  - 文件锁：复用 `写入协调.mjs` 的按文件锁；
  - 校验：`validate` 用 OpenXML schema（可选：先用结构自检 + 现有 `office规范` 验收）。
- `server/office.mjs` 路由改为：**原生编排器优先 → CLI 兜底**；保留现有 `needsCli` 能力矩阵，逐步把命令从 `requiresCli` 移到 `native`。
- CLI 只保留：`watch/mark/goto`（人工交互）、`view html/screenshot/svg/pdf`（渲染）、图表/透视/修订/Morph/SmartArt/OLE/媒体、`validate`（schema 严格校验）、`refresh`（Word 域）、`merge`（模板合并可逐步原生）。

### 选项 C：只替换“文本编辑”最小闭环（渐进）

- 先覆盖 `get/query/set/add` 的 docx 段落/run/样式/表格/图片/批注/查找替换；
- xlsx/pptx 先只做 `get/query/set` 的单元格/文本/形状；
- 其余继续 CLI。
- 这是 B 的第一阶段，适合作为 P1。

## 5. 内部编排架构（建议）

```
Agent 工具 officecli(args)
   ↓
server/office.mjs 路由
   ├─ 文档编辑编排器（新，纯 Node）
   │    ├─ 能力路由（needsNative）
   │    ├─ OOXML 解包/解析（jszip + XML）
   │    ├─ 结构化编辑（段落/run/样式/表格/图片/批注/页眉页脚/查找替换）
   │    ├─ 原子写 + 校验 + 回滚
   │    └─ 事件：office_native_started/finished/failed（新增需登记）
   └─ OfficeCLI（长尾兜底）
        ├─ watch/mark/goto（人工交互）
        ├─ 渲染（html/png/svg/pdf）
        ├─ 图表/透视/修订/Morph/SmartArt/OLE/媒体
        └─ validate/refresh/merge（逐步迁移）
```

关键约束：

- 工具名与参数形状**不变**（模型无感），只换执行引擎；
- 原生失败必须回退 CLI，不能因原生 bug 中断任务；
- 原生写必须走现有审批、按文件锁、暂存与回滚；
- 任何新事件必须先登记 `server/事件注册表.mjs`；
- 不新增数据库/微服务；只允许新增 Node 库（需用户确认，见 §8）。

## 6. 分阶段计划

### P0：先证明“卡在哪”（1–2 天）

1. 给每条 OfficeCLI 调用记录：排队等待、执行时长、退出码、`code`、是否超时、是否锁冲突、重试次数、输出字节、文档大小/格式。
2. 新增诊断接口/任务中心展示：最近 50 条 OfficeCLI 调用的 p50/p95、超时率、锁冲突率、按命令分组。
3. 拦截长驻命令：`watch` 除非带 `mark`/`get-marks`/`goto`，否则直接返回可解释错误；`open` 确认语义。
4. 把 `officeLimiter` 从 1 调到 2（需评估文件锁冲突），或按文件分桶并发。
5. 验收：连续 3 个真实写作任务，能量化“卡住”是排队、冷启动、锁、超时还是模型重试。

### P1：文本编辑原生层（1–2 周，按能力分批）

1. docx：`get/query` 段落与 run、`set` 文本/样式、`add` 段落/表格/图片、`remove/move`、批注、页眉页脚、目录、查找替换。
2. xlsx：`get/query/set` 单元格与区域、行/列插入删除、基础样式、图片。
3. pptx：`get/query/set` 形状文本、占位符、基础样式、图片、表格。
4. `validate`：先做结构自检（ZIP 完整性、必需部件、关系完整），严格 schema 仍走 CLI。
5. 每批能力必须有：单元测试（构造 OOXML → 编辑 → 回读）、真实文件回归、损坏回滚测试。

### P2：高频模板与合并（1 周）

- 模板占位符合并、目录生成、页眉页脚、页码、图片替换、批量查找替换；
- 把 `merge` 从 CLI 迁到原生（保留 CLI 兜底）。

### P3：长尾评估（按调用量）

- 只对真实高频的长尾做原生（例如某种图表），其余永久保留 CLI；
- 明确“永不替换”清单：Morph/SmartArt/OLE/媒体/高保真渲染/PDF/加密/签名。

## 8. 需要用户拍板

1. **范围**：是“替换所有文本编辑”，还是“替换高频文本编辑、保留长尾 CLI”？后者可行，前者不建议。
2. **依赖**：是否允许新增一个成熟 XML 解析库（如 `fast-xml-parser`）？现有 `文档引擎.mjs` 用正则解析 XML，做读取够用，做任意编辑不够稳。
3. **校验标准**：P1 原生写是否必须过 OpenXML schema（仍需 CLI `validate`），还是先结构自检 + 现有 Office 规范验收？
4. **并发**：`officeLimiter` 是否允许从 1 调到 2？需要接受同文件锁冲突由 `写入协调.mjs` 处理。
5. **迁移顺序**：先 docx 还是先 xlsx？建议 docx（调用量最高、模板/写作主场景）。
6. **是否先做 P0 埋点**：建议先做，否则无法证明替换后“卡住”真的减少。
