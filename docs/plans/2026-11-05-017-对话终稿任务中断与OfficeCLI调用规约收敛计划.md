## 0. 结论摘要

今天暴露的三个问题，根因不在同一层：

| 编号 | 问题 | 根因 | 优先级 |
|---|---|---|---|
| A | `think` 推理有部分被渲染成“成果/结论” | 前端把每个 `text` 块标成“阶段结论”；无权威终稿时把最后一段 `text` 当最终答复；模型存在“只输出 thinking、不输出 text”的正常 `stop` 回合；模型把 `<ask_user .../>` 写进正文 | P0 |
| B | 任务“总是自己中断” | 混合了 7 类：thinking-only 假中断、401 鉴权失败、400 thinking 配置不兼容、服务进程退出/监督器重启、45 回合硬预算、流水线/看门狗超时、用户主动取消 | P0/P1 |
| C | Office CLI 什么时候能用、为什么一开始用不了 | 路由把“既有 Office 文件 + 修改意图”误判成 `template`，模板闸门禁止 `officecli` 写；同时 `cp` 被误判成“生成 docx”；`read` 路由反而允许写 | P0 |

本计划的核心收敛：

1. **意图文本与自动上下文字段分离**：路由只读用户原始意图，不读 `[当前打开文件: ...]`、`[当前地图项目: ...]`、附件/检索上下文等自动前缀。
2. **`edit` 优先于 `template`**：既有 Office 文件 + 编辑意图必须走 `edit`，不再因为文件名里含“可行性研究”而命中模板。
3. **Office CLI 唯一判定源**：新增纯函数 `officeCliPolicy(...)`，把“模式 × 路由 × 命令 × 流水线状态”收敛成一张表，能力计划、提示词、执行闸门、测试共用。
4. **终稿边界**：只有 `assistant_final`/权威终稿进入“成果/最终答复”；thinking-only 回合显式标记 `final_text_missing`，不再用最后一段进度文本兜底。
5. **中断分类**：Run 的 `error/recovery/finalText` 归约为 `provider_auth / provider_config / service_restart / budget_hard / pipeline_timeout / watchdog / final_text_missing / user_cancel`，前端分别给出原因和动作。
6. **前序内容不重做**：006 的归档、运行宪法、工作区初始化、技能钩子，015 的消息极简、历史导轨、Tabler 图标全部保留；本计划只在其上增加边界。

## 1. 今日问题与证据

### 1.1 问题 A：think 被渲染成“成果类”

#### 1.1.1 服务端没有把 thinking 混进终稿

`server/agent.mjs:397` 的 `assistantText()` 只收集 `type === "text"`：

```js
return content.filter((part) => part?.type === "text").map((part) => String(part.text || "")).join("");
```

`agent_settled` 时 `assistant_final` 也只发这段文本（`server/agent.mjs:5083-5086`）。所以“thinking 从服务端泄漏到终稿”不是事实。

#### 1.1.2 前端把每个 `text` 块标成“阶段结论”

`client/src/会话流投影.js:169-171`：

```js
case "text":
  items.push({ kind: "text", id, cap: "阶段结论", text: String(block.text || "") });
```

但模型的 `text` 经常是过程性推理/进度播报，例如最近会话里的：

- “大纲为空，可能是标题未使用样式。我看一下正文与统计。”
- “Node 可用。我用 node 提取文档正文，以便精确定位内容。”
- “我发现了严重问题：删除操作命中了错误段落……”

这些在实时时间线里都被渲染成“阶段结论”，看起来就是成果。

#### 1.1.3 没有终稿时，最后一段进度文本被当成最终答复

`client/src/components/ChatPanel.jsx:5743-5756`：

```js
let finalTextBlockIndex = -1;
if (authoritativeFinalText) {
  // 匹配权威终稿对应的 text block
}
const finalAnswerBlockIndex = finalTextBlockIndex >= 0 ? finalTextBlockIndex : lastTextBlockIndex;
```

当 `authoritativeFinalText` 为空时，最后一个 `text` 块被当作最终答复。最近会话里 `run_ab4cadd6`、`run_395f42a2`、`run_261ad2ed` 都是这种情况：Run 状态 `completed`，但 `finalText` 为空，最后一轮 assistant 只有 thinking，没有 text。

会话 JSONL 的 assistant 元数据：

```json
{"stopReason":"stop","contentTypes":["thinking"],"text":""}
```

- `65e056a3`：thinking 6758 字，无 text
- `d55b72d3`：thinking 3261 字，无 text
- `17f40eae`：thinking 2130 字，无 text

Pi 认为这是一次正常 `stop`，OAW 正常发 `run_finished`，但前端没有权威终稿，只能拿前一段进度文本兜底，或者显示空白。用户看到的就是“推理变成了结果/任务自己中断了”。

#### 1.1.4 模型把工具标签写进正文

`run_21f4a89e` 的最终文本：

```text
写入被"篇幅"闸门拦住，必须由你的回答放行……
<ask_user question="……" options={[...]} />
```

模型没有真正调用 `ask_user`，而是把工具调用意图写进了 `text`，前端按 Markdown 原样渲染成最终答复。这是“推理/工具意图被渲染成成果”的直接案例。

#### 1.1.5 验收口径

- 有 `assistant_final` 时，成果区只显示该文本；过程性 `text` 不进入成果区。
- 没有 `assistant_final` 时，显示“本轮没有最终答复”，不能把最后一段进度文本升级为最终答复。
- thinking 块只出现在过程区，且默认折叠。
- 正文中的 `<ask_user .../>`、`<tool .../>`、`<function_calls>` 等工具标签不得按 Markdown 渲染成答复。

|---|---|---|---|
| `final_text_missing` | Run `completed`，`finalText` 为空；最后一条 assistant `contentTypes:["thinking"]`、`stopReason:"stop"` | 否，是假中断 | 补一次收尾回合；或显式显示“没有最终答复” |

| `budget_hard` | `run_132aec60`：`TURN_BUDGET_HARD`，45/45 回合，进入受限收尾 | 是，预算硬停 | Office 长任务放宽/显式继续加预算；UI 给出继续按钮 |
| `pipeline_timeout` | `run_22248d15`：`流水线 writer 阶段子会话未完成：子 Agent 执行超过 240 秒` | 是，内部子任务超时 | 路由修正后既有文档不再走流水线；新文档分批/提高超时 |
| `watchdog` | `模型连接超过 45 秒没有响应`、`模型流式输出超过 120 秒没有新事件` | 是，应用保护 | 保留保护；UI 明确“模型无响应，已中止” |
| `user_cancel` | `cancelReason: 用户在对话栏请求中断` / `用户请求取消以恢复会话` | 是，用户主动 | 保留现状；与故障分开显示 |

#### 1.2.2 会话列表状态被最近一次失败覆盖

`GET /api/sessions` 当前返回的 `runStatus` 取最近一次 Run。`run_46a803e3` 已经完成且有终稿，但 02:48 的 401 让整个会话显示 `runStatus: "failed"`。用户会以为“整个任务失败了”，实际上只是最后一次重试失败。

**建议**：会话列表同时保留 `lastRunStatus` 与 `lastSuccessfulRunAt/lastSuccessRunId`；最近一次失败时文案改成“最近一次重试失败（此前已完成）”，不要覆盖已完成事实。

#### 1.2.3 验收口径

- 七类中断在 UI 上有不同标签、不同颜色、不同动作，不能统一显示“中断/失败”。
- `final_text_missing` 必须提供“继续/重试”，不能只显示空白。
- `provider_auth` 必须提供“去设置更新 Key”的动作。
- `service_restart` 必须明确是服务重启，不是模型失败。
- 会话列表不得因为一次失败重试而抹掉上一轮成功。

### 1.3 问题 C：Office CLI 什么时候用、为什么一开始用不了

#### 1.3.1 当前实际行为

| 模式 | 是否暴露 `officecli` | 依据 |
|---|---|---|
| Chat | 否 | `READ_ONLY_TOOLS` 不含 `officecli`（`server/task.mjs:20`） |
| Work (`agent`) | 是 | `AGENT_TOOLS` 继承 `OFFICE_TOOLS`（`server/task.mjs:33`） |
| Review | 是 | `REVIEW_TOOLS` 明确包含（`server/task.mjs:31`） |
| Office（历史兼容） | 是 | `OFFICE_TOOLS`（`server/task.mjs:27`） |

| 路由 | `officecli` 定位 | 预检 | 写命令 |
|---|---|---|---|
| `edit` | preferred | 阻塞式 `checkOfficecli()`（`server/index.mjs:4820`） | 放行；闸门关闭（`server/office规范/执行闸门.mjs:268`） |
| `template` | fallback | 后台惰性预检（`server/index.mjs:4827`） | 澄清前全部写工具被拦；澄清后仍要等 `editorial_pipeline` 产出（`执行闸门.mjs:254/294`） |
| `generate` | fallback | 同上 | 同上 |
| `read` | 能力计划不声明，但 Work/Review 工具集仍可见 | 无 | **当前闸门关闭，读写都放行**（缺口） |

#### 1.3.2 为什么一开始用不了

链路：

1. 前端把当前文件拼进 `text`：
   - `client/src/components/ChatPanel.jsx:3691`：`[当前打开文件: ${selectedCurrentDoc}]`
   - `:3711`：`fullText = mentionPrefix + contextPrefix + ... + rawText`
   - `:3795`：`text: fullText`
2. 服务端用这个 `text` 做能力规划：`server/index.mjs:4818`。
3. 文件名含“可行性研究”，模板匹配命中：`server/office规范/模板匹配.mjs:17`。
4. 路由判定先模板、后编辑：`server/task.mjs:205`（template）先于 `:214`（edit）。
5. 模板路由打开 `officeFormat` 闸门（`server/运行开关.mjs:255`），随后：
   - 澄清未完成 → 所有写工具被 `CLARIFICATION_REQUIRED` 拦截（`执行闸门.mjs:254`）；
   - 澄清完成后 → `officecli create/add/set/remove` 仍被 `OFFICE_PIPELINE_REQUIRED` 拦截（`:294`）。
6. `bash cp` 也被 `DOCX_GENERATION` 的 `cp|copy|mv|move` 正则命中（`执行闸门.mjs:166`），复制副本也被当成“生成 docx”。

最小复现（当前代码）：

```text
[当前打开文件: ...可行性研究（修改稿）.docx]\n继续
→ route = template
→ shouldAsk = true
→ missing = [length, audience, source, style]

[当前打开文件: ...]\n继续修改
→ route = template（仍然）

去掉前缀：
读取一下这个文本做如下修改：1.1.名称改成……
→ route = edit
→ shouldAsk = false
```

#### 1.3.3 Office CLI 本身能改

`run_d58e8aa6` 走 `edit` 路由：

```text
officecli set "松阳/2...（修改稿）.docx" / --find "浙西南（松阳）零碳货运基础设施保障工程" --replace "..." --json
→ success, 6 matched
```

所以 CLI 能力没有问题；问题在路由和闸门。

#### 1.3.4 结构性编辑风险

`run_22248d15` 用 `remove /body/p[305]` 这类段落序号删除，前面的编辑导致索引漂移，误删图 5-8、图 5-11、图 5-12 和部分正文。**Office CLI 要改结构时，必须先 `query/get` 拿 `@paraId`，再按 `/body/p[@paraId=...]` 定位，不能批量按序号删。**

#### 1.3.5 验收口径

- 既有 Office 文件 + “修改/编辑/替换/删除/批注”等意图 → `edit` 路由，`officecli` 首选，不澄清、不强制流水线。
- 新建/套模板 → `template/generate`，先 `editorial_pipeline`，产出后才允许 `officecli` 精修。
- 只读查看 → 只允许只读子命令，写命令拒绝。
- 复制 docx 不再被当成“生成 docx”；复制走 `review_copy`/普通拷贝，不触碰内容生成。
- `officecli` 未知子命令默认按写处理，不能默认放行。

## 3. 修改方案

### 3.1 P0-1：意图文本与路由

#### 3.1.1 前端：把“原始意图”和“自动上下文”分开

`client/src/components/ChatPanel.jsx` 发送 payload 增加：

```js
{
  text: fullText,            // 保留：给 Pi 的完整 prompt（含当前文件/地图/引用/附件）
  intentText: rawText,       // 新增：只含用户输入 + 显式 @引用，不含自动前缀
  task: { goal: text, ... }  // 保留
}
```

`rawText` 已经是用户输入；`fullText` 继续承载上下文。`intentText` 不要拼接：

- `[当前打开文件: ...]`
- `[当前地图项目: ...]`
- `[当前地图视图: ...]`
- `[已上传附件: ...]`
- `## 当前检索上下文`
- `## 已注入上下文`
- `@智能体[...]` 角色前缀（角色不是任务意图）

#### 3.1.2 服务端：规划只读意图

`server/index.mjs` 两处 `planTaskCapabilities`（`:4736`、`:4818`）改为：

```js
const planningText = String(intentText || taskInput?.goal || "").trim()
  || stripAutoContextPrefix(normalizedText);
```

新增 `stripAutoContextPrefix`（`server/task.mjs` 或 `server/context.mjs`）：

- 按行删除上述自动前缀；
- 保留用户正文与显式 `@文件[...]`/`@模板[...]`/`@知识库[...]`；

// 仅当当前文件是 Office、上一轮路由是 edit/template/generate、文本是继续类短句时，沿用上一轮路由

### 3.3 P0-3：终稿边界

#### 3.3.1 服务端：识别 thinking-only 回合

新增纯函数 `server/agent.mjs`（或 `server/终稿.mjs`）：

```js
export function finalAnswerState(message) {
  const content = Array.isArray(message?.content) ? message.content : [];
  const text = content.filter((p) => p?.type === "text").map((p) => String(p.text || "")).join("").trim();
  const toolCalls = content.filter((p) => p?.type === "toolCall");
  const thinking = content.filter((p) => p?.type === "thinking").map((p) => String(p.thinking || "")).join("").trim();
  return {
    hasText: Boolean(text),
    hasToolCall: toolCalls.length > 0,
    hasThinking: Boolean(thinking),
    thinkingOnly: Boolean(thinking) && !text && !toolCalls.length,
    text,
  };
}
```

在 `agent_end` / `agent_settled`：

- 若 `finalAnswerState(message).thinkingOnly` 且本 Run 还没有补过：
  - 发 `final_text_missing` 事件（`{ runId, reason: "thinking_only" }`）；
  - 通过 `session.followUp` 或 `steer` 发一次系统提醒：“请用正文给出最终答复；不要只输出思考。”

- 若补完后仍无 text：
  - `run_finished` 的 `completion.incomplete` 加 `"final_answer_missing"`；
  - `finalText` 保持空，不伪造摘要。

不建议无限重试；一次足够验证模型是否只是偶发。

## 4. Office CLI 调用规约（规范正文）

> 本节是实施后的规范口径；落地时同步到 `docs/规范/Office CLI 调用规约.md`，并在 `AGENTS.md` §5 增加一行索引（不改强制条款）。

### 4.1 基本原则

1. 所有 Office 文档操作必须通过 `officecli` 工具，不允许 `bash officecli`。
2. `officecli` 只负责“既有文档的读取与精确编辑”；新建/套模板优先 `editorial_pipeline`/原生生成，生成后再用 CLI 精修。
3. 只读查看不得写；写操作必须有明确的编辑意图和目标文件。
4. 未知子命令按写处理；默认拒绝，不默认放行。
5. 结构性编辑按 `@paraId` 定位，不按段落序号批量删改。

### 4.2 模式

| 模式 | 是否暴露 |
|---|---|
| Chat | 否 |
| Work | 是 |
| Review | 是（仅副本/批注；原文写回需确认） |
| Office（历史兼容） | 是（按 Work 处理） |

### 4.3 路由

| 路由 | 触发条件 | CLI 策略 |
|---|---|---|
| `edit` | 既有 Office 文件 + 修改/编辑/替换/删除/批注等意图 | 首选；读写都允许；不澄清；不强制流水线 |
| `template` | 显式 `@模板[...]`，或没有既有文件且命中模板关键词 + 生成意图 | 只读允许；写命令必须 `pipelineProduced=true`；澄清前置 |
| `generate` | 有生成意图 + Office 意图，无既有文件/无模板 | 同 template |
| `read` | 其余 | 只读允许；写命令拒绝 `OFFICE_READONLY_ONLY` |

### 4.4 命令

| 级别 | 命令 | 说明 |
|---|---|---|
| 只读 | `view/get/query/validate/dump/help/watch/unwatch` | 可随时执行（编辑路由/模板路由均允许） |
| 写 | `create/add/set/batch/import/remove/move/swap/delete/save/close` | 受路由/流水线/澄清约束 |
| 未知 | 任意其他 | 按写处理，默认拒绝 |

### 4.5 预检

| 路由 | 预检 |
|---|---|
| `edit` | 阻塞式 `checkOfficecli()`；不可用直接拒绝 admission |
| `template/generate` | 后台惰性预检，不阻塞生成主链 |
| `read` | 无 |

### 4.6 明确禁止

- Chat 模式调用 `officecli`。
- `read` 路由写文件。
- 模板/生成路由在 `pipelineProduced=false` 时 `create/add/set/remove`。
- 用 `bash` 执行 `officecli`。
- 用 `cp/copy` 伪装“生成 docx”的检查（复制不是生成）。
- 按段落序号批量 `remove`；必须先取 `@paraId` 并回读。

## 7. 测试计划

### 7.1 单元/契约

1. `task:complexity`：
   - `[当前打开文件: ...可行性研究...] + 继续修改` → `edit`；
   - `读取一下这个文本做如下修改` + docx → `edit`；
   - `按模板写一份新的可研` + 无文件 → `template`；
   - `继续` + 上一轮 edit → `edit`；
   - 地图前缀不影响 Office 路由。
2. `office:cli-policy`：
   - 模式/路由/命令/流水线/澄清组合矩阵；
   - 未知命令按写；
   - `cp` 不再命中 `isDocxGenerationCommand`；
   - `save/close` 按写。
3. `final-answer`：
   - thinking-only → `final_text_missing`；
   - text+thinking → 终稿 text；
   - toolCall-only → 不结束；
   - `<ask_user .../>` 清洗；
   - 历史无终稿不兜底。
4. `interruption`：8 类 fixture 的 `kind/label/action`。

### 7.2 集成/回归

- 用现有 `scripts/CI运行测试.mjs` 跑受影响套件。
- `npm run verify`。
- 用一个 fixture 工作区：
  - `报告.docx` + 用户“读取一下并修改标题” → 断言 route=edit，`officecli set` 允许；
  - 用户“按模板写一份新的可研” → route=template，`officecli set` 在 pipeline 前拒绝；
  - 用户“只看一下报告” → route=read，`officecli set` 拒绝 `OFFICE_READONLY_ONLY`。

  - 打开含 thinking-only 的会话，确认成果区显示“没有最终答复”，过程区保留 thinking；

## 10. 不做清单与风险

### 10.1 不做

- 不改 Logo、`ProviderIcon`、Tabler 图标映射、文件类型彩色底、地图图例、内置浏览器光标。
- 不改 015 的消息极简结构、历史导轨位置、Word 预览样式。
- 不改 006 的归档接口/运行宪法/技能草稿确认规则。
- 不修改 `node_modules/` 或 Pi SDK 源码。
- 不自动切换模型；401 只提示更新 Key。
- 不把任意工具标签解析成真实工具调用；只清洗显示。
- 不默认提高全局 45 回合硬预算；Office 任务级放宽需单独确认。
- 不为了“看起来完成”伪造 finalText 或把 thinking 当终稿。

### 10.2 风险

| 风险 | 缓解 |
|---|---|
| edit 优先导致“想新建却改了旧文件” | 仅当 `officeRefExists && editIntent`；显式 `@模板`/无既有文件仍走模板 |
| 短句“继续”沿用上一轮 route 误写 | 仅当上一轮是 edit/template/generate 且当前文件是 Office；read 不沿用 |
| thinking-only 自动补终稿增加一次模型调用 | 每 Run 最多一次；失败后显式提示，不循环 |
| `read` 路由拒绝写让模型反复重试 | 错误码 + 提示“明确说修改”；提示词说明 |
| 中断分类误判 | 以 `error/recovery/events` 优先，`finalText` 最后；测试 fixture 固定 |
| 会话列表改动影响任务中心 | 保留 `runStatus` 兼容字段，新增 `lastRunStatus`/`lastSuccessful*` |
| 与并发会话文件冲突 | 只暂存本计划 hunk；提交前 `git diff --cached` 审核 |
