## 三、与既有桌面端成果的关系（关键决策依据）

### 3.1 事实

`github.com/sungatetop/open-plan` 是**已完成的 Electron 桌面端**（`electron/` 344 文件，main/preload/renderer/shared，TS 化 + IPC `op:*` 直调，NSIS 安装包，89 个 vitest）。

| 指标 | 数值（2026-11-06 实测） |
|---|---|
| `fork/main` 领先 develop | **190 提交** |
| `fork/main` 落后 develop | **257 提交** |
| `fork/main` vs `develop` 合并冲突文件 | **406 个** |
| 分叉点 | 2026-10-19（`235e9cf4`） |

### 3.2 结论变化（相对 2026-11-02 计划）

2026-11-02 的路线 1 是「把 fork 的 `electron/` 搬回来，桌面端成为主形态，web 降级」。当时基线是 v0.13.3，develop 独有 177 提交。

**现在 develop 又长了 v0.13.4→v0.13.24 一整年量的功能**（预览治理、CAD、浏览器可观测性、会话流恢复、Goal、记忆、Office 写作层、模板库、地图 G 线…），而 fork 自己没有前进。这意味着：

- 「搬回来再补功能」的迁移量从 177 提交涨到 **257 提交、406 冲突文件**；
- fork 的 IPC 化重写（`server/*.mjs` → TS）会让**主线 192 个 `.mjs` 测试与全部服务端逻辑需要二次重写**；
- 而主线现在有大量**与进程边界无关**的纯逻辑（事件注册表、审批、写入协调、Run 终态），重写它们几乎不产生用户价值。

**因此本方案建议改为「壳优先」路线**（见 §四），并把 fork 当作**能力参考**而非代码底座。

## 四、桌面形态选型（三选一，建议 A′）

| 方案 | 做法 | 改动面 | 收益 | 风险 |
|---|---|---|---|---|
| **A′ 壳优先（推荐）** | Electron 主进程 `import('./server/index.mjs')` 进程内起现有 Express（监听 `127.0.0.1` 随机端口），`BrowserWindow` 加载 `client/dist`；渲染层沿用 fetch + SSE | **小**：新增 `desktop/` 目录 + 少量桥接，`server/`、`client/` 基本不动 | 1–2 周拿到可安装桌面端；192 个测试继续有效；web 形态无损保留 | 主进程跑后端会与 UI 抢线程（Node 侧影响小）；端口/单实例需处理 |
| **B 全 IPC 化（fork 形态）** | `server/*.mjs` TS 化进主进程，前端 `api.js` 换 IPC 客户端，删 express | **大**：重写服务端 + 前端 API 层 + 测试体系换 runner | 无端口、启动更快、体积略小 | 257 提交功能要重搬；测试双 runner；回归面覆盖全产品 |
| **C Tauri** | Rust 壳 + 系统 WebView | **大**：Rust 侧要重写所有原生能力，或退回 sidecar（= 自己起 Node 服务） | 体积最小（~10MB） | 与「Node 后端进程内直调」不兼容；Windows WebView2 版本依赖强；地图/officecli 子进程管理复杂 |

### 4.1 为什么推荐 A′

1. **最大改动面留给真正需要的部分**：桌面化的核心价值是「免装 Node、双击即用、原生窗口、随包工具链」，这些都在壳层；业务层重写不产生产品价值。
2. **保住 192 个测试与全部治理**：A′ 下 `npm run verify` 语义不变，B/C 都要重建测试体系（2026-11-02 计划里 P5「测试体系归一」就是被这块卡住的）。
3. **与 ADR 0002 冲突最小**：A′ 仍是「单仓 + 单服务 + SPA」，只是把服务收进 Electron 主进程；B 才真正推翻 ADR 0002。
4. **可回滚**：桌面端出问题，`npm start` 的 web 形态原样可用。

### 4.2 A′ 的具体形态

```
GuiJu.exe
├─ Electron main（Node 22 运行时）
│   ├─ import server/index.mjs → Express 监听 127.0.0.1:<随机端口>
│   ├─ 单实例锁（app.requestSingleInstanceLock）
│   ├─ 原生桥：文件/目录对话框、系统打开、托盘、更新检查
│   └─ 子进程：officecli、ODA/LibreDWG、浏览器（见 §六）
├─ Renderer（BrowserWindow → 加载 client/dist，或 dev 时 vite devServer）
│   └─ 继续用 fetch + SSE（带 token，防本机其他进程直连）
└─ 打包：electron-builder → NSIS（per-user），extraFiles 带 bin/*
```

**必做的 4 个安全项**（桌面端新增暴露面）：

1. `nodeIntegration: false`、`contextIsolation: true`、`sandbox: true`，只经 `preload` 暴露白名单 API；
2. 后端只监听 `127.0.0.1`，并强制 `OAW_API_TOKEN`；渲染进程从 preload 拿 token；
3. 工作区路径校验沿用 `resolvePath` 边界（禁止 `..` 逃逸）；
4. 外部链接一律 `shell.openExternal` + 协议白名单。

## 六、浏览器模块：可以换技术方案（这是桌面端最大红利）

### 6.1 现状（v0.13.24）

- 服务端 `server/内置浏览器.mjs`（**1880 行**）：spawn 系统 Edge/Chrome（`--headless=new` + 独立 profile）→ Node 内置 WebSocket 直连 CDP → 工具层用 `Runtime.evaluate`（快照）/`Input.*`（点击输入）/`Page.captureScreenshot`；
- 画面：`Page.startScreencast` → 90→120ms 节流 → SSE base64 → 前端 `Blob URL` 渲染（本轮已做参数治理与隐藏停流）；
- 用户接管：服务端 lease 仲裁（3 分钟），前端虚拟鼠标（`agent-action` 事件）；
- 前端 `client/src/components/内置浏览器面板.jsx`（**681 行**）。

### 6.2 四个候选方案

| 方案 | 画面来源 | 延迟/带宽 | 依赖 | 改动面 | 结论 |
|---|---|---|---|---|---|
| **A. 现状：系统 Edge + CDP + SSE 帧流** | screencast JPEG → SSE base64 | 本地 7–30 Mbps（已优化到 q55/1280/120ms） | 依赖用户机装 Edge/Chrome | 0 | web 形态继续用 |
| **B. Electron `WebContentsView` + `webContents.debugger`（推荐）** | **页面直接渲染在原生视图里，不需要传画面** | 0 传输开销、原始帧率 | Electron 自带 | 中：替换 `内置浏览器.mjs` 的「启停/screencast」两段，工具层 100% 复用 | ✅ 桌面端首选 |
| C. Playwright / Puppeteer | 仍需 screencast/video 回传 | 同 A | 数十 MB + 浏览器内核 | 大：换驱动层但画面问题不变 | ❌ 不值得 |
| D. WebView2 / Tauri WebView | 原生视图 | 0 | Windows 限定；需换壳 | 大 | ❌ 与 Electron 方案冲突 |
| E. noVNC / WebRTC 像素流 | 远端桌面编码流 | 低延迟但需编码器 | ffmpeg/GStreamer | 大 | ❌ 本地同机场景属过度设计 |

### 6.3 方案 B 为什么能**整段删掉**帧流

Electron 的 `webContents.debugger` 就是 CDP 客户端，`sendCommand('Page.navigate', …)` 与现在 Node 直连 CDP 的调用**逐字相同**；而页面由 `WebContentsView` 原生渲染，用户看到的就是真实页面：

```
现在：CDP → JPEG 编码 → WS → 服务端节流 → base64 → SSE → 前端解析 → Blob → <img>
之后：WebContentsView 直接绘制（工具层发 CDP 指令不变）
```

可删除的代码（估计 **600–900 行**）：`startScreencast/stopScreencast/captureFrame/queueFrameBroadcast/ensureWatching`、`/api/browser/stream` SSE 帧流、`/api/browser/input` 坐标换算、前端帧渲染与 Blob 回收、`browserAdaptiveStream` 等开关。

保留的语义：`browser_open/snapshot/click/type/press/scroll/tabs/screenshot` 全部工具不变；用户接管改为「直接操作视图」+ 主进程仲裁（不需要 lease 也能做，但建议保留以保护 Agent 动作与用户动作互斥）。

### 6.4 方案 B 的实施要点与坑

| 点 | 说明 |
|---|---|
| 视图类型 | Electron ≥ 30 用 `WebContentsView`（`BrowserView` 已废弃） |
| 调试器独占 | 一个 `webContents` 同时只能挂一个 debugger；与用户按 F12 打开 DevTools 冲突 → 工具操作前 `attach`、空闲 `detach`，或禁用内置 DevTools |
| CDP 域子集 | Electron 的 debugger 支持 Page/Runtime/Input/Accessibility，但部分域（如 `Target.*`）受限；多标签需用多个 `WebContentsView` 而非 `Target.attachToTarget` |
| 会话隔离 | 用 `session.fromPartition('persist:browser')` 保留登录态，替代现在的独立 profile 目录 |
| 下载/弹窗 | 需 `will-download`、`setWindowOpenHandler` 显式处理，否则静默失败 |
| 截图与导出 | `Page.captureScreenshot` 仍可用；地图批量导出可改用 `webContents.printToPDF` / `capturePage`，摆脱「开一个隐藏浏览器」的旧路 |
| 回滚 | web 形态保留方案 A（现有实现不动），用开关 `OAW_BROWSER_DRIVER=system\|embedded` 切换 |

### 6.5 结论（直接回答你的问题）

**可以换，而且桌面端应该换。** 但不是换「自动化引擎」（Playwright/Puppeteer 都不解决画面回传，反而增加依赖），而是**换「宿主」**：把浏览器从「外部进程 + 像素流」变成「Electron 内嵌视图 + CDP 指令」。这是唯一能让「卡」从根上消失的方案，同时把 1880 行的浏览器模块砍掉近一半。

## 八、分阶段路线图

> 原则：每阶段可独立验证、可独立回滚；**D2 完成前不碰 `server/` 与 `client/` 业务代码**。

### D0 · 基线冻结（已完成）
版本口径收敛到 v0.13.24（未发布）+ 工作树干净 + `verify` 绿。

### D1 · 壳骨架（1 周）
| 步骤 | 内容 | 完成判据 |
|---|---|---|
| D1-1 | 新增 `desktop/`（Electron 37 + electron-vite），主进程 `import` 现有 `server/index.mjs` | 双击启动，窗口里出现完整 SPA |
| D1-2 | 随机端口 + `OAW_API_TOKEN` + preload 注入；单实例锁 | 端口不冲突，未授权进程无法调 API |
| D1-3 | 原生文件/目录对话框桥（替换 file input 与「选择工作区」） | 选文件/目录可用 |
| D1-4 | `npm run desktop:dev` / `desktop:dist`（NSIS per-user） | 出安装包，装完可跑 |

**交付态**：桌面端能跑现有全部功能（浏览器仍是方案 A），web 形态无损。

### D2 · 浏览器换宿主（1–2 周，收益最大）
| 步骤 | 内容 | 完成判据 |
|---|---|---|
| D2-1 | 抽象 `浏览器驱动` 接口（`open/snapshot/click/type/press/scroll/tabs/screenshot/close`），现有 CDP 实现作为 `system` 驱动 | 接口测试与现有 `test:browser` 等价通过 |
| D2-2 | 新增 `embedded` 驱动：`WebContentsView` + `webContents.debugger` | 同样 8 个工具在嵌入视图上全部可用 |
| D2-3 | 面板改造：内嵌视图宿主容器 + 用户直接操作 + 接管仲裁 | 用户可登录/过验证码；Agent 动作可见（用视图内高亮替代虚拟鼠标） |
| D2-4 | 删除帧流链路（screencast/SSE/base64/Blob/自适应推流） | 桌面端无 `/api/browser/stream` 帧流量；web 形态开关回退 |
| D2-5 | 地图批量导出改 `printToPDF`/`capturePage` | 批量导出 PDF/PNG 与现在一致 |

**交付态**：桌面端浏览器零帧流、原生渲染；web 形态保持现有实现。

### D3 · 能力补强（1 周）
| 步骤 | 内容 |
|---|---|
| D3-1 | 知识库首次索引移出主线程（worker_threads 或后台任务） |
| D3-2 | 服务监督 → 主进程生命周期（启动/崩溃重启/退出清理子进程） |

| D3-4 | 更新通道（electron-updater 或自建 manifest）——需你确认签名策略 |

### D4 · 交付与对等验收（1 周）

## 九、风险与不做清单

**风险**

| 风险 | 影响 | 对策 |
|---|---|---|
| 主进程跑后端，重任务（知识库扫描、Office 渲染）卡住 UI | 体感差 | D3-1 移出主线程；officecli 本就是子进程 |
| `webContents.debugger` 与 DevTools 冲突 | 浏览器模块时好时坏 | 统一 attach/detach 生命周期 + 禁用内置 DevTools |
| 打包体积（Electron ≈ 90–150MB + officecli/ODA） | 分发成本 | 首版接受；后续可做按需下载 ODA |
| ODA File Converter / LibreDWG 许可证 | DWG 能力合规 | 需你确认分发方式（或改为「首次使用引导用户自装」） |
| 192 个测试在桌面端仍为 web 形态验证 | 桌面专属路径缺测试 | D2 给驱动加接口测试；桌面壳加 smoke |
| 与并行会话的文件冲突 | 提交互相覆盖 | 桌面端改动集中在 `desktop/` 新目录 + 少量桥接文件，避开 `server/`、`client/` 热点文件 |

**不做**

1. 不整支合并 `fork/main`（406 冲突 + 190/257 双向差异）；
2. 不采用 Tauri（与 Node 进程内直调不兼容，原生能力要重写）；
3. 不用 Playwright/Puppeteer 换浏览器引擎（不解决画面问题，反增依赖）；
4. 不在 D1 阶段改 `server/`、`client/` 业务代码；
5. 不把用户会话/工作区数据搬到 `userData`（避免用户数据搬家与迁移风险）。
