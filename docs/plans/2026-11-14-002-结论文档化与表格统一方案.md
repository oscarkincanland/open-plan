## 1. 现状诊断（证据）

### 1.1 表格在 4 个入口的实际差异

`.markdown-body table` 是唯一一套表格样式（`client/src/styles.css:1304-1324`），但**字号由宿主覆盖**，于是同一张表在不同入口尺寸不同：

| 入口 | 选择器 | 实际字号 / 行高 | 表格观感 |
|---|---|---|---|
| 会话流结论（历史轮次） | `.sum-body .markdown-body`（`styles.css:11911`） | 14px / 1.75 | 1px 全网格 + 表头底色 |
| 会话流终稿（运行结束） | `.flow-markdown .markdown-body`（`styles.css:1177`） | 14px / 1.8（继承基座，**未同步 1.75**） | 同上 |
| 文档预览 DocViewer | `.mdview .markdown-body`（`styles.css:664`） | 13px / 1.8 | 同上 |
| 任务中心完成说明 | `.task-center-completion-markdown .markdown-body`（`styles.css:566`） | 10.5px / 1.7 | 同上，表格明显偏小 |
| 知识库 / 思维导图 / 模板库 | `.markdown-body` 基座（`styles.css:1221`） | 13px / 1.8 | 同上 |

当前表格样式本身（`styles.css:1304-1324`）：

```css
.markdown-body table { border-collapse: collapse; width: 100%; margin: 8px 0; font-size: inherit; }
.markdown-body th, .markdown-body td { border: 1px solid var(--border); padding: 5px 10px; }
.markdown-body th { background: var(--panel2-bg); font-weight: 600; }
```

即：**四边全网格 + 表头实底 + 窄内边距**——更像 Excel 截图，而不是文档里的表。

### 1.2 三个根因

1. **字号是"容器的事"，表格只是继承**：四个入口各写各的 `font-size`，表格的行高、换行、内边距观感随之漂移；`flow-markdown` 只改了 14px，没有同步行高，与 `sum-body` 的 1.75 不一致。
2. **两套横向滚动**：`MarkdownBody` 的 `table` 包裹层 `.md-table-wrap { overflow-x:auto }`（`styles.css:1627`），而 `.sum-body .markdown-body` 又加了 `overflow-x:auto`（`styles.css:11915`）——外层与包裹层同时可滚，窄屏下会出现"表头与内容错位 / 滚动条常驻"的老问题（`styles.css:11912-11914` 的注释记录过一次修复，属补丁叠加）。
3. **文档形态只存在于 DocViewer**：`DocViewer` 有 `MarkdownToc` + `withToc`（`DocViewer.jsx:962-965`），会话流结论区**没有**目录/锚点；`rehypeSlug` 虽然一直在插件链里（`MarkdownBody.jsx:185`），但结论区没有消费它。

### 1.3 与 DSH 的差异（同屏观感）

DSH 的表格是"文档表"：只保留横线（0.5px），无竖线、无斑马纹，单元格 10×16，≤3 列撑满、≥4 列横向滚动，单元格 `max-width` 约 320px（`dsh-web-frontend` 构建产物 CSS）。我们目前是"网格表"：全边框、5×10、始终 100%。

差异不是审美偏好问题：全网格在 720px 的内容列里会把中文长句压成 3–4 字一行的碎列。

## 2. 方向判断：三种"文档"不是一回事

用户的问题「是不是直接渲染一个 markdown 文件、总体形成一个文档」，落到实现上其实是三件事，必须分开决定：

| 层 | 是什么 | 现状 | 建议 |
|---|---|---|---|
| **L1 结论区 = 一篇连续正文** | 一轮结束后，结论 + 详细内容合并渲染成一块无框 Markdown（14px、无分节标签、h2 自动编号） | **已实现**（`SummaryBlock.jsx`、`.assistant-final-answer`；规范 §5） | 保留并强化：加目录、锚点、阅读宽度、复制为 Markdown |
| **L2 结论文档 = 归档的 `.md` 文件** | 终稿另存 `回报/*.md`，用 DocViewer 打开（有目录、可检索、可引用） | **已实现**（ADR 0030；Chat 讨论记录由服务端归档） | 保留；Work 模式可补"导出为文档"入口 |
| **L3 整轮 / 整会话 = 一个 Markdown 文件** | 把用户消息、过程、工具、ask、产物全部拍平成一篇文章，聊天流只渲染这篇 | **不存在**，也不建议 | **不做**（见下方理由） |

不做 L3 的四条理由：

1. **与既有决策冲突**：ADR 0030 明确「结论文档不参与对话内渲染」，规范 §5 同款条款；要做 L3 必须先改 ADR，属于决策变更而不是实现选择。
2. **交互模型会被拍平**：ask / 审批 / 中断 / 重试 / 分页 / 翻页定位 / 折叠状态都挂在节点树上（`会话流投影.js` 与时间线），压成一篇纯 Markdown 后这些交互没有落点。
3. **性能反向**：整篇 Markdown 每来一个 token 就要重解析并重建 DOM；现在的 `MarkdownBody` 已经在防"每秒 500 次 DOM 变动"（`MarkdownBody.jsx:139-141,190-191`），L3 会把这个问题放大一个量级。
4. **信息会丢**：过程、工具入参、耗时、产物归属、运行状态都依附节点；L3 要么丢弃它们，要么在正文里重排一遍——等于把结构化数据降级成文本。

**结论**：文档化应该发生在「结论区」这一层（L1），以及「归档文件」这一层（L2）；不要把聊天流本身文档化。

## 3. 方案

### 3.1 P0：表格统一为一套 `.md-table` 规范层（0.5–1 人日）

目标：4 个入口的表格**看起来是同一张表**，并且从"网格表"变成"文档表"。

| 项 | 现在 | 改为 |
|---|---|---|
| 竖线 | 每格 `border: 1px` 全网格 | 去掉竖线，只留 `th/td` 下边 0.5px 发丝线（`color-mix(in srgb, var(--border) 62%, transparent)`） |
| 表头 | `--panel2-bg` 实底 | 不加底色；`font-weight: 600` + 下边线加深一档 |
| 内边距 | `5px 10px` | `8px 12px`，首列左内边距 0、末列右内边距 0（贴齐正文） |
| 字号 | 继承容器（13/14/10.5） | 跟随宿主正文，**表格本身不再声明字号**；DocViewer 基座由 13 → 14，任务中心容器单独缩到 12 |
| 宽度 | 一律 `width: 100%` | ≤3 列 `width: 100%`；≥4 列 `width: max-content; min-width: 100%`，滚动交给外层 |
| 数字 | `tabular-nums` | 保留，并对 `th/td[align=right]` 右对齐 |
| 滚动 | `.md-table-wrap` + `.markdown-body` 双滚动 | 只保留 `.md-table-wrap` 一层；删除 `.sum-body .markdown-body { overflow-x:auto }` |
| 圆角 | 无 | 表格容器 8px（`--radius-lg`）；首行不再撑破圆角 |

落地方式：

- 新增一节 `/* ===== 文档表格（.md-table 规范层）===== */`，放在 markdown 渲染段之后，**只新增不重写**，旧规则被后置覆盖或直接替换对应 4 行；
- `MarkdownBody` 的 `table` 组件保持不变（已经是 `.md-table-wrap`）；
- 不在组件里写内联样式，全部令牌化（颜色一律 `var()` / `color-mix`，符合 `界面一致性守护测试` 的硬编码色值基线）。

### 3.2 P1：结论区文档化（1–2 人日）

只改结论区（`.sum-body` / `.assistant-final-answer`），不动过程区与折叠结构：

1. **目录**：结论正文二级标题 ≥ 3 时，在首屏之后浮出轻量目录（复用 `MarkdownToc`，与 DocViewer 同一组件），点击滚动到锚点；<3 时不显示，避免空目录。
2. **锚点**：`rehypeSlug` 已在链上，补 `scroll-margin-top` 与平滑滚动；目录项 `aria-current` 跟随。
3. **阅读宽度**：结论区维持 `--msg-content-max`（720px），文档模式不额外加宽——宽屏下由 DocViewer 承载长文，会话流不做第二套排版。
4. **复制为 Markdown**：结论区右上角一个动作（先 hover 显示），复制原始终稿文本（不是渲染后的 innerText），复用现有复制反馈。
5. **导出为文档**：仅 Work 模式，落 `回报/YYYY-MM-DD-<主题>.md`（沿用 ADR 0030 的目录与命名），入口在结论区动作条；Chat 仍由服务端自动归档，不新增模型写工具。

### 3.3 P2：细节对齐（0.5 人日）

| 项 | 现在 | 改为 |
|---|---|---|
| 代码块 | `border-radius: 4px` + 1px 边框 + 10×12 内边距 | 圆角 8px（`--radius-lg`）、去掉 1px 边框改 0.5px 发丝线、内边距 12×14；语言条 sticky 保留 |
| 链接 | 常态下划线 | 常态无下划线，hover/focus 才 `underline dotted` + `underline-offset: 3px`；正文色仍用 `--accent` |
| 引用 | 3px 左线 + `--muted` 文字 | 2px 左线、文字回 `--text`（引用不应比正文更浅） |
| 分割线 | 1px `--border` | 0.5px 发丝线，上下 24px |
| 行高 | 基座 1.8 / 结论 1.75 混用 | 统一 `1.75`（DESIGN §5.6 口径） |

## 4. 验收

1. **一致性**：同一张 5 列表格在「会话流结论 / DocViewer / 知识库」三处截图对比，字号、内边距、线宽一致；
2. **稳定性**：≥4 列表格在 720px 列宽下只出现一层滚动条，表头与内容不错位；
3. **可访问性**：目录可键盘操作，锚点跳转后焦点落在标题；`prefers-reduced-motion` 下平滑滚动降级为瞬时；
4. **回归**：`node scripts/会话流排版回归测试.mjs`、`node scripts/Markdown预览增强测试.mjs`、`node scripts/界面一致性守护测试.mjs`、`node scripts/无障碍与窄屏测试.mjs`、`npm run verify` 全绿；
5. **无新增**：运行时依赖、字号档位（仍是 12/14/16）、字体族、硬编码色值。

## 5. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 表格变"轻"后信息密度下降 | 去掉竖线后，宽表对齐依赖行距与内边距 | 内边距加到 8×12，表头加粗一档；对比截图后再定 |
| 结论区加目录变成"第二套导航" | 与右侧导轨/TurnRail 重复 | 仅在 h2 ≥ 3 时出现，且是结论区局部浮层，不做常驻侧栏 |
| 导出为文档与 Chat 归档口径重叠 | 两个入口写 `回报/` | 命名与追加规则沿用 ADR 0030，Work 手动导出、Chat 自动归档，互不覆盖 |
| DocViewer 13 → 14 影响存量文档观感 | 长文密度变化 | 先只统一表格，DocViewer 字号单列一个决策点（见 §6） |

## 6. 请确认的决策点

1. **表格**：是否接受"去竖线、只留 0.5px 横线、8×12 内边距"的文档表？（推荐：是）
2. **DocViewer 字号**：是否把 13px 提到 14px 与结论区统一？（推荐：是；若不改，则表格必须显式声明 14px，与"不声明字号"冲突）
3. **L3 整轮文档化**：确认不做，还是需要先改 ADR 0030 再评估？
4. **导出为文档**：Work 模式是否需要这个入口，还是统一走"产物卡 + 归档"？
5. **实施顺序**：P0 → P1 → P2 分期，还是只做 P0 + 表格相关 P2？
