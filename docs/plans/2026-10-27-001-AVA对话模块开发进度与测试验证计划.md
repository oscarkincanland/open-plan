## 1. 版本列车

### 1.1 版本粒度规则

- **minor 线 = 功能主题**：如 v0.12.x 为“队列与消息基础”，v0.13.x 为“目标与工作面板”；一条 minor 线不跨主题。
- **patch = 线内小步交付**：每个 patch 必须可独立交付、独立验证、独立回滚，只交付一个主题切片；不得把整条线的全部工程条目塞进 `x.y.0`。
- 每条 minor 线至少拆成 **3 个 patch**，版本号连续（v0.12.0 → v0.12.1 → …），不跳号、不回退到“一版一个大功能”。
- 每个 patch 必须列出：范围（ENG）、开发内容、用户可见验证功能、测试命令、前置依赖、退出标准、状态；**未列验证功能的 patch 不得进入开发**。
- 每个 patch 只能依赖前序 patch 已交付的能力；队列单源、历史/分支等状态模型契约未稳定前，后续 patch 不得并行改动同一状态模型。
- 每个 patch 单独更新 `变更日志.md`、`版本管理计划.md` 与本计划台账，并留下验证证据；不出现“代码已做、文档仍写未开始”。
- 后续线在启动前 2 周把占位细化到与 v0.12.x 同级的 patch 表；未冻结的线只保留主题占位，不承诺日期。
- 收口 patch（如 v0.12.9）只做全量回归、缺陷修复、文档同步与 release candidate，不夹带新功能。

## 2. 阶段门禁

| 门禁 | 名称 | 进入条件 | 必须产出 | 退出条件 |
|---|---|---|---|---|
| G0 | 范围冻结 | 需求/冲突/工时确认 | 版本范围、测试清单、影响文件 | 用户/负责人确认；无未决 ADR 阻塞 |
| G1 | 开发完成 | G0 通过 | 代码、最小注释、变更日志草稿 | 本地自测；无 console error；关键路径可走通 |
| G2 | 目标测试 | G1 通过 | 目标测试脚本/手工记录 | 目标 `test:*` 通过；失败项有结论 |
| G3 | 全量回归 | G2 通过 | 回归矩阵结果、截图/证据 | `npm run verify` + 受影响关键 `test:*` 通过 |
| G4 | 文档同步 | G3 通过 | 变更日志、DESIGN/PRD 相关段落、版本计划、计划实施记录 | 文档与代码一致；无未说明差异 |
| G5 | 合并/发布 | G4 通过 | 合并记录、tag（如发布）、回滚说明 | 合并回 develop；稳定后 main + tag |

> 门禁按 **patch** 逐个执行：每个 patch 独立完成 G0–G5 并留下证据；收口 patch（v0.12.9）额外承担线内全量回归与 release candidate。

- 每个 patch 保留回滚点：新行为可通过开关/降级回退；数据结构只增不改，兼容旧会话。
- 不修改 `node_modules/`、Pi SDK；不新增数据库/消息队列/微服务/桌面壳。
