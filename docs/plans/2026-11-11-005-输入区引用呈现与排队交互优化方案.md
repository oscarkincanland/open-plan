## 1. 用户报告

1. 引用文件 / 插入文件（含图片）的呈现“显示在外面”，希望只显示成**一个不可编辑的小 tab**；`@文件` 也应一样。
2. 输入框顶部的「当前任务中新输入 / 立即执行 / 排队执行 / 注入上下文」视角“有点死板”，希望优化交互。

## 2. 现状与证据（只读定位，2026-11-11 10:40–10:46）

### 2.1 三类 chip 都渲染在输入卡外面（问题 1 的直接原因）

`ChatPanel.jsx` 的 DOM 顺序（`:5473` 图片、`:5491` 附件、`:5514` 引用、`:5525` 队列坞、`:5536` GoalBar、`:5558` 输入卡 `.chat-compose`）表明：`img-preview-row` / `att-preview-row` / `reference-bar` 与输入卡是**兄弟节点**，渲染在卡片上方外部，不是输入区的一部分。

实测（1440×900，`.reference-bar` 用与 JSX 完全一致的 DOM 结构注入后测量）：

| 元素 | 实测 |
|---|---|
| `.reference-bar` | y=684，h=31（在卡片外，`.chat-compose` 从 y=715 开始） |
| `.reference-chip` | 220×25，`scrollWidth`=311 → 路径被截断；chip 文本是 `@` + 完整 target（如 `@designs/open-plan画布/project/boards/03-viewport.dc.html`） |
| 卡内「本轮目标 · 参考文件 N」 | 与 chip 行表达同一事实，形成重复 |

`DESIGN.md:53` 把「chip 条」明确归入**输入区外壳（Composer）**，当前实现是设计偏差。

### 2.2 `@文件` 标记以长路径文本形式留在输入框内

选中 `@` 候选后，`insertText`（`ChatPanel.jsx:2011`）把 `@文件[完整路径]` 原样写进 textarea，再由输入监听（`:1584`）解析出 chip。于是同一引用同时存在两份：**输入框里的长路径文本** + **卡外的 chip**。用户看到的“显示在外面/不像一个 tab”即由此而来。

附带缺陷（同一次排查发现，见 §6）：
- 输入框文本被清空后 chip 不消失（`parseReferenceMarkers` 无命中时 `:1585` 提前 return，未清理已失效引用），出现“文本没了、卡外 chip 还挂着”的怪状态；
- `@` 同时弹出两个面板（文件候选 `.composer-suggestions` 与智能体候选 `.composer-suggestions.mention-menu`）叠在一起，且输入清空后不自动关闭；DESIGN `:313` 要求“任一符号只出现一个面板”。

### 2.3 忙碌态投递方式控件偏“死板”

`ChatPanel.jsx:5573-5581`，实测样式：

| 项 | 实测 |
|---|---|
| 整行 `.busy-input-mode` | 692×26，占满输入卡一整行，`margin-bottom: 5px` |
| 文案 | `当前任务中新输入：` + 3 个等权按钮 + 一句 `<small>` 提示 |
| 按钮 | 56/56/66 × 23，字号 **10px**，与工具条 28px/14px 体系不一致 |
| 提示文字 | **9.17px**（小于正文元信息 12px 档，可读性偏低） |

问题不只是“不好看”：三态（打断 / 排队 / 注入）是**投递方式**，属于低频设置，却常驻占一整行；提示文案与发送按钮 `title` 重复表达同一件事；忙时输入区被这一行额外顶高，正文可视高度被压缩。

## 3. 方案 A：引用 / 附件 / 图片统一为卡内只读 tab（推荐）

### A1 结构（必做）

- 把 `img-preview-row`、`att-preview-row`、`reference-bar` **移入 `.chat-compose` 卡片内部**，与「本轮目标」同区、置于输入框上方（结构：`卡片头部 chip 行 → 本轮目标行 → textarea → 工具条`）。
- 三类 chip 统一为 `.composer-token` 只读小 tab：`[类型图标] 短名 [×]`
  - 短名 = 文件 basename（保留扩展名），`max-width: 180px`，中间省略；**完整相对路径只放 `title`**，不再裸奔在界面上；
  - 22px 高、`--radius-md`、`--panel2-bg` 底 + 1px `--border`，11px 字，与工具条控件同高体系（28px 交互区、图标 14px，token 本身 22px 视觉高）；
  - 图片 token：24×24 缩略图 + 文件名 + ×（替代现在 56×42 的大预览）；
  - 附件 token：文件类型图标 + 文件名 + 大小 + ×；
  - 引用 token：`@`/`&` 用图标区分类型（file/session/skill），不再前缀裸字符。
- 去掉卡内「参考文件 N」计数 chip，改为直接展示引用 token（同一事实只出现一次）；工作区 chip 与当前文件 chip 保留。
- 修陈旧引用：`input` 变化后若无对应标记，移除该引用（引用与文本双向同步），与 composerUnified 路径对齐。

### A2 输入框里的 `@文件[...]`（可选，二选一）

| 选项 | 做法 | 代价 |
|---|---|---|
| **A2-甲（推荐）** | 选中 `@` 候选时不再把 `@文件[长路径]` 写进 textarea，只插入短 token 文本 `@文件名`；完整路径由 `references` 状态承载，发送时由结构化 `references` 字段下发（服务端 `/api/agent/prompt` 已接收 `references`，`ChatPanel.jsx:4226` 已合并 state 与文本标记） | 需同步“历史消息回显 / 编辑重发”路径（`:4870` 已从 `message.references` 恢复），并在 `test:ref-parser`、`test:composer-refs` 补回归 |
| A2-乙（最小改动） | 保留 textarea 内的完整标记，只把卡外 chip 移进卡内并 token 化 | 输入框里仍会看到长路径文本，与“只要一个小 tab”不完全一致 |

## 4. 方案 B：忙碌态投递方式重构（推荐 B1）

| 选项 | 交互 | 评价 |
|---|---|---|
| **B1（推荐）** | 折叠为 chip 行右侧一个紧凑控件：`[图标] 排队 ▾`（当前模式），点击向上弹出三选一（立即执行 / 排队 / 注入上下文），复用既有 popover 样式与 Esc/外部点击关闭；发送按钮图标随模式变化（↑ 立即 / ⇥ 排队 / ⧉ 注入），Enter 与按钮语义一致 | 平时只占一行 chip 的位置，忙时不额外占行；语义清晰 |
| B2 | 保留行内三按钮，改图标 + tooltip、去掉长提示与左侧文案，压到 22px 与 chip 行同高 | 改动最小，但仍是常驻一行 |
| B3 | 三态收进发送按钮的下拉（点箭头选投递方式），行内只显示当前模式文字 | 最省空间，但每次切换多一次点击 |

无论选哪个，都统一：移除 9.17px 提示文字（改为 `title`/浮层内说明）、按钮字号不低于 11px、`aria-pressed` 保留、键盘可达。

## 5. 验收口径

1. 卡片几何：三类 token 的 `getBoundingClientRect()` 完全落在 `.chat-compose` 卡片内（含 border 内边距），不再出现兄弟节点在卡外。
2. token 视觉：文件名可见、路径不出现在正文、hover 有完整路径 tooltip、22px 高、× 可移除且移除后输入框对应标记同步消失。
3. 发送正确性：含引用/附件/图片三种组合各发一次，服务端 Run 的 `task.references` 与用户看到的一致（A2-甲 需专门验证“输入框无长标记但 references 完整”）。
4. 忙碌态：忙时 chip 行高度不超过 1 行；切换投递方式后发送行为随之改变（可断言 busy + 排队 → 进入队列坞；busy + 立即执行 → 直接提交）。
5. 回归：`npm run verify`、`test:chat-layout`、`test:chat-layout-columns`、`test:workspace-panel`、`test:composer-refs`、`test:ref-parser`、`test:a11y`、`test:ui-guard`（后两个当前有既有失败，需在实施记录中证明未新增）。
6. 真实浏览器：1440×900 / 1280×800 / 1024×768 三档截图，暗/亮主题各一张。
