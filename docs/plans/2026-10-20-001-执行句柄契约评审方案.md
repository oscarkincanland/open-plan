# P1-a 执行句柄契约（评审方案）

> 路线图 P1-a（Qoder 对标 P1-1 延续）。**本文是评审材料，不是实施记录**：
> 按"需评审+灰度"约束，评审签字前不动 `index.mjs` 主链路。
> 现状勘测基于 v0.11.55（38ccbf87 + P1/P3 未提交批次）。

## 1. 背景与问题

Run 的执行/中断/交互/订阅四类操作目前没有统一入口，散落在三层：

| 关注点 | 现状位置 | 问题 |
|---|---|---|
| 执行 | `index.mjs` 发送路由内联编排（beginRun → capability plan → agentManager 调用 → onEvent 回调接 emitChannel，~4460-4800） | 发送路由 400+ 行，编排逻辑无法单测 |
| 中断 | 两条路径各自拼装：`/api/runs/:id/cancel`（runs.mjs `requestRunCancellation`）与 `/api/agent/abort`（`requestRunCancellation` + `listPendingCancellations` 排空 + stillQueued 回执） | 语义重复且不完全一致；新增取消入口容易漏排空/漏回执 |
| 交互（HITL） | `agentManager.submitAnswer`（agent.mjs:914，迟到续跑排队接力）、审批作用域在 agent 内部；index.mjs 只做 HTTP 壳 | 交互归属（P1-4）与续跑语义分散在两处，契约不可见 |
| 订阅 | `emitChannel(entry, type, data)` 在 index.mjs 全文 20+ 处直接调用；agent.mjs 侧另有 `emitChannelSafe` | 事件出口无统一门（配额/stale/schema 校验各自挂在端点层） |

Qoder 对标结论：执行器把"一次 Run 的所有操作"收敛为一个句柄对象（open → steer/interrupt/answer/close），
调用方不感知内部排队/排空/回放细节。本方案对齐该形态，但**不改任何运行语义**。

## 2. 目标与非目标

**目标**
1. 抽 `server/执行句柄.mjs`：一次 Run 生命周期的统一操作面（start / interrupt / submitAnswer / resolveApproval / subscribe / snapshot）。
2. `index.mjs` 发送路由改用句柄编排（路由瘦身，编排逻辑可单测）。
3. 中断双路径合并为同一实现（排空 + stillQueued 回执行为保持逐字一致）。
4. 事件出口收敛：emitChannel 调用经句柄的 subscribe 门转发（门内逐字转发，不加逻辑）。

**非目标**
- 不改 runs.mjs 的记录语义、不改 agent.mjs 的排队/续跑/排空内部实现。
- 不动事件协议（V2 schema/代际/游标）。
- 不做前端改动。

## 3. 契约草案

```js
// server/执行句柄.mjs（纯编排层，零 I/O 假设，依赖注入）
createExecutionHandle({
  clientKey,            // agentKey(client, thread)
  agentManager,         // 复用现有实例（不新建 Runtime）
  runsApi,              // runs.mjs 的 begin/finish/cancel/pendingCancellations…
  emit,                 // (type, data) => void  —— 即 emitChannel(entry, …) 的柯里化
  runtimeFlags,         // 运行开关快照（灰度判定）
}) => ({
  start(payload),        // 执行编排：capability plan → 提交 → 事件接线（现发送路由内联段）
  interrupt(reason),     // 合并取消/中断：requestRunCancellation + 排空 + 返回 { cancelled, stillQueued }
  submitAnswer(answer),  // 透传 agentManager.submitAnswer（live/queued_resume/resumed 语义不变）
  resolveApproval(id, decision),
  subscribe(listener),   // 事件出口门：逐字转发（灰度期）；
  snapshot(),            // { runId, status, queuedCount, busy, compacting }（读现有 entry/runsApi，不新增状态源）
})
```

## 4. 改动面清单

| 文件 | 改动 | 灰度分支 |
|---|---|---|
| `server/执行句柄.mjs` | **新建**（契约实现，~200 行） | — |
| `server/index.mjs` | 发送路由内联段 → `handle.start()`；两条中断端点 → `handle.interrupt()`；`/api/agent/answer` → `handle.submitAnswer()` | flag 开走句柄，关走原路径（两套并存一个迭代周期） |

| `scripts/执行句柄契约测试.mjs` | **新建**：契约单测（fake agentManager/runsApi/emit，断言 start 编排顺序、interrupt 等价性、submitAnswer 透传、subscribe 逐字转发） | — |

## 5. 灰度与回滚

- 开关 `OAW_EXECUTION_HANDLE`（默认关）：关闭时代码路径与基线**逐字一致**（句柄文件存在但不被调用）。
- 打开方式：env 或 `OAW_QODER_ALIGN=1` 整族联动（与 P1 系列一致）。
- 回滚 = 关开关，无残留（句柄文件保留不影响基线）。
- 灰度观察点：`/api/diagnostics/streams` 与 runs 记录的中断/取消成功率、stillQueued 回执值、ask 续跑 mode 分布。

## 6. 验证方案

1. `test:execution-handle`（新）：契约单测 + 「开关关=基线逐字一致」源断言（同 P1-6/P3-b 守护测试模式）。
2. 全量既有门禁：`npm run verify`、`test:abort-drain`（中断排空语义）、`test:approval`（审批作用域）、`test:task-center`、`test:main-flow`、`test:chat-flow` 必须全绿——这些直接覆盖被迁移的语义。
3. live 冒烟：开关开跑一次真实 Run（含 ask_user 续跑 + 中断排空），对照开关关的 runs 记录差异。

## 8. 实施排期（评审通过后）

1. 契约单测先行（含假依赖）→ 2. 句柄实现 → 3. index.mjs 三处调用点迁移（flag 双路径）→ 4. 全量门禁 + live 冒烟 → 5. 默认开（用户批准后）→ 观察一个迭代周期后删除旧路径。
