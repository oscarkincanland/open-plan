### 0.2 冲突裁决顺序（从上到下，前者优先）

1. **代码的实际可运行行为**（最终事实）
2. `AGENT.MD`（硬规则与权限边界）
3. `02-开发规范` / `04-验收清单`（过程与完成定义）

发现文档与代码冲突：**先停下报告**，确认后改文档；禁止用"猜"补齐。历史文档（`docs/`、`REQUIREMENTS.md`、`变更日志.md`）作为证据与背景保留，**冲突时以本体系为准**。

### 0.3 编号契约

- `R-xx`：需求域编号，沿用 `REQUIREMENTS.md` R1–R15，**不复用、不重排**。

## 1. 一页纸

- **用户是谁**：交通规划工程师、规划院/设计院的方案编制与审查人员（单机、少人数协作，不是面向公众的产品）。
- **他们现在的做法**：Word/Excel/PPT 之间反复复制粘贴；交通数据在 Excel 与 GIS 软件之间来回导；规范审查靠人工逐条比对；材料版本散落在本地文件夹。
- **痛点**：一份规划材料要在"写作—算数据—出图—审规范—改稿"之间切换五六个工具，重复劳动多、口径难统一、过程不可追溯。
- **做成之后的可见变化**：在同一个工作台里完成"对话下指令 → Agent 读写 Office 文档 / 分析交通数据 / 出专题图 → 产物自动落工作区并可回滚 → 审查报告绑定规范依据"。
- **明确不做**：见第 6 节。这一节与功能清单同等重要。

## 2. 产品定位与业务目标

**Open Plan（规聚）**：面向交通规划工程师的**本地化 AI 办公工作台**。

- 形态：Web 工作台（Express 单服务 + React SPA），浏览器/桌面端访问 `127.0.0.1:3002`。
- 内核：Pi Agent SDK（进程内调用，不改内核）+ officecli（Office 文档受控操作）。
- 部署：本地单机优先；工作区即本地文件系统（`office-workspace/`），**数据不出本机**。

| # | 业务目标 | 落点（实现域） | 状态（v0.11.55） |
|---|---|---|---|
| B1 | 办公文档 AI 协作：查看/编辑/生成 docx/xlsx/pptx，保真预览 | 文档引擎、officecli、DocViewer 家族 | 已完成主链路 |
| B2 | 审查合规：依据规范库审查材料，产出报告 + 批注副本，确认后才写回原文 | Review 模式、review_source 台账 | 已完成 |
| B3 | 知识资产沉淀：Obsidian 式知识库、图谱、全文检索、@引用分析 | KnowledgeBase、kb_search/kb_read | 已完成 |
| B4 | 交通 GIS 沙盘：路网底图、图层模型、空间分析、分析模板、批量导出 | maps/ 项目体系、MapPanel | 进行中（真实流量数据待接入） |
| B5 | 多模型 Agent 编排：30+ 模型、推理三档、子代理编排、编辑流水线、MCP 桥 | agent.mjs、子代理编排器、编辑流水线 | 已完成 |
| B6 | 交付可信：产物暂存→发布、写入清单、运行记录、回滚、验收台账 | `.oaw/runs`、写入协调、成果管理 | 已完成 |

**判断产品有用的标准**（上线第一天可观察）：用户能在不离开工作台的情况下，完成一次"读文档 → 改文档 → 出数据图 → 导出产物"的完整任务，且刷新/重启后能追溯每一步。

## 3. 核心场景（最多 3 条）

### S-01：规划公文/报告的编制与修订

- **谁**：规划院方案编制人员。
- **什么时候**：收到一份待修改的 docx/pptx，或需要从零起草汇报材料。
- **想做什么**：让 Agent 读原文、按意见修改、保留格式，并生成一份可交付的新版本。
- **期望看到**：文档在工作区生成/更新，预览保真；本次改动的每个文件出现在「本轮产物」并可回滚。
- **怎么算对**：第三个人按"打开文件 → 对照修改意见 → 检查产物清单"三步能独立确认；未授权时原文不被覆盖。

### S-02：交通数据分析与专题图

- **谁**：交通规划工程师。
- **什么时候**：手上有 OD/客流/路网数据，需要出热力图、OD 期望线、等时圈或对比分析。
- **想做什么**：用自然语言描述分析目标，让 Agent 调用地图工具生成临时可视化，必要时保存为正式图层。
- **期望看到**：地图上出现正确图层，图层面板能看到、能显隐、能删除；写操作有审批；Chat 模式下不落盘。
- **怎么算对**：切换 Chat/Work 两种模式，行为边界与第 4 节一致；刷新后正式图层仍在，临时层不残留。

### S-03：材料合规审查

- **谁**：审查岗/校核人。
- **什么时候**：材料送审前，需要按规范逐条核对。
- **想做什么**：指定材料与规范库，要求输出审查报告和带批注的副本。
- **期望看到**：每条结论都绑定实际读取的规范文件；写回原文前必须经 `ask_user` 确认。
- **怎么算对**：抽查任意一条结论，能定位到具体规范文件与原文位置；拒绝确认时原文保持字节级不变。

## 4. 用户角色与四种工作模式

四种模式由 `server/task.mjs` 的 `toolPolicyForMode` 统一约束工具白名单；**声明了却调不到**视为缺陷。

| 模式 | 定位 | 能力边界（硬约束） | 典型入口 |
|---|---|---|---|
| **Chat** | 检索问答 | 只读：知识库/Skills/工作区资料/地图只读四件套；不写盘 | 对话栏 Chat |
| **Office** | 文档处理 | 只读工具 + officecli；不开放 `bash`、通用写入与地图工具 | 对话栏 Office |
| **Work（agent）** | 全能执行 | 完整工具链：分析、写盘、地图写入、浏览器、编辑流水线；写操作需审批 | 对话栏 Work |
| **Review** | 规范审查 | 本地材料 + 规范库；不联网、不用 `bash`；报告 + 副本，确认后写回 | 对话栏 Review |

补充规则：

- 地图写工具（`map_edit` / `map_import` / `map_save_analysis`）**只在 Work**；Chat 要求写操作时必须提示切模式，禁止绕过。
- `run_subagent` 只在 Chat / Work 声明；子代理 `worker` 仅在父会话可写时生效，否则降级 `scout`。
- CAD 能力由 `cadPreview` / `cadAgent` 双开关控制，默认关；关闭时行为与基线逐字一致。

## 7. 明确不做（非目标）

写下来是为了防止 AI 自作聪明加功能，也防止需求无限扩张。以下条目来自对标报告 §6.2 与历史决策，全程有效：

- 不做 Qoder 皮肤引擎（多 Flavor × Swatch）；只对齐视觉语言，不追求复刻界面。
- 不把对话流改为手写 SSE 解析（保留原生 EventSource）。
- 不修改 Pi 内核；不引入官方不存在的 subagent / plan mode 能力假设。
- 不新增独立应用 / 独立前端工程 / 独立后端服务。
- 不做移动端适配；只在桌面浏览器（≥1280px）使用。
- 不做多租户与公网部署；默认无权限体系，所有人本机使用。
- 不引入数据库服务（PostgreSQL/MySQL/Redis）；持久化用本地文件 + `node:sqlite`（如确需）。
- 不新增 npm 依赖（硬约束，见 D-004）；确需新增须走 06 决策流程。
- 不提交 `.oaw/` 运行记录、视频类文件、构建产物、密钥。
- 不做老格式 `.doc/.ppt/.xls` 的转换队列（按 415 拒绝，需要时再立项）。
- 不做关系图视图、RAG 问答等未立项能力（等路线图排期）。

| 规划院现有 Office + GIS 流程 | 术语、材料类型、审查口径 | 把多工具切换收敛到一个工作台 | 全套 GIS 桌面软件能力 |

**对标只定结构，不定功能清单。** 参考产品里我们不做的功能，必须写进第 7 节。
