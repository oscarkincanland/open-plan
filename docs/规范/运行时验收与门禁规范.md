> 状态：生效　版本：1.1　更新：2026-11-18
> 依据：[全仓缺陷复盘](../audits/2026-11-17-全仓缺陷复盘/00-复盘报告.md) §3.3/§3.4、[功能验证测试规范](功能验证测试规范.md)、[计划 2026-11-17-003](../plans/2026-11-17-003-评审四目标与测试路径落地计划.md)、`AGENTS.md` §7.1 提交门禁、§8 完成定义
> 适用：本仓库全部前端渲染改动、提交与 CI

---

## 0. 为什么需要这一层

`node --check` / `vite build` / 源码字符串断言能证明「代码写着什么」，不能证明「用户打开页面看到什么」。历史上同一类缺陷重复出现：

- TDZ / 作用域错误 **6 次**（`36153ede`、`1f1dcb2e`、`4ab158b0`、`006cc699`、`10537845`、`6b211910`），加上 2026-11-15 v3 改造的 2 次 `ReferenceError` 与 1 次无效 hook 调用；
- `变更日志.md:2146` 的原话：**「`npm run verify`、49 步 CI 全绿都发现不了它（TDZ 只在特定分支执行时才抛）」**；
- v3 改造中还出现「删掉结论卡 → 部分轮次结论消失」「旧执行流未收敛 → 中断后老式界面复现」等**多通道**问题。

本规范把「运行时验收」固化为三条门禁：**G1 运行时冒烟、G2 已知失败基线、G3 提交意图门禁**。

## 1. G1 运行时冒烟（`npm run test:ui-smoke`）

### 1.1 定义

用真实浏览器（Playwright，本机已装；优先 chromium，回退 msedge/chrome）打开本机服务，**必须真的进入一条有消息的会话**，然后断言：

| # | 判据 | 失败含义 |
|---|---|---|
| 1 | 不出现错误边界（「组件出错，请刷新页面」） | 渲染分支抛错（ReferenceError / hook 违规等） |
| 2 | 不出现应用错误页 | 顶层崩溃 |
| 3 | 无 `pageerror`、无非噪声 `console.error` | 运行时异常被吞 |
| 4 | `.msg` ≥ 1（**空会话视为失败**） | 没测到消息组件＝冒烟无效 |
| 5 | 折叠头开合位移 ≤ 2px | 折叠补偿失效（用户可感知的位置跳变） |
| 6 | （报告项）会话流字号 ⊆ 规范 §4 白名单 | 只告警并列出，不阻塞 |

### 1.2 何时必须跑

- 任何改动 `client/src/components/ChatPanel.jsx`、`client/src/会话流/**`、`client/src/components/会话流/**`、`client/src/styles.css` 的提交；
- 任何新增/修改渲染通道的提交（见《[会话流渲染通道清单](会话流渲染通道清单.md)》）；
- 发版前与 `npm run verify` 一起跑。

### 1.3 环境约定

- 需要服务在跑：`npm start`（默认 `http://127.0.0.1:3002`）；服务不可达时脚本退出码 `2`（**跳过**，不算失败，但不得当作通过写进交付说明）；
- 可指定目标：`node scripts/聊天界面冒烟检查.mjs <baseUrl> [clientId] [sessionId] [workspace] [截图]`；
- 脚本会自动挑选「本机 cwd 存在」的会话，避免命中未挂载磁盘的移动硬盘会话。

## 2. G2 已知失败基线（`npm run test:known-failures`）

### 2.1 原则

**既有失败可以暂时存在，但必须被登记、被追踪、会过期**；未登记的新失败一律视为回归。

### 2.2 基线文件

`scripts/门禁已知失败基线.json`，每条必须包含：

```json
{
  "id": "test:ui-guard",
  "script": "界面一致性守护测试",
  "expect": "fail",
  "signatures": ["功能代码无 emoji 图标", "界面色值走令牌"],
  "owner": "前端",
  "reason": "为什么暂时不修",
  "expires": "2026-12-15"
}
```

| 字段 | 约束 |
|---|---|
| `signatures` | 失败输出里必须出现的特征串；用于区分「已知失败」与「同套件的新失败」 |
| `owner` / `reason` | 必填，禁止只写「与本次无关」 |
| `expires` | 必填；过期未清则 `test:known-failures` **失败**（禁止永久豁免） |

### 2.3 校验逻辑

1. `expect: fail` 且实际失败：输出必须命中全部 `signatures`，否则判「未登记的新失败」→ 退出码 1；
2. `expect: pass` 且实际失败：判新增回归 → 退出码 1；
3. `expect: fail` 但实际通过：提示从基线移除（不阻塞）；
4. 过期未清 → 退出码 1；
5. `--update` 按实际结果重写 `expect`/`signatures`（保留 owner/reason/expires），用于清理与登记，**不得用来掩盖新失败**。

### 2.4 当前登记（2026-11-17）

## 3. G3 提交意图门禁（`npm run check:commit-gate`）

### 3.1 规则

| 级别 | 规则 | 依据 |
|---|---|---|
| **失败** | 同一提交**新增** `docs/plans/*.md` 且同时修改 `client/` 或 `server/` → 计划与实现同提交 | AGENTS §7.0 文档先行 |
| 警告 | 改了代码但没有测试文件伴随 | §7.1-2 |
| 警告 | 提交信息没有需求编号/缺陷/计划线索 | §7.1-1 |
| 警告 | 同时改计划与代码但信息未引用计划号 | §7.1-6 |

### 3.2 用法

```bash
node scripts/提交门禁检查.mjs                 # 检查 HEAD
node scripts/提交门禁检查.mjs 7fa33087        # 检查指定提交
node scripts/提交门禁检查.mjs --range origin/develop..HEAD
```

已知历史违规示例：`7fa33087`（v3 实现与 `2026-11-14-001` 两份计划同提交）会被判失败。

## 4. 与既有门禁的关系

| 门禁 | 职责 | 关系 |
|---|---|---|
| `npm run verify` | 平台边界、验证脚本、API 冒烟 | **不够**：只串 2 个脚本，不含前端运行时 |
| CI（67 步） | 多套件静态/接口断言 | **不够**：约 72% 的 `test:*` 未进 CI |
| G1/G2/G3 | 运行时 + 失败可区分 + 意图可判 | 补上上面两者的缺口 |
| G4 业务流验收 | 浏览器里「输入 → 产物」的关键业务流（`:live`） | **补缺口**：G1 只测渲染，G4 测业务完成；判据见《[功能验证测试规范](功能验证测试规范.md)》§8.2 |

**推荐执行顺序**：`npm run build` → `npm start` → `npm run test:ui-smoke` → `npm run test:known-failures` → `npm run check:commit-gate` → `npm run verify`；**发布前**再加 `npm run test:e2e:live -- --flow=chat|work|review`（G4，见《功能验证测试规范》§8.2）。

## 5. 维护

- 本规范由「流程优化」计划驱动，修改需同步 `变更日志.md`；
- G4 的流清单、判据与证据格式以《[功能验证测试规范](功能验证测试规范.md)》§8.2 为唯一事实来源，本规范只维护门禁定位与执行顺序；
- 基线清零不代表门禁失效：`expect` 全部为 `pass` 时本规范仍然有效（它保证「没有未登记的失败」）；
- 若某套件长期无法修复，正确做法是把它从默认套件移出并单独登记「暂停原因 + 复核日期」，而不是在基线里延期。
