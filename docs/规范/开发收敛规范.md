# 开发收敛规范

> 状态：生效　版本：1.0　基线：v0.13.3　更新：2026-11-02
> 依据：[AGENTS.md](../../AGENTS.md)、[文档管理规范](文档管理规范.md)、[功能验证测试规范](功能验证测试规范.md)、[架构规范](架构规范.md)、[代码规范](代码规范.md)
> 适用范围：仓库内全部功能开发、缺陷修复、文档与决策记录
> 来源：[开发收敛与质量门禁计划](../plans/2026-11-01-001-开发收敛与质量门禁计划.md)（2026-11-01/02 审计与收敛的产物）

## 0. 目的与核心命题

2026-10-25 至 2026-10-31 一周的审计结论不是"没做事"，而是**做的事比记录更实，但记录与门禁跟不上**：

- 主体功能真实落地（画布、会话切换、Harness 16 模块、Office 规范层 12 模块、GIS 四需求），且有对应测试；
- 但 `npm run test:harness` 当时是**红的**（7 个后加工具没同步元数据表）；
- 文档里"已完成"的断言大面积不实（追踪矩阵 17 行写"未开始"、盘点表把已落地项标"未实现"）；
- 版本状态在四个文件里有四种说法；
- 7 个事件"已登记却从不发射"，文档把它们列为已交付；
- ADR 0012 被 checkpoint 提交覆盖成 0 字节空文件，且无人索引。

所以本文约束的不是"写更多文档"，而是**让四条线始终一致**：

| 线 | 唯一事实来源 | 其他地方的正确角色 |
|---|---|---|
| 能力（有哪些工具/模式可用） | `server/task.mjs` | 只能引用，不得复制 |
| 契约（工具属性、事件类型） | `server/工具元数据.mjs`、`server/事件注册表.mjs` | 契约变更必须同提交同步 |
| 行为（功能是否实现、测试是否守护） | 代码 + `scripts/` 下的测试 | 文档只能描述，不得替代 |
| 状态（做到哪、什么版本） | `版本管理计划.md` | 变更日志只描述不裁决 |

**判定规则**：任何一处文档/代码与另一处不一致，都算缺陷；修复方向永远是"让副本回到事实源"，而不是"给副本加一段说明"。

## 1. 能力线：加工具的五步清单

任何新增或改名工具，**同一个提交内**必须完成：

1. `server/agent.mjs`（或对应模块）实现工具；
2. `server/task.mjs` 加入需要它的模式白名单；
3. `server/工具元数据.mjs` 补 `meta(...)` 条目：`readOnly`/`destructive`/`sideEffectScope`/`riskLevel`/`needsApproval`/`resultBudget`；
4. 若产生新事件 → `server/事件注册表.mjs` 登记（含 payload schema）**并**在同一处发射；
5. 契约测试转绿：`npm run test:tool-metadata`、`npm run test:capability-contract`。

> 2026-10-29 之后的 7 个工具（`map_layer_info`/`map_reset`/`map_project_create`/`browser_wait_for`/`browser_act`/`browser_extract`/`browser_select_option`）正是漏了第 3 步，导致 Harness 契约测试长期变红而无人发现。

**禁止第二份工具名清单**：`server/agent.mjs` 不得再出现硬编码的工具名数组，需要集合时从 `server/task.mjs` 的 `allModeToolNames()` 派生。`npm run test:tool-metadata` 会断言这一点。

**内部工具**（浏览器、编辑流水线、`run_subagent`）可以不在能力计划里，但必须在白名单或动态注入中可追溯（AGENTS.md §5）。

## 2. 契约线：事件与元数据必须双向一致

- 事件注册表是事件流的唯一事实来源；**登记即必须有发射点**。`npm run test:event-emission` 守护这条（已用反证验证：移除发射点即报错）。
- 事件一旦产生，**必须有消费方**（前端投影、诊断 API 或审计用途）；只有登记没有消费的"死事件"要么接上消费方，要么从注册表移除。
- 契约测试必须**双向**：既查"该有的有没有"，也查"多出来的有没有"。只做正向覆盖会漏掉"后加的工具没登记"这类问题。
- 工具改名/删除 = 契约变更：走 ADR，同步清理白名单、元数据表、事件注册表、图标映射与测试断言。

## 3. 测试线：分层与门禁

| 层 | 位置 | 目的 | 要求 |
|---|---|---|---|
| 单元 | `scripts/*测试.mjs` | 纯函数/模块行为 | 覆盖边界与异常分支 |
| 契约 | 能力契约 / 工具元数据 / 事件注册表 / 事件发射点 / 决策记录索引 / 规范索引 | 跨文件事实源一致性 | 双向断言 |
| 集成 | `Office*测试.mjs`、`写入锁并发测试.mjs` | 多模块协作 | 必须真并发或真进程，不能只断言源码字符串 |
| 端到端 | `*端到端测试.mjs`、`GIS*测试.mjs` | 用户可见路径 | 需要真实数据样本 |

**门禁分层**

| 门禁 | 内容 | 维护要求 |
|---|---|---|
| `npm run verify` | 语法 + 构建 + css-syntax + API 冒烟 | 契约层测试（能力/元数据/事件发射点/索引守护）与关键回归（写锁、恢复隔离、Office 闸门、并发回归）必须在内 |
| CI | 多步测试 | 与 `verify` 不重复但更全；**不得引用已删除的脚本** |
| 手动 | 浏览器视觉、L4、真实模型并发 | 发布前必跑并留证据到 `docs/audits/` |

`node scripts/CI全量复跑.mjs` 可一次性复跑 CI 声明的全部步骤并统计红绿，同时报出"CI 引用了已删除脚本"的配置漂移。

**不接受"只读源码正则"作为主要守护**：正则断言无法发现 CSS 语法错误、懒加载 chunk 失效、真实粘贴/布局问题。要么用 `getBoundingClientRect()` 之类真实测量，要么明确标注为"结构断言"并在文档里承认它不验证视觉结果。

## 4. 文档线：状态必须可数

- **计划三态**：未开始 / 进行中 / 已实施。标"已实施"必须**有同序号 `实施记录.md`**（写清改动文件、测试、偏差、遗留），且计划内完成定义复选框已勾、状态与正文无矛盾。
- **数字必须能数出来**：写"N 例通过"时，数字必须能从脚本里数出来；同一文档里同一指标不许出现两个数字；引用不存在的文件前先确认它存在。
- **状态列写实测结论**；写"通过"必须指向一个可复跑的命令。
- **不允许孤儿文档**：`docs/规范/`、`docs/决策记录/` 的每个文件都必须能从 `AGENTS.md §10` / 决策记录索引到达，且**不允许 0 字节**。由 `npm run test:spec-index`、`npm run test:adr-index` 守护。
- **不得描述未验证的"理想状态"**（文档管理规范 §9）。
- 规范状态为"草案"的不得作为实施依据；若已被已采纳 ADR 引用，要么晋升为"生效"，要么改掉引用。

## 5. 提交线：一个提交一个意图

- 格式：`类型(范围): 描述`；类型限 `feat/fix/docs/refactor/test/perf/build/ci/chore`。
- **新增行为的测试必须同提交**：`feat`/`fix`/`perf`/`refactor` 触及 `client/` 或 `server/` 源码时，同提交内必须新增或修改至少一个 `scripts/` 下的测试文件；确无自动化测试（如纯样式）需在提交正文写明理由。
- **禁止 checkpoint / 暂存型提交**：切换分支前用 `git stash` 或独立 worktree，不提交"暂存"。这类提交是 ADR 0012 变空文件、备份文件入库的直接成因。
- 不提交运行时产物（`.oaw/`、`.规聚会话/`、`client/dist/`、日志、备份文件）。
- 高风险改动点名人工复核：往白名单加工具（看契约层）、标记/命令解析（看解析层）、多标签页 SSE/leader 仲裁（看真实连接数）、无障碍/键盘（确认守护脚本**真的读了**该组件文件）、版本/发号（同步四处状态）。

## 6. 版本线：一个裁决者

- `版本管理计划.md` 是版本状态的**唯一裁决者**；`变更日志.md` 只描述"改了什么"；`package.json` 的 `version` 始终等于**当前已发布版本**，发布时才提升。
- patch 编号在变更日志落段时分配并写入版本管理计划表格，线内连续递增、不跳号。
- 状态区分两级，不得混用：
  - **已发布** = 已在 `main` 且打了 tag；
  - **已完成** = 已在 `develop` 但尚未发布。
- 发布（合并 `develop` → `main` 并打 tag）属发版动作，需用户确认后执行。

## 7. 默认关闭必须显式

- 新增运行开关必须在 `server/运行开关.mjs` 登记，并在文档里写明"默认关闭，需 `XXX=1` 启用"。
- **"关开关 = 基线"必须有测试守护**；若某能力在开关关闭时仍无条件生效，需在文档里如实说明（不得宣称已回滚）。
- 文档写"已落地"时，必须区分"能力代码就位"与"用户默认体验已生效"。

## 8. 每次开发的标准动作

1. **读**：AGENTS.md → `docs/规范/` 相关规范 → 本主题的计划/ADR → 代码。
2. **认领事实源**：确认这次改动落在哪条线上，该线的唯一事实来源是哪个文件。
3. **同提交闭环**：实现 + 契约同步（第 1、2 节清单）+ 测试（第 3 节）+ 文档同步（第 4 节）+ 变更日志（第 6 节）。
4. **自检**（三条全绿才算完成）：
   ```bash
   npm run verify
   npm run -s test:harness
   node scripts/CI全量复跑.mjs
   ```
5. **写记录**：计划类改动补实施记录；架构/契约改动开 ADR 并更新索引。
6. **报**：交付总结写清"改了哪个事实源、哪个测试守护、哪些文档同步、哪些已知未同步"。

## 9. 完成定义（DoD 收敛版）

在 AGENTS.md §8 基础上补充四条可判定项：

- [ ] **事实源一致**：白名单、元数据表、事件注册表、图标映射之间无漂移（契约测试双向通过）。
- [ ] **门禁绿**：`npm run verify`、`npm run test:harness`、CI 全步骤均通过。
- [ ] **文档可数**：文档中的用例数、文件引用、状态与仓库实际一致。
- [ ] **提交干净**：`feat`/`fix` 同提交带测试；无 checkpoint 型提交；无运行时产物。

## 10. 例外与复核

- 纯文档改动不要求同提交带测试，但**数字与引用必须可数**。
- 依赖本机环境（officecli、浏览器、真实模型）的用例走 `:live` 套件，在发布前手工执行并留证据，不进默认 CI。
- 本文与 `AGENTS.md` 冲突时以 `AGENTS.md` 为准，并按 AGENTS.md §7 开 ADR 记录本次规则变更的理由。
