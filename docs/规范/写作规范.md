## 1. 目的与适用范围

本规范约束产品生成的中文书面产物：Markdown 终稿，以及由同一份 Markdown 直通生成的 docx/pptx 正文。适用文体包括公文、规划/研究报告、汇报材料、说明文档、审查/评审意见与演示文稿文案。

不约束：用户手写内容、代码注释、日志、系统提示语；版式、字体、页边距等排版要求见 [Office 排版规范](Office排版规范.md)，本规范只管"写什么、怎么写"。

## 2. 写作宪法（强制）

### 2.1 禁用清单

- **空转套话**：删去不损失信息的开场与过渡，如"随着……的不断发展""在当今……背景下""值得注意的是"（无实际转折时）；"综上所述"只在确实做总结时保留。
- **意义拔高**：无证据的"具有重要意义""里程碑""开创性""赋能""抓手"等评价性词汇；判断必须由事实与影响支撑。
- **重复结论**：同一结论在开头、中间、结尾反复复述；结论段不再重复背景与过程。
- **空序列**：没有真实层级关系时不用"首先/其次/最后"凑结构；编号只用于有顺序或可引用的条目。
- **无主语承诺**："将进一步提升""持续优化"这类没有主体、对象、时限或度量的承诺；写清谁、何时、做到什么程度。
- 结尾不用"已完成/通过校验/建议后续"替代交付事实；交付信息按 §4 的交付三句写。

### 2.2 具体化

- 每 500 字至少 3 个可核验事实：数字、日期、文件名与章节、来源、范围、约束、责任人。
- 引用落到文件与章节（如"《XX 规划》第 3 章"），不写"有关文件/相关资料/上级要求"。
- 无来源的数据与结论标注"待核实"，不得编造来源或把推测写成事实。
- 至少一处使用来自用户材料的细节（专有名词、统计口径、字段名、案例），不得只复述通用知识。
- 数字前后一致：同一指标在全文使用同一口径与单位，不得前后矛盾。

### 2.3 结构与节奏

- 结构随文体，不套固定六步模板；短文本不强行分节，长文本按"结论—依据—行动"组织。
- 先结论后依据；标题必须承载信息，空标题删除，不用加粗行冒充小节标题。
- 段落长度与信息量匹配；避免连续三段以上同长同构；一段一个判断，长段按语义拆分。
- 表格用于三项以上对比或并列数据，否则用列表或正文；列表项平行、长度接近。
- 节奏有变化：关键结论短句直给，依据与限定条件可以展开；不靠形容词制造强调。

### 2.4 voice sample

- 工作区存在 `memory/style-{project}.md`（200–500 字用户旧文）时，按其句长、用词、称呼与开头方式匹配，不复制原句。
- 无样例时使用通用专业书面语；不模仿网络流行语，不堆叠感叹与口语。
- voice sample 只对当前工作区生效，不跨项目复用；用户明确指定文风时以用户要求优先。

## 3. 各文体的要旨

| 文体 | 首要目标 | 结构与要点 | 禁止 |
|---|---|---|---|
| 公文/通知 | 依据充分、要素齐全、可执行 | 依据 → 事项 → 要求/时间/责任分工；使用规范公文语体，遵循 GB/T 9704 版式要求 | 口语化、夸张评价、评论式收尾 |
| 规划/研究报告 | 结论先行、数据可核验、口径一致 | 结论 → 背景与问题 → 方案/论证 → 依据与风险 → 下一步 | 无来源数字、意义拔高、只给观点不给依据 |
| 汇报材料 | 一页一结论、进展与问题清楚 | 结论/判断 → 关键数据 → 问题与原因 → 下一步动作 | 流水账、过程旁白、只报喜不报忧 |
| 说明/操作文档 | 读者能照做 | 前置条件 → 步骤 → 验证方式 → 失败处理与回退 | 隐含前提、"自行处理"、缺验证步骤 |
| 审查/评审意见 | 问题可定位、建议可执行 | 问题 → 依据（文件/章节）→ 影响 → 建议 四段式 | 无依据判断、人身评价、笼统"建议优化" |
| 演示文稿（PPT） | 每页一个判断 + 证据 | 标题即结论；页面以数字/图表/引用支撑；正文少而可读 | 整段搬运报告、一页多个结论、纯装饰页 |

## 4. 交付自检

生成结束前按下列项自检，不通过则重写对应段落，不整体放弃：

- **套话词表扫描**：命中禁用清单即改写或删除。
- **重复句检测**：同一结论重复出现即合并删除。
- **段长方差**：段落长度过于均匀（模板感）或单段超过 300 字（可读性差）时拆分或合并。
- **无数字段落比例**：正文中没有任何可核验事实的段落占比过高时，补事实或标"待核实"。
- **引用检查**：每条引用能落到文件/章节；无来源不写成事实。
- **一致性检查**：术语、口径、单位、时间范围全文一致。
- 回归口径：`scripts/文风自检测试.mjs`（`test:writing-style`）；脚本失败时重写对应段落，不降低规则。
- 交付三句：做了什么 / 产物路径 / 假设与未完成项。

## 5. 与生成流程的关系

- **一次成稿**：Markdown 正文即终稿，不先出大纲；仅用户显式要求或正文预计 >8000 字时附可选大纲。
- **预览即终稿**：预览自动打开即确认入口；用户修改后重排一次，不重走流程；写回原文件仍需确认（不可逆）。
- **一次验收**：officecli `validate` + 规则闸门一次，失败自动修一次；版式精修使用一次 `batch`，禁止逐属性 `set`。
- **提问预算**：篇幅、受众、风格、章节顺序一律给默认假设并注明；禁止"是否继续/下一步/是否写回"类收尾确认。
- **回合预算**：写作路由软 30 / 硬 60；命中后先收尾并如实记录，不伪装完成。

## 6. 例外与复审

- 用户明确指定文风、模板或篇幅时，以用户要求优先；本规范退让并在交付中说明。
- 法规、公文格式或行业规范有强制要求时，按强制性规范执行。
- 复审触发：文风人工盲评 <4/5；套话/重复检测出现明显误报或漏报；出现未标注"待核实"的事实性错误；用户反馈"机械感"集中出现。

## 7. 验收

- 计划 §20 A-33～A-38：一次成稿、预览即终稿、提问预算、batch 排版、文风自检、写作指标。
- 测试：`test:writing-oneshot`、`test:writing-style`；真实写作 10 例重放 + 3 例真实执行（用户参与），人工盲评 ≥4/5。
- 指标：写作 Run p50 ≤2 分钟 / p90 ≤6 分钟；回合 p90 ≤20；首字 p50 ≤4s。
