## 3. 删除/收敛顺序（建议）

1. **C4 旧执行流**：v3 下已关闭；下一步从基线路径也删掉，并把 `messageExecutionFlow` 的重复投影移除。**注意**：`messageExecutionFlow` 目前还被 C7 的无过程块轨迹合成使用，删除前必须先把该用途迁到投影层，不能直接删计算。
2. **C5 结论卡**：v3 下已关闭且终稿已由 C2 承担；基线路径待产品确认后删。
3. **C6 `RunSummary`**：只在历史 `system` 消息与 Review 轮出现，等历史数据迁移后收敛。
4. **C3 基线折叠**：等 v3 开关**默认打开**并观察一个版本后删除，届时 `transcriptV3` 开关本身也一并移除。
5. **C8 / C9**：C8 与 C6 同源，先合并为一个 system 摘要通道；C9 是缺失提示，不与正文冲突，长期保留。

> 目标终态：**C1 + C2（Work/Chat 运行轮）+ C7（无 runId 的纯问答/Review）+ C9（缺失提示）**，即从 9 条收敛到 4 条。

## 4. 变更本表的规矩

- 新增/删除任一通道，必须同时更新本表与《会话流前端规范》§2；
- 新增通道若与既有通道覆盖信息重叠，必须在表 §2 矩阵里显式写出重叠项，并在计划里说明收敛计划；
- 改动任一通道的渲染分支后，必须跑 `npm run test:ui-smoke`（打开有消息会话的运行时冒烟），见《运行时验收与门禁规范》。
