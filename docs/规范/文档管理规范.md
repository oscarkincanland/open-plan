# 文档管理规范

> 状态：生效　版本：1.1　基线：v0.11.55　更新：2026-10-26
> 依据：[AGENTS.md](../../AGENTS.md)、[产品需求文档](../../REQUIREMENTS.md)、[设计规范](../../DESIGN.md)。适用于仓库内全部 Markdown 文档、计划、报告、规范与决策记录。

## 1. 目的

让文档可发现、可追溯、可维护：

- 一个主题只有一个事实来源；
- 新人/智能体能在 3 次点击内找到现行规范；
- 计划、实施、验收、决策不混写；
- 历史可追溯，不用删除来“清理”。

## 2. 文档分层与唯一事实来源

| 类型 | 位置 | 命名 | 说明 |
|---|---|---|---|
| 工程宪法/智能体入口 | `AGENTS.md` | 固定 | 最高工程约束、智能体能力边界、规范索引；`AGENT.MD` 仅保留为历史指针 |
| 项目总览 | `README.md` | 固定 | 对外介绍、快速开始、质量门禁、分支说明 |
| 产品需求（PRD） | `REQUIREMENTS.md` | 固定 | 目标用户、范围、R1–R16 需求、非功能与验收 |
| 设计规范 | `DESIGN.md` | 固定 | 信息架构、布局、组件交互、设计令牌、双主题、无障碍 |
| 版本与发版 | `版本管理计划.md` | 固定 | 语义化版本、分支、发版流程 |
| 变更记录 | `变更日志.md` | 固定 | 按版本倒序的 Added/Fixed/Changed/Removed/Docs |
| 长期规范 | `docs/规范/` | `<主题>规范.md` | 稳定约束，不写一次性方案 |
| 决策记录 | `docs/决策记录/` | `NNNN-<标题>.md` | 有备选方案与后果的架构/契约决策 |
| 实施计划 | `docs/plans/` | `YYYY-MM-DD-NNN-<标题>.md` | 可执行、带复选框与验收口径 |
| 实施记录 | `docs/plans/` | `YYYY-MM-DD-NNN-实施记录.md` | 计划的实际结果、偏差、验证 |
| 审计/验收 | `docs/audits/` | `YYYY-MM-DD-<主题>/` | 证据、截图、报告、验收结论 |
| 调研/分析 | `docs/` | `YYYY-MM-DD-<标题>.md` | 一次性研究，结论可被 ADR 引用 |

判定规则：

- **规范**回答“以后都怎么做”；**计划**回答“这次怎么做”；**决策记录**回答“为什么这样选，放弃了什么”；**实施记录**回答“实际做成了什么”。
- 同一主题出现两份相似文档时，保留一份为事实来源，另一份改为链接或标记“已被替代”。
- 根目录既有的一次性文档保持原位，不再新增；新增文档一律进入 `docs/` 对应分层。

## 3. 命名规范

- 所有**新增**文档必须中文命名；例外仅限既有固定文件名：`AGENTS.md`、`AGENT.MD`（历史指针）、`README.md`、`REQUIREMENTS.md`、`DESIGN.md`。
- 代码文件按语言惯例（`.mjs` / `.jsx` / `.css`），文件名部分优先中文，如 `server/写入协调.mjs`、`client/src/components/工作产物面板.jsx`。
- 日期统一 `YYYY-MM-DD`；计划序号三位，从 `001` 起，按当天递增。
- 文件名不包含空格、括号、版本号；使用连字符 `-` 连接日期、序号与标题。
- 决策记录编号四位，如 `0003-事件注册表作为事件流唯一事实来源.md`。
- 标题可保留不可翻译的技术专名（React、JSONL、Pi、SSE 等），但主体必须是中文。
- npm 测试别名可使用英文 kebab-case（兼容命令行），但脚本文件名必须是中文，如 `test:map-chat` → `scripts/地图对话栏适配测试.mjs`。
- 禁止 `新建文档.md`、`未命名.md`、`最终版.md`、`最终版2.md` 之类无法检索的名称。

## 4. 文档头与状态

规范性文档、计划、审计报告必须在标题后给出元信息：

```markdown
> 状态：草案 | 生效 | 已完成 | 已废弃 | 被 NNNN 替代
> 基线：v0.11.55
> 更新：2026-10-25
> 关联：AGENTS.md / PRD / DESIGN / 相关规范 / 相关计划 / 相关代码路径
```

要求：

- **规范**必须有状态、版本、基线、更新日期、依据。
- **计划**必须有目标、范围/不做清单、验收口径、实施记录链接。
- **审计报告**必须有审计基线、结论、证据、局限与未验证项。
- 状态为“草案”的文档不得作为实施依据；“已废弃/被替代”的文档保留原文，只在头部标注替代关系。

## 5. 写作规范

- 一事一文档；结论先行，背景其次，细节最后。
- 可执行优先：步骤带命令、路径、验收条件；避免“适当优化”“进一步完善”等无法验证的表述。
- 引用代码必须写相对路径；可附带行号区间。引用外部资料必须给出来源与访问日期。
- 表格用于对比与清单；代码块必须带语言标签；架构图优先 ASCII，保证纯文本可读。
- 不粘贴密钥、Token、用户隐私、完整运行日志；运行证据引用 `.oaw/` 本地路径并说明不随仓库提交。
- 不复制大段代码到文档；用路径 + 符号名 + 行号引用，避免文档与代码双份事实。
- 中文为主；技术专名、API、事件类型、字段名保留原文，首次出现可加中文解释。

## 6. 生命周期与归档

```text
草案 → 生效 → 已完成 / 已废弃 / 被替代
```

- 计划完成后：在计划末尾追加“实施结果”，或新建同序号 `实施记录.md`；写明改动文件、测试、偏差、遗留。
- 规范升级：更新版本与日期；旧约束被删除时要写“移除原因”，不能静默消失。
- 决策变更：不修改原 ADR 的“决策”结论；新建 ADR 并在原记录状态写“被 NNNN 替代”。
- 审计报告视为不可变证据；补充内容以“补记”形式追加，不改原结论。
- 历史文档不删除；确需清理时移到 `docs/归档/` 并在索引中保留链接。

## 7. 变更联动

| 改动 | 必须同步 |
|---|---|
| 任何用户可见功能/修复 | `变更日志.md` |
| 新功能/大改动 | `docs/plans/` 计划 + 实施记录 + 验收证据 |
| 架构、契约、依赖、存储、内核变更 | `docs/决策记录/` + 对应规范 |
| 新增/修改规范 | 规范自身 + `AGENTS.md` 索引 + 相关代码注释中的依据 |
| 缺陷修复 | 回归测试 + `变更日志.md` |
| 删除能力/接口 | ADR 或计划中的“不做清单” + `变更日志.md` 的 Removed |
| 版本发布 | `版本管理计划.md` 状态 + `变更日志.md` + tag |

禁止“代码改了、文档以后再说”。无法同步时，在交付总结中明确未同步项与原因。

## 8. 索引与发现

- `AGENTS.md` 第 10 节必须列出 PRD、DESIGN、全部长期规范与决策记录索引。
- 新增规范或 ADR 的同一个提交内，必须更新上级索引。
- `README.md` 只保留总览级链接，不复制规范细节。
- 不允许“孤儿文档”：任何 `docs/规范/`、`docs/决策记录/` 文档都必须能从索引到达。
- 计划文档之间可以互相引用，但不要形成循环依赖。

## 9. 禁止事项

- 新建英文命名文档（固定文件除外）。
- 同一需求重复建计划；应更新原计划或标记替代关系。
- 用文档描述与代码不一致的“理想状态”而不标注差距。
- 把决策记录写成流水账；没有备选方案与后果的不算 ADR。
- 在文档中承诺未经验证的能力、性能数字或兼容性。
- 提交运行时产物、用户文档、日志、密钥、个人路径截图。

## 10. 既有文档处理

根目录已有的一次性文档（如 `第一阶段修改计划与执行记录.md`、`遗留十项一次收口记录.md`）保持原位，视为历史资料；新增同类内容进入 `docs/`。不做批量搬迁或重命名，避免破坏外部链接与提交历史。
