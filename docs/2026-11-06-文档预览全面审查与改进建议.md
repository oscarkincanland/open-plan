## 一、结论摘要

1. **CAD「预览不了」不是坏了，是默认关闭**：`cadPreview` 是 `readFlag`（默认 false，`server/运行开关.mjs:194`），关闭时 dxf/dwg **连文件树白名单都不进**（`server/workspace.mjs:49`），点开只会落到 OfficeCLI 兜底页并显示「该格式暂不支持内嵌预览」。要让它显示，需先设 `OAW_CAD_PREVIEW=1` **并重启服务**（开关是模块加载期静态快照），且界面上没有任何开关入口或提示。**这是 P0 体验缺陷，不是功能缺失。**

2. **Word 慢是可量化的**：同一份 17 MB 文档实测，批注查询冷启动 **2626 ms**、高保真 HTML 渲染 **3057 ms** 且产出 **18.22 MB** HTML；小文档（27 KB）批注查询仍需 **1557 ms**（其中进程启动固定成本 **303 ms**）。叠加前端「渲染 → 等图片最多 6 s → 破图则**整篇重渲染一次**（再等 8 s）→ 二次分页 → 建目录」的五段串行链路，以及 `no-store` 导致的**每次打开都全量重下 17 MB**，共同造成体感极慢。

3. **批注定位错位有确定性根因**：docx-preview 每条批注会生成 **两个** HTML 注释锚点（`start of comment #N` 与 `comment #N by …`，见 `docx-preview.js:3556` 与 `:3584`），而 `CommentMarker.collectCommentAnchors` 的正则把两者都收进同一个数组，再用 `anchors[index]` 按批注序号取——**从第 2 条批注起，索引整体偏前一位**，于是几乎所有批注都跳到上一条批注的位置。兜底的关键词匹配又拿「批注正文」去匹配「文档正文」，本来就不该命中。

4. **定位偏差的第二个独立根因是 CSS zoom 与滚动量的单位错配**：默认「适应宽度」会把正文缩到 ~70%（A4 794px 塞进右侧栏），`getBoundingClientRect()` 返回视觉像素而 `scrollTop` 是布局像素，两者相差 1/zoom 倍；目录跳转与批注滚动都用「视觉像素差值」直接改 `scrollTop`（见 3.x），所以**越往文档后面偏得越多**。

5. **设计一致性有 4 处明确偏离 DESIGN**：标题行常驻文字徽标（DESIGN §8 明确要求收进 ⓘ）、`:root` 未定义却被使用的 `--warn` 导致「部分可用」状态显示成强调色、`--danger`/`--error` 双失败色、以及设计令牌棘轮门禁**当前是红的**（125/87 基线 → 实测 127/89，其中 1 处是我上一轮浏览器时间线引入的冗余 hex fallback）。

## 二、预览全景（现状）

| 格式 | 渲染路径 | 首屏成本 | 已知缺口 |
|---|---|---|---|
| docx | 前端 `docx-preview`（native，默认）｜可切 OfficeCLI 高保真 iframe | 全量下载 + 整篇渲染 + 破图重渲染 + 二次分页 | 无大小预算、EMF/WMF 不支持、批注锚点错位 |

## 四、P0-2：Word 加载慢（实测 + 六个成因）

### 4.1 实测数据（本机，OfficeCLI 1.0.160）

| 操作 | 17.07 MB 文档 | 27 KB 文档 |
|---|---|---|
| 副本拷贝（`withPreviewCopy`） | 109 ms | ~2 ms |
| `query … comment --json` 冷启动 | **2626 ms** | **1557 ms** |
| 同上第二次（进程已存在） | 675 ms | 447 ms |
| `view … html --out`（高保真） | **3057 ms**，产出 **18.22 MB** | 607 ms，产出 47.8 KB |

### 4.2 六个成因

| # | 成因 | 证据 | 量级 |
|---|---|---|---|
| W1 | **每次打开都全量重下**：raw 路由写死 `no-store, max-age=0`，无 ETag/304 | `server/index.mjs` raw 路由内 `res.setHeader("Cache-Control","no-store, max-age=0")` | 17 MB / 次，切标签来回即重复 |
| W2 | **破图触发整篇二次渲染**：`brokenImages(6000)` 最多等 6 s，发现破图就用 `useBase64URL` **重跑一遍 `renderAsync` 整篇文档**，再等最多 8 s | `client/src/components/DocxViewer.jsx:248-271` | 渲染成本×2，等待上限 14 s |
| W3 | **EMF/WMF 必然破图**：`docx-preview` 对 `emf/wmf` 零支持（库源码 grep 命中 0 次），而本文档含 5.36 MB EMF | `docx-preview.dist` 无 emf/wmf 分支 | 对这类文档，W2 的二次渲染是**必然而非偶发** |

| W6 | **批注查询串行叠加**：每次渲染后 `loadComments()` → 服务端 `withPreviewCopy`（整文件拷贝）+ 起 `officecli` 进程 | `DocxViewer.jsx:287,301-315`；`server/office.mjs:242-251,285-289` | 冷启 1.5–2.6 s；虽未 `await`，但与主进程抢 IO/CPU |

## 五、P0-3：批注与目录定位不准（三个独立根因）

### 5.1 根因 A：docx 批注锚点索引错位（确定性 bug）

- docx-preview 每条批注生成 **两个** 注释节点：
  - `start of comment #N`（范围起点，`docx-preview.js:3556`）
  - `comment #N by … on …`（引用处，`docx-preview.js:3584`）
- `collectCommentAnchors` 的正则 `/^(start of comment #|comment #\d+ by)/` **两个都收**（`CommentMarker.jsx:57`）→ `anchors` 长度约为批注数的 2 倍。
- 随后 `const anchor = anchors[index]`（`CommentMarker.jsx:83`）按批注序号取数组下标：
  - `index=0` → `start of comment #1` ✅
  - `index=1` → `comment #1 by …`（属于第 1 条）❌ 偏前一位
  - `index=2` → `start of comment #2`（属于第 2 条）❌ 同样偏前一位
- **结果：除第 1 条外，所有批注都定位到上一条批注的段落。**

修复：改为**按批注 id 建映射**，不要用数组下标。

```js
// 锚点：从注释文本里解析 id，建 Map<id, node>
const anchorsById = new Map();
// "start of comment #12" / "comment #12 by 张三 on ..." → 12
const m = t.match(/^(?:start of comment|comment) #(\d+)/);
if (m) anchorsById.set(Number(m[1]), n);

// 定位：用批注自身 id
const anchorNode = anchorsById.get(Number(comment.id)) || null;
```

### 5.2 根因 B：关键词兜底用的文本根本对不上

- `extractKeywords(comment.text)` 从**批注正文**里抽 4 字以上中文串（`CommentMarker.jsx:30-43`），然后用 `el.textContent.includes(kw)` 在**文档正文**里找（`:99-104`）。
- 批注正文是「这条批注说了什么」，被批注的是「文档里哪句话」——两者通常没有交集。于是要么误命中正文里偶然出现的词，要么全部落空。
- 而且 `candidates.find(...)` 取的是**全文档第一个**命中，同词多次出现时必然错。

修复：服务端批注查询若能带出**被批注范围原文**（officecli `query comment` 的 `preview`/`text` 字段需确认语义），应改为：`先按 id 锚点 → 锚点所在段落即答案`；只有拿不到锚点时才用「被批注原文」匹配，并**从当前滚动位置就近查找**、禁止取首个命中。

### 5.3 根因 C：CSS zoom 下的滚动换算（同时影响批注与目录）

- `applyZoom` 用 `host.style.zoom = next/100`（`DocxViewer.jsx:184-188`），默认「适应宽度」会把 A4 794px 缩到栏宽（常见 70–85%）。
- `jumpToPage` / `scrollHostTo`（`DocxViewer.jsx:410-434`）与批注滚动（`CommentMarker.jsx:144-152`）都用：
  `host.scrollTo({ top: host.scrollTop + (rect.top - base.top) })`
- `rect.top - base.top` 是**视觉像素**（受 zoom 缩放），而 `host.scrollTop` 是**布局像素**。zoom = 0.7 时视觉位移只有布局位移的 0.7 倍，直接相加 → **滚过头约 1/0.7 − 1 ≈ 43%**，越往文档后面偏得越多（目录第 10 页、批注第 20 条最明显）。
- 这解释了「同一个批注，有时候差几行、靠后差半页」的现象。

修复：换算回布局像素再滚动，或统一用「页 + 页内偏移」定位：

```js
const zoomFactor = zoomRef.current / 100;
const layoutDelta = (rect.top - base.top) / zoomFactor;   // 视觉 → 布局
host.scrollTo({ top: Math.max(0, host.scrollTop + layoutDelta - offset) });
```

> 验证只需 1 分钟：把文档缩放到 70%，点目录第 10 条或第 5 条批注，观察是否停在目标**之后**；改成 100% 再点，若明显变准即证实。

### 5.4 「书签」现状

- **文档内没有书签功能**：全仓 grep 的「书签」只剩地图视角书签（`MapPanel.jsx:1685`，`mapBookmarks` 开关）与会话收藏图标。
- 若你指的是 **Word 书签 / 交叉引用 / 目录域**：docx-preview 与 OfficeCLI 路径都**没有解析 `w:bookmarkStart`**，这类锚点无法定位——属于功能缺失，不是 bug。
- 若指**目录（大纲）跳转**：见 5.3，是 zoom 换算问题。

### 5.5 html/MD 标注（另一个定位体系，同样靠文本匹配）

- 标注只存 `{id, type, text, created}`（`DocViewer.jsx:443-448`），**没有位置/偏移/上下文**。
- 恢复时 `wrapFirstTextMatch` 取「文档中第一个未被包裹的匹配」（`:23-59`）：
  - 同文多次出现 → 恒落第一处；
  - 选区跨多个文本节点（含加粗/链接）→ `surroundContents` 抛错，**静默丢失**（`:56-58` 只返回 false）。
- 修复方向：存「文本 + 前后各 30 字 + 出现序号 + 所在块 id」，恢复时按「块 + 序号」定位；跨节点选区用 `Range` + 多段包裹替代 `surroundContents`。
