# 项目文件管理与测试验收规则

> 生效日期：2026-10-20（2026-10-30 按 ADR 0012/0013 修订命名与上位文件）。本规则对**所有会话/所有工作流**生效；与 `AGENTS.md` 冲突时以宪法为准，修订需在变更日志登记。
> 目的：让每一次提交都"可执行、功能无误、边界干净"，让每一轮改动都有明确的验收口径。

## 一、文件管理规则

### 1.1 目录职责（写入位置即职责）

| 位置 | 职责 | 入库 |
|------|------|------|
| `server/` | 服务端模块（L1-L3，新增英文命名、存量冻结） | ✅ |
| `client/src/` | 前端源码（组件/投影/开关/样式） | ✅ |
| `scripts/` | 回归测试与运维脚本（`test:*` 必须可重复执行） | ✅ |
| `docs/` | 设计/方案/验证报告，`YYYY-MM-DD-标题.md` | ✅ |
| `docs/plans/` | 编号执行计划，`YYYY-MM-DD-NNN-主题.md` | ✅ |
| `.oaw/` | 运行数据（runs/events/pending-asks） | ❌ 永不入库 |
| `运行日志/`、`dist/`、`node_modules/` | 构建与运行产物 | ❌ 永不入库 |
| `office-workspace/` | **用户工作数据**；地图项目（maps/）改动须单独评审提交，不与代码混提 | ⚠️ 受限 |
| 仓库根目录 | 禁止堆积一次性产物（脚本/草稿/媒体），即用即删 | — |

### 1.2 命名规则

1. **新增代码文件英文命名、存量中文文件冻结**（ADR 0012，见 `docs/规范/代码规范.md` §2）；文档仍中文命名（`AGENTS.md` 等固定文件除外）。
2. 临时验证脚本必须带 **`临时-` 前缀**（如 `scripts/临时-日期格式验证.mjs`），**当次会话结束前删除**——不允许带 `临时-` 前缀的文件存活到提交。
3. 文档双前缀：日期 + 主题；计划文档带编号（001/002…递增）。

### 1.3 多工作流共存规则（本仓库核心风险）

同一工作树常有**多条工作流并行**（如：任务编排、GIS、软著材料）。铁律：

1. **一次提交 = 一条工作流**。提交前逐文件核对 diff 归属，无法确认归属的文件宁可留在工作区。
2. 已知的多工作流共享文件（`styles.css`、`ChatPanel.jsx`、`App.jsx`、`.gitignore`）提交前必须审查暂存/未暂存 diff 中是否混有其他工作流内容：
   - 干净 → 随本工作流提交；
   - 混有他人改动 → 本工作流提交**跳过该文件**，或拆分到独立提交并在提交信息中注明。
3. 提交用 `git commit -m "…" -- <文件列表>`（pathspec 提交），只收本工作流文件，**不使用 `git add -A` / `git add .`**。
4. 其他工作流已暂存（staged）的内容保持原状，不代为提交、不随意 unstage（内容不丢失前提下才可整理）。
5. `.gitignore`、地图项目配置等与远程合并/其他工作流相关的文件，改动前先看是否与 origin/main 重叠。

### 1.4 提交信息规范

- 格式：`类型(范围): 描述`，类型 ∈ feat / fix / docs / chore / test / perf / refactor。
- 描述写"为什么+做了什么"，不写流水账。
- 每条提交在 `变更日志.md` 登记后推送（网络可用时）。

## 二、测试规则

### 2.1 分级门禁（提交前按改动面执行，从上到下必须全绿）

| 级别 | 门禁 | 何时必跑 |
|------|------|---------|
| L1 语法 | `node --check <改动的 server/scripts 文件>` | 任何服务端/脚本改动 |
| L2 构建 | `npm run build` | 任何 client/ 改动 |
| L3 定向回归 | 按 2.2 对照表选择 | 对应模块改动 |
| L4 总门禁 | `npm run verify`（语法+构建+API 冒烟） | **每次提交前必过** |
| L5 端到端 | `test:gis-e2e` / `test:map-export:live` 等 | 涉及交付链路（出图/导出/报告） |

### 2.2 改动面 → 必跑测试对照表

| 改动面 | 必跑 |
|--------|------|
| 事件系统（事件注册表/存储/协议） | `test:event-registry`、`test:event-payload` |
| agent.mjs（工具/HITL/Run 生命周期） | `test:run-trace`、`test:run-budget`、`test:repeat-guard`、`test:interaction-owner` |
| 完成/结论语义（运行轨迹/complete_task） | `test:run-trace` |
| ChatPanel/投影/前端展示 | `test:run-view`、`test:icons`、（样式改动加）`test:motion`、`test:component-spec` |
| 预览（DocViewer/Excel/Word） | `test:motion`、`test:component-spec`、手工走查清单 §3.4 |
| GIS server | `test:spatial`、`test:map-layers` |
| 运行开关 | 所涉及能力的定向测试 + `test:interaction-owner`（开关管线） |
| 服务监督/运维脚本 | `test:service-supervisor` |

### 2.3 测试纪律

1. 失败先定位根因再重跑；**禁止**为过测试修改断言（确需改断言，提交信息中说明理由）。
2. 新能力必须带对应测试（至少定向回归一项），否则不满足 DoD。
3. 服务端改动后重启 3002 服务再做功能验证；前后端版本不一致的接口会 404（如审批接口）。

## 三、验收标准（Definition of Done）

一次改动"完成"必须同时满足：

1. **功能无误**：主链路手工走查通过；改动对应的 2.2 定向回归全绿；L4 verify 绿。
2. **基线兼容**：新能力默认关（或用户批准默认开）时，关=旧行为逐路径一致；开关回退路径已验证。
3. **边界干净**：提交只含本工作流文件（§1.3）；无 `临时-` 文件；无调试 console 残留。
4. **可追溯**：`变更日志.md` 已登记；影响架构/决策的更新对应 ADR；影响计划进度的同步勾选。
5. **可回滚**：feature flag 或独立提交保证可整体回退。
6. **服务生效**：服务端改动重启 3002 后健康检查通过，关键接口冒烟通过。

## 四、标准走查清单（预览/交互类改动附加）

- [ ] 打开 docx：分页/中文字体/表格线正常，页签来回切换 <2s（缓存命中）
- [ ] 打开含日期/合并单元格/宽列的 xlsx：显示值正确（非序列号）、合并与列宽还原、0-based 无偏移
- [ ] @引用：行内徽章渲染、整块删除/选中、发送后引用条清空
- [ ] ask_user：等待窗口/超时卡/迟到回答自动续跑（忙=排队、空闲=新 Run）
- [ ] 任务结束：结果卡结论为实质总结；产物页签自动切换；"有未完成项"横幅仅在确有未完成项时出现
